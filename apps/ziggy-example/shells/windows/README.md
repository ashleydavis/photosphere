# Ziggy example, Windows shell

The Windows executable of the Ziggy example. `src/main.zig` names the app and hands it to `ziggy-shell-windows` (`packages/ziggy/native/windows`), which does everything else.

## What the shell does

- Creates a Win32 window. `-geometry=WxH` or `-geometry=WxH+X+Y` sets the page size in pixels at 96 DPI, and the position is honoured.
- Hosts the page in WebView2, through its native COM interface. The declarations come from `zig translate-c` on the SDK's own `WebView2.h`, and the SDK's static loader library is linked into the executable, so no DLL is needed.
- Injects `ziggy-inject.js` with `AddScriptToExecuteOnDocumentCreated`, and loads the page only after that has completed.
- Passes page messages (`WebMessageReceived`, read with `TryGetWebMessageAsString`) to `ziggy_post_message`.
- Delivers core messages by `ExecuteScript("window.__ziggyReceive(...)")` on the UI thread. The core delivers from any thread, so messages are queued under a lock and the UI thread is woken with a window message.
- Serves the page from the files embedded in the executable: it answers every request to `https://ziggy-app.invalid/` (a host name that can never be looked up) from the list, through the web view's `WebResourceRequested` event, and decides every navigation (`NavigationStarting`) and new window request (`NewWindowRequested`) with `ziggy_check_url`. External links open in the system browser.
- Keeps the app's data under `%LOCALAPPDATA%\<app id>`, which is also WebView2's profile directory (in `WebView2` inside it).
- Draws the app's menu as a native Win32 menu bar. After the core is created the shell reads the menu from `ziggy_menu_json`, and parses each shortcut with `ziggy_parse_accelerator`. The shortcut is shown after a tab in the Windows style (`Ctrl+Shift+I`). A menu with no menus shows no menu bar.
- Makes the shortcuts work. With the keyboard inside the web view, WebView2 consumes key presses, so the shell uses the controller's `AcceleratorKeyPressed` event: a key that matches a menu shortcut runs its action and is marked handled (a held key does not repeat an action). The editing shortcuts (undo, redo, cut, copy, paste, select all) are left to the web view, which does them natively. With the window itself holding the keyboard, an accelerator table in the message loop does the same, and menu clicks arrive as `WM_COMMAND`.
- Performs these actions itself: `quit` (posts a close to the window) and `close-window` (the same), `reload` (`ICoreWebView2::Reload`), `toggle-devtools` (`ICoreWebView2::OpenDevToolsWindow`, with `put_AreDevToolsEnabled` set in every build, release included; WebView2 has no call to close them, so when a window titled "DevTools" of the web view's browser process is showing it is sent a close instead), `toggle-fullscreen` (a borderless window over the monitor, hiding the menu bar, restoring the saved window placement), `zoom-in`, `zoom-out` and `zoom-reset` (`ICoreWebView2Controller::put_ZoomFactor`, steps of 0.1 between 0.25 and 5), and the editing actions from the menu. `undo`, `redo` and `select-all` run `document.execCommand` through `ExecuteScript`. Chromium refuses `execCommand` copy, cut and paste to a script, and WebView2 has no clipboard commands, so `copy` and `cut` read the selected text from the page with a script and put it on the clipboard with Win32 (`cut` then runs `execCommand("delete")`), and `paste` runs the web view's own paste command, sent as `Input.dispatchKeyEvent` with `"commands":["paste"]` through `ICoreWebView2::CallDevToolsProtocolMethod`, so a paste is an undo step of its own. Only text is copied. Every other action is sent to the core as `{"channel":"menu-action","data":{"action":"<action>"}}`, and the core hands it to the page as an event.
- `toggle-devtools` only opens the developer tools window. WebView2 has no call to close it, so the window is closed by the user.
- Shows the file and folder dialogs the core asks for through the `pick_paths` host callback, with the Windows Common Item Dialog (`IFileOpenDialog` with `FOS_ALLOWMULTISELECT` to open files, with `FOS_PICKFOLDERS` to choose a folder, and `IFileSaveDialog` with `SetFileName` for the suggested name when saving). The core calls the callback from a worker thread. The callback posts a window message to the UI thread and waits on a Win32 event, the dialog runs on the UI thread owned by the main window (its own modal loop keeps the web view working), and the chosen items are read as file system paths (`SIGDN_FILESYSPATH`) and written as a JSON array of UTF-8 strings, `[]` when the user cancels. If the window closes while a dialog is open the waiting worker gives up and the callback fails, because closing waits for the workers.
- Implements the `menu_action` host callback, which the test control connection uses to choose a menu item. It runs on that connection's thread, so it posts a window message carrying a copy of the action to the UI thread, which runs the same function a menu click and a shortcut run. An action that is not one of the shell's own goes to the core like any app action.
- Notes for tests: `reload`, `zoom-*` (the page's viewport size changes with the zoom factor), `toggle-fullscreen` (the window covers the monitor and the viewport follows) and `quit` (a close is posted to the window) can be seen from the page or the process. `toggle-devtools` opens the developer tools in their own window, so the page's viewport does not change and nothing in the page shows they opened. The keyboard path (`AcceleratorKeyPressed`) and the drawn menu bar are not exercised by `menu_action`.
- Destroys the core once when the window closes.
- With a test hooks build and `ZIGGY_TEST_MODE` set, tells the core it is in test mode, passes `ZIGGY_TEST_PORT_FILE` to it, and adds `?testMode=1` to the page address.

Every failure prints a message and ends the process with a non-zero code.

## Building

From a Git Bash terminal at the repository root, run `bun run --filter=ziggy-example setup` once to fetch the WebView2 SDK and the WiX Toolset and install the C++ toolchain and the Windows SDK where they are missing, then `bun run build:ziggy-example:windows` or `bun run run:ziggy-example:windows`. See the example's README for what Windows needs. The build installs `ziggy-example.exe`, which is the whole app, into `zig-out/ziggy-example`. The scripts are described beside them. The shell needs the WebView2 runtime on the machine, which Windows 11 and current Windows 10 have.

Dropped files: the inject script posts the dropped Files to the host with `chrome.webview.postMessageWithAdditionalObjects`, and the web message handler reads each File's path (`ICoreWebView2File::get_Path`) and records the paths with the core.
