# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Platforms

This is crass platform app. Developed on Linux, but delivered and tested on Windows, Linux, MacOS, Android and iOS. All tests and smoke tests be cross platform to work on the platforms where they are delivered, here is the list of apps and where they run:

- CLI tool: Windows, Linux and MacOS.
- Desktop app: Windows, Linux and MacOS.
- Mobile app: Android and iOS.

## Rules

- SHARED STATE BETWEEN ZIG THREADS IS BANNED. All communication between threads is done with JSON messages: the only thing two threads both touch is a message queue, and the only thing that crosses it is a copy of JSON text.
  - Never add a mutex or lock to Photosphere's Zig code unless the human explicitly asks for it.
  - Memory allocated on one thread is never freed on another, and no allocator is used by two threads: each thread makes its own.
  - System services (an Io, an allocator, the timers, the handler, menu and task services) are never stored in a struct: each function that uses one takes it as an argument.
- When writing plans, do not add any steps for "Human Verification" or "Human Testing", plans you write should be automatically tested by unit tests and smoke tests. No human will be testing your work.
- YOU ARE RESPONSIBLE FOR THE CODE IN THIS REPO. IT DOESN'T MATTER "IF IT WAS ALREADY LIKE THAT" - YOU ARE EXPECTED TO FIX IT.
- IF YOU DON'T KNOW WHO WROTE THE CODE, IT MEANS YOU (CLAUDE) WROTE THE CODE.
- IT IS ALWAYS YOUR RESPONSIBILTY TO FIX COMPILE ERRORS AND FAILING TESTS. NEVER USE THE "PREEXISTING" EXCUSE.
- ANY addition of "test only" scaffolding to the app code must be approved by the human user first, or not added at all. That means anything shipped in the app that exists solely to let tests set up or inspect state: seeding functions, injection points, test-only commands, events or globals. If a test needs state, set it up from outside the app (write the config file, place the data on disk) the way the desktop tests do.
- Never reinvent a third-party tool or library unless the human explicitly asks for it. Always use the official version.
- Never change a third-party tool, library or its code without an explicit request from the human.
- The same applies to tests: do not make a test pass by faking the thing under test, skipping it, or gating it behind an environment variable that is normally unset. A test that reports success without asserting anything is worse than no test. If a test needs real infrastructure, provision it (see `docs/plans/` for the local S3 server approach).
- NEVER WRITE A FAKE TEST. A fake test is any test that cannot fail when the thing it names is broken. This includes: a test written against a UI, API, element id, route, function or file that you have not verified exists; a test whose assertions you invented from what you imagined the code does rather than read from the code; a test that skips by default so its body has never executed; and a test you have never watched run. Every one of these reports success for work that was never checked, which is worse than having no test, because a green tick stops anyone looking. If you cannot run a test you have written, say so in that message and say plainly that it is unverified. Do not report it as passing, and do not count it toward "all tests green".
- RUN EVERY TEST YOU WRITE.
- DO NOT DELETE A FAILING TEST. GET IT WORKING. That covers removing it, commenting it out, skipping it, loosening its assertions and catching the error. If a test will not run, fix the runner or the import. Deleting a test whose subject no longer exists is fine.
- REMOVING, TRIMMING, LOOSENING, SKIPPING OR WORKING AROUND A TEST TO STOP IT FAILING IS CHEATING AND IS NEVER ALLOWED. That covers deleting the failing assertion and keeping the rest, widening what an assertion accepts, adding a wait or retry so a race passes, ignoring an error line in a check, and changing what a port of a test asserts so it differs from the test it ports. A failing test is a bug in the code or in the test: find the cause and fix it. A port of a test asserts what the original asserts.
- NEVER LIE ABOUT WHAT YOU HAVE DONE OR VERIFIED. Do not say a thing works, passes, is tested, is verified, or is complete unless you ran it and read the result in this session. Do not describe an intention as an outcome. Do not present a skipped test, a compile that merely succeeded, or a code reading as evidence that behaviour is correct. If you are inferring rather than observing, use words that say so, and say what you did not check. A confident summary that turns out to be unfounded costs more than saying "I have not verified this".
- NEVER SHIP A STUB THAT PRETENDS TO WORK. A function, class or method that silently does nothing (returns the argument, returns an empty result, swallows an event, or has an empty body) will be called by something eventually and will fail invisibly, often far from the cause. If you genuinely cannot implement something now, make it throw with a message naming what is missing, so the failure is loud and points at itself. Never leave a no-op in a code path that a caller will treat as success.
- ALL FAILURES MUST BE NOISY. Never write a path that discards an error, drops data, or returns a success value when the work did not happen. Unhandled errors get thrown, not swallowed. A missing capability throws and names itself. Prefer a loud crash over a quiet wrong answer, always.
- YOU FIND A BUG, YOU FIX IT. A test that failed once and passed the next time is a bug: it is telling you the code or the test has a race, a fixed timeout that load can exceed, or a resource it does not own, and every one of those is findable and fixable. Find the cause and fix the cause.
  - "It passed on the retry" is not a result. Neither is "it fails only under load", "it is unrelated to my change", or "it was already like that". The first two describe the bug; the third is answered by the rule above that this repository's code is yours whoever wrote it.
  - Do not write a bug down instead of dealing with it. Do not start a registry, a known-issues list, a section in a doc, or a TODO comment naming a test that sometimes fails. A record of a bug is a bug nobody is fixing, and it reads as permission to leave the next one too.
  - No bug here is unfixable, so "I could not fix it" is not an outcome. The only failures outside your reach are the ones outside the machine: a network that dropped, a disk that filled or failed, a remote service that was down. Those you cannot fix, and the code should expect them and fail loudly and clearly when they happen, which is a thing you can fix. Everything else is yours: keep going until you have the cause, and if you cannot find it yet, say what you have ruled out and what you will look at next, in the message you are writing.
- NEVER USE EM DASHES.
- Never use memory.
- All Claude configuration goes in this repository only, not in the home directory.
- Slash commands go in `.claude/commands/`, as a markdown file per command, grouped in a subdirectory where there is more than one of a kind: `.claude/commands/ux/review/create.md` is `/ux:review:create`. A request for a "skill" means one of these. Do not create a `.claude/skills/` directory or a `SKILL.md`, and do not put a command in the home directory, whatever the word used to ask for it. Read the existing commands before adding one and follow what they do: frontmatter carrying `description` and nothing else, then the prompt as ordinary markdown with a heading and steps. The `description` is what the human sees in the command list, so it says what the command does, not when to trigger it.
- Never write `mise exec --` in docs, READMEs, comments or script help text. Users run commands without it. It is only for commands Claude runs itself.
- Never say "you are right", "you're right" or any other agreement as a way to open a reply. Say what was wrong and what you will do about it. Never tell the human untested code can be committed now and tested later: say it is untested, and say what would test it.
- Never stash code unless asked.
- Never use `cd` to permanently change directories within the repo. Use it on case-by-case and temporary basis as part of a command to run the command from a particular directory. Use of `cd` by itself will leave you in the wrong directory meaning other commands won't work.
- Never invoke shell scripts directly (e.g. `./apps/cli-zig/smoke-tests-zig.sh`). Use the `bun run` equivalent from `package.json` (e.g. `bun run test:cli:zig`, `bun run test:ziggy`).
- When running smoke tests, do not manually `rm -rf` the test's `tmp/` directory — the runner already cleans it before each test.
- HIGH PRIORITY: `rm -r` is banned, in every form and every flag combination that includes it (`-r`, `-R`, `--recursive`, `-rf`, `-fr`), unless the human asks for that exact deletion in the message you are acting on. This covers commands you run yourself, commands you ask the human to run, and any `rm -r` you write into a script, a test, a runner or a hook, where it will run later without anyone watching. A recursive delete takes everything under a path, and the path is often built from a variable: when that variable is empty, wrong, or points somewhere shared, what goes is not what you meant to go, and there is nothing to undo it with. This has already cost this repository real work. Removing a single file by name is not covered by this and is fine.
- NEVER WAIT FOR ANOTHER WORKTREE'S TESTS TO FINISH BEFORE RUNNING YOUR OWN. Running beside other suites is what this repository is built for, not a hazard to be avoided, so start the run you need when you need it and never delay it, schedule it for later, or wait for the machine to go quiet. Do not watch for other runs, do not poll for them, and never treat another worktree's activity as a reason to hold off. If a run of the human's and a run of yours contend, that is the contention these rules exist to surface and it is worth knowing about; a run you postponed tells nobody anything. This holds however busy the machine looks, and it holds for the interference check as much as for anything else, since a machine with nothing else on it is precisely the machine that check cannot learn anything from.
- EVERY TEST IN THIS REPOSITORY MUST SURVIVE RUNNING BESIDE ANOTHER COPY OF ITSELF AND BESIDE EVERY OTHER SUITE, INCLUDING ONES STARTED FROM A DIFFERENT WORKTREE. The human works in several worktrees at once and runs tests in all of them at the same time, so at any moment there may be two, three or four independent runs on this machine that know nothing about each other. `test:everything` also starts its own suites in parallel lanes within a single run. A test that only works when it is the only thing running is broken, whatever it does on its own.
  - Nothing may claim a machine-wide resource by a fixed name. That means no hardcoded port, no fixed path under `/tmp` or anywhere else, no fixed database, bucket, vault, config or lock path, and no fixed device. Allocate a free port, and use the per-test temp directory allocator (`scripts/lib/allocate-test-temp-dir.sh`) rather than naming a directory yourself.
  - EVERY PROCESS A TEST SUITE STARTS MUST HAVE ITS PID RECORDED AT THE MOMENT IT IS STARTED, so it can be cleaned up reliably at the end. Recording is the launcher's job, not the cleanup's: a process nobody wrote down cannot be cleaned up except by guessing at it, and guessing is what makes cleanup dangerous. Never run a long-lived helper in the foreground, because a foreground child has no pid anything else can see; start it in the background, keep `$!`, and `wait` on it, which blocks and reports the exit code exactly as the foreground call did. Kill through `kill_process_tree` rather than `kill`, because `bun run` is a wrapper and the process holding the port, the socket or the server is its child, so killing the pid alone leaves that child running. A watchdog or trap that must see pids recorded after it forked needs them in a file, since a subshell only gets a copy of the variables that existed when it started.
  - NEVER kill a process by matching its command line. `pkill -f`, `pkill`, `killall` and anything else that selects by name asks the kernel about every process on the machine, and the CLI's command line is identical whichever checkout launched it, so it kills the identical process belonging to another worktree's run. This has already broken this repository once: a `pkill -f "bun run.*secrets (send|receive)"` in one LAN share suite's exit trap SIGTERMed another suite's sender mid-test, and the failure it produced named an innocent test and said nothing about the kill. Scoping the match to your own process group is not a fix either: `scripts/test-everything-parallel.sh` starts its lanes as plain background jobs, so every lane of one run shares a single group and cannot be told apart that way. Kill the pids you started and their descendants, with `kill_process_tree` from `scripts/lib/process-control.sh`.
  - Interference is not flakiness and must never be dismissed as it. A suite that passes alone and fails in company is telling you it contends on something shared. Run `bun run test:parallel` (`scripts/check-parallel-tests.sh`), which runs each suite alone and then every pair together and reports only what fails in company. Self-pairs are included, which is the cheapest way to surface a fixed port or a fixed path, because a suite holding one always collides with a second copy of itself.
  - `SERIAL_GROUPS` in `scripts/test-everything-parallel.sh` is the last resort, not the fix. It keeps two suites apart inside one run of `test:everything` and does nothing about a second worktree, so reach for it only when the contention genuinely cannot be removed.
- NEVER CREATE A GIT WORKTREE UNLESS THE HUMAN ASKS FOR WORKTREES IN THE MESSAGE YOU ARE ACTING ON. That includes starting a subagent with worktree isolation and making branches for one. Running subagents in parallel is not a request for worktrees.
- When creating a new worktree, never use `EnterWorktree` with a `name` parameter. Instead: (1) run `git branch --show-current` to get the current branch, (2) run `git worktree add -b <new-branch> .claude/worktrees/<name> <current-branch>` to create the worktree explicitly branching from the current branch, (3) then use `EnterWorktree` with the `path` parameter to enter it.
- The commands the human uses to run the software always rebuild it automatically, so the running app is always built from current source. A code change that does not show up is never caused by a stale build or a missing rebuild. Never tell the human to rebuild and never blame a missing change on the build being out of date. Find the real cause (a responsive breakpoint, caching, the wrong code path, a logic bug).
- Never assume whether the Android emulator pool is up or down. Run `bun run emu:and:pool:status` and read the exit code: 0 means at least one pool emulator is running and on the LAN bridge, 1 means none is. Add `-- --quiet` to use it directly in a condition. You have got this wrong every time you have guessed at it, and the way you get it wrong is always the same: a reading taken earlier in the session, never looked at again, and then stated later as a current fact. The human starts and stops emulators whenever they like and does not announce it, so any reading is stale the moment after you take it. Run the check at the point you need the answer, not before. This applies just as much to saying the pool is up as to saying it is down, and to anything that follows from either, such as warning the human that a command will fail for want of devices. If the check disagrees with what you expected, the check is right.
- Never repair an emulator while the pool monitor is running: `bun run emu:and:pool:monitor` fixes every broken pool emulator by itself, within seconds, so anything you start is a second repair racing it. Run `flock -n /tmp/photosphere-emulator-pool-monitor.lock true` at the moment you need the answer, never from memory, because the human starts and stops the monitor without saying so. Exit 1 means it is running: report the broken emulator, say the monitor will deal with it, and leave it. Exit 0 means it is not, and the commands below are yours.
- You may repair a broken pool emulator, and only in these ways. Each one needs no root, touches no tap and no bridge, restarts one emulator at a time, and skips any emulator a test run is holding: `bun run emu:and:pool:repair` (restart the broken ones; `-- --index N` for one) and `bun run emu:and:pool:diagnose` (read-only, everything readable about every pool emulator). Not `bun run emu:and:pool:monitor`: that brings the whole pool up when it is not there, which asks for sudo, and it is the human's to run. Everything else about the pool is still the human's: never run `emu:and:up`, `emu:and:down`, `emu:and:restart`, `emu:and:pool:up`, `emu:and:pool:down` or `emu:and:pool:restart`, never create or remove a tap or the bridge, and never run sudo. See `scripts/android/CLAUDE.md`.
- When the human asks what went wrong with the pool earlier, read the monitor's rolling logs before asking the human anything or guessing: `/tmp/photosphere-emulator-pool-monitor.log` (every line it said, plus a summary a minute giving the healthy count, CPU, memory, swap and each emulator's state) and `/tmp/photosphere-emulator-pool-monitor-repairs.log` (each repair's own output). Both keep one previous generation as `<name>.1`, and both are cleared by a reboot. They are written whether the monitor was watched on a terminal or redirected to a file. `emu:pool:diagnose` says how the pool is now; these say how it got there.
- Never say something was "intentionally done" unless the human explicitly asked for that exact behaviour. Describing a behaviour as intentional when the human never asked for it is an excuse for getting it wrong, especially when the human is reporting that something does not work right. Do not decide to "intentionally" do something the human did not request; if you did, you got it wrong. State plainly what the code does and own the mistake.
- Just because you (the AI) have previously written something in a plan does not mean that the human approves of or accept that thing. Never use "it was in the plan" as the reason something was done. Whenever the human asks "What is the reason for X?" they mean "Why was that change necessary?". If you think to answer with "because it was in the plan", know that it is the wrong answer. You may take the human's question to mean "Why did you plan to make that change?" and answer that question instead.
- Plans are transient. Everything under `docs/plans/`, `new/` and `done/` alike, is scratch working material that gets cleaned out of the repo once the work is finished, so never reference a plan from anything that stays: not from documentation, not from a slash command, not from code or comments, not from a commit message, and not from another doc that outlives it. A reference to a plan is a link that will be dead shortly after it is written, and the reader is then left with a pointer to something they cannot read. If a plan contains something worth keeping, the plan is the wrong home for it: copy the content itself into the thing that needs it, or into a permanent doc under `docs/`, and say it there in full rather than pointing at where it came from.
- Avoid an explosion of Electron IPC channels. Do not add new, action-specific IPC channels (for example a dedicated `toggle-devtools` channel). Reuse an existing channel, or use the generic `main-command` channel that dispatches named actions from the renderer to the main process. If you add new, specific IPC channels the human will generally revert those changes.
- Background work the user should be able to see and stop is grouped into named jobs, and jobs live only in the frontend. Whatever queues the task puts an `IJobTag` (`id`, `name`, and `cancelSource` when it can be cancelled from the interface) in the task's input data, and the handler reports progress with `sendJobProgress` from wherever it already reports progress. The interface counts the tasks reporting each job id and drops the row when the last one completes. Nothing in a worker pool or a worker keeps job state or decides when a job is over, and a flow does not grow its own progress panel: the navbar indicator and the sidebar jobs list are where background work is shown. See [Tasks](docs/tasks.md).
- The `packages/user-interface` package is shared across all platforms (web, desktop/Electron, iOS, Android). It is not acceptable to put platform-specific code in that package: no Electron IPC or `window.electronAPI`, no Capacitor, no iOS/Android specifics. Keep platform-specific code in the relevant app/frontend (for example `apps/desktop-frontend`) and pass it into the shared UI via props or an existing platform abstraction.
- You are not to commit, stage, push, revert, or perform any other dangerous or hard-to-reverse Git operation (including `git add`, `git commit`, `git push`, `git reset`, `git restore`, `git checkout` of changes, `git rebase`, `git merge`, force-push, branch creation/deletion) without an explicit direction to do so in that message. An earlier instruction to do one of these is a one-time direction; it does not authorise repeating the operation after later edits. When in doubt, leave the Git state alone.
- Expect the human to stage things. They often `git add` your work as they review it, and they commit whenever they choose, so the staging area and the working tree change under you without warning and without being mentioned. Finding your edits staged, or finding files you never touched appear, disappear or move between staged and unstaged, means the human has been working. It is never a mystery to investigate and never a sign that something has gone wrong. Deal with it: use `git status` and `git diff HEAD` (or `git diff --cached`) rather than a bare `git diff`, which shows only unstaged changes and will report nothing at all for work that has already been staged. Do not conclude your edit failed or was lost because `git diff` came back empty, do not go digging through the reflog over it, and above all do not "tidy it up" by unstaging, resetting, checking out or otherwise putting the Git state back how you remember it. The rule above still holds: leave the Git state exactly as you find it.
- NEVER COMMIT WITH VERIFICATION DISABLED. `git commit --no-verify` (`-n`), `git push --no-verify` and every other way of skipping the hook (repointing `core.hooksPath`, altering or removing a hook, an environment variable a hook checks, an alias, a wrapper, a subagent) are banned for you, whatever the reason. If the hook refuses a commit, report the refusal and its output. Only the human runs `--no-verify`.
- ALWAYS START `git commit` AS A BACKGROUND COMMAND. The pre-commit hook runs the whole test set, which takes longer than a foreground command is allowed to run for, so a commit started in the foreground is killed part way through the hook every time. Nothing is recorded, everything stays staged, and the ten minutes it spent are gone. This is not a reason to reach for `--no-verify`, which is banned above, and not a reason to write a script that detaches the commit, which is banned below: the harness can start a command in the background, so start it that way and read the result when it finishes. The human has watched this same mistake made three times in one sitting.
- NEVER modify the git hook or the scripts it calls: `.githooks/pre-commit` and `scripts/install-hooks.sh`. They are verified by hand and frozen, and an edit of any size, including a comment or a fix, throws that verification away.
- NEVER ADD A NEW GITHUB ACTIONS WORKFLOW. Do not create a file under `.github/workflows/`, including a temporary, diagnostic or one-off workflow, unless the human explicitly asks for that workflow in the message you are acting on.
- A SUBAGENT GIVEN ONE FAILING TEST TO FIX RUNS ONLY THAT TEST. Do not tell it to run any other suite as well, such as `test:zig` or a full run, because every agent running the same extra suite at once is wasted time. Run the wider suites once, yourself, after the agents' changes are combined.
- THIS REPOSITORY USES TYPESCRIPT, ZIG AND SHELL SCRIPT. NOTHING ELSE. Zig is a primary language here, declared through `mise.toml`, and is the language for the backend, background tasks and shared code of new work. Do not introduce another language. `python3`, perl, Ruby, Go and friends are banned outright, including as an undeclared dependency: nothing here declares them, so every one is a thing that has to happen to exist on every developer machine and every CI runner. Java, Kotlin, Objective-C and Swift inside the native mobile projects are an exception, because iOS and Android require them. Swift is also allowed for the MacOS desktop native app, and C++ (Windows) and C (Linux) for a desktop native app only where Zig cannot host the system web view. None of that is licence to add more native code than the platform forces.
- A SHELL SCRIPT CONTAINS SHELL. Do not embed another language inside one, in any form: not `python3 -c "..."`, not `bun -e "..."`, not a `node -e`, not a heredoc feeding an interpreter, not an awk program that is really a program. Embedded code is a string as far as the shell is concerned, so `$`, backticks and quotes inside it are live shell syntax waiting to bite; nothing type-checks it, nothing lints it, `bun run compile` never sees it, and a syntax error in it surfaces only when that one code path runs. This holds however short the snippet is. "It is only one line" is how every one of them starts.
- When a shell script needs something that looks beyond shell, find the shell answer first, because there usually is one: `stat` for a modification time, `cmp` for an exact file comparison, `uuidgen` for a UUID, `od` for a binary field, `jq` for anything JSON. Only when there is genuinely no shell answer (speaking a vendor's API through its SDK, running a long-lived server) does it become a TypeScript helper: a real `.ts` file under `scripts/`, with a comment block saying what it is for and a documented argument list, invoked as `bun scripts/thing.ts <args>`. See `scripts/seed-s3-bucket.ts` for the shape. That file gets type-checked, read and tested like the rest of the codebase. A string inside a shell script gets none of that.
- When the human asks for an ETA, give one at once, as a time range with what it depends on. Never refuse, argue or ask a question first.
- Keep this file terse. It is loaded into context for every task, so state the rule and stop: no lists of examples, no worked illustrations.
- EVERY NEW SCRIPT COMES WITH A MARKDOWN FILE BESIDE IT, named after the script, covering what it is for, how it is invoked and what each argument means. Keep it current, and link to a fuller guide under `docs/` rather than repeating one.
- DO NOT WRITE TESTS FOR SHELL SCRIPTS or create `*.test.sh` files.
- TEST MARKER FILES ARE BANNED. Do not add a file whose only job is to tag a test directory so a runner treats that test differently, whatever it is called (`.slow` was one, and it has been removed). A marker records a judgement made once, by measuring or by guessing, and then nothing ever re-checks it: the test it describes gets faster or slower, or is deleted, or a new test that needed the marker never gets one, and the file goes on saying the same thing while quietly meaning something else. Nothing fails when it goes stale, so nobody finds out. If a runner needs to know something about a test, it must read it from the test itself or work it out at the time.
- DO NOT PASS `--force` TO `test:everything` UNLESS THE HUMAN ASKS FOR IT. Without it only the suites whose watched paths changed since they last passed are run, which is the point of the change gate and is usually a couple of minutes. Forcing runs every suite including the whole mobile set, which is where the ten minutes goes, and it is almost never what a change needs. Use the plain `bun run tev`. Force it only when the human asks for the whole set. A rebase is not a reason: the gate compares file content against the last passing run, so it is unaffected by commits being rewritten underneath it and reports exactly the files that actually differ.
- Assume there IS a shell answer until you have tried it and watched it fail. Eight helpers were once written here on the judgement that shell could not do their job, and six of them were later replaced by shell that does exactly that: finding a free port, decoding a little-endian binary field, percent-encoding, escaping and reading JSON, resolving a package path, and rewriting a file. Every one of those had a comment asserting there was no shell answer, and the assertion was the only evidence behind it. If you are about to write that sentence in a new helper, that is the moment to go and try the shell version instead.
- The local iOS development environment is fixed: macOS 12.7.6 and Xcode 14.2. That is why the project is stuck on Capacitor 5 (later Capacitor requires a newer Xcode/macOS). Never bump tool or framework versions that would break this environment: do not upgrade Capacitor past 5, and do not require an Xcode or macOS version newer than Xcode 14.2 / macOS 12.7.6. When mobile code needs a newer API, prefer an availability guard or a compatible approach over raising a version.
- When the human asks you to record a note or a todo, never change their writing or distort it in any way.

## Project Overview

Photosphere is a self-hosted, cross-platform photo and video management application built as a monorepo using Bun workspaces. It includes web, desktop (Electron), mobile (iOS/Android), and CLI interfaces.

## Commands

### Setup
- `bun install` (from repo root) - You must do this before you can run any other scripts.
- `mise install` (from repo root) - Installs the pinned tools, including Zig for the `*-zig` packages.
- `bun run setup` - One-time, per-platform environment setup after `bun install`. Fans out to each package's own `setup` script via `bun --filter '*' setup`: the Photosphere App's (`apps/photosphere`, via `scripts/setup.sh`) installs the Android SDK toolchain on Linux/macOS (`scripts/android/install-android-sdk.sh --install`), does the iOS setup on macOS and the Windows setup on Windows. Git hooks (`bash scripts/install-hooks.sh`) and the pinned toolchain (`mise install`) are deliberately separate steps, not part of this.

### Run from repo root:
- **`bun run test:everything` (alias `bun run tev`) IS THE CANONICAL WAY TO TEST A CHANGE.** Whenever you need to know whether a change is good, whether that is before a commit, after a rebase, at the end of a piece of work, or because you were asked to "run the tests", this is the command, and plain, with no flags. `-- --force` makes every suite run regardless of what the change check thinks changed: it is for after a rebase, or when the human asks for the whole set, and not otherwise, because it is the difference between a couple of minutes and ten. Do not assemble your own sequence of `bun run compile`, `bun run test` and the smoke suites instead: that combination silently covers no mobile suite, so it passes while the mobile app is broken, and it is not what the git hook runs. The individual scripts below exist for narrowing down a failure once this one has told you there is one.
- **RUN THE WHOLE SET AT ONCE. NEVER SPLIT IT INTO SEQUENTIAL RUNS.** `test:everything` runs its suites in parallel lanes, and that is the point of it: the whole set takes about as long as its slowest suite instead of the sum of all of them. Splitting it up, whether that is running the mobile suite on its own first and the rest afterwards, or naming a subset of scripts to keep two runs from overlapping, turns fifteen minutes into an hour and makes a person wait for something the machine was doing anyway. Do not do it to avoid contention, do not do it to be careful with memory, and do not do it because a run failed once for a reason that has since gone. If a suite genuinely cannot run beside the others, that is a bug in the suite and it gets fixed there, not worked around by pacing the runs by hand. Naming particular scripts is for narrowing down a failure you already have, never for a full check of a change.
- `bun run compile` - Compile all TypeScript
- `bun run test:everything` (alias `bun run tev`) - Run the genuine full set for this platform, all at once (compile, unit, the Zig unit tests, the Zig CLI suite, the Photosphere App on the host and the Photosphere App on Android, or on iOS on macOS). Use this when asked to run "all tests". The only Release workflow test jobs it leaves out are the stories runs, the packaging builds, and `perf-tests`. A script is only run when the paths it watches (see `what-changed.yaml`) differ from what they were at the last passing run, so a docs-only change runs nothing. Exit code 0 means the tests passed, and that includes "Nothing to run: nothing has changed since the last passing run". Pass `-- --force` to run everything regardless, `-- --plan` to print the decision without running anything. Pass script names to consider only those, still in parallel. This is what the git hooks run; see `docs/git-hooks.md`. It needs the `what-changed` executable on your PATH, from https://github.com/ashleydavis/what-changed/releases.

## Architecture

- **Storage**: `packages/storage` abstracts filesystem (`fs:path`), S3-compatible (`s3:bucket/path`), and encrypted storage.
- **Frontend**: React 18 + TypeScript, Vite, shared UI in `packages/user-interface`.
- **Mobile**: Capacitor wraps the frontend for iOS/Android. Background tasks run in an embedded JS engine (JavaScriptCore on iOS, QuickJS on Android) driven by the native `JsEngine` Capacitor plugin via a `host.*` bridge, off the WebView. Shared TypeScript lives in `packages/mobile-frontend` (the `EmbeddedJsQueueBackend`, the `JsEngine` plugin interface, the mobile platform provider) and `packages/mobile-worker` (the embedded worker runtime, host-bridge machinery, and `worker.bundle.js` build). All 30 host functions the task handlers need (storage `fs`, hashing, media tools, networking, crypto) are implemented on both platforms; the NOT IMPLEMENTED error is a safety net for any Node.js API a background task calls outside that set.
- **Desktop**: Electron embeds the frontend via `apps/desktop`.

## Code Style
- **Types**: Use interfaces with PascalCase (`IStorage`) for types, explicit return types
- **Interface names always start with `I`** (`IStorage`, `IFileLister`, `IConfig`). This applies to every interface without exception, including ones that describe plain data and ones that describe a function. A new interface that does not start with `I` is wrong and must be renamed.
- **Naming**: camelCase for variables/methods, PascalCase for classes/interfaces
- **Imports**: Named imports for functions, default imports for modules
- **Functions**: Named functions for top-level methods, arrow functions for callbacks
- **Async**: Use async/await pattern for asynchronous code
- **Error Handling**: Try/catch blocks with specific error handling, custom error classes
- **Formatting**: 4-space indentation, braces on same line as control statements
- **Comments**: Line comments with `//` preceded by blank line, method docs above function. Use `//` comments for method docs.
- All global symbols (functions, types, interfaces, classes, constants) must have a `//` comment block above them explaining their intent.
- All fields in interfaces and classes must have a `//` comment explaining their purpose.
- Never use single-character variable names, including arrow function parameters (e.g. use `fileName => ...` not `f => ...`). Use long descriptive identifiers.
- Do not introduce a constant that is used once. A value used in one place goes inline at that place, where the reader can see it. `const IMPORT_RECORD_FILE_NAME = "imports.dat";` above the one function that joins it onto a directory says nothing the literal did not, and costs the reader a jump to find out. A constant earns its name when the value is used in more than one place, so that changing it in one and not the other is impossible, or when the literal genuinely does not explain itself and the name is what says why that value. Neither is true of a file name used once.
- Avoid single line if statements. All if statements should have curly brackets around the function body.
- Never put multiple statements on one line. Each statement should be on its own line.
- Never write an object literal on one line. Open the brace, put each property and each spread on its own line ending in a comma, and close the brace on its own line. This holds wherever the literal appears: an argument, a return value, an element of an array, a branch of a ternary. The only exception is an empty `{}`. A one-line literal makes a diff say the whole object changed when one property did, and it hides a property added to the end of a long line.
- Use 4 space tabs for indentation.
- Put `else` and `catch` blocks on a new line.
- Tests should go under the directory src/test in each package.
- Use `test(` not `it(` in Jest test files.
- Do not write unit tests for React components, contexts, or hooks. Do not use `@testing-library/react`, `renderHook`, or any component/hook rendering in tests. A React component/context/hook must be a thin shell. Only significant logic is worth extracting and testing: if a component/context/hook contains non-trivial logic, factor that logic out into a plain function under a `lib/` directory and unit-test the plain function. Do not extract or test trivial logic (for example a one-line string or URL builder) just to gain a test; leave it inline in the component and untested.
- You do not have to invent a new file to "get a test on it". A new file, a new exported interface and a new test file, so that a two-token change can be asserted, is a worse change than the one it was hiding: it is more to read, more to maintain, and it moves the code away from the thing it belongs to. This has happened here: a six-line function that built a log line and a comparison key was pulled out into `import-progress-line.ts` with its own interface and its own test file, sixty-one lines in total, for a fix that was dropping one field out of a key. It went back inline with the comment that explains it. When the logic genuinely belongs to something that already exists, put it there: the twin of that same fix went into `import-timings.ts`, which was already the home for that kind of decision and already had tests, and cost nothing. When it belongs nowhere and is small enough to read in one go, leave it where it is with a comment saying why it is written that way, and let the behaviour be covered by the test that exercises the feature. Reaching for a new file is a decision about where code lives, and "otherwise I cannot unit test it" is not on its own a good enough reason to make it.
- Refrain from using the `any` type in normal code, although it's ok sometimes in test code.
- Never use anonymous object types inline (e.g. `Promise<{ foo: number }>`). Always define a named interface instead, unless specifically asked to use an anonymous type.
- Never use IIFE async generator pattern (`(async function* () { ... })()`). Extract to a named `async function*` instead.
- Never use `ReturnType<typeof ...>`. Use the actual type directly (e.g. `NodeJS.Timeout` instead of `ReturnType<typeof setTimeout>`).
- Never use the `unknown` type. Use the actual type directly.
- Global variables are generally frowned on. Do not add one (a module-level mutable variable, a Zig top-level or struct-level `var`, or a `threadlocal`) unless the human explicitly asks for it. Pass the value down from whoever owns it instead.

## Restrictions
- TypeScript code should always compile after making changes.
- All tests should pass after making changes.
- Prefer to minimize the size of code changes.
- Prefer not to update test code unless needed.
- Add new tests for new code. Every function that is new, that you edit, or that the user asks you about should have unit tests. The exception is React components, contexts, and hooks, which are not unit tested (extract any testable logic into a `lib/` function and test that instead).
- Backward compatibility is not required.
- Use imports instead of requires.
- All imports should be at the top of the file and not inside any functions.
- Don't use dynamic imports.
- Don't add exception handling unless the human asks for it.
- Don't use default or optional parameter values unless specifically asked to.
- Never reformat or rewrite entire files. Only edit the specific lines that need to change.
