# Photosphere on Ziggy

The Photosphere App is built on [Ziggy](https://github.com/ashleydavis/ziggy), the Zig and system web view application framework. Ziggy's parts, its message protocol, how to add a message type, a task type or a native host callback, and its test hooks are described in [Ziggy's architecture guide](https://github.com/ashleydavis/ziggy/blob/main/docs/architecture.md). This guide covers how Photosphere is built on it.

## Taking Ziggy

Ziggy is not part of this repository. Photosphere takes every part of it from a checkout of [Ziggy's repository](https://github.com/ashleydavis/ziggy) in the directory beside this one, named `ziggy`:

- The Zig package: the `ziggy` dependency in `build.zig.zon` (`.path = "../ziggy"`). It gives the module `ziggy`, which holds Ziggy's core and its task queue (`@import("ziggy").task_queue`), and the build functions `build.zig` uses to build the app's core and its Linux and Windows native apps.
- The frontend package: `ziggy` in `apps/photosphere-frontend/package.json` (`file:../../../ziggy`).
- The Android native app: the `includeBuild` in `apps/photosphere/native/android/settings.gradle`, which builds Ziggy's Android native app from the checkout in place of the dependency `dev.ziggy:ziggy-native-android` in `apps/photosphere/native/android/app/build.gradle`.
- The Apple native apps: the local Swift package `../../../../../ziggy` in the Xcode projects under `apps/photosphere/native/ios` and `apps/photosphere/native/macos`, with the products `ZiggyNativeIOS` and `ZiggyNativeMacOS`.

Every one of these takes the same checkout. After changing Ziggy, run `bun install` to update `bun.lock` and run the whole test set.

Within one program, the app, `photosphere-core` and every package in `packages-zig` take Ziggy's core from the same `dependency` call in `build.zig`, so they share one copy of the task queue and its registries. Ziggy's task queue is written with helpers that Photosphere's `utils-zig` and `node-utils-zig` also have (the log, errors, the console, the uuid generators, the timestamp providers, the host requester, the process environment, running tools and a few more). Those helpers keep state of their own and their types pass between the task queue and Photosphere's code, so there must be one copy of each: the index files of `utils-zig` and `node-utils-zig` export Ziggy's (`@import("ziggy").task_queue.utils`) under the same names, and the files of those helpers in the two packages are not used.

## Where Photosphere lives


- **Core library:** `packages-zig/photosphere-core`, which gives Ziggy's core Photosphere's message handler and task handlers and builds the libraries the native apps link.
- **Native apps:** `apps/photosphere/native/<platform>`, the app half of each native app: the photo library, pickers, menu content, permission strings and background work. The iOS project builds with Xcode 14.2 on macOS 12.7.6, and no version is raised.
- **User interface:** the shared `packages/user-interface`, with its platform layer in `apps/photosphere-frontend`. The layer implements the shared UI's `IQueueBackend` (the queue backend) and `IPlatformContext` (the platform provider) on top of `window.ziggy`.
- **Zig packages:** the existing ports of the TypeScript packages in `packages-zig/*`. The rest of the non-frontend TypeScript is ported into them, each Zig file beside the Zig package that mirrors the TypeScript package it came from.

**Asset server:** images, video and asset writes go through an HTTP server on loopback that the core runs, not through JSON messages. It is the `asset-server` task (`packages-zig/node-api-zig/src/lib/asset-server.worker.zig`), which the page queues like any other task. It binds `127.0.0.1` at a port the operating system chooses and serves `GET /asset`, `POST /asset` and `POST /apply-database-ops` with the status codes and headers of the Express server it ports, including a CORS header that allows any origin (the page's origin is `ziggy-app://app` or `https://ziggy-app.invalid`, never `file://`). Like that server it ignores a `Range` header and answers the whole asset, and `POST /apply-database-ops` reads a JSON body of at most the size `express.json()` reads. The task reports the port to the page in an `asset-server-ready` task message, which is also passed to the page as the `restApiUrl` query parameter. A connection serves one request and is closed. The HTTP server is `node-utils-zig`'s `http_server`, built on `std.http.Server`, and the routes and the core are `node-api-zig`'s `asset_server_routes` and `asset_server_core`; `rest-api-zig` is the port of `createAssetServer`, for a caller that wants the server without a task. Cancelling the task closes the server, waiting for requests that are being answered.

**Messages:** every app message is Photosphere's; Ziggy's own task, platform, menu and test hook messages are system messages, which the page sends only through Ziggy's own `window.ziggy` calls and which never reach Photosphere's handler. On the wire an app message is `{"kind":"app","id","name","data"}` (the `id` only on an `invoke`) and an app event is `{"kind":"app","data"}`; Photosphere's messages are databases, secrets, config, state, import, sharing, notifications, pickers and the mobile permission and export calls. The page sends each of Photosphere's messages with its name and its payload, `window.ziggy.invoke(name, data)` or `send(name, data)` (`apps/photosphere-frontend/src/lib/app-messages.ts`), and the core's message handler (`handleMessage` in `handlers.zig`) routes it by `message.name` and gives the handler `message.data`; a name it does not answer is the error `UnknownMessageName`. Photosphere's events reach the page as `{type, data}`, and the page routes them by type. A desktop menu item that is not one of Ziggy's standard actions reaches the same listener as Ziggy's app event `{type: "menu", item}`, which the platform provider handles (`apps/photosphere-frontend/src/lib/menu-actions.ts`); the menu itself is `packages-zig/photosphere-core/src/lib/menu.zig`. Photosphere's generic message for named actions is `main-command`.

**Handlers:** Photosphere's handlers are in `packages-zig/photosphere-core/src/lib`, one Zig file per group of messages (`vault.zig`, `databases.zig`, `recents.zig`, `pickers.zig`, `saving-assets.zig`, `config-and-state.zig`, `mobile-requests.zig` for the requests only a phone can answer, `share-import.zig`, `tools.zig`, `update-and-news.zig`, `logging.zig`, `main-process.zig` for the main command and the notifications that a database was opened, closed or edited, and `events.zig` for the events sent to the page), with the state the main process keeps in `main-state.zig` and the file logger in `file-logger.zig`. The app declares itself in one file, `apps/photosphere/core/src/app.zig`, with `ziggy.core.App`: every message with its handler, every task type with its task, the menu, the page and the hooks. A message whose work waits on something slow (the keychain, a file, a dialog, the phone) is passed to a task by its handler. That handler returns `.task`, so the work never holds up the thread that handles the page's messages. Each handler takes the payload the shared UI sends and replies in JSON, with `null` for no value. The core's `describe_error` is `describe_error.describeError` (`describe-error.zig`). A handler that cannot do what was asked throws a sentence the user can act on (`utils.errors.throwError`), never a bare error name, and `describeError` gives that sentence to the page; for the common errors the system returns (a missing file, a refused permission, a full disk) it gives a sentence of its own. Its tests run the real core on a fake native app with the settings directory and the vault pointed at directories the test owns (`src/test/test-support.zig`), and every test of code that logs captures the console, because the test program's standard output is how the build system talks to it.

**Startup and shutdown:** the work the app does as it starts and before it quits is done by the main process state (`main-state.zig`) when the core makes and destroys it. Starting it reads the process environment into `node-utils-zig`'s `process_env` (`environment.zig`; a core a native app hosts has no `main` to hand it over, and `PHOTOSPHERE_CONFIG_DIR`, `PHOTOSPHERE_VAULT_DIR` and `PHOTOSPHERE_LOG_DIR` move the settings, the vault and the logs), makes the file logger in the `logs` folder of `PHOTOSPHERE_LOG_DIR` (or of `photosphere` in the temporary folder), installs it as the log and logs that the app is starting, then registers the task handlers and starts the periodic sync and the timer thread. The asset server is started when the native app asks for the page's query (`page-query.zig`), because the page cannot render without its address: the query is `restApiUrl`, `theme` and, in a test build in test mode, `testMode=1`. Stopping it stops the periodic sync, cancels automatic import and the debounced sync and logs that the app is shutting down, before the task runner stops; destroying it, after the task runner has stopped, closes the file logger last and puts the earlier log back.

**MCP server:** the desktop app runs an MCP server so that an MCP client can work on the open database. It is the `mcp-server` task (`packages-zig/photosphere-core/src/lib/mcp-server.zig`), queued when the main window is created and run for the life of the app. A phone has none. It listens on `127.0.0.1` at the fixed port 3475 (a free port in test mode), and serves `POST /mcp` and `GET /mcp` over the Streamable HTTP transport of `mcp-zig` (`packages-zig/mcp-zig`, the protocol that `psi mcp` runs too). It offers these tools (`list_databases`, `open_database`, `close_database`, `get_database_summary`, `list_media_files`, `search_media_files`, `get_media_file_info`, `open_media_file`, `save_media_file`, `import_media_files`, `update_media_file`, `delete_media_file` and `verify_database`), and none of them does the work itself: each sends the page an `mcp-tool-request` event holding `{requestId, tool, args}` and waits for the page to answer with an `mcp-tool-response` message with `{requestId, result}` or `{requestId, error}` (`mcp-bridge.zig`). A failure to start the server is logged and the app carries on without it, and a server that stops after it was running is started again.

**Single instance:** the packaged desktop app runs once. The first copy keeps a lock on `single-instance.lock` in the app's data directory, which the operating system releases when the process ends in any way. A second copy that cannot take it leaves `single-instance.signal` beside it and asks the native app to quit, and the first copy finds the signal on its timer and asks the native app for the `focus-window` action. The rule does not apply to a build with no version, to a test or to a phone (`single-instance.zig`).

**Jobs:** background work the user can see and stop is grouped into named jobs, and jobs live only in the frontend. Whatever queues the task puts an `IJobTag` (`id`, `name`, and `cancelSource` when it can be cancelled from the interface) in the task's input data, and the handler reports with `sendJobProgress`. Nothing in Zig keeps job state or decides when a job is over. The interface counts the tasks reporting each job id and drops the row when the last one completes.

**Platform code and the shared UI:** `packages/user-interface` is shared by every platform and holds no platform code: nothing that touches `window.ziggy`, a native app or a phone's own features. That code lives in the platform layer in `apps/photosphere-frontend`, which passes it into the shared UI through the platform abstraction the shared UI defines.

**UI changes:** running the shared UI on Ziggy needed these edits to it, in `packages/user-interface/src/components`:

- `entity-card.tsx`: the actions `Dropdown` is wrapped in a `Box` with `display: contents`. The card hands its last child a `data-last-child` prop, and `Dropdown` renders no element of its own, so React warned that the prop reached a DOM node that does not take it. The wrapper takes the prop instead and changes nothing in the layout.
- `navbar.tsx`: the Import button carries `data-id="navbar-import-button"`. The test driver finds what it clicks by `data-id`, and the import cancel smoke scenario (`33-import-cancel`) has to press that button to go back to the import page after it has cancelled an import, when the gallery's own import button may no longer be on screen.

**Adding a task type:**

1. Write the handler in Zig. For a port of a TypeScript handler, put it in `packages-zig/node-api-zig/src/lib/<name>.worker.zig`, one file per `.worker.ts`, keeping the function names and control flow.
2. Register it in `packages-zig/node-api-zig/src/lib/task-handlers.zig` under the same task type string the TypeScript uses.
3. Report progress with the task context's `sendEvent`. For a job, report `job-progress` events through `sendJobProgress`, with the same fields as `packages/task-queue/src/lib/job-progress.ts`, carrying the `IJobTag` found in the task's input data.
4. Check `isCancelled` at every step of long work and finish as cancelled when it is set.
5. The queue backend in `apps/photosphere-frontend` forwards `add-task`, `cancel-tasks`, `task-event` and `task-completed`, and the jobs indicator and sidebar list show the job.
6. Write the unit test in the package, and a smoke test scenario when the task is reachable from a page.

**Test hooks:** Photosphere's own test mode switch is `PHOTOSPHERE_TEST_MODE=1`, which the smoke tests and the story player set together with Ziggy's `ZIGGY_TEST_MODE`. The shared `packages/user-interface/src/lib/test-driver.ts` performs `click`, `type`, `get-value` and the other DOM actions by `data-id` in the page. `PHOTOSPHERE_TEST_PICK_FILE_PATH` and `PHOTOSPHERE_TEST_DOWNLOAD_FOLDER` answer the file and folder dialogs. In test mode the update check is skipped, and the news check is skipped unless `PHOTOSPHERE_NEWS_URL` names a feed (the page starts both checks, once, by sending `page-loaded` in a `main-command` message when it has loaded), and the MCP server binds a free port.

**Stories:** the stories browser in `packages/user-interface` runs unchanged on every platform. On desktop it opens from the Developer menu, whose content the core defines, and on Android and iOS from the hidden Developer screen. The story player (`stories:ziggy`, `stories:ziggy:and`, `stories:ziggy:ios`) launches the app in test mode, navigates it to the stories cycle and takes a screenshot of each story through the test control connection. The Android and iOS runs render every page at phone resolution, which is how pages that do not fit a small screen are found. See the [stories README](../packages/user-interface/src/stories/README.md).
