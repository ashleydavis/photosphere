# Flaky-test failure registry

A repo-wide record of every known intermittent (flaky) failure mode across the test suites in this repo (unit, CLI smoke, Electron smoke, mobile smoke, LAN-share, and any future suite). Each entry captures the mode's stable signature, which suite it came from, its root cause, and whether it is believed fixed. Match a failure's output against the patterns below, so a recurrence of a checked (fixed) mode is caught as a regression and its fix removed.

## Rules for categorizing a flaky failure

1. Only record a mode here if it is flaky: it has passed before and fails intermittently. A failure that happens every run is a deterministic bug, not a flaky mode. Fix it directly and do not add it here.
2. Fingerprint the failure by its earliest root error line, never by a downstream cascade. If one component never starts, a later "not ready" line is a symptom of the same mode, not a separate one.
3. Normalize out volatile tokens before matching. Strip ports, PIDs, timestamps, file paths, correlation/command ids, durations, attempt counts, and hashes. Keep only the invariant words.
4. One entry per distinct root cause. Same wording but a different root cause is a different entry. Different wording but the same root cause is one entry that lists both patterns.
5. Every entry carries: id, a Fixed checkbox, suite (the test suite and command it was seen in), pattern (a regex over the invariant text), fix commit, first seen, recurrences, root cause, and evidence.
6. A mode's Fixed box stays unchecked until a fix has landed AND a repeated run of the suite passes clean. Only then tick the box and record the fixing commit hash in Fix commit.
7. Recurrence rule: if a new failure matches the pattern of a checked entry, that fix is disproven. Untick the box, append the recurrence date, and remove the failed fix commit so a fresh fix can be tried. A checked box is only as good as the next matching failure.
8. The pattern must match invariant text only. Use `port \d+`, never `port 43227`.
9. Checked means the Fixed box is ticked AND Fix commit records the commit hash that fixed it. That commit is what to remove if the mode ever recurs.

## Parallel-only failure modes

Modes in this section are not flaky in the ordinary sense. The suite is sound when it is run on its own and fails only in company: two scripts running at the same time contend on a file, a port, a directory, a lock or a device, and one breaks the other. `bun run test:everything` starts the suites concurrently and is what `.githooks/pre-commit` runs, so a mode here refuses a commit with a failure that does not reproduce when the suite is rerun alone.

Entries here carry the same fields as the main registry plus two of their own:

- **Pair**: the two scripts that must run together to produce it. It may name the same script twice, which is a self-pair: the suite cannot be run twice at once, so a second worktree or a rerun started before the last one finished will break it.
- **Shared resource**: the path, port, lock or device they contend on.

Rules for this section, on top of the ones above:

1. A mode only belongs here when `bun run test:parallel` classified it `interference`, meaning both scripts passed alone and at least one failed when they were run together. A verdict of `inconclusive` is not evidence: it means a script was already unreliable on its own, and that belongs in the main registry.
2. A mode reproducible from a single script alone belongs in the main registry, not here, even if it was first noticed under the parallel runner.
3. Record the detecting session directory under `tmp/parallel-check/<timestamp>/` in Evidence, the same way the main registry records `find-flakey-tests` sessions.

`SHARE-DB-REVIEW-STEP-NEVER-REACHED` below is the shape a self-pair finding takes: its root cause names another worktree's Electron suite announcing on the LAN during this one's discovery window, which is one copy of `test:electron` breaking another. It is left in the main registry because it also reproduces from one suite alone, against unrelated LAN traffic.

The first three entries here came out of the first run of `bun run test:parallel` over the fast set, and all three are self-pairs: `test`, `test:cli` and `test:electron` each failed against a second copy of itself, while the three cross pairs between them were all `ok`. That is what the check predicted: a suite that hardcodes a path is guaranteed to collide with a second copy of itself, and until then nothing looked.

Two of the three are now fixed by the per-test temporary directories on the `mobile` branch (`scripts/lib/allocate-test-temp-dir.sh`, sourced by both shell suites). Re-running the same check over the merged tree gives `ok` for all six combinations except `test` against itself, which is unchanged: the allocator is a shell helper and the surviving mode is inside a Jest test, so nothing reaches it. Session `tmp/parallel-check/20260805-062649`.

A single run is not enough to see it: an earlier run the same day that made one attempt came back `ok` and would have been read as a fix. `bun run test:parallel` now makes exactly one attempt per combination, so it would not have found this mode on its own, and a similar intermittent conflict in future will need `bun run find-flakey-tests` to surface it.

When a second run's `afterAll` removes the directory inside that window, the write has no parent directory and fails with ENOENT. Run on its own the suite never sees this, because only one process ever owns the directory.
- Evidence: session `tmp/parallel-check/20260804-115249`, `pair-test-test-side1-1.log` at the `encryption test:` lines: `FAIL src/test/key-utils.test.ts`, `1 failed, 34 passed`, the ENOENT naming the exact path, and the stack pointing at `src/test/key-utils.test.ts:107:9`, which is the `await fs.writeFile(keyPath, privateKeyPem)` two lines after the `mkdir`. ### JOB-CONTROL-PROBE-READ-AFTER-EXIT

- [x] Fixed. Not yet 10x clean: the full run of `bun run test:parallel` after the fix gives `ok` for all ten combinations (session `tmp/parallel-check/20260812-105148`), where the run before it gave `interference` for this pair (`tmp/parallel-check/20260812-085928`). One clean run says the cause is gone, not that the mode is retired, because the failure needs the machine loaded enough to delay one `ps` past a second and so will not appear on every run.
- Fix commit: 26d026f2 "Stopped the job-control probe dying before its process group was read". The probe in `process_control_verify_job_control` (`scripts/lib/process-control.sh`) sleeps 60 seconds instead of 1, and is still killed the moment its group has been read.
- Suite: mobile smoke tests (`bun run test:and`), test 2 (create-database). Nothing about it is specific to that test or that suite: every suite that launches a process through `scripts/lib/process-control.sh` runs this check once per shell, so any of them can be hit by it.
- Pair: `test` with `test:and`
- Shared resource: not a file, port or device. What is contended is the machine's CPU: the mode needs enough load elsewhere to delay a single `ps` call past one second.
- Pattern: `bash job control did not put a background job in a process group of its own on this host \(probe pid \d+ landed in group '', this script is in group \d+\)`
- First seen: 2026-08-12, the first run of `bun run test:parallel` over the full set including the mobile suites, session `tmp/parallel-check/20260812-085928`. Both scripts were clean alone and `test:and` failed when the two ran together; the other nine combinations in that run were `ok`.
- Recurrences: none yet
- Root cause: **the check read the process group of a probe that had already exited, and read the empty answer as proof that job control was broken.** `process_control_verify_job_control` proves once per shell that a background job lands in a process group of its own. It started the probe as `sleep 1 &` and then read its group with `process_group_of`, which forks a subshell and execs `ps -o pgid=`. `ps` prints nothing for a pid that no longer exists, so on a machine busy enough for that read to take more than a second the probe was gone before it was looked at and the group came back empty. The check has no way to tell that apart from a host that does not make groups, so it recorded the shell as unable to launch anything and every later launch in that shell refused. The suite then waited out both of its 120s readiness attempts against an app that was never started, which is the 258s the failing test took.
- Evidence: session `tmp/parallel-check/20260812-085928`, `report.txt` and `pair-test-test-and-side2.log`, with the test's own log at `/tmp/photosphere-tests/2-create-database-SaJ5s5/test-run.log` holding the message above followed by `Cannot start the control bridge without a process group of its own`, an empty port in `Waiting for app to be ready on port `, and `adb: error: Invalid source port: ''`. The same message reports a non-empty group for the script itself, which is what rules out `ps` being unable to read groups on that host: only the probe's group was empty. Reproduced directly: a one second probe read after a two second delay reports an empty group while the shell's own group still reads fine, and a sixty second probe read after the same delay reports its own pid.

### BRIDGE-START-BIND

- [ ] Fixed and verified (10x clean)
- Suite: mobile smoke tests (`bun run test:and` / `bun run test:ios`)
- Pattern: `Control bridge did not start on port \d+ within \d+s`
- Also matches (same mode, message since reworded): `is still running but did not answer on port \d+`
- Cascade symptom (same mode, not a new entry): `Timed out waiting for app to be ready after \d+s`
- Fix commit: none. The entry previously named an uncommitted working change as the fix, so nothing ever landed and the mode stayed live.
- First seen: 2026-07-06, local 10x loop, run 10 of 10, test 3 (open-database). Runs 1 to 9 passed.
- Recurrences:
  - 2026-07-06, skill loop iteration 7 of 100 (`bun run test:and`), failed on run 10 of 10 with `Control bridge did not start on port N within 20s`.
  - 2026-07-07, skill loop iteration 15 of 100 (`bun run test:and`), failed on run 7 of 10 with the same bridge bind failure.
  - 2026-07-07, skill loop iteration 18 of 100 (`bun run test:and`), failed on run 2 of 10 with the same bridge bind failure.
  - 2026-07-07, skill loop iteration 21 of 100 (`bun run test:and`), failed on run 7 of 10 with the same bridge bind failure.
  - 2026-07-30, five occurrences in one day under `bun run test:everything` (tests 13, 17, 11, 2 and 31; five different ports, five different PIDs, never the same test twice).
  - 2026-07-30, reproduced deliberately 7 times with full evidence: once in `bun run test:and` (test 19, port 42071) and 6 times across 4000 instrumented bridge starts (ports 42691, 35793, 33303, 42329, 40939, 42329). Root cause established, see below. No fix applied.
- Verified: the 2026-07-09 "verified" claim stands only against the old explanation. The real cause below was never addressed, and the mode recurred.
- Root cause: **the probe talks to the Android emulator instead of the bridge, because `localhost` is not `127.0.0.1` as far as curl is concerned.**
  - `ControlBridge.start()` calls `httpServer.listen(0, "0.0.0.0")`, so the bridge listens on **IPv4 only** and the OS assigns a port from the ephemeral range (`net.ipv4.ip_local_port_range` = 32768-60999).
  - Each Android emulator's QEMU process holds several listeners on **`[::1]`** (its console and QMP ports), drawn from that same ephemeral range. With the 5-emulator pool up there are ~25 of them.
  - Binding `0.0.0.0:P` while `[::1]:P` is already held **succeeds**, because they are different address families. Verified directly: every other combination (`127.0.0.1:P` vs `0.0.0.0:P` in either order, `[::]:P` vs `0.0.0.0:P`) is refused with `EADDRINUSE`. So the bridge legitimately ends up sharing a port number with a QEMU console.
  - `wait_for_bridge` probes `http://localhost:$port/ready`. **curl carries its own built-in mapping of the name `localhost` to both `::1` and `127.0.0.1`, and tries IPv6 first**, regardless of `/etc/hosts` or `getaddrinfo`. On this machine `getent hosts localhost` and `getaddrinfo` both return `127.0.0.1` only (there is no `::1 localhost` line), which is why the IPv6 explanation was wrongly dismissed in earlier investigations.
  - So the probe connects to `[::1]:P`, which is the emulator console, not the bridge. The TCP connection **succeeds**, so curl never falls back to IPv4. The console speaks its own protocol, so curl fails at the HTTP layer with exit 1 (`Received HTTP/0.9 when not allowed`) or exit 56 (`Recv failure: Connection reset by peer`).
  - This is deterministic for the whole 40s: all 200 probes hit the console. The bridge is alive, listening and healthy throughout, and answers instantly on `127.0.0.1`.
  - Rate: ~25 QEMU `[::1]` listeners over a 28232-port range is 1 collision per ~1129 bridge starts. The Android suite performs 38 bridge starts per run, so ~3.4% of runs. Observed 6 failures in 4000 starts against 3.5 predicted.
- Evidence (2026-07-30, all 7 reproductions identical in shape):
  - `The control bridge (PID 1634885) is still running but did not answer on port 42071 within 40s (last curl exit 1, 200 probes in 43s).` The probe count is measured, not assumed: it is 200 fast failures, not one hung curl.
  - `curl via localhost: exit 1 -- curl: (1) Received HTTP/0.9 when not allowed`
  - `curl via 127.0.0.1: exit 0` (the bridge answers immediately, in the same second)
  - `curl via [::1]: exit 1 -- curl: (1) Received HTTP/0.9 when not allowed` (identical to the name, which is the point)
  - `lsof -i :42071` shows both owners at once: `bun 1634885 IPv4 TCP *:42071 (LISTEN)` and `qemu-syst 3156721 IPv6 TCP [::1]:42071 (LISTEN)`.
  - The bridge process is `S`/`ep_poll` with 13 open descriptors: idle and healthy, not blocked, not out of descriptors.
  - Confirmed in isolation: with a listener bound only on `[::1]:P` and nothing on `127.0.0.1:P`, `curl http://localhost:P/` reaches it and reports `Received HTTP/0.9 when not allowed`, while `curl http://127.0.0.1:P/` gets connection refused.
- Note on the earlier explanation: the process is not dying and there is no `EADDRINUSE`. The bind always succeeds. The previous entry's three "compounding factors" describe a different failure that a retry-on-EADDRINUSE would not have touched.

The desktop path does not use `useAssetServer`: `apps/desktop-frontend/src/app.tsx` reads `restApiUrl` from a query parameter and throws when it is missing, so an unset url is ruled out. What is not known: whether the connection was refused, reset, or resolved to an address nothing was listening on, because the client reports every one of those as the same bare `Network Error`.
- Why it was not diagnosable: the catch block logged `Failed to load asset: thumb:<id>` and the error's message, and an HTTP client's message for any no-response failure is the constant string `Network Error`. No code, no status, nothing to separate ECONNREFUSED from ECONNRESET from a bad address. The change records the code and status. **It does not stop the mode**: the run still fails and the green count still resets. It makes the next occurrence say which failure it was.
- Retry (added on the human's instruction, after the entry above was first written): every GET through `axiosApi` retries a transient failure, up to `HTTP_REQUEST_ATTEMPTS` (3) attempts `HTTP_RETRY_DELAY_MS` (250ms) apart, logging a warning on each retry (packages/user-interface/src/lib/retry-http-request.ts).
- **The first version of that retry never fired for this mode, and the claim that it would stop the mode was wrong.** `isTransientHttpError` asked only whether the error carried a response object. This failure carries one, with `status: 0`, which is not an answer from the server but what the client fills in when the request failed at the network layer. The predicate read that as a considered answer and did not retry. Proved by the recurrence below: four `Failed to load asset` errors and zero retry warnings in the same app log. The predicate now also treats a response with status 0 as transient. It still does not explain why the request failed, and the retry warning is the thing to look for in a future log. POST is deliberately not retried: the database ops it carries include `push` and `pull`, so re-sending a request whose response was merely lost would apply the op twice.
- Root cause, established on the second recurrence: **the renderer was told to reach an IPv4-only server by a name that can resolve to IPv6 first.** `createAssetServer` binds `127.0.0.1` only (packages/rest-api/src/lib/asset-server.ts), while `apps/desktop/src/main.ts` handed the renderer `http://localhost:<port>`. Nothing normally listens on `[::1]:<port>`, so the connection falls back to IPv4 and the name appears to work. But the server takes an OS-assigned port from the ephemeral range (32768-60999) and each Android emulator holds console ports on `[::1]` from that same range: 25 of them were confirmed live with the pool up. When the two collide the connection to `::1` succeeds, so there is no fallback, and every asset request reaches an emulator console instead of the asset server. This is the same mechanism as BRIDGE-START-BIND, which was reproduced 7 times in this repository and fixed the same way.
- Fix: the URL is now the literal `http://127.0.0.1:<port>` in apps/desktop/src/main.ts, in packages/user-interface/src/lib/use-asset-server.ts and in the asset server's own log line, and `apps/desktop-frontend/index.html` now allows `http://127.0.0.1:*` and `ws://127.0.0.1:*` in its content-security policy.
- **What is proved and what is not.** Proved: the server binds IPv4 only; the URL used the name; 25 QEMU listeners hold `[::1]` ports in the same ephemeral range; the failure persisted across all three retry attempts within ~500ms, so it was not transient. Not proved: that Chromium chose `::1` in either occurrence. The ports involved (37371, 35617) are long gone and cannot be checked after the fact, and a probe written to demonstrate the hazard showed Bun's `fetch` prefers IPv4, so it does not stand in for Chromium. The fix is justified regardless, because binding one address family and connecting by a name that can resolve to another is wrong on its own terms, but the causal link is inference and the next recurrence is what would disprove it.
- **A trap found while fixing it, worth knowing:** switching to the literal without updating the content-security policy turned a roughly 0.4% intermittent failure into 5 of 25 Electron tests failing every single run, with a byte-identical signature: `code=ERR_NETWORK, status=0`, persistent, retries not helping. A CSP block and a connection to the wrong process are indistinguishable in the log. That is worth remembering before reading this signature as a network problem again.
- Not done deliberately: the test's `no errors in app.log` assertion was left exactly as it is. The app really did log an error, and loosening the assertion would hide the mode rather than fix it.
- Evidence: `apps/desktop/smoke-tests/20-download-multiple-assets/tmp/app.log` from run 247, lines 6, 30 to 39 and 44. The new helper was watched failing on all four of its unit tests against a deliberately broken version before being accepted.
