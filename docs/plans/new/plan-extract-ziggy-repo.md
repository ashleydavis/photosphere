# Extract Ziggy into its own repository

## Overview

Ziggy (the Zig core, the native shells and the TypeScript bridge in `packages/ziggy`) moves to a repository of its own named `ziggy`, so that Photosphere and any new app use one copy. Ziggy is a package. The repository also contains the Ziggy example (`apps/ziggy-example`), which shows how to use the package and is what a new app is copied from. Nothing is published to npm or any other registry, and no Ziggy source is ever copied into an app.

The `ziggy` repository is new, with no history. It is a directory named `ziggy` beside this repository's checkout. It has no URL until the human publishes it. Until then, an app uses Ziggy from that directory by a local path. Once published, an app uses Ziggy from its git URL, pinned to a version tag. Version tags exist only for that: to release a version of the package and to pin it from another repository. They have nothing to do with the release workflow.

The agent runs no git command in any repository during this work: no init, no staging, no commit, no tag, no push. Every git operation, including creating the `ziggy` repository's git history, publishing it and cutting its tags, is the human's.

The work is done in these phases, each finished and proven before the next starts:

1. Move Ziggy and the example into the `ziggy` repository, and prove the framework tests, the example and the example's tests all work there.
2. Build a test app in a new repository of its own, from the example, using `ziggy` as a package, to prove a separate app can use it.
3. Remove the Ziggy code from this repository.
4. Connect this repository to the `ziggy` package, and prove every Photosphere test, app and smoke test works.

"Works" means works on every platform Ziggy delivers to: Linux, Windows and macOS for the desktop shells, Android and iOS for the mobile shells. Linux and Android run on this machine. Windows, macOS and iOS run in the release workflow, which can only run once the human has published the repository. iOS must build in the fixed local iOS environment (macOS 12.7.6, Xcode 14.2), so nothing in the Swift packages or the Xcode projects may need a newer Xcode.

## Issues

- Ziggy's core imports `task-queue-zig`, `utils-zig` and `node-utils-zig` from `packages-zig`. `task-queue-zig` is used whole. `utils-zig` and `node-utils-zig` are mostly Photosphere code (photo folders, image, reverse geocoding, TOML, YAML, an HTTP server); Ziggy and `task-queue-zig` use only `console`, `errors`, `host_requester`, `json`, `log`, `random_uuid_generator`, `timestamp_provider` and `uuid_generator` from `utils-zig`, and `in_process_tools`, `process_env`, `test_timestamp_provider` and `test_uuid_generator` from `node-utils-zig`, plus whatever those files import in turn. Only those parts move to `ziggy`. "node" is not an appropriate name for anything in a Zig package, and a "-zig" suffix says nothing inside one, so neither name goes with them. Photosphere's own packages use the moved parts too, so after the move Photosphere takes them from the `ziggy` dependency. The comment on `IQueueModules` in `build.zig` explains why Ziggy and the app must share one copy of each.
- `addZiggyCore` uses `packages-zig/android-libc.zig` for the Android build of the core. It moves to `ziggy`. Photosphere uses it too, so either Photosphere takes it from the dependency or it stays as well; decide at step 12 by what compiles.
- The example's Android scripts and smoke tests source Photosphere's `apps/android-frontend/scripts/android-env.sh` and `emulator-config.sh` (through `ZIGGY_CAPACITOR_ANDROID_DIR` in `apps/ziggy-example/scripts/android-common.sh` and `apps/ziggy-example/smoke-tests/lib/android.sh`). The `ziggy` repository cannot reach those. `emulator-config.sh` is how the example's smoke tests find Photosphere's emulator pool (its `psphere-pool` AVD prefix) and take Photosphere's per-device lock (`/tmp/photosphere-android-device-<n>.lock`). Ziggy must not depend on Photosphere's emulators.
- The example's smoke tests source `scripts/lib/test-lib.sh`, `test-timeout.sh` and `process-control.sh` from this repository's root.
- Photosphere's app is wired to Ziggy by relative paths: `apps/photosphere/shells/android/settings.gradle` (the `:ziggy-shell-android` project), both Xcode projects under `apps/photosphere/shells/ios` and `apps/photosphere/shells/macos`, and `"ziggy-bridge": "workspace:*"` in `apps/photosphere-frontend/package.json`.
- The `build.zig` functions for Ziggy are now `addZiggyCore`, `embedPage`, `addZiggy`, `addLinuxShell`, `addWindowsShell`, `findRuntimeLibrary`, `library_directories`, `linux_runtime_libraries`, `IZiggyCore`, `IShellApp`, `IQueueModules` and `addQueueModules`, plus the helpers they call (`addDirectoryTests`, `IImport`, `internalStep`). `addPhotosphere` calls `addZiggyCore`, `addLinuxShell` and `addWindowsShell`.
- A local path to the `ziggy` directory resolves only from this repository's main checkout. From a worktree under `.claude/worktrees/` the same relative path points somewhere else, and on a GitHub runner there is no `ziggy` directory at all, so this repository's Release workflow cannot build against a local path.

## Steps

### Phase 1: the `ziggy` repository

1. Create the `ziggy` directory beside this repository's checkout. Copy into it, by plain file copy, `packages/ziggy`, `apps/ziggy-example` and `packages-zig/android-libc.zig` at the same paths. Copy `packages-zig/task-queue-zig` into `packages/ziggy/task-queue`, and copy the parts of `packages-zig/utils-zig` and `packages-zig/node-utils-zig` listed under Issues, with their tests, into that same task queue package: the helpers get no package of their own. Rename the core's module from `ziggy-core` to `ziggy`, and change every `@import("ziggy-core")`, `@import("task-queue-zig")`, `@import("utils-zig")` and `@import("node-utils-zig")` in the copied code to `@import("ziggy")` or `@import("task-queue")`. Copy no build output and nothing git ignores (`node_modules`, `.zig-cache`, `zig-out`, `dist`, `out`, `build`, `release`, downloaded SDKs). Do not run `git init`.

    Done. Copied with rsync, leaving out build output, caches and downloaded SDKs; no git command was run. Decisions: the task queue is `packages/ziggy/task-queue`, with the helpers in `src/lib/utils/` and exported as `@import("task-queue").utils`, so code that used `utils-zig` or `node-utils-zig` changes only its import line. The moved helpers are the ones listed under Issues plus everything they import (`standard-streams`, `wrapped-error`, `format`, `js-number`, `js-string`, `utils-zig`'s `test-uuid-generator`, `exec`, `path`) and `sleep`, which a moved test uses. `node-utils-zig`'s `test-uuid-generator.zig` became `file-test-uuid-generator.zig` (`file_test_uuid_generator`), because `utils-zig` has a file of the same name. Two moved tests used `node-utils-zig`'s `fs`, which stays in Photosphere: they now use the standard library for the same check (`pathExists`) and write (`createDirPath` and `writeFile`), with the assertions unchanged. The fixture generators (`generate.ts`) were not copied, because they run Photosphere's TypeScript; their JSON output was. Every `node_utils` name in the copied code became `utils`. The Linux shell named Photosphere in two strings (a refused host request and the suspend inhibit reason); both now name no app.

2. Give `ziggy` its own setup: `mise.toml` pinning the Zig, Bun and Node versions from this repository's `mise.toml`; a root `package.json` with Bun workspaces for `packages/ziggy/bridge` and `apps/ziggy-example`, carrying the `*:ziggy-example:*` and `test:ziggy-example*` scripts from this repository's `package.json`; `.gitignore`; `LICENSE` (the same license as this repository); and `bun.lock` from `bun install`.

    Done. `mise.toml` pins Zig, Bun, Node and jq (the example's scripts use jq; `what-changed` is Photosphere's and was left out). The root `package.json` also has `setup`, `compile`, `test`, `test:zig`, `test:android-shell`, `test:zig:android` and `test:zig:ios`, and its `main` and `types` point at the bridge, so `ziggy-bridge` can be installed from the repository's git URL (see step 6). The licence is MIT with the copyright line naming Ziggy's contributors.

3. Write `build.zig` and `build.zig.zon` for `ziggy`. Move in the functions listed under Issues, except `addPhotosphere`. Make it usable from another build: the package is named `ziggy` and exposes these modules with `b.addModule`, `ziggy` (the core, which an app imports as `@import("ziggy")`) and `task-queue` (the task queue and the helpers moved with it, for code that needs the task queue without the app shell, such as Photosphere's CLI), and export as `pub fn` what an app's build needs (making the core for a target with or without test hooks, `embedPage`, `addLinuxShell`, `addWindowsShell`, `IShellApp`). The `test` step runs the tests of the core, the shells, the moved packages and the example's core. Keep the `test-hooks` and `optimize` options working through a dependency.

    Done. The `pub` functions are `dependency` (Ziggy for a target, with or without the test hooks, as `IZiggy`), `addAppCore` (an app's core library and its `<name>-core` step, which replaced the copy of that code in `addZiggy` and `addPhotosphere`), `addLinuxShell`, `addWindowsShell`, `embedPage` and `addDirectoryTests`, with `IShellApp`, `IAppCore`, `IAppCoreLibraries` and `IImport`. They take Ziggy's files from the dependency (`ziggy.dependency.path`) and the app's from the app's build. Decision: the example is a Zig package of its own (`apps/ziggy-example/build.zig` and `build.zig.zon`, with Ziggy as the dependency `ziggy` at `../..`), so it uses Ziggy exactly as an app in another repository does and is the template for one. The root `test` step builds the example's page and then runs the example's `zig build test` as a program of its own, because the example's core embeds the page, which its build reads when it starts. The console program that checks the real stdout moved with `console.zig` and runs under `test` too.

4. Copy the shell libraries the example sources from `scripts/lib/` (`test-lib.sh`, `test-timeout.sh`, `process-control.sh`, and whatever those source in turn) into `ziggy`'s `scripts/lib/`, each with its markdown file, and fix every `$REPO_ROOT/scripts/lib/...` reference. Copy `android-env.sh` (and whatever it sources) from `apps/android-frontend/scripts` into `ziggy`, and change `android-common.sh` to source the copy. Remove `emulator-config.sh` from the example: `smoke-tests/lib/android.sh` uses whatever Android emulator or device is attached (the ones named in an environment variable of Ziggy's own when it is set), with no knowledge of Photosphere's pool, its AVD names or its locks. It takes a per-device lock of Ziggy's own, named so it cannot collide with Photosphere's, so that two Ziggy runs never install over each other. `ziggy` may have emulator scripts of its own, but its tests do not require them. Fix `zig-packages.sh`, `test-zig-mobile.sh` and the markdown links that point outside the two moved folders.

    Done. The libraries were copied with Photosphere's names changed to Ziggy's (`PHOTOSPHERE_*` to `ZIGGY_*`, `photosphere_test_temp_dir` to `ziggy_test_temp_dir`), and `test-lib.sh` keeps only the per-test directory, the one part the example uses. `install-android-sdk.sh` was copied as well, because the example's `setup-android.sh` ran Photosphere's. The example's Android project now has its own `variables.gradle` (SDK levels and NDK), because it read them from Photosphere's Android app, and Ziggy's Android shell sets its own and is a Gradle build of its own (see step 6). The lock is `$TMPDIR/ziggy-android-device-<serial>.lock`, the variable naming devices is `ZIGGY_ANDROID_DEVICES`, and `run-android.sh` picks a device the same way. Every script now builds from the example's own `build.zig`. In phase 2 these libraries moved again, into the example (see step 10).

5. Write `ziggy`'s release workflow, `.github/workflows/release.yml`, from this repository's `.github/workflows/ziggy-example.yml` with paths fixed for the new layout. It runs on every push and has nothing to do with tags. It builds and runs every test (the unit tests, the example's build and the example's smoke tests) on every platform, packages the example for every platform with the example's own package scripts (as the `ziggy-example-package` job does now), and, only when every one of those passed, publishes the packaged example apps with release notes from a copy of `scripts/release-notes.sh`. A failed run publishes nothing. The workflow does not run until the human publishes the repository.

    Done. The workflow itself cannot run before the repository is published, as this step says, and no git command may be run, so it has not run on GitHub. Its Linux and Android commands were run here and passed: `bun run compile:zig` (the zig-build job), `bun run package:ziggy-example:linux` (a zip and a .deb) and `bun run package:ziggy-example:android` (an APK per architecture), besides the unit and smoke test commands under step 8. Jobs: `zig-build`, `unit-tests` (adds the Android shell's JUnit tests and the Zig tests on an emulator and a simulator), `smoke-tests` (adds Android on an emulator and iOS on a simulator, which the old workflow did not run), `package` and `publish`. Decisions: `publish` runs only for a push to the default branch, so other branches and pull requests test everything and publish nothing; the packages go to a GitHub release named "Ziggy example" on the tag `example`, which the workflow deletes and makes again on each publish, because a GitHub release needs a tag and the workflow must not touch version tags. The `retry-install` and `install-apt-packages` actions were copied. The file parses as YAML.

6. Make each part of Ziggy usable by an app both from a local path (now) and from a git URL pinned to a version tag (once published): the Zig package through `build.zig.zon` (`.path` now; the tag's `archive/refs/tags/<tag>.tar.gz` URL and hash once published), `packages/ziggy/native/macos/Package.swift` and `packages/ziggy/native/ios/Package.swift` as Swift packages (a local package now; a git URL and tag once published), `packages/ziggy/native/android` as a Gradle dependency (an included build now; a source dependency, `sourceControl { gitRepository(...) { producesModule(...) } }` in the app's `settings.gradle`, once published), and `ziggy-bridge` through `package.json` (a `file:` dependency now; a git URL and tag once published). If the Android dependency does not build, stop and report it; do not publish a library and do not copy source.

    Done for a local path, and checked by the example and the test app on Linux and Android. The Android shell is a Gradle build of its own (`settings.gradle`, its own plugin and SDK versions, `group` `dev.ziggy`), which the app includes with `includeBuild` and depends on as `dev.ziggy:ziggy-shell-android`; it builds. For a version tag: a `Package.swift` at the root of the repository holds both Apple shells (Swift Package Manager fetches a package only from a repository's root); the source dependency names `rootDir = 'packages/ziggy/native/android'`; and the root `package.json` points at the bridge, because Bun installs a git dependency from the repository's root. Decision: version tags are `v` and the version, such as `v0.1.0`. None of the version tag lines can be tried until the repository is published, and they have not been.

7. Write `ziggy`'s README and `docs/`, each guide covering every platform:
    - Integrating Ziggy: what the package contains, and the exact lines an app adds to use it from a local path and from a git URL and version tag, in `build.zig.zon`, `build.zig`, the Xcode projects, `settings.gradle` and `package.json`, and how to move an app to a newer tag.
    - Building your app: starting a new app from the example (copy, rename, change identifiers), the parts of an app (core, page, handlers, shells), and the commands to set up, build, run and test on each platform.
    - Distributing your app: packaging for each platform with the package scripts, signing for each platform, and getting a build to testers and stores, including the content of this repository's `docs/android-tester-distribution.md` as it applies to a Ziggy app.
    - Releasing Ziggy: what the release workflow does on each push and how to read a failed run, and how a version tag of the package is cut for apps to pin.
    Move `packages/ziggy/docs/architecture.md` in with them.

    Done: `README.md`, `docs/integrating-ziggy.md`, `docs/building-your-app.md`, `docs/distributing-your-app.md`, `docs/releasing-ziggy.md` and `docs/architecture.md`, and the READMEs of `packages/ziggy` and the example rewritten. The architecture guide's section "Photosphere on Ziggy" was left out of Ziggy's copy and replaced by where Ziggy's parts are; its content stays in this repository's copy and has to be kept in Photosphere's docs in phase 4.

8. Prove phase 1 on this machine: in `ziggy`, run the unit tests, build and run the example, and run the example's smoke tests on Linux and Android. Windows, macOS and iOS are proven by the release workflow once the human publishes the repository and pushes.
