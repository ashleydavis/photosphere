## Decisions not approved by a human

Made by the agent while fixing this plan's issues. Each follows from a settled choice or an existing behaviour; none reopens the human's choices.

- A typing shortcut on a letter, a digit, `Plus`, `Minus`, `Equal` or `?` is matched by the character it types (`KeyboardEvent.key`), keeping what GTK and macOS do today on non-US layouts; named keys stay matched by `KeyboardEvent.code`.
- A typing shortcut that holds Shift with a digit, `Plus`, `Minus` or `Equal` fails the build.
- A `radio` and a `range` input count as text boxes; a focused button, link or checkbox does not, so a typing shortcut on Enter or Space runs there in place of the element's own response.
- The listener reads `event.composedPath()[0]` in place of `event.target`, so a text box inside an open shadow root keeps its keys.
- Windows matches a `Plus` shortcut on the key that types `=` in the current layout; macOS matches `=` for a `Plus` menu item in a local key monitor in place of a hidden alternate menu item.
- The docs say a page's `keydown` handler added on `window` in the bubbling phase runs after Ziggy's and does not keep the key, in place of the inject script deferring its decision.

## Overview

Ziggy's docs say a shortcut works wherever the focus is, and the code does that on every desktop platform: the native app takes the key before the web view sees it. That is wrong for the keys a text box uses. An app whose action is on Escape, Enter or an arrow key takes that key from a text box the user is typing in. Per platform, today:

- Windows (`packages/ziggy/native/windows/src/lib/native-app.zig`, `acceleratorInvoke`, line 1622): WebView2's `AcceleratorKeyPressed` fires before the page sees a key. Microsoft's docs state that it fires for every key that "does not map to a character" and that "the `Escape` key is always considered an accelerator", so it fires for the arrow keys and Escape. For a key that matches a shortcut the code calls `put_Handled(1)` and runs the action, so the shortcut wins over the text box.
- Linux (`packages/ziggy/native/linux/src/lib/native-app.zig`, `buildMenu`, line 616, and `addStandaloneActionShortcuts`, line 722): every shortcut is a GTK accelerator on the window's `GtkAccelGroup`. GTK 3's window handles accelerators before it passes a key to the focused widget (the web view), so the shortcut is expected to win. GTK's source could not be fetched while writing this plan, so step 2 runs the new smoke scenario against the current code to observe it.
- macOS (`ZiggyMenu.swift`, `apply(accelerator:to:)`, line 197, and `ZiggyActionShortcuts.swift`, line 44): a menu item's shortcut is an AppKit key equivalent, and an action with no menu item is matched in a local key monitor (`NSEvent.addLocalMonitorForEvents`), which sees every key press before any window and returns `nil` for a match. The monitor wins over the text box for certain.
- Dev mode (`packages/ziggy/dev/src/lib/dev-client.js`, line 148): a `keydown` listener on `window` runs every shortcut and calls `preventDefault`, with no check of the focus, so it wins too.
- iOS and Android register no shortcut.

"The feature list" in this plan is `ziggy-updates.md`, in the directory that holds the four repositories (its "Shortcuts and text boxes" section, lines 72 to 79, and its feature lines 13 and 14). Graft, named there, is a Git client built on Ziggy.

This plan moves the typing shortcuts (those with no Ctrl, Alt or Cmd, other than function keys) into one `keydown` listener in the inject script (`packages/ziggy/core/src/lib/ziggy-inject.js`), which runs on every platform and skips the key when the element the key press started at (`event.composedPath()[0]`, the focused element: `event.target` before a shadow root retargets it) is a text box. The native apps stop registering typing shortcuts and keep every other shortcut. A typing shortcut is never shown in a menu: the build fails for a menu item that has one, so an action with a typing shortcut has no menu item. The same section of the feature list asks that shortcuts never clash with the web view's own keys and that `Ctrl+=` zoom in: Windows turns WebView2's browser accelerator keys off, and a `Plus` shortcut also runs on `=` on Linux and macOS. Windows' `accelerator.zig` matches `Plus` and `Equal` on `VK_OEM_PLUS` with Shift optional (lines 61 and 131), which is the `=` key on a US layout but the `+` key on a German one, where `=` is Shift and `0`; so Windows also matches a `Plus` shortcut on whichever key and Shift state types `=` in the current layout. Dev mode already matches a `Plus` shortcut on the `Equal` code with Shift not held (`browserKeyCode` in `dev-shortcuts.zig`); this plan lets Shift be held there too. The zoom items are `.standard` items, which dev mode does not run, so dev mode's part concerns an app's own `Plus` actions only. The zoom items are already in `listActions` whenever the app's menu has them: `listActions` in `core/src/lib/system-messages/action.zig` (line 67) lists every `.standard` item with its shortcut, and the template's View menu has Zoom In, Zoom Out and Actual Size with `CmdOrCtrl+Plus`, `CmdOrCtrl+Minus` and `CmdOrCtrl+0`. This plan adds a smoke test that proves it. It also lets an action have the shortcut `?`, which Graft's shortcuts overlay (feature list line 76) needs to open and close, while `?` still types a question mark in a text box. Today `?` cannot be a shortcut at all: `shortcut.parse` (`packages/ziggy/core/src/lib/shortcut.zig`, `writeKey` lines 95 to 123) knows letters, digits, function keys and a list of named keys, so `"?"` fails with `UnknownKey` and `rejectInvalidActions` (`action.zig` line 42) stops the build. A bare `?` is a typing shortcut, so the inject script's listener runs it. `?` has no fixed `KeyboardEvent.code`, because the key that types it differs between keyboard layouts (Shift and `/` on a US layout, Shift and `,` on a French one), and the same holds for letters, digits, `+`, `-` and `=` (AZERTY, Dvorak and German put them on other keys). GTK (keyval) and macOS (`charactersIgnoringModifiers`) match those keys today by the character the layout types. So this plan adds `?` to the shortcut grammar, matches a typing shortcut whose key is a letter, a digit, Plus, Minus, Equal or `?` by the character it types (`KeyboardEvent.key`) and only the named keys (Escape, Enter, the arrows and the like, which sit on the same key on every layout) by `KeyboardEvent.code`, teaches each desktop native app the key's name where it presses it for `press-key`, and adds a smoke scenario that presses `?` in and out of a text box. `window.ziggy.listActions()` reports the shortcut as `?` with no change to its code, because `writeDisplayText` writes a one character key as `std.ascii.toUpper` of it.

## Notes

- A typing shortcut is any shortcut with no Ctrl, Alt or Cmd (Meta) modifier whose key is not a function key; Shift is allowed. A focused text box types, moves its cursor or extends its selection with every such key, and with no function key, so this is the set the feature list's arrow keys, Enter and Escape belong to.
- Only the frontend knows which element has the focus, and a native app cannot ask the page before it decides on a key, so typing shortcuts are run by the inject script's `keydown` listener on every desktop platform and in dev mode, never by a native app. The feature list foresees this ("handles shortcut keys in JavaScript in the frontend").
- Shortcuts with Ctrl, Alt or Cmd, and function keys, stay with the native apps unchanged.
- The listener skips a key press whose `defaultPrevented` is set. It listens on `window` in the bubbling phase, so a page's own handler on an element, on `document` or on `window` in the capture phase has seen the key first, and one that calls `preventDefault` (or `stopPropagation`, which keeps the key from reaching `window` at all) has taken the key for itself. The inject script runs at document start, before the page's scripts, and listeners on one target in one phase run in the order they were added, so a page's handler added on `window` in the bubbling phase runs after Ziggy's: by then a typing shortcut has run and called `preventDefault`. The docs say so in place of claiming that every page handler keeps the key.
- The listener also skips a key press whose `isComposing` is true, so a key an input method uses while composing text runs no shortcut. This came from the `?` plan this plan absorbed.
- A text box is a `textarea`, a `select`, an element whose `isContentEditable` is true (which also covers a child of an editable element, as hotkeys-js checks), or an `input` of any type but `button`, `checkbox`, `color`, `file`, `hidden`, `image`, `reset` and `submit`: the elements that take typed text or move a cursor or choice with the arrow keys and Enter. A `radio` and a `range` input move their choice with the arrow keys, so they are text boxes under this rule.
- A focused button, link or checkbox is not a text box, so a typing shortcut on Enter or Space runs there and its `preventDefault` stops the element's own response to the key. Running the shortcut without `preventDefault` would run both. This follows the human's choice that only a text box keeps its keys.
- A `keydown` in a text box bubbles to `window` like any other, so the listener has to check the element the key press started at, as the human chose (`event.target`). At `window`, `event.target` for a key press inside an open shadow root is the shadow host, so the listener reads `event.composedPath()[0]`, which is the same element `event.target` names before it is retargeted. A closed shadow root hides its elements from `composedPath()` too, so an `input` inside one is seen as its host and a typing shortcut takes its keys; no page API reaches inside a closed shadow root.
- A typing shortcut on a letter, a digit, `Plus`, `Minus`, `Equal` or `?` is matched by the character the key types (`KeyboardEvent.key`), as GTK (keyval) and macOS (`charactersIgnoringModifiers`) match today, so moving it from the native apps to the frontend keeps its behaviour on AZERTY, Dvorak and German layouts. Named keys (Escape, Enter, Space, Tab, the arrows, Home, End, Page Up, Page Down, Delete, Backspace) sit on the same physical key on every layout and are matched by `KeyboardEvent.code`. Letters are compared lower-cased so Shift and Caps Lock change only the Shift check. On a layout whose letter keys type no Latin letter, a letter typing shortcut does not run; this plan does not check what GTK or AppKit do there today.
- A digit, `+`, `-`, `=` and `?` need Shift on some layouts and not on others, so their entries have `shiftOptional` set, and a typing shortcut that names Shift with one of them fails the build: no layout-independent rule says which key press it means.
- Windows matches `Plus` on the key that types `=` in the current layout, read with `VkKeyScanExW` in each key press, with that layout's own Shift state. Shift stays exact there, because on a German layout `0` without Shift is Actual Size's key. A layout that needs Ctrl or Alt to type `=` gets no `=` match. macOS matches `=` for a `Plus` menu item in a local key monitor with `.shift` removed from both sides, the rule `ZiggyActionShortcuts` uses, in place of a hidden alternate menu item whose matching with Shift held is AppKit's to decide. Linux registers GTK's `equal` keyval, which is the character, not the key. Each smoke run uses the machine's layout only; the Windows rule is unit tested with US and German scan values. Skipping shortcuts while a form field has the focus is what the common web shortcut libraries do by default:
    - Mousetrap: shortcuts do not fire inside a `textarea`, `input` or `select`, and its source also skips `contentEditable` elements (https://craig.is/killing/mice).
    - hotkeys-js: "by default, hotkeys are not enabled for INPUT, SELECT, or TEXTAREA elements", and its default filter also skips `isContentEditable` (https://www.npmjs.com/package/hotkeys-js).
    - react-hotkeys-hook: `enableOnFormTags` defaults to `false` ("hotkeys are disabled when a form element is focused") and `enableOnContentEditable` defaults to `false` (https://www.npmjs.com/package/react-hotkeys-hook).
- The inject script gets its typing shortcuts from the new system message `list-typing-shortcuts`, the same way it already gets `list-actions` through `invokeSystem` (`ziggy-inject.js` line 360). The list holds parsed shortcuts, so the script needs no copy of the shortcut parser. A phone gets an empty list because it registers no shortcut.
- `ziggy_dev_shortcuts_json` lists only the shortcuts a native app registers. Dev mode's script stands in for the native app, and the inject script runs the typing shortcuts there as everywhere else.
- Typing shortcuts are never shown in a menu on any platform.
- A menu item with a typing shortcut, of any kind, fails the build in `rejectInvalidMenu` (step 4), as other invalid menus do. Dropping the shortcut silently or showing it with no effect would hide the mistake, and a `.standard` item's action is run by the native app, never through `menu-action` (`dev-shortcuts.zig` top comment), so the inject script could not run it anyway. Because no menu entry the core gives a native app holds a typing shortcut, no native app needs its own check, and `ziggy_menu_entry` keeps its layout.
- Windows turns WebView2's browser accelerator keys off, because the feature list requires that shortcuts never clash with the web view's own reload, zoom and developer tools keys. Turning them off is what meets that requirement: with them on, a key the app does not define (F5) still reloads the page.
- This plan owns `Ctrl+=` zooming in, as the human chose: a shortcut written with `Plus` also runs on the same modifiers with `=` on Linux and macOS, with Shift held or not; Windows matches it on `VK_OEM_PLUS` today (`accelerator.zig` lines 61 and 131) and gains the layout's `=` key (step 6), and dev mode already matches `=` without Shift and gains Shift held. `plan-key-press-test-command.md` does not cover it.
- `listActions` gives each shortcut as the platform shows it, and the menu shows `Ctrl++`, so it lists `Ctrl++` once with no second entry for `Ctrl+=`.
- Two shortcuts that differ only in `Plus` and `Equal` are the same key press, so the existing duplicate check in `rejectInvalidMenu` fails the build for them once it compares with `is_same_key_press`.
- A held typing-shortcut key runs its action once per press.
- The inject script's listener skips a keydown whose `repeat` is true, so this holds on every platform and in dev mode. The Linux and macOS native apps and `dev-client.js` run their own shortcuts again on each auto-repeated key press today, and the Windows native app runs them once per hold (`acceleratorInvoke` checks `WasKeyDown`, line 1647); this plan does not change that for the shortcuts they keep.
- Windows behaviour today is confirmed from Microsoft's docs (https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller) and the code. macOS is certain for actions with no menu item (the local key monitor). Linux's GTK order and macOS key equivalents for menu items are inferred; step 2 observes the machine's own desktop platform, and Ziggy CI's jobs cover the others.
- WebView2's `AreBrowserAcceleratorKeysEnabled` keeps movement and editing keys (Home, End, Page Up, Page Down, Ctrl+X, Ctrl+C, Ctrl+V, Ctrl+A, Ctrl+Z) working, per https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings3, and has no effect on `AcceleratorKeyPressed`, so Ziggy's own shortcuts keep working.
- Ziggy's `toggle-devtools`, `reload` and zoom standard actions on Windows call WebView2's APIs (`put_ZoomFactor` at line 1327), not its browser keys, so turning the keys off leaves them working.
- Shortcuts a text box also uses with a modifier (Ctrl+Left, Alt+Left on macOS, Shift+arrows) are not typing shortcuts under this rule and still go to the native app. The feature list names arrow keys, Enter and Escape on their own.
- `?` takes no modifiers because a modified `?` would have to be matched by a native app, and every native app matches by a fixed key (GTK keyval with its modifiers, a Windows virtual key, a macOS key equivalent), while the key that types `?` changes with the layout. The feature list asks for a bare `?`.
- `?` is matched by `KeyboardEvent.key` because no `KeyboardEvent.code` stands for it on every layout; `shiftOptional` is set for the same reason.
- A `list-typing-shortcuts` reply that is not a list of shortcuts is logged as an error and leaves the list empty, so the failure shows in the log when the page loads, not as a `TypeError` on a later key press.
- The check for two off-menu actions with the same shortcut closes a gap that is not specific to `?`: the inject script runs only the first match, so the second action never runs from its key, and nothing says so. Ziggy's rules require such a failure to be loud.
- The other web view keys (reload, zoom, developer tools) all use Ctrl, Cmd or a function key, so a bare `?` clashes with none of them.
- The `?` action is added to the test app in step 7, after the core and native app changes, because before step 3 a `?` shortcut fails the test app's build.
- The test app's `show-help` action is part of the test app, which ships in no app, so they are not a test hook.
