## Decisions not approved by a human

- Windows: the press calls the app's `AcceleratorKeyPressed` handler, `acceleratorInvoke`, itself, with event arguments the native app makes (`PressKeyArgs`), for a key WebView2's documented rule counts as an accelerator, and sends a key the handler leaves, or one that is no accelerator, to the page with `Input.dispatchKeyEvent`. This replaced posting key messages through the window's accelerator table, which is not the path a user's key takes while the web view has the keyboard.
- Windows: WebView2's "does not map to a character" is read as `MapVirtualKeyW(<virtual key>, MAPVK_VK_TO_CHAR)` giving 0.
- Linux: every hand-made `GdkEventKey` and `GdkEventFocus` is read back through GTK's getters, and a mismatch stops the app with `std.debug.panic`.
- macOS: the press makes the app active and its window key, because AppKit hands a key event only to the key window of the active app. Two macOS runs side by side take the active app from each other, so the macOS `press-key` scenarios run one at a time and are left out of the second-copy check.

## Overview

Smoke tests can choose a menu item (`menu`) but cannot press a key, so nothing tests that a shortcut works for a user: Ziggy's `12-menu-view` chooses the zoom items and never presses Ctrl+Plus. This plan adds a remote control command, `press-key`, that has the native app deliver a key press to its own window at the point the platform's real key events enter the app, so the press takes the same path a user's does and a broken shortcut fails the test. It acts only when the app is started with `--remote-control`, like every remote control command. The feature list `~/projects/photosphere/ziggy-updates.md` (line 12, "Key press test command") is the human's request for this test hook, as Ziggy's `CLAUDE.md` requires. It is used here by a Ziggy scenario that presses the zoom keys, by a template scenario and a scenario in each example app (`ziggy-example-vite`, `ziggy-example-rsbuild`) that press an action's shortcut, and by a Photosphere scenario that presses Ctrl+N and Ctrl+O. `plan-frontend-shortcuts.md` uses it for the arrow keys, Enter, Escape, `=` and `?`.

## Notes

- `~/projects/photosphere/ziggy-updates.md` lists "Key press test command" ("the remote control connection can press a shortcut the way a user does"), which is the human's request for this test hook. The human chose a command that presses real keys through each native app's own key input path, so shortcuts are tested, rather than one that runs an action. Like every remote control command it acts only when the app is started with `--remote-control`: the `press-key` command exists only on the remote control connection, which only starts then.
- The command is `{"command": "press-key", "key": "<shortcut>"}`, the same shape as the other remote control commands (`menu`, `screenshot`). The key is written in Ziggy's shortcut syntax because the feature list asks to press a shortcut, and that syntax is how an app writes its shortcuts.
- A key that does not parse with `shortcut.parse` is refused with `InvalidKey` in the core before any native call, so every platform refuses the same keys.
- The core sends the native app a `key-press` call with a `has_key_press` flag in `ziggy_config`, as `screenshot` does with `has_screenshot`. Phones and dev mode reply `NativeCallMissing`, as `menu` and `screenshot` do there: a phone has no shortcuts and dev mode has no native app. The dev host and iOS zero their config, so `has_key_press` stays false there with no change.
- The reply waits until the native app has delivered the key down and the key up, so a scenario's next check sees what the press did.
- The press enters each platform where real key events enter the app, so whatever handles shortcuts (GTK accelerators and the web view on Linux, AppKit key equivalents and the local key monitor in `ZiggyActionShortcuts.swift` on MacOS, the `AcceleratorKeyPressed` handler `acceleratorInvoke` and the web view on Windows, and the frontend's JavaScript for the shortcuts `plan-frontend-shortcuts.md` moves there) sees it as it sees a user's. Calling `performAction` or `runAction` directly was rejected: that is what `menu` already does, and it skips the shortcut.
- Linux hands GDK key events to `gtk_main_do_event`, the function GDK hands every real event to, and sends a focus-in event first when the window is not active. Linux and MacOS press and release each modifier key around the key, as a keyboard does. The key's physical key and the extra Shift a character needs (Plus, `?`) come from the keyboard layout in use on each platform. On Linux the extra Shift is pressed as its own `Shift_L` key, like the shortcut's own modifiers.
- MacOS makes the app active and the window key when they are not, then posts the events to the application's queue. It parses the key with `ziggy_parse_accelerator` itself because `ZiggyMenu.parseShortcut` returns AppKit's key equivalent, not the key name the `kVK_` table needs, and gives the failure as the press's reason. Activating the app is what makes AppKit hand the posted events to the key window, and it is why two macOS runs cannot press beside each other.
- System-wide injection (XTest, `xdotool`, `SendInput` on Windows, `CGEventPost` on MacOS) was rejected: it needs the keyboard focus of the whole desktop, so two runs on one machine take it from each other, which breaks Ziggy's and Photosphere's rule that every test survives running beside another copy of itself.
- Windows, settled from the code and Microsoft's docs:
    - `plan-frontend-shortcuts.md` keeps Ctrl, Alt and Win shortcuts and function keys native on Windows: a menu action's `binding` feeds both the window's accelerator table (`buildAcceleratorTable`) and `acceleratorInvoke`, and both match it against Control, Shift, Alt and the Windows key read with `GetKeyState` in the native app's UI thread (`heldModifiers`, line 963), never from the event.
    - WebView2's documentation of `add_AcceleratorKeyPressed` (`ICoreWebView2Controller`): "`AcceleratorKeyPressed` runs when an accelerator key or key combo is pressed or released while the WebView is focused. A key is considered an accelerator if either of the following conditions are true. Ctrl or Alt is currently being held. The pressed key does not map to a character. A few specific keys are never considered accelerators, such as Shift. The `Escape` key is always considered an accelerator." `is_web_view_accelerator` is that rule. "Does not map to a character" is read as `MapVirtualKeyW(<virtual key>, MAPVK_VK_TO_CHAR)` giving 0, the Win32 call that maps a virtual key to its character. The keys where another reading could differ (Tab, Enter, Backspace with no modifier) carry no native binding once `plan-frontend-shortcuts.md` moves the shortcuts with no Ctrl, Alt or Win to the frontend, so either reading gives the same result: `acceleratorInvoke` matches nothing and the key goes on to the page.
    - The press calls `acceleratorInvoke` itself with arguments of its own, because no API lets the app make WebView2 raise `AcceleratorKeyPressed` without a real key from the desktop, and that is the system-wide injection rejected above. Everything from the handler on is a user's path: the same handler, `heldModifiers` reading the key state, the same bindings, the editing shortcuts left to the web view and `runAction` for the rest. So a broken `acceleratorInvoke` or binding fails the press.
    - `SetKeyboardState` "copies an array of keyboard key states into the calling thread's keyboard input-state table. This is the same table accessed by the GetKeyboardState and GetKeyState functions. Changes made to this table do not affect keyboard input to any other thread." So the press sets the modifiers only for this app's UI thread, and a second run on the same machine is untouched. The saved state is put back once the handler has run.
    - `Input.dispatchKeyEvent` through `CallDevToolsProtocolMethod` (already used for paste, line 1356) reaches only this app's web view and carries its own modifiers, so a key the frontend handles reaches the page's `keydown` with them set, and an editing shortcut the handler left (Ctrl+C) reaches Chromium's own handling. It enters Chromium below the native app, so it raises no `AcceleratorKeyPressed`, which is why the press calls the handler first. The completion handler gets only an error code and a result, so the parameters of the remaining events are kept on `NativeApp` in `key_press_events`.
    - Not covered: a user's key while the window itself, not the web view, has the keyboard goes through the window's accelerator table and `TranslateAcceleratorW` (the message loop, line 582). The press does not take that path, and nothing in this plan tests the table. A broken table entry with a working `acceleratorInvoke` passes.
    - A shortcut with the Windows key and a character key is no accelerator by WebView2's rule (only Ctrl and Alt count), so the press sends it to the page, as WebView2 does with a user's.
    - `accelerator.zig` imports only `std` and its tests run on every platform, so the virtual key codes it needs are written there as numbers and checked against `c.VK_*` in `native-app.zig`'s `comptime` block.
- Checked by reading the sources for this plan:
    - GTK, `gtk-3-24` branch. `gtk/gtkmain.c` `gtk_main_do_event`: a `GDK_KEY_PRESS` or `GDK_KEY_RELEASE` goes to the widget of the event's `GdkWindow` (or a grab widget) through `gtk_propagate_event`, and nothing there checks `send_event` or whether the window is active; a `GDK_FOCUS_CHANGE` goes to the widget of the event's window. `gtk/gtkwindow.c`: `gtk_window_key_press_event` tries the window's mnemonics and accelerators (`gtk_window_activate_key`) first, then the focus widget (`gtk_window_propagate_key_event`); `gtk_window_focus_in_event` sets `has-toplevel-focus` and `is-active` when the window is visible, checking nothing else of the event. `gtk/gtkkeyhash.c` `_gtk_key_hash_lookup`: the accelerator's keyval is worked out from the event's `hardware_keycode`, `state` and `group` with the layout (`_gtk_translate_keyboard_accel_state`), not taken from the event's `keyval`, and the modifiers the layout consumed (Shift for `plus`) are masked out of both sides of the comparison, so Ctrl and Shift with the `=` key match a `Ctrl+plus` accelerator.
    - WebKitGTK, `Source/WebKit/UIProcess/API/gtk/WebKitWebViewBase.cpp` on WebKit's `main` branch (not the exact release the machine has): `webkitWebViewBaseKeyPressEvent` reads the keycode, state and keyval with `gdk_event_get_keycode`, `gdk_event_get_state` and `gdk_event_get_keyval` and hands the event to the page (`handleKeyboardEvent`), with no check of focus or of the window being active.
    - AppKit (Apple's documentation): `NSEvent.addLocalMonitorForEvents` is called for "events that are dispatched through the applications sendEvent(_:) method", and `NSApplication.sendEvent` is what the main event loop calls for each event, with key events "forwarded to the appropriate NSWindow object". Which window that is for a key event, and whether it is delivered when the app is not active, the documentation does not say. The macOS press makes the app active and its window key, so its events go to the key window, as issue 6's decision records; the macOS smoke run is what checks it.
- The GTK 3 development headers are not installed on this machine (only `gtk-4.0`), and Ziggy CI installs only `libgtk-3-0`, so no build here compiles against `gdk/gdkevents.h`. `gtk.zig` declares GTK by hand, which is how every declaration there is written. The field lists were read from `gdk/gdkevents.h` on GTK's `gtk-3-24` branch. The layout is held to the C library by the read-back in `press_key_send_event`: GTK's own getters must return the type, window, keyval, keycode and state written, else the app panics. `group` and `is_modifier`, which GTK 3 has no getter for, are the two bytes right after the checked `hardware_keycode`, as the header declares them.
- Security: `press-key` is a remote control command, so it exists only when the app is started with `--remote-control`, which only the smoke tests pass; without the flag there is no connection and no command. With it, the remote control server listens on `127.0.0.1` with no authentication (`tools/remote-control-server/src/index.ts`), so a process of the same user on the machine can send it commands. That process can already run any menu action (`menu`), quit the app (`quit`), and type into the page's text boxes (the frontend's `type` and `insert`). `press-key` adds the keys the web view itself handles (Chromium's or WebKit's own shortcuts, such as Ctrl+C) to that. A process of the same user can already read and write the app's files and drive the desktop's own input, so this gives it nothing it lacks. No change is made for it.
- The key's text uses Ziggy's shortcut syntax, so `?` works in `press-key` once `plan-frontend-shortcuts.md` adds it to `shortcut.zig` and to each platform's key table. The MacOS character search needs no change for it.
- Ctrl+= zooming in is `plan-frontend-shortcuts.md`'s, which presses it in its own `browser-keys` scenario. This plan's `zoom-keys` scenario presses only the shortcuts the test app declares.
- Scenario numbers are taken at implementation time, by the rule given in steps 5 and 9, because sibling plans add scenarios to the same directories.
- `press_key` goes into Ziggy's and the template's `smoke-tests/lib/common.sh` and Photosphere's `apps/photosphere-smoke-tests/lib/common.sh`, because each suite's scenarios source their own copy.
- The example apps `ziggy-example-vite` and `ziggy-example-rsbuild` get `press_key` and the `hello-action-shortcut` scenario in this plan, and are built and tested against the local Ziggy with `zig build --fork=../ziggy`, as Photosphere's `CLAUDE.md` does for a change that spans repositories. Their pins stay at `v0.0.23`: moving them to a new tag happens with the Ziggy release, as Ziggy's `CLAUDE.md` says. Until then their CI and their macOS smoke run (whose native app is the Swift package the Xcode project takes from the tag) are CI-only.
- Swift `ZiggyKeyPress` unit test: Ziggy's Swift package has no test target, and one would have to link the core's static library, which `ZiggyBridge.swift` calls. `ZiggyKeyPress` stays covered by the macOS smoke run, whose press reaches it and whose zoom shortcuts fail when it delivers the wrong key. Its key table and key code search are read against Carbon's constants and the current layout, and the run is what checks the delivered key.
- The upgrade note goes under `## v0.0.24`: `v0.0.23` is Ziggy's latest tag and the top heading of `docs/upgrade-notes.md`.
- Typing text into a text box stays the frontend's `type` and `insert` commands; `press-key` is for keys a shortcut or a text box's own handling reacts to.
- Window targeting (`"window": 2`) is `plan-remote-control-window-targeting.md`'s. This plan neither needs it nor changes it. That plan's server takes the `window` field off every line before the app sees it, so once both are in, a `press-key` line with `"window": 2` presses in window 2 with no change here.
