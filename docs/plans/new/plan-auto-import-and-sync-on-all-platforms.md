### What follows from those words, and is deliberate

- **Step 1 is research by the executing session.** The human told the session writing this plan not to research it. The executing session does the research, records it in step 1 and adapts the later steps to what it finds. A checker does not replace step 1 with research of its own, and does not mark the plan unfinished because the writing session left the research to step 1.
- **The steps name outcomes, not exact edits, wherever the code was not read.** The facts in step 1 were read in the code. Everything else is described by what it must achieve, so it is not made up. A checker does not ask for invented file names, function names or signatures to be added.
- **One code path is the requirement, not a preference.** A step that adds a desktop-only or mobile-only path is wrong unless its code comment gives the strongest justification. A checker does not propose a separate desktop implementation as a simplification.
- **Desktop runs only while the app is open.** No desktop service, daemon or start-at-login is added.
- **The manual tests are the specification.** The onboarding tests and the automatic import tests describe the behaviour wanted on every platform they name. Where the app and a test differ, the app changes.

## Decisions not approved by a human

- With **Only sync over Wi-Fi or wired network** on, `wifi`, `wired` and `unknown` are allowed and `cellular` is refused, as `cellular` is today. `unknown` stays allowed because the switch is on by default and a VPN-only, Bluetooth or USB connection reports `unknown` for good: refusing it would stop syncing for those users with no error.
- The config key keeps its name, `only_on_wifi` under `[sync]` in `config.toml` (`SYNC_ONLY_ON_WIFI_CONFIG_KEY`), and so do the identifiers and the JSON field `onlyOnWifi` that carry it. Only the label and the meaning change, so the settings parse in `sync-settings.zig` cannot fall out of step with the interface.
- The connection type on desktop comes from the operating system, read by Photosphere's own code in the core, not from the web view's Network Information API and not from Ziggy. That keeps the change inside this repository.
- The core's reading is the one source of the connection type on every platform. The interface gets it through the platform abstraction instead of reading the browser, so the interface and the background loops decide from the same value.
- The interface asks the core for the connection type every 15 seconds while something is subscribed, and treats only `none` as disconnected. It no longer reads the browser's online state.
- The browser network code in `packages/user-interface/src/lib/network-info.ts` is deleted once nothing calls it.
- `planMobileAutoImport` is renamed `planAutoImport`, because it runs on every platform.
- The manual tests' lines about the sync switch change to the new label and rule. That is the one place the tests change instead of the app, because the human named the new label and rule.

## Acceptance criteria

- Automatic import and background syncing run on Linux, macOS, Windows, Android and iOS through one code path. Every platform difference is a condition inside that path, never a second path.
- On desktop, both run only while the app is open, as a standard Ziggy background task.
- The switch reads **Only sync over Wi-Fi or wired network** on every platform. When it is on, syncing runs over Wi-Fi or a wired network and is refused over cellular. Every platform reports `wired` for an Ethernet connection.
- Linux and Android are checked on the machine that runs this plan, and this plan is complete when they pass. The macOS, Windows and iOS code and tests are written to the same standard and recorded as unrun; CI checks them when the human pushes, which is outside this plan.
- The app does what the manual tests describe, on every platform they name: `docs/testing/e2e/onboarding/onboard-existing-remote.md`, `docs/testing/e2e/onboarding/onboard-new-remote.md` and every test in `docs/testing/e2e/mobile/auto-import/`.
- Comprehensive unit tests and smoke tests cover the behaviour on desktop and on mobile, and `bun run tev` passes.

## Overview

Automatic import and background syncing work only on mobile today. The human wants them on every platform, working as close as possible to the mobile version, with the same code everywhere. On desktop they run while the app is open, as a standard Ziggy background task; mobile keeps running them in the background as it does now. The Wi-Fi-only switch becomes a Wi-Fi-or-wired switch that works on every platform, because a desktop is usually on a wired network. The manual tests listed in the acceptance criteria are the specification: the onboarding tests already describe desktop behaviour as though it worked.
