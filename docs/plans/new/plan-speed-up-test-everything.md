# Speed up `test:everything --force`

## Overview

`bun run tev -- --force` runs every suite at once on one machine and finishes when its slowest lane finishes. The `--force` set is now twelve scripts (`scripts/test-everything-parallel.sh:85`), and only two lanes are still serialised: the Android pair and the iOS pair, each because their members drive the same Gradle or Xcode project. Everything else is a lane of its own, so the wall clock is simply the slowest single suite. On this machine the recorded durations of the last passing runs (`.test-durations`) are `test:electron` 377s, `test:cli` 206s, `test:and` 201s, `test` 55s, `test:and:unit` 27s, `test:harness` 21s, `compile` 21s, `test:cli:hash-cache` 10s, which makes `test:electron` the one to beat. What is wasting the machine is that each suite fixes its own concurrency at a number chosen when it was written and never revisited: `apps/desktop/smoke-tests.sh:375` runs batches of 2 and `apps/cli/smoke-tests.sh:98` runs batches of 5, on a machine with 24 cores and 62GB. The goal is under four minutes, and under two if the floors allow. This plan measures first, because five of the twelve scripts in the `--force` set have no recorded duration at all and the decision about where to spend effort depends on them.

## Issues

## Steps

1. **Make a run's internals readable, in `scripts/test-everything-parallel.sh`.** `LOG_DIR` is a `mktemp -d` (line 170) that `cleanup()` deletes on exit (line 198), so every suite's own output, including the per-test durations each suite prints, is thrown away at the end of the run. Add a `--keep-logs <dir>` option to the argument loop (line 65, beside `--force` and `--plan`): when given, `LOG_DIR` is that directory instead, it is created if missing, and `cleanup()` leaves it alone. Update the usage comment at the top of the file. This is what makes every later step measurable rather than guessed.

2. **Record the baseline.** Run `bun run tev -- --force --keep-logs ./.test-logs-baseline`, first checking `bun run emu:and:pool:status` and reading its exit code, since `--force` includes the Android suites and the runner refuses the whole run when no emulator is on the LAN bridge. From the kept logs and the runner's own `Results:` block, write down: each lane's total, and inside `test:electron`, `test:cli` and `test:and`, the per-test durations and how much of the suite is fixed setup (the desktop bundle, the Capacitor sync and Gradle build, the APK install) rather than tests. The five scripts in the `--force` set with no entry in `.test-durations` (`test:cli:encrypted`, `test:cli:lan-share`, `test:cli:sync`, `test:cli:write-lock`, `test:lan-share:cli-desktop`) get their first real number here, and any one of them could turn out to be slower than `test:electron` and so be the actual target. Steps 6 and 7 below are decided by these numbers, so do not skip ahead.

3. **Add `scripts/lib/test-concurrency.sh`.** A new sourced library beside `scripts/lib/allocate-test-temp-dir.sh` and `scripts/lib/process-control.sh`, which the suites already source. Two functions, each with a comment block above it in the style of `process-control.sh`:
   - `detect_cpu_count` - prints the usable core count: `nproc` on Linux, `sysctl -n hw.ncpu` on macOS, and 4 when neither answers, so a CI runner or an unknown shell still gets a sane number rather than an empty string.
   - `resolve_test_parallel <fallback>` - prints `PHOTOSPHERE_TEST_PARALLEL` when it is set and is a positive integer, otherwise a value derived from `detect_cpu_count`, never below the given fallback. The fallback is what each suite uses today, so a machine that reports nothing behaves exactly as it does now.
   - Both must run under the bash macOS ships (3.2): no `${var,,}`, no associative arrays, no `mapfile`, matching the constraint already noted at `apps/smoke-tests/lib/runner.sh:676`.

4. **Take the CLI suite's batch size from the budget.** In `apps/cli/smoke-tests.sh`, source the new library beside the existing sources at lines 56 and 67, and set the `PARALLEL_N=5` default at line 98 from `resolve_test_parallel 5`. The explicit `--parallel N` option must still win over both, so the arg loop near line 939 stays as it is. Update the `--parallel` line in `show_usage()` (line 857) to say where the default now comes from.

5. **Take the Electron suite's batch size from the budget.** In `apps/desktop/smoke-tests.sh`, source the new library beside lines 9 and 14, and set `local parallel_n=2` in `main()` (line 375) from `resolve_test_parallel 2`. `--parallel N` still wins. Update `print_usage()` (line 91). Leave `run_mixed`'s handling of `.sequential`-marked tests alone: `7-share-secret` and `8-share-database` still run alone whatever the batch size is.

6. **Give the whole run one concurrency budget, in `scripts/test-everything-parallel.sh`.** This is the step that stops step 4 and step 5 from fighting each other: the `--force` set now launches ten lanes, and suites each sizing themselves to 24 cores would put well over a hundred test processes on the machine, so the run would get slower, not faster. Source `scripts/lib/test-concurrency.sh`, and in `run_script()` (line 247) export `PHOTOSPHERE_TEST_PARALLEL` for that script, computed once before the lanes start: the detected core count divided across the lanes about to be launched, never below 2, weighted so a lane with a large recorded duration in `.test-durations` gets a larger share than a lane with a small one (`recorded_duration_for` at line 216 already reads that file for the estimate it prints). A lane with no recorded duration gets an average share until step 2's measurements give it one. Print each lane's share in the lane listing the runner already prints before it starts, so a run says what it decided.

7. **Decide the Android lane from the step 2 numbers, not from this plan.** `test:and:unit` (27s) and `test:and` (201s) are serialised in `SERIAL_GROUPS` (line 138) because both drive Gradle against `apps/android-frontend/android`. Unserialising them needs the two builds separated, which is real work for at most 27s, so do it only if step 2 shows the Android lane is the one setting the wall clock after steps 4 to 6. What step 2 should be read for instead is the split inside `test:and` between the fixed cost (`bun run sync`, the Gradle build, the APK install) and the 41 tests: the tests already spread across every emulator in the pool through `run_pool` in `apps/smoke-tests/lib/runner.sh`, so if the fixed cost dominates, more concurrency cannot help and the two-minute target depends on that build instead. Do not change `TEST_BATCH` (`apps/smoke-tests/lib/runner.sh:40`): it is a fair-share floor for suites competing over emulators, not a cap on how many a suite uses.

8. **Re-measure and tune the shares.** Run `bun run tev -- --force --keep-logs ./.test-logs-after` and compare lane by lane against the baseline from step 2. If a lane got slower, its share is too large or the machine is oversubscribed; adjust the weighting in step 6 and measure again. Record the before and after wall clock. If neither four nor two minutes is reached, the kept logs say exactly which lane is the floor and why, and that is the answer to report rather than a further guess.

9. **Prove the higher concurrency is stable, not just fast.** Raising how much runs at once is exactly the change that turns a stable suite flaky, and a faster suite that fails one run in ten is worse than the slow one. Run `bun run find-flakey-tests -- --target 20` and require twenty consecutive green runs at the new settings. A failure here is a result, not an obstacle: it names the test that does not tolerate the new concurrency, and either that test gets fixed or the share that broke it comes back down.

10. **Update the documentation that is now wrong.** The comment block at the top of `scripts/test-everything-parallel.sh` says the full set "takes about as long as the slowest one, which is roughly three and a half" minutes; the recorded durations say the slowest suite alone is over six. Correct it to the measured figure from step 8. Add `PHOTOSPHERE_TEST_PARALLEL` and `--keep-logs` to `docs/testing/README.md`.

## Unit Tests

None, and this is deliberate. Every change in this plan is shell script. `CLAUDE.md` states plainly that tests are not to be written for shell scripts, that no `*.test.sh` files are to be created, and that the rule requiring a unit test for every new or changed function does not apply to shell. So `scripts/lib/test-concurrency.sh` gets no test file, and nothing is added beside the existing `apps/smoke-tests/runner.test.sh`, `android-lock.test.sh` and `timeout.test.sh`. What proves this work is the real suites running through it twenty times in step 10.

## Smoke Tests

The suites being changed are the end-to-end coverage and they already exist. What the changes add is a handful of properties to check directly, each a single fast command:

- `PHOTOSPHERE_TEST_PARALLEL=3 bun run test:cli -- --list` and the equivalent for the Electron suite report a batch size of 3 in the line they already print before running.
- With `PHOTOSPHERE_TEST_PARALLEL` unset on a machine where `detect_cpu_count` fails (simulate by putting a `nproc` that exits non-zero earlier on `PATH`), both suites fall back to their original 5 and 2.
- An invalid `PHOTOSPHERE_TEST_PARALLEL` (`0`, `-1`, `abc`) is refused loudly rather than silently treated as one or as unset.
- `bun run tev -- --force --plan` still prints its decision and runs nothing, and `--keep-logs` combined with `--plan` does not leave a directory behind.
- After a `--keep-logs` run the directory holds one `.log`, one `.exit` and one `.seconds` file per script, and the logs contain the per-test lines the suites print.

- `bun run emu:and:pool:status` is run and its exit code read immediately before any Android run, rather than assumed either way.
- `bun run tev -- --force` passes with every lane green, and its `Results:` block is captured before and after so the change in wall clock is a measurement and not a claim.

- The git hook still passes on a real commit, since `tev` is what it runs.

## Notes

- **The lanes are already as wide as they get.** `SERIAL_GROUPS` (line 138) now holds only the Android and iOS pairs, so with `--force` the run is ten lanes and the wall clock is the slowest single suite. There is no lane left to unpick: from here the only way down is to make a suite itself faster, which is what every step below does.
- **Two desktop bundles now run at the same time.** `bundle_app` (`apps/desktop/smoke-tests.sh:364`) and `bundle_desktop` (`cli-desktop-lan-share-smoke-tests.sh:70`) both call the root `bun run bundle`, and now that their lane is split they call it concurrently, writing the same output. Nothing in this plan depends on that and it is out of scope here, but it is worth a look on its own: two writers over one `bundle/main.js` is the kind of thing that fails once in fifty runs and looks like a flaky test when it does.
- **Both parallelism defaults are original values, not tuned ones.** `git log -S` shows `parallel_n=2` arrived with the commit that created the Electron suite (`7d2dcfcb`) and `PARALLEL_N=5` with the commit that added parallel batches to the CLI suite (`f3969894`). Neither was lowered in response to a failure, so raising them is untested ground rather than the reversal of a fix. That is also why step 10 is not optional.
- **Both suites barrier each batch.** `run_parallel_batch` in `apps/desktop/smoke-tests.sh:174` and `run_parallel` in `apps/cli/smoke-tests.sh:524` wait for every test in a batch before starting the next, so one slow test idles the rest of its batch. Larger batches make each barrier cost more, not less. If step 9 shows the batch barrier eating the gain, the fix is a work queue like the one `apps/smoke-tests/lib/runner.sh` already implements for the mobile suites, and that is a separate piece of work worth its own plan.
- **Two floors that parallelism cannot remove.** Every Electron test launches the app and waits for its control port, and every `test:and` run pays a Capacitor sync, a Gradle build and an APK install before its first test. Four minutes looks reachable by concurrency alone; two minutes probably requires attacking one or both of those, and step 2's measurements are what will say which.
- **Oversubscription is the real risk, and the emulators are the fragile part.** This machine has 24 cores and 62GB, but the Android emulators have run out of memory before under repeated load: `docs/plans/new/plan-emulator-oom-isolation.md`, `plan-find-and-fix-emulator-memory-leak.md` and `plan-oom-kill-mitigations.md` all exist for that reason. Step 6's budget deliberately covers only the suites whose concurrency this plan changes; the mobile suites keep taking their share through the existing emulator registry.
- **`--force` is the target on purpose.** The normal `tev` already skips whatever did not change, so the run this plan speeds up is the one after a rebase, the one the hook runs on a wide change, and the one used to check a finished piece of work. It is also the worst case, so anything it gains, every smaller run gains too.
- **The `--force` set grew recently.** It is now twelve scripts (`scripts/test-everything-parallel.sh:85`) where it was five, so a `--force` run today covers the four extra CLI suites, the CLI-to-desktop LAN share suite and the harness tests as well. The recorded durations quoted above pre-date that, which is another reason step 2 measures before anything is changed.
