# Find test scripts that interfere with each other when run in parallel

## Overview

`bun run test:everything` runs the suites concurrently, so any two of them that touch the same file, port, directory, lock or device can fail each other in ways that never show up when the suite is run alone. That is a distinct failure class from ordinary flakiness: the suite is not unreliable in itself, it is unreliable in company. Today nothing detects it. `scripts/test-everything-parallel.sh` encodes two hand-found conflicts in `SERIAL_GROUPS` (the Android pair and the iOS pair, which share a build directory), and those were found by being bitten, not by testing for it. This plan adds `scripts/check-parallel-tests.sh`, which runs every script alone to establish a baseline, then runs every pair concurrently, and reports only the failures that appear in company and not alone. It also adds a harness test that proves the detector actually detects, using fixture scripts that collide on purpose.

## Issues

## Steps

1. **Create `scripts/check-parallel-tests.sh` with its argument handling and script list.** Accept `--runs N` (default 3), `--scripts "a b c"` (default the fast set: `compile test test:cli test:electron`), `--include-mobile` (adds `test:and test:and:unit` on Linux and `test:ios test:ios:unit` on macOS, chosen by `uname -s` the same way `scripts/test-everything-parallel.sh` does), `--pairs-only`, `--baseline-only` and `--help`. Write logs under `tmp/parallel-check/` relative to the repository root, which is already covered by the `tmp/` entry in `.gitignore`. The script must create directories and write new files only: it must never delete, clear or overwrite an existing path, including its own log directory, so name each run's directory from a counter that skips names already present. Requires `bash -n` to pass.

2. **Add baseline mode to `scripts/check-parallel-tests.sh`.** Add a function `run_alone` that runs one script by name via `bun run <script>` from the repository root, capturing combined output to `tmp/parallel-check/<run-dir>/alone-<script>-<attempt>.log` and recording its exit code to a sibling `.exit` file, repeated `--runs` times. Add `baseline_verdict`, which reads those exit files and prints one of `clean` (every attempt passed) or `unstable-alone` (any attempt failed) per script. A script that is `unstable-alone` is ordinary flakiness and must be excluded from pair classification, because it cannot be shown to have been broken by a partner. Requires `bash -n` to pass and the harness test from step 5 to cover both verdicts.

3. **Add pair mode to `scripts/check-parallel-tests.sh`.** Add `generate_pairs`, which prints every unordered pair of the selected scripts, one per line, excluding self-pairs. Add `run_pair`, which starts both scripts of a pair concurrently as background jobs from the repository root, waits for both, captures each side's output to `tmp/parallel-check/<run-dir>/pair-<a>-<b>-<side>-<attempt>.log`, and records both exit codes. Repeat each pair `--runs` times. Both sides must be started as close together as possible so their setup phases overlap, since that is where fixed paths and fixed ports collide. Requires `bash -n` to pass.

4. **Add classification and the summary report to `scripts/check-parallel-tests.sh`.** Add `classify_pair`, which combines the baseline verdicts with the pair exit codes and yields exactly one of: `ok` (both sides passed every attempt), `interference` (both scripts are `clean` alone but at least one side failed when paired), or `inconclusive` (at least one script is `unstable-alone`, so the pair result proves nothing). Add `print_summary`, which prints a table of pair, verdict, failing side and the path of the first failing log, sorted so every `interference` row comes first. Exit non-zero when any pair is `interference`. Print an explicit count of pairs skipped as `inconclusive` rather than silently dropping them. Requires `bash -n` to pass.

5. **Create `scripts/check-parallel-tests.test.sh`, the harness test, following the shape of `apps/smoke-tests/android-lock.test.sh` and `apps/smoke-tests/runner.test.sh`.** It must drive `scripts/check-parallel-tests.sh` against fixture scripts rather than the real suites, by pointing it at a fixture package directory it creates under `tmp/parallel-check-fixtures/` and passing their names via `--scripts`. Cover four cases: (a) two fixture scripts that touch nothing in common, expected verdict `ok`; (b) two fixture scripts that both write and then read back one fixed path under the fixture directory, so concurrent runs corrupt each other, expected verdict `interference`; (c) a fixture script that fails on a fixed proportion of attempts when run alone, paired with a clean one, expected verdict `inconclusive` and not `interference`; (d) the exit code of the whole check is non-zero for case (b) and zero for case (a). The fixtures must create files only, never delete them. Requires the harness test to pass.

6. **Watch each assertion in `scripts/check-parallel-tests.test.sh` fail before accepting it.** For each of the four cases, temporarily break the thing it covers, confirm the test reports failure, then restore. Specifically: make `classify_pair` always return `ok` and confirm case (b) fails; make it always return `interference` and confirm cases (a) and (c) fail; make `print_summary` always exit zero and confirm case (d) fails. Record in the plan's Notes that this was done. A test that has only ever passed does not count as complete for this step.

7. **Add the positive control over the real suites.** Add a `--serial-groups-are-expected` flag that marks the pairs named in `SERIAL_GROUPS` in `scripts/test-everything-parallel.sh` (`test:and:unit` with `test:and`, and `test:ios:unit` with `test:ios`) as expected interference: they are reported, and are not counted toward the non-zero exit. Read those pairs by parsing the `SERIAL_GROUPS` array out of `scripts/test-everything-parallel.sh` at run time rather than restating them, so the two cannot drift apart. `scripts/test-everything-parallel.sh` is frozen and must not be edited; this step only reads it. These pairs are known to conflict, so a run with `--include-mobile` that does not report them means the detector is not working.

8. **Add the entry points to `package.json` at the repository root.** Add `"test:parallel": "bash ./scripts/check-parallel-tests.sh"` and `"test:parallel:self": "bash ./scripts/check-parallel-tests.test.sh"`. Do not attempt to add either to the default script list in `scripts/test-everything-parallel.sh`: that file is frozen, so the harness test is wired into CI in the next step instead. Requires `bun run test:parallel:self` to pass.

9. **Add a CI job for the harness test in `.github/workflows/release.yml`.** Follow the shape of the existing job that runs the Android lock stress test: `runs-on: ubuntu-latest`, checkout, Setup Bun, Setup Node.js, Cache Bun dependencies, Install dependencies, then `bun run test:parallel:self`. Give it a `timeout-minutes` value in line with the other small harness jobs. Do not add the full parallel check itself to CI: it runs the real suites many times over and its cost belongs in a deliberate local run.

10. **Add a "Parallel-only failure modes" section to `docs/flaky-tests-registry.md`.** Follow the existing entry format and add two fields specific to this class: `Pair` (the two scripts that must run together to produce it) and `Shared resource` (the path, port, lock or device they contend on). Add a rule stating that a mode only belongs in this section when the detector classified it `interference`, meaning both scripts passed alone and failed together, and that a mode reproducible from a single script alone belongs in the existing section instead.

11. **Document the check in `docs/testing/README.md`.** Add a short section covering what the check is for, `bun run test:parallel` for the fast set, `--include-mobile` and why it is slow and needs the emulator pool up, `--runs` for widening the search, and how to read the three verdicts. State plainly that `inconclusive` means ordinary flakiness masked the answer and that the single-suite flaky check should be run first in that case.

## Unit Tests

The deliverable is shell, so it carries no new TypeScript functions and therefore no Jest tests. This matches the existing precedent for shell harnesses in this repository (`apps/smoke-tests/android-lock.sh` is covered by `apps/smoke-tests/android-lock.test.sh`, and `apps/smoke-tests/lib/runner.sh` by `apps/smoke-tests/runner.test.sh`), and the coverage requirement is met by the harness test in step 5 rather than by Jest.

If any step turns out to need something shell genuinely cannot do (the repository's rule allows a TypeScript helper only in that case, as a real file under `scripts/` invoked as `bun scripts/<name>.ts`), then that helper gets a Jest test under the owning package's `src/test` directory covering every exported function, and this section must be updated to name it before the step is considered complete.

## Smoke Tests

- `scripts/check-parallel-tests.test.sh` case (a): two independent fixture scripts run as a pair are classified `ok` and the check exits zero.
- `scripts/check-parallel-tests.test.sh` case (b): two fixture scripts contending on one fixed path are classified `interference` and the check exits non-zero.
- `scripts/check-parallel-tests.test.sh` case (c): a fixture script that is unreliable on its own is classified `inconclusive`, never `interference`, and is counted in the skipped total.
- `scripts/check-parallel-tests.test.sh` case (d): the summary names the failing side and the path of a log file that exists and is non-empty.
- Positive control over the real suites: `bun run test:parallel -- --include-mobile --serial-groups-are-expected` reports the two `SERIAL_GROUPS` pairs as expected interference, which is the end-to-end evidence that the detector finds a real conflict rather than only a fixture one.

## Notes

- `scripts/test-everything-parallel.sh` is frozen by the repository rules and must not be edited by any step here. Step 7 reads it, which is allowed, and step 8 explains why the harness test cannot be added to its default script list.
- The check must invoke each suite directly through `bun run <script>` and never through `test:everything`. Going through the gate would write `.cache/what-changed`, which is shared mutable state, and concurrent gate runs would then be measuring the gate rather than the suites.
- Candidate shared resources found while researching, useful for interpreting an `interference` verdict: fixed paths under `/tmp` used by several suites (for example `/tmp/test-run.log`, `/tmp/photosphere`, `/tmp/testing`); the Android device locks at `/tmp/photosphere-android-device-<serial>.lock`; the Capacitor and Gradle output inside `apps/android-frontend/android`; the equivalent Xcode project for iOS; and `apps/cli/test/tmp`, which `apps/cli/smoke-tests.sh` already allows to be moved with `TEST_TMP_DIR` precisely so parallel runs do not collide. Ports are largely safe already, since the harnesses bind port 0 and read the assigned port back, but a fixed port would show up here as an `interference` verdict.
- Cost is the main constraint. Pairs grow as n(n-1)/2, so the four fast scripts are 6 pairs and adding the two mobile scripts takes it to 15, each pair repeated `--runs` times, with the mobile suites taking minutes per run. Default to the fast set, make `--include-mobile` opt-in, and expect a mobile-inclusive run to be an hours-long deliberate exercise rather than something run casually.
- Memory is a real constraint on the development machine: running two heavy suites concurrently is the workload that has exhausted it before. The check should not be run with a large `--runs` alongside other work, and `--include-mobile` requires the emulator pool to already be up.
- The check must never start, stop or restart an emulator. Per `apps/android-frontend/CLAUDE.md` that is the human's job, so `--include-mobile` must fail loudly with a clear message when `bun run emu:and:status` does not report ready, rather than trying to bring the pool up itself.
- No step here may write a destructive command. The check only creates directories and files, and the fixtures in the harness test do the same. Leftover fixture and log directories under `tmp/` are acceptable and must be left for the human to clear.
- An `interference` verdict names a pair, not a cause. Finding which shared resource is behind it is a follow-up investigation, and a static scanner over the suites for fixed paths and fixed ports would be one way to speed that up. It is deliberately not part of this plan, which is about detection.
