# One form for every kind of handler in Ziggy and Photosphere

## Overview

Goal, in the human's words: "There should only be one way to write each type of handler in Ziggy and Photosphere." "Should be only one main way to run a task."

Today a task handler can be written in four forms (Ziggy's raw `TaskHandler`, Ziggy's typed form that `wrapTask` takes, the task queue package's `TaskHandler` taking an `ITaskContext` and Photosphere's `ToolTaskHandler`) and Photosphere wraps them in `withMediaSources`, `withTools`, `fromNodeApiHandler` and `logExceptions`. A task inside a task is started either with `TaskServices` (`queueChild`, `awaitTask`, `runChild`) or with a `TaskQueue` on the worker's queue backend. A message handler can be written in four forms (plain `!Result`, `!Response(T)`, `!Response(T)` with a `Reply(T)` parameter and the unparsed `Message` returning `MessageResult`). A menu item does frontend work either as a `.ui` item, which sends the `menu` app event, or as an `.action` item, which runs a registered action.

After this plan:

- A task handler has one form, Ziggy's typed form: `fn (services: TaskServices, timers: Timers, io: std.Io, allocator: std.mem.Allocator, context: TaskContext, payload: P) !R`. `TaskServices` becomes an interface like `HandlerServices`, so a test calls a handler directly with a fake. It also carries what the other forms supplied: the uuid generator, the timestamp provider, the session id (on `TaskContext`), job progress, an independent task start and a way to take whichever child ended next. A new app hook, `.before_task`, runs on the worker before each task and replaces `withMediaSources`. A failed task's error is logged by Ziggy's worker, which replaces `logExceptions`. The three tool handlers become comptime functions of `Tools` that make the tools themselves, which replaces `withTools`.
- Inside a task, child tasks and other tasks are started only through `TaskServices`. `TaskQueue` stays only for a thread that owns a worker pool and runs no task (the Photosphere CLI's thread and tests). The worker's queue backend goes.
- A message handler has one form: `fn (services: HandlerServices, timers: Timers, io: std.Io, allocator: std.mem.Allocator, payload: P) !Response(T)`, where `Response(T)` has only `.now` and `.later`. No message handler ever starts a task through its return value: the return value is only the response now or the response later. A handler that needs a task starts it with a function call, as the plan that removes `.task` defines. The later reply handle and the message's name and id are reached through `HandlerServices`.
- A menu item does frontend work only as an `.action` item. `.ui` items, the `menu` app event and `IMenuEvent` go. `.zig` items stay.

This plan is implemented after `docs/plans/new/plan-start-tasks-by-call.md` (see Notes) and its steps are written against the state that plan leaves: `Response(T)` and `MessageResult` have no `.task` variant, `ResponseTask` is gone and a message whose work is slow returns `.later` and starts a task with a function call.

Photosphere, at `/home/ash/projects/photosphere/photosphere`, is then pointed at that local checkout for the length of the plan and converted. Everything removed is removed in the last step, Clean up, which also points Photosphere back at its tag.

## Notes

- Decided before this plan, not to be reopened: no documentation step at the start and no review stop, step 1 is implementation and the last implementation step writes the docs; every kind of handler is covered; the task form is Ziggy's typed form; the raw form, the task queue form, `ToolTaskHandler`, `withMediaSources`, `withTools`, `fromNodeApiHandler` and `logExceptions` go; the message form is `Response(T)`; `.ui` items, the `menu` event and `IMenuEvent` go and `.zig` menu functions stay.
- Hard requirement: no message handler may start a task through its return value. `Response(T)` and `MessageResult` have no `.task` variant and no other return value queues a task; a handler starts a task with a function call, as `plan-start-tasks-by-call.md` defines. That plan is implemented before this one and removes `.task`; this plan's steps assume its result and Verify checks it. It did not exist on disk when this plan was written; its function for starting a task is whatever it defines and this plan names it only as "the call that starts a task".
- Message form chosen: `Response(T)` with `.now` and `.later`, over a plain result with the later reply on `HandlerServices`. `Response(T)` needs one type and states in the handler's return type whether it answers now or later. A plain result has no way to say "later": the handler would still have to return a `T` and a second rule would be needed for when that value is dropped. Plain handlers become `.now` returns.
- The compile check that a `Reply(T)` matches the handler's `Response(T)` is lost, because the reply now comes from `services.laterReply(T)`, where the handler's type is unknown. A reply of the wrong type is a JSON response of another layout, which the frontend's own types catch.
- `HandlerServices` reaches the message through a slot the main thread fills for each handler call. The main thread runs one handler at a time, so one slot holds; the slot is part of the main thread's own services, so no state is shared between threads. `NoMessage` keeps calls from a timer or a menu function from reading a stale message.
- Child tasks: inside a task the one way is `TaskServices`. `TaskQueue` on a worker goes with the worker's queue backend. Research found the CLI's pool needs `TaskQueue` only on the CLI's own thread, which owns the pool and runs no task (`addPaths`, `checkPaths`, `verify`, `replicateDatabase` and the add and consolidate commands, all called only from CLI commands), so `TaskQueue`, `IQueueBackend` and `MockWorkerPool` stay for that thread and for tests and the CLI's pool already carries `TaskServices` children (it handles `queue-task` and sends every `task-completed` to every worker). Converting the CLI's drivers to `TaskServices` would need a services implementation on a thread with no task and was not chosen.
- `takeEndedChild` was added because `import-assets` runs a pipeline: a hash that ends queues an upload while the scan goes on, which needs "whichever child ended next" with a time limit and `awaitTask` waits for one named child. It is a pull in place of `TaskQueue`'s completion callbacks.
- `TaskServices.addTask` was added because `load-assets` starts `prefetch-database` under another source at background priority and must not wait for it; a child would hold `load-assets` open until the prefetch ended, since a task's end waits for its children.
- `import-assets` children now run under the import's own source in place of its session id. A cancel of the import's source cancels them through the pool, as the deferred `shutdown` did through the session id. When the scan fails, children already running (at most the concurrency limit) finish before the task reports its failure, where `shutdown` cancelled them; files not yet handed out are never handed out. The test of `shutdown` is deleted as its subject is gone.
- `TaskServices` becomes a pointer and a table of functions, as `HandlerServices` already is in Ziggy. `zig.md` prefers other layouts when porting a TypeScript interface; this is not a port and one layout for both services keeps one pattern for a reader and lets a test fake either one in a test file, which `testing.md` requires (product code never references test code).
- Test fakes: one `RecordingTaskServices` in node-api's tests replaces `RecordingTaskContext`, `TestTaskContext` and the direct use of Ziggy's `task_context.TaskContext`; mobile-worker's sandbox already imports node-api's test helpers by relative path. Ziggy's `task_context.TaskContext` existed only for such tests and goes.
- Setup hook: `.before_task` runs before each task, not once per thread. `withMediaSources` registered the media sources before every task and Photosphere's version needs the task's services to know whether a native caller exists, which a hook at thread start cannot see. Registering is a `put` into a per-thread map, so running it per task costs what it costs today.
- `withTools` is replaced without a Ziggy hook: the three tool handlers become comptime functions of `Tools` that make the tools themselves, as `withTools` made them per call. `Tools` differs per program (the CLI and app's `ThreadTools`, the tests' `NoTools`), so the handler cannot name it.
- Error logging: Ziggy's worker logs every failed task's error with the task type, which every app gets. `logExceptions` gave each handler its own text; the task type now names the failure.
- `fromNodeApiHandler` put the data dir into the payload; the typed form has `context.data_dir`, which `taskDatabaseBaseDir` now takes.
- `withNodeApiTasks` in Photosphere's `app.zig` adds node-api's list of task types to the app's; it is registration, not a handler form and stays. node-api's list is made with `ziggy.core.taskTable`, so it gets the same checks as the app's `.tasks`.
- Timers: `TimerCallback` keeps its untyped `services` argument. It already has one form; the argument is untyped because one timer list serves the main thread and the workers and `handlerServicesOf` and `taskServicesOf` give the typed services. Typing it is not needed for one handler form.
- Actions, `on_create`, `on_destroy`, `on_task_end`, `on_task_event`, `ui_query` and `describe_error` already have one form and are unchanged.
- The examples (`ziggy-example-vite`, `ziggy-example-rsbuild`) lock Ziggy to v0.0.23 and have one plain message handler each, no `.ui` item and a typed task. Ziggy's `CLAUDE.md` moves them to a new version only after a release, so they move with the next release, when their message handler becomes `Response(T)`.
- Photosphere takes Ziggy from a tag. For the length of the plan its `build.zig.zon` uses `.path = "../ziggy"` (every Zig build of Photosphere reads that one file) and its frontend uses `file:../../../ziggy`; Clean up restores both. Releasing Ziggy, tagging it and moving Photosphere's tag are outside this plan; until then Photosphere's checked-in dependency is v0.0.23 and it needs the new Ziggy to build.
- No commit, push, tag or release is part of this plan.
