## Overview

An app needs an action, such as File > New Window (`CmdOrCtrl+N`) in Graft (a Git client being built on this Ziggy release; the list of what that release needs is `~/projects/photosphere/ziggy-updates.md`, section "New window"), that opens another window of the app with arguments it chooses. Each window is a process of its own on every desktop platform (Linux, Windows and macOS), with one window, its own backend and task queue, and the app adds no code of its own to start a process. The native app starts the app's own executable again with the given arguments (on macOS the executable inside the bundle, started directly), so the new process stays in its parent's process group and a smoke test that ends the group ends every window. Under remote control the new window gets the same `--remote-control` address and connects to the same server. Closing a window ends only its own process. Each platform's Quit behaves as its users expect: on macOS Cmd+Q and on Linux Ctrl+Q in any window end every window's process of the app, including windows opened from a window that has since closed, and Windows has no app-wide Quit (closing or quitting a window ends only its process). Android, iOS and dev mode have no new window and fail with `NewWindowUnavailable`. This plan adds `window.ziggy.newWindow(arguments)` and `HandlerServices.new_window`, the `new-window` call to the native app, a C function that starts the app again, a record of the app's window processes in its data directory that Quit reads, a "New Window" action in the template and the test app, log file names that carry the process id, and smoke scenarios that open, use, close and quit windows.

## Notes

- A process per window is the design the human chose for every desktop platform, written in the "New window" section of `~/projects/photosphere/ziggy-updates.md` (the list of what the next Ziggy release needs, outside the four repositories): each window a separate process with its own backend and task queue, the app adding no code to start a process, closing one window never ending the others, and the new instance staying in its parent's process group so a smoke test that ends the group ends every window it caused. It needs no change to the core's C interface state in `ziggy-api.zig`, which stays one core per process.
- Quit reaches the native app by three routes, and on macOS and Linux all three end every window's process: the Quit menu item (Cmd+Q on macOS, Ctrl+Q on Linux), the app's own code's `HandlerServices.quit`, and the remote control `quit` command. The last two send the core's `quit` call, and each native app's quit does the app-wide work whichever route called it. Windows has one route's worth of work: its `quit` call and Quit item close only their own window.
- Quit across processes on macOS and Linux: each window's process records itself as `<data dir>/windows/<pid>`, and Quit sends SIGTERM to every other recorded process whose executable is this one's. Rejected: signalling the process group, because the group a window runs in is whatever launched the first window (a shell job, the smoke harness's group with its display server) and holds processes that are not the app's; walking parent and child process ids, because a window whose opener has closed is no longer the opener's child; finding processes by executable path alone, because parallel smoke runs of one build share the path and one run's Quit would end another's windows, while each run has a data directory of its own. The data directory is the app's, so a window the person launched separately is also ended by Quit, which is what Quit means on these platforms.
- The record needs no lock and no shared memory: each process creates and removes only its own file, Quit reads the directory and only removes files whose process is gone, and every function runs on one UI thread with its own `Io` and arena for the call. A record left by a process that crashed is removed by the next Quit, and the executable check stops a reused process id from being signalled.
- SIGTERM ends a window as its own Quit does (GLib's `g_unix_signal_add` on Linux, a `DispatchSource` signal source on macOS), so its core stops and writes its log footer, which the scenario checks; a SIGTERM never ends another window, so ending one window's process from outside ends only it. A SIGTERM that arrives before the handler is installed ends the process at once, which is still the end the Quit asked for, and its record is removed by the next Quit. A window started in the moment after a Quit read the directory is not ended by that Quit.
- The smoke harness ends a group with SIGTERM and then SIGKILL after a grace (`kill_process_group`), so handling SIGTERM lets the windows end cleanly within the grace and changes nothing about cleanup.
- `ziggy_start_instance` is in the core, shared by all three native apps, because Zig's `std.process.spawn` starts the executable directly and leaves the process group alone (`SpawnOptions.pgid` defaults to null), on macOS too, where `std.process.executablePath` gives the executable inside the bundle. Foundation's `Process` is not used, so nothing depends on how it sets the child's group. It is not compiled for Android or iOS (comptime branch), where a new window does not exist.
- Reaping: a process started with `std.process.spawn` stays a zombie until its parent waits for it, and `kill -0` succeeds on a zombie, so each native app reaps the windows it starts (GLib's child watch on Linux, a `DispatchSource` process source and `waitpid` on macOS); Windows has no zombies and closes the handles at once. The scenario's closing of window 4 while window 1 runs proves the reaping. A window whose opener has ended is reparented and reaped by the system.
- The `new-window` call stays a native call, rather than the core starting the process on its main thread, because the process must be reaped by the native app's own event loop, and a native app states with `has_new_window` that it does the call, as with `has_screenshot`. `has_new_window` is true on Linux, Windows and macOS and false on Android, iOS and in dev mode.
- Linux keeps `G_APPLICATION_NON_UNIQUE` (`native-app.zig` line 114): each window's process runs its own `GApplication`, so no session bus is involved and the smoke tests need no `dbus-run-session`.
- Linux smoke display: `xvfb-run` kills its Xvfb when the process it started exits, and every other window then loses its display, so the test app's library starts Xvfb on its own with `-displayfd`, in a group recorded apart from the app's, so `ziggy_platform_wait_exit` still waits for the app's processes only. The template's and Photosphere's libraries keep `xvfb-run`, because none of their scenarios outlives window 1.
- Log file names carry the process id, because two windows started in the same second are two processes. Photosphere's CLI (`apps/cli-zig/src/lib/log.zig`) uses the same file log, so its names carry the id too; its tests and `bug.zig`'s `psi-*.log` match only the prefix and the `-errors.log` end. Photosphere's `app-log.sh`, `ios-device.sh`, `ios.sh` and `android.sh` match the whole name and are updated.
- Windows starts the new process through the same `ziggy_start_instance`; it has no process groups, so its smoke library ends each new window by the process id in the core's `Started a new window, process <pid>.` line, an ordinary info line, not a test hook. That line is written right after the native app starts the process, so the pid is on record from the moment the window starts, as Ziggy's `CLAUDE.md` asks of every process a suite causes, and the `EXIT` trap's `ziggy_platform_stop` reads it whether the scenario passed or failed. Windows has no app-wide Quit: its `quit` call and Quit item close only their window, as today.
- The smoke scenario sees a window close by its log footer (`--- Log End ---`, written by `FileLog.close` as its core stops), which every platform writes, so no test hook is added; the remote control server has no list command, and a command to a window that has gone waits the server's whole timeout.
- Windows 3 and 4 are opened before any window closes in the scenario, because the server gives a new app the lowest free number, and whether a closed window's number is free by then depends on when the server sees its connection end.
- `wait_for_ready` fails at once on `AppNotConnected`, as `plan-remote-control-window-targeting.md` leaves it, and is used unchanged.
- `window.ziggy.newWindow(arguments)` and `HandlerServices.new_window` are added because actions run on either side (`window.ziggy.runAction` and `HandlerServices.runAction` both exist) and `ziggy-updates.md` requires the new window to take arguments, which a standard action cannot carry. A standard action takes no arguments, so New Window is an app action whose handler calls `window.ziggy.newWindow`, which also keeps the shortcut and menu placement the app's.
- The arguments after the program's name are the app's own. Of the opener's command line the new window gets only `--remote-control`, so `-geometry=` and the app's options are passed only when the app passes them.
- Android and iOS have no new window: `jni.zig` holds one core per process, the iOS bridge one core, and an Android multi-instance task or iPad scene is out of this plan's scope. Dev mode has no new window: its frontend is a browser tab served by one dev host.
- Windows share the data directory, so the web view's stored data and the config and state files are shared. Atomic config and state updates are the work of `plan-config-and-state.md`, which handles several processes writing the same file.
- Photosphere gets no New Window action: `ziggy-updates.md` asks for the action in Ziggy, for Graft. Photosphere takes the new interface members in its test fakes and the new log file names, built against the local Ziggy its `build.zig.zon` names by path. Its macOS and iOS Xcode projects take the Swift bridges from the same local checkout (`plan-theme.md`), so the bridges and the core agree on `ziggy_config`, and Photosphere's macOS app gets step 7's bridge changes with no change of its own. Its macOS app delegate and Linux smoke library stay as they are.
- New Zig functions and files are `snake_case`, as `rules/zig.md` asks, though the existing Ziggy and Photosphere code is `camelCase` with kebab-case file names; existing names are left alone. The JavaScript and TypeScript `newWindow` and the Swift code keep their languages' `camelCase`.
- The example repositories are not changed: Ziggy's `CLAUDE.md` moves them to a new Ziggy tag at release, when they take the template's changes.
- The upgrade notes go under `## v0.0.24`, because v0.0.23 is the newest heading in `docs/upgrade-notes.md` and actions shipped in v0.0.23.
- The remote control server gets no command that lists windows: the human chose this, though `ziggy-updates.md` says "The server can list the windows connected to it". The scenario tells windows apart by `wait_for_ready <n>`, the process ids in window 1's log and each window's log footer.
- New test files go under `core/src/test`, as Ziggy's build (`addFilteredDirectoryTests`) and every existing core test have them and Photosphere's `CLAUDE.md` asks ("Tests should go under the directory src/test in each package"); the project's rule wins over `rules/zig.md`'s test file beside the code.
- A smoke scenario is run by `smoke-tests/run.sh` with no arguments, so it prints no usage message, as every existing scenario; `rules/general.md`'s usage message is for scripts that take arguments.
- `ziggy_start_instance` passes the environment explicitly: its `std.Io.Threaded` is made with `.init_single_threaded`, whose environment is empty on Linux and macOS, so `.environ_map = null` would start the window with no `DISPLAY`, `HOME`, `XDG_DATA_HOME` or test directory overrides. The unit test of `start_instance` with a given variable catches a regression.
- A menu label in the template's style is Title Case ("Close Window", "Select All"), hence "New Window".
