# New window: more windows of the app, numbered by the remote control server

## Decisions not approved by a human

- On macOS and Linux, a quit the app's own code asks for (`HandlerServices.quit`) and the remote control `quit` command end every window's process, as the Quit menu item does, not only the window whose core asked.
- The documentation is written in the last step, after the code, with no review stop.
- The `AppNotConnected` error names the line as the script sent it, with its `window` field, while the app gets the line without that field. `IWaitingLine` carries both `text` (for the app) and `line` (for the error).
- `acceptApp` removes the waiting lines it sends from `state.waiting`, so a later app that takes the same window is not sent them again. Its final assert checks that no waiting line is for that window.
- The window-targeting smoke scenario runs on Windows and macOS as well as Linux, because neither native app has a single-instance guard. A later change that adds one fails the scenario on that platform.
- `readTarget` reads the window value as `JsonValue | undefined` and narrows it with `typeof windowValue === "number"` before `Number.isInteger` and the range checks, so the code type-checks under `strict`.

## Acceptance criteria

- The remote control server accepts many app connections, numbers each from 1 as a window, and sends each line to the window its `window` field names (window 1 when it has none).
- A line for a window that is not connected waits for it, and a `window` that is not a whole number from 1 to `WINDOW_COUNT_MAX` gets `InvalidWindow`.
- `window.ziggy.newWindow(arguments)` and `HandlerServices.new_window` start another window of the app as a process of its own on Linux, Windows and macOS.
- The new window receives the arguments given, and under remote control the same `--remote-control` address, and runs its own backend and task queue.
- Closing a window ends only its own process.
- On Linux and macOS, Quit (the menu item, `HandlerServices.quit` and the remote control `quit`) ends every window's process of the app; on Windows Quit ends only its own window's process.
- Android, iOS and dev mode fail with `NewWindowUnavailable`.
- Log file names carry the process id.
- The template and the test app have a New Window action.
- The server's unit tests and both new smoke scenarios pass, and the existing scenarios, the template's suite and Photosphere's tests still pass.
- The new smoke scenarios pass on Linux, and on Windows and macOS in CI.
- All unit tests and smoke tests pass.
- The documentation and the server's README describe the new server behavior, and the upgrade notes are updated.

## Overview

An app needs an action, such as File > New Window (`CmdOrCtrl+N`) in Graft (a Git client being built on this Ziggy release; the list of what that release needs is `~/projects/photosphere/ziggy-updates.md`, section "New window"), that opens another window of the app with arguments it chooses.

The remote control server must number those windows first. Today it takes one app connection at a time, and a new app replaces the one before it, so a script has no way to address a second window. The first steps here let the server hold many app connections at once, give each the lowest number from 1 that no connected app holds, and send each script line to the window its `"window": <n>` field names (window 1 when it has none). A line for a window that is not connected waits for it, as a line waits for the app today. The server takes the `window` field off before the app sees the line, so the app never sees it.

Each window is then a process of its own on every desktop platform (Linux, Windows and macOS), with one window, its own backend and task queue, and the app adds no code of its own to start a process. The native app starts the app's own executable again with the given arguments (on macOS the executable inside the bundle, started directly), so the new process stays in its parent's process group and a smoke test that ends the group ends every window. Under remote control the new window gets the same `--remote-control` address and connects to the same server, where it is the next window number. Closing a window ends only its own process. Each platform's Quit behaves as its users expect: on macOS Cmd+Q and on Linux Ctrl+Q in any window end every window's process of the app, including windows opened from a window that has since closed, and Windows has no app-wide Quit (closing or quitting a window ends only its process). Android, iOS and dev mode have no new window and fail with `NewWindowUnavailable`.

A window is one app connection to the server: it gets a number only while it has a WebSocket connection of its own, opened when the window starts and ended when the window closes. Since each window is a process, each opens its own connection.

The plan adds, in order: the server's window numbering and routing; the smoke library's `window_control`, a `wait_for_ready` that takes a window, and a restart that starts a new server; log file names that carry the process id; `window.ziggy.newWindow(arguments)` and `HandlerServices.new_window`; the `new-window` call to the native app; a C function that starts the app again; a record of the app's window processes in its data directory that Quit reads; a "New Window" action in the template and the test app; and smoke scenarios that use a targeted command, open, use, close and quit windows.

### Ziggy repository

1. Read which window a script line is for. In `tools/remote-control-server/src/lib/remote-control-server.ts`, add the declarations below at the end of the file, after `listeningPort` (ends line 495). Each gets a comment block.
    - `export const WINDOW_COUNT_MAX = 100;`, with a comment saying why: a smoke test opens a few windows, so more than this many apps means a test is starting apps in a loop. It limits both the window numbers a line may name and the apps the server holds.
    - `export interface ILineTarget { window: number; text: string; }`: the window the line goes to and the text to send the app. Each field gets a comment block.
    - `export interface IInvalidWindowError { name: "InvalidWindow"; text: string; }`: a line whose `window` is not a whole number from 1 to `WINDOW_COUNT_MAX`, with the line as it came.
    - `type JsonValue = object | string | number | boolean | null;` (not exported), with a comment block saying it is what `JSON.parse` can return, named so the parsed value is typed without `any`, `unknown` or a cast.
    - `export function readTarget(text: string): Result<ILineTarget, IInvalidWindowError>` (using `Result`, `ok` and `err`, which the file already imports from `./result`). It parses the line with `JSON.parse` inside `try`/`catch` (see Notes for why the catch is allowed), into a variable declared `let parsed: JsonValue;`. The plain-object check is `typeof parsed === "object" && parsed !== null && !Array.isArray(parsed)`. The object's keys are read with `const fields: Map<string, JsonValue> = new Map(Object.entries(parsed));`, the window value is `const windowValue: JsonValue | undefined = fields.get("window")` when `fields.has("window")`, and the text without it is `fields.delete("window")` then `JSON.stringify(Object.fromEntries(fields))`, which keeps the other keys in their order, except a key whose name is an integer-like string, which comes first. This shape type-checks under the package's `tsc` settings (`strict`): `typeof windowValue === "number"` narrows `windowValue` to `number` before `Number.isInteger` and the range checks, so the `window` in `ok` is a `number`. A line that does not parse, or parses to something other than a plain object (`null`, an array, a string, a number or a boolean), is `ok({ window: 1, text })` with the text unchanged, so the app still answers it with `InvalidCommand` (scenario `7-control-reports-bad-commands`). An object without a `window` key is `ok({ window: 1, text })` with the text unchanged, byte for byte. An object with a `window` key that is a whole number (`typeof windowValue === "number" && Number.isInteger(windowValue)`) from 1 to `WINDOW_COUNT_MAX` is `ok({ window: windowValue, text: JSON.stringify(<the object without its window key>) })`. That text is the parsed value written again, so it can differ from the script's bytes: an integer beyond 2^53 comes out rounded, a number spelling (`1.0`, `1e2`) comes out as `JSON.stringify` writes the number (`1`, `100`), a string escape comes out as `JSON.stringify` writes it, a key given twice comes out once with its last value, a number outside the double range (`1e999`) becomes `Infinity` and `JSON.stringify` writes it as `null`, and a key whose name is an integer-like string comes out before the other keys. Notes says why that is accepted. Say so in the comment block above `readTarget`. Any other `window` value (0, a negative number, a fraction, a string, `null`, a number above `WINDOW_COUNT_MAX`) is `err({ name: "InvalidWindow", text })`. Assert that the text has no newline, and that an `ok` window is a whole number from 1 to `WINDOW_COUNT_MAX`.
    - In `tools/remote-control-server/src/test/lib/remote-control-server.test.ts`, add `readTarget` and `WINDOW_COUNT_MAX` to the import from `../../lib/remote-control-server` (line 11), and add a `describe("readTarget", ...)` at the end of the file with a `test` for each `readTarget` case listed under Unit Tests.
    - `bun run --filter=ziggy-remote-control-server compile` and `bun run --filter=ziggy-remote-control-server test` pass. Save the compile output to `tmp/evidence/compile/` and the test output to `tmp/evidence/tests/` as the work is done.

### New window

- A process per window is the design for every desktop platform, written in the "New window" section of `~/projects/photosphere/ziggy-updates.md` (the list of what the next Ziggy release needs, outside the four repositories): each window a separate process with its own backend and task queue, the app adding no code to start a process, closing one window never ending the others, and the new instance staying in its parent's process group so a smoke test that ends the group ends every window it caused. It needs no change to the core's C interface state in `ziggy-api.zig`, which stays one core per process. Each window opens its own connection to the remote control server, which is what gives it its window number.
- Quit reaches the native app by three routes, and on macOS and Linux all three end every window's process: the Quit menu item (Cmd+Q on macOS, Ctrl+Q on Linux), the app's own code's `HandlerServices.quit`, and the remote control `quit` command. The last two send the core's `quit` call, and each native app's quit does the app-wide work whichever route called it. Windows has one route's worth of work: its `quit` call and Quit item close only their own window.
- Quit across processes on macOS and Linux: each window's process records itself as `<data dir>/windows/<pid>`, and Quit sends SIGTERM to every other recorded process whose executable is this one's. Rejected: signalling the process group, because the group a window runs in is whatever launched the first window (a shell job, the smoke harness's group with its display server) and holds processes that are not the app's; walking parent and child process ids, because a window whose opener has closed is no longer the opener's child; finding processes by executable path alone, because parallel smoke runs of one build share the path and one run's Quit would end another's windows, while each run has a data directory of its own. The data directory is the app's, so a window the person launched separately is also ended by Quit, which is what Quit means on these platforms.
- The record needs no lock and no shared memory: each process creates and removes only its own file, Quit reads the directory and only removes files whose process is gone, and every function runs on one UI thread with its own `Io` and arena for the call. A record left by a process that crashed is removed by the next Quit, and the executable check stops a reused process id from being signalled.
- SIGTERM ends a window as its own Quit does (GLib's `g_unix_signal_add` on Linux, a `DispatchSource` signal source on macOS), so its core stops and writes its log footer, which the scenario checks; a SIGTERM never ends another window, so ending one window's process from outside ends only it. A SIGTERM that arrives before the handler is installed ends the process at once, which is still the end the Quit asked for, and its record is removed by the next Quit. A window started in the moment after a Quit read the directory is not ended by that Quit.
- The smoke harness ends a group with SIGTERM and then SIGKILL after a grace (`kill_process_group`), so handling SIGTERM lets the windows end cleanly within the grace and changes nothing about cleanup.
- `ziggy_start_instance` is in the core, shared by all three native apps, because Zig's `std.process.spawn` starts the executable directly and leaves the process group alone (`SpawnOptions.pgid` defaults to null), on macOS too, where `std.process.executablePath` gives the executable inside the bundle. Foundation's `Process` is not used, so nothing depends on how it sets the child's group. It is not compiled for Android or iOS (comptime branch), where a new window does not exist.
- Reaping: a process started with `std.process.spawn` stays a zombie until its parent waits for it, and `kill -0` succeeds on a zombie, so each native app reaps the windows it starts (GLib's child watch on Linux, a `DispatchSource` process source and `waitpid` on macOS); Windows has no zombies and closes the handles at once. The scenario's closing of window 4 while window 1 runs proves the reaping. A window whose opener has ended is reparented and reaped by the system.
- The `new-window` call stays a native call, rather than the core starting the process on its main thread, because the process must be reaped by the native app's own event loop, and a native app states with `has_new_window` that it does the call, as with `has_screenshot`. `has_new_window` is true on Linux, Windows and macOS and false on Android, iOS and in dev mode.
- Linux keeps `G_APPLICATION_NON_UNIQUE` (`native-app.zig` line 114): each window's process runs its own `GApplication`, so no session bus is involved and the smoke tests need no `dbus-run-session`.
- Linux smoke display: `xvfb-run` kills its Xvfb when the process it started exits, and every other window then loses its display, so the test app's library starts Xvfb on its own with `-displayfd`, in a group recorded apart from the app's, so `ziggy_platform_wait_exit` still waits for the app's processes only. The template's and Photosphere's libraries keep `xvfb-run`, because none of their scenarios outlives window 1.
- Log file names carry the process id, because two windows started in the same second are two processes. Photosphere's CLI (`apps/cli-zig/src/lib/log.zig`) uses the same file log, so its names carry the id too; its tests and `bug.zig`'s `psi-*.log` match only the prefix and the `-errors.log` end. Photosphere's `app-log.sh`, `ios-device.sh`, `ios.sh` and `android.sh` match the whole name and are updated.
- Windows starts the new process through the same `ziggy_start_instance`; it has no process groups, so its smoke library ends each new window by the process id in the core's `Started a new window, process <pid>.` line, an ordinary info line, not a test hook, and in every window log file's name, which carries the pid as soon as that window's core writes its log. The line is written right after the native app starts the process, so the pid is on record once the call returns, and a window whose opener ends before the line is written is still found by its own log file's name. The `EXIT` trap's `ziggy_platform_stop` reads both whether the scenario passed or failed. Windows has no app-wide Quit: its `quit` call and Quit item close only their window, as today.
- The new-window scenario sees a window close by its log footer (`--- Log End ---`, written by `FileLog.close` as its core stops), which every platform writes, so no test hook is added, and by the server's window numbering through `wait_for_ready <n>`.
