## Decisions not approved by a human

- The documentation is written in step 16, after the code and before the clean up.
- A bad `ziggy.theme` extra on Android fails the start with `UnknownTheme`, as a bad `--theme` does on the desktop. The extra is the Android form of the command line, as `ziggy.remoteControl` is, and any app on the device can already start the exported activity with any extra; a launch with a bad extra fails only that launch, and the user's own launch carries no extra.
- The `system-theme` system message is not limited to the native app. The core cannot tell who posted it: the native app's `ziggy_send_message` is the same path every frontend message takes. The page is the app's own frontend, which `ziggy_check_url` keeps to the app's address, can already change the setting with `setTheme`, and with `system-theme` changes only what `system` resolves to until the next system change, with no write to the config file.
- The scenario that changes the device's appearance runs only on a platform whose library says it can do that (`ziggy_platform_changes_appearance`), so it is not listed on a connected iPhone or iPad, where no command changes the appearance, as the `desktop-only` scenarios are not listed on a phone.

## Overview

Ziggy gains theme support: a theme setting (`light`, `dark` or `system`) stored as the `theme` key of the config file that plan-config-and-state.md adds, a `--theme` argument that overrides it for one run, OS integration on Linux, Windows, macOS, iOS and Android that reads the system theme and follows its changes, and no flash of the wrong theme at start-up. The page gets the theme through the web standard: each native app sets its web view's colour scheme to Ziggy's effective theme (from the setting, `--theme` or the system), so a page styles itself with CSS `@media (prefers-color-scheme: dark)` and hears every change with `matchMedia("(prefers-color-scheme: dark)").addEventListener("change", ...)`, at once and on every platform, iOS included while the app stays in front. `window.ziggy.getTheme()` and `setTheme()` read and change the setting, and the system event `theme-changed` reports every change of the setting or the theme, for a control that shows the setting and for the cases the standard cannot reach. The native app paints the app's background colour for the theme and sets the web view's colour scheme before it loads the page, so the first paint is right with no script. A change made in another window or in an editor while the app runs is not part of this plan's work. Ziggy owns the setting, the argument and the OS integration; the app owns how its pages look. Photosphere today keeps its own `theme` config key, passes it in the page's query, forces a theme with the build-time `PHOTOSPHERE_THEME` variable and lets MUI Joy follow `prefers-color-scheme` for `system`; this plan moves it onto Ziggy's theme, with Joy always in its `system` mode. The plan depends on plan-config-and-state.md, which must be implemented first: it provides the config file, reading it on the core's main thread at start-up and the atomic write of one key. The smoke tests use `--theme` to take screenshots in light and dark and prove the page sees each change through `matchMedia`.

## Notes

- Pages follow the theme through `prefers-color-scheme`, `matchMedia` and Ziggy's `theme-changed` event.
- The per-theme background colours come from the optional app field `.backgrounds`.
- The Android status and navigation bars are left alone.
- The limits are accepted: on Android 7 to 9, in dev mode with a fixed setting, and on Linux with `GTK_THEME` naming a dark theme, `prefers-color-scheme` does not follow the theme and the page sees it only through `getTheme()` and `theme-changed`.
- There is no log line shipped only for a test; Photosphere's theme smoke test checks screenshots.


- On Android 7 to 9 (API 24 to 28) the web view's `prefers-color-scheme` is always light, because the `android:isLightTheme` attribute the WebView reads exists only from Android 10; there a page sees the theme only through `getTheme()` and the `theme-changed` event.
- In dev mode the browser's own `prefers-color-scheme` reaches the page, so a `light` or `dark` setting that differs from the browser's scheme does not; there the page sees it only through `getTheme()` and the `theme-changed` event.
- On Linux, when the `GTK_THEME` environment variable names a dark theme, WebKitGTK reports dark to the page even when Ziggy's theme is light; there the page sees the light theme only through `getTheme()` and the `theme-changed` event.

- Checked against the code: Ziggy has no theme code today (`grep -rni theme` finds only Mermaid diagram settings, the Android manifest theme and `color-scheme: light dark` in the template and test app pages). plan-remote-control.md is implemented (`remote-control.zig`, `remote-control-arguments.zig`, `tools/remote-control-server`), so this plan builds on `--remote-control` as it is.
- The app declares the native window colour for each theme as the optional `ziggy.core.App` field `.backgrounds` (white and black by default), so the window matches the page before the page draws.
- The Android native app sets only background colours and the web view's colour scheme. It leaves the status bar and navigation bar as the app's Android theme sets them: the style it applies to the activity's theme holds only `android:isLightTheme`, and the bars are drawn from the theme the window was created with.
- The page hears every change of the theme through the web standard: each native app sets its web view's colour scheme to the effective theme before the page loads and on every change, and the web view re-evaluates `prefers-color-scheme` and fires `matchMedia` `change` events. Per platform, each checked against the code or docs named:
    - Linux: WebKitGTK 2.52.6 (the version installed here) decides dark in `SystemSettingsManagerProxy::darkMode` (`Source/WebKit/UIProcess/gtk/SystemSettingsManagerProxyGtk.cpp` at tag `webkitgtk-2.52.6`): `gtk-application-prefer-dark-theme` true, else `GTK_THEME` ending in `-dark`, `-Dark` or `:dark`, else `gtk-theme-name` ending in `-dark` or `-Dark`. It listens to `notify::gtk-application-prefer-dark-theme` and `notify::gtk-theme-name`, so a change is live. This machine's desktop theme is `Yaru-purple-dark`, so light needs the name without its suffix as well as `prefer-dark` false. GTK 3 falls back to Adwaita for a theme name it cannot find (`_gtk_css_provider_load_named`, `gtk/gtkcssprovider.c` on `gtk-3-24`), so the shortened name is always safe. A value the app sets with `g_object_set` has the source `GTK_SETTINGS_SOURCE_APPLICATION`, which the desktop's later settings never replace (`settings_update_xsetting`, `gtk/gtksettings.c`), so once Ziggy has changed `gtk-theme-name` a desktop theme change made during that run does not reach it. `GTK_THEME` is read by both GTK and WebKitGTK from the environment, which the app may not change, hence the limit in Notes above.

- The no-flash design: the native app paints the window and web view in the theme's background colour and sets the web view's colour scheme from `ziggy_theme` before it loads the page, so CSS `@media (prefers-color-scheme: dark)` and `color-scheme: light dark` match from the first paint without any script, and an inline script in `<head>` that reads `matchMedia` (Photosphere's Joy attribute, the test app's `first-media-theme`) sees the right value. Ziggy injects no theme script.
- `theme-changed` stays a system event: a change of the setting alone (`dark` to `system` while the system is dark) leaves `prefers-color-scheme` as it was, so a control that shows the setting needs it, and the three limits in Notes have no other way to reach the page. `getTheme` is a system message answered by the core, because no page needs the theme synchronously any more.
- For the setting `system`, macOS, iOS and Windows hand the web view's scheme back to the platform (`NSApp.appearance = nil`, `.unspecified`, `COREWEBVIEW2_PREFERRED_COLOR_SCHEME_AUTO`), so the page follows a system change at once and the core learns of it through `system-theme`. Linux and Android set the resolved theme, because WebKitGTK's own idea of dark is the GTK theme name rather than the portal's `color-scheme`, and the activity theme the template uses (`Theme.DeviceDefault.NoActionBar`) does not follow night mode.
- iOS follows the system theme while the app stays in front: with the override `.unspecified` the web view's own `traitCollectionDidChange` fires when the system appearance changes, before the core hears of it. iOS also flips the style while it takes the app switcher's snapshots in the background (developer reports and the radar FB8734191, not documented by Apple), so the web view posts only while the application state is `.active`, and `didBecomeActiveNotification` posts the current value from `UIScreen.main.traitCollection`, which the window's override does not reach. Ziggy's iOS package owns the web view (`ZiggyBridge.init`) but not the view controller (the app's `ViewController.swift`), so the trait hook is a `WKWebView` subclass.
