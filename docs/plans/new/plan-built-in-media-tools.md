# Run ImageMagick and FFmpeg only from the built-in libraries in the Zig CLI and the Photosphere App

## Overview

ImageMagick and FFmpeg are already built from source under `third-party/` and linked into `packages-zig/media-tools-zig`, whose `MediaTools` runs `magick`, `ffmpeg` and `ffprobe` inside the program's own process through Ziggy's `InProcessRunner` interface (re-exported by `packages-zig/node-utils-zig/src/index.zig` from `ziggy-core`). The Photosphere App (`packages-zig/photosphere-core/src/lib/main-state.zig`) already makes a `MediaTools` and hands its runner to Ziggy's queue backend and to its file logger. The Zig CLI (`apps/cli-zig`) does not link `media-tools-zig` at all and passes `null` for the runner everywhere, so every command it runs for ImageMagick or FFmpeg is started as an installed program found on `PATH`. Any App path that passes `null` falls back to installed programs the same way. This plan removes that fallback from the Zig code so that the CLI and the App can only run the built-in libraries, runs the tests to find every caller that still depended on the installed programs, and then hands those callers the built-in runner. Only the Zig CLI and the Photosphere App are in scope. The TypeScript CLI (`apps/cli`), the Electron app (`apps/desktop`) and the shell scripts, test fixtures, test helpers and workflows that run installed `magick`, `ffmpeg`, `ffprobe` or `identify` themselves are not changed, except that workflows stop installing the tools in a job where nothing in that job runs them.

8. **Stop a timed-out `ffmpeg`.** `WorkerPoolBun.handleTaskTimeout` calls `poolTask.context.cancel()` and abandons the thread. That cancel only sets the task's flag, which a handler reads between its own steps; `ffmpeg_main` never reads it, and the runner is called through Ziggy's `exec` with no task context, so it cannot read it either. An `ffmpeg` call on the abandoned thread would hold `Ffmpeg.mutex` and block every later `ffmpeg` and `ffprobe` in the process. The CLI owns its `MediaTools`, so the pool stops `ffmpeg` through it directly, beside the existing cancel; `InProcessRunner` (Ziggy's) is not changed. The App runs tasks on Ziggy's queue backend, which has no task timeout and abandons nothing, so it needs none of this.
    - In `third-party/ffmpeg/ffmpeg-main.c` (Photosphere's wrapper, which includes `fftools/ffmpeg.c`; the vendored source is not edited), add `void ffmpeg_request_stop(void)`, which does what `sigterm_handler` does for one signal (sets `received_sigterm` to `SIGTERM` and increments `received_nb_signals`), and `void ffmpeg_reset_stop(void)`, which sets both back to 0. ffmpeg's own `decode_interrupt_cb` and transcode loop then end the run as they do on Ctrl+C.
    - In `packages-zig/media-tools-zig/src/lib/ffmpeg.zig`, declare both as `extern`. Add a second mutex, `stop_mutex`, and a `running_thread: ?std.Thread.Id` field, each with its `//` comment. `runFfmpeg`, holding `mutex` as now, sets `running_thread` to the current thread under `stop_mutex` before `ffmpeg_main`; after `ffmpeg_main` it takes `stop_mutex`, sets `running_thread` to `null` and calls `ffmpeg_reset_stop`, then puts the counts back to zero as now. Add `pub fn stopIfRunningOn(self: *Ffmpeg, thread_id: std.Thread.Id) void`, which takes `stop_mutex` and calls `ffmpeg_request_stop` only when `running_thread` is that thread. Because the check, the request and the reset are all under `stop_mutex`, a request can never land after its run has ended and stop the next one.
    - `WorkerPoolBun.init` takes `*media_tools.MediaTools` instead of the runner alone (the CLI's `main` owns it, step 5) and keeps it; the runner it hands tasks is `media.runner()`. Each worker records its thread id when it starts a task, and `handleTaskTimeout` calls `media.ffmpeg.stopIfRunningOn` with the timed-out worker's thread id, next to the existing `poolTask.context.cancel()`.
    - `ffprobe` has no stop flag in `fftools/ffprobe.c` and probes only the header of a file; it is not covered, and Notes says so.
    - Tests: see Unit Tests. `zig build test -Dtest-file=media-tools-zig/ffmpeg.test.zig` and the CLI worker pool test file must pass.

## Notes

- The human chose no documentation review step for this plan, so implementation starts at step 1, nothing in the plan stops for review, and the documentation is written last (step 13).
- Step 1 is what makes step 3 work without uninstalling anything: once the runner is required, every caller that would have used an installed tool fails to compile, and every task run with Ziggy's `null` `toolRunner` fails with the unwrap's message. It also means the build is broken from step 1 until step 6; nothing is committed in between unless the human asks.
- Ziggy's `exec` still starts a program for a command whose first word is not exactly `magick`, `ffmpeg` or `ffprobe` (a path, quotes, `.exe`). Photosphere never builds such a command (step 1 checks), so that does not reach the installed tools. Making Ziggy refuse them would need a new Ziggy version, which is not part of this plan.
- Ziggy's `TaskContext.taskContext()` always sets `toolRunner = null`. The CLI sets the field on the copy it passes to the handler, so Ziggy needs no change. If that turns out not to be possible, stop and ask before changing Ziggy.
- Step 8 adds two functions to `third-party/ffmpeg/ffmpeg-main.c`, which is Photosphere's own wrapper around `fftools/ffmpeg.c`; FFmpeg's vendored source is not edited. If the stop flags cannot be reached from the wrapper, stop and ask the human.
- Running in process removes the isolation a child process gave: a crash in ImageMagick or FFmpeg on a malformed file ends the whole `psi` run (or the App), and a decoder memory bug runs in the process that holds vault secrets and storage credentials. That follows from the human's request, and the App already runs this way on every platform. Step 9's policy narrows what ImageMagick will open; the delegates are already only JPEG, PNG, WebP and zlib, and FFmpeg's decoders are whatever `third-party/ffmpeg/generate-config.sh` enables.
- `ffprobe` cannot be stopped once started (step 8). It reads only a file's header, so a hang there is less likely than in `ffmpeg`, but a hung `ffprobe` would still hold the mutex.
- `docs/plans/new/plan-remove-zig-globals.md` also changes `Image`'s and `Video`'s struct-level variables. Step 2 deletes them, which removes those entries from that plan. Whichever plan is done second must be updated against the other.
- `docs/plans/new/plan-zig-cli-port.md` requires the Zig CLI's output to match the TypeScript CLI exactly. After this plan `psi tools`, `psi version`, `psi bug` and the missing-tools paths of `init`, `add`, `info` and `upgrade` will differ from the TypeScript CLI, because the human asked for the installed tools to go. `104-no-typescript-runtime` still works, because the tools it puts on `PATH` are never used.
- `psi` grows by the size of the linked ImageMagick and FFmpeg archives. The Release workflows already build those archives for every target the CLI is released for, because the App links them.
- `ImageMagick.init` calls `MagickWandGenesis`, which costs start-up time on every `psi` run, including `--help`. If step 3 or step 12 shows that matters, make the `MediaTools` on first use, still owned by `main`.
- The FFmpeg runner allows one command at a time (its mutex). The CLI's worker pool runs tasks on several threads, so video imports in `psi add` are serialised on FFmpeg where the installed program ran them in parallel. Step 12 measures it; if it is much slower, raise it with the human rather than working around the mutex.
- Out of scope, per the human: the TypeScript CLI, the Electron app, and every shell script, fixture generator and test helper that runs installed tools itself.
