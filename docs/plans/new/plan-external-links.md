## Overview

A link to an outside page must open in the system web browser, not inside the app's web view, on Linux, Windows, macOS, Android and iOS: a plain link, a link with `target="_blank"` and a call to `window.open`. Ziggy already decides every navigation with the core's origin check (`origin-check.zig`, through `ziggy_check_url`), and each native app opens an external address with the platform's opener: `gtk_show_uri_on_window` on Linux (`onDecidePolicy`), `ShellExecuteW` on Windows (`navigationInvoke`, `newWindowInvoke`), `NSWorkspace.shared.open` on macOS and `UIApplication.shared.open` on iOS (`decidePolicyFor`, `createWebViewWith`) and an `ACTION_VIEW` intent on Android (`shouldOverrideUrlLoading`, with `setSupportMultipleWindows(false)` so a new window loads as a navigation). What fails today is a `window.open` or `target="_blank"` that no user gesture is behind: WebKitGTK's `javascript-can-open-windows-automatically` defaults to false (documented in the installed `WebKit-6.0.gir`; Ziggy links `libwebkit2gtk-4.1.so.0`, whose `WebKitSettings` property of the same name has no gir installed on this machine), WKWebView's `javaScriptCanOpenWindowsAutomatically` defaults to false on iOS and Android's `setJavaScriptCanOpenWindowsAutomatically` defaults to false, and Ziggy sets none of them, so the web view's popup blocker drops the request before any handler of Ziggy's sees it. A frontend meets this whenever it opens a window after the gesture has expired, such as after a timer or a slow `await`. Photosphere's Help menu item (`apps/photosphere-frontend/src/lib/platform-provider-ziggy.tsx`, the `open-url` case of `runMenuEffect`) and bug report button (`packages/user-interface/src/lib/bug-report.ts`, `openBugReport`, which calls `window.open` after an `await`) both call `window.open` from a message the native app delivers with `webkit_web_view_evaluate_javascript`, which WebKitGTK runs as a user gesture, so whether either is dropped today on Linux is not established; `<M>-external-links` guards them after the change. This plan turns those settings on, since the handlers never create a window, makes a failed open on Linux report itself instead of being discarded, and adds smoke scenarios to Ziggy and Photosphere that open each kind of link on all five platforms. On Linux and Android they prove the system was asked to open the address. On Windows, macOS and iOS, where no test hook is added (the human's choice), they check what a script can see from outside the app: the app is still running five seconds after each open and, on Windows and macOS, the frontend still holds what it held before.

## Notes

- The fix turns on each web view's setting that lets script open windows without a user gesture, so every `window.open` and `target="_blank"` reaches the navigation handlers Ziggy already has. The handlers (`ziggy_check_url` and the per-platform callers) stay as they are and stay the only place an address is judged. No `window.ziggy` call, system message or native call is added, so no app changes its code, and no Ziggy upgrade note is written (Ziggy `CLAUDE.md` asks for one only when an app has to change its code or files).
- Turning on automatic window opening cannot open a window: every native app's new-window handler either opens the address with the system's opener or drops it (Linux ignores the decision, Windows sets `Handled`, macOS and iOS return nil, Android loads it as a navigation that `shouldOverrideUrlLoading` decides). Only the app's own frontend runs in the web view, because the origin check blocks every other page.
- Security: the setting gives a script in the frontend no new reach. From a reading of `onDecidePolicy` (Linux), a script can already send the system browser to any `http`, `https` or `mailto` address with no user action by setting `window.location`: that is a navigation, which the origin check answers with "open externally", and no native app checks for a gesture. What the setting adds is the same through `window.open`. The risk is a script running in the frontend at all, which the origin check (only the app's own frontend loads) and React's escaping of text such as news, database and file names guard against; this plan changes neither. No limit on how many addresses a script opens is added, since none exists for `window.location` either.
- WebKitGTK runs every script the native app evaluates as a user gesture (`webkitWebViewEvaluateJavascriptInternal` in `Source/WebKit/UIProcess/API/glib/WebKitWebView.cpp` passes `ForceUserGesture::Yes`), and `DOMTimer` carries a gesture into a timer for at most `UserGestureToken::maximumIntervalForUserGestureForwarding`, 1 s (`Source/WebCore/dom/UserGestureIndicator.h`). Both were read in WebKit's current source, not in the version installed here, which is why step 6 runs the scenario before the fix. The remote control's `click`, Photosphere's `menu` command and the reply to an `invoke` all arrive through `evaluate_javascript`, so on Linux a direct click never reaches the popup blocker; the test app's 6 s timers do.
- Linux today discards the result of `gtk_show_uri_on_window` (`onDecidePolicy` passes no error and ignores the return), which the rule "failures must be noisy" forbids, so step 6 reports it on standard error, as macOS and iOS already do. This is not the error handling Ziggy's `CLAUDE.md` bans without a request ("Don't add exception handling unless I ask for it"): nothing is caught, retried or recovered, and the decision is ignored as before; the error GTK already produces is printed instead of thrown away. Only the scheme and host are printed, because an address can carry personal details (Photosphere's bug report address holds the log header and the user agent) and standard error goes into the app's log. The GError's message is not printed, so an address in it cannot reach the log. Windows already ends the app with `fatal` when ShellExecute fails, which is loud, so it needs no change. Android already writes `Nothing on this device can open <url>` to the device log (`ZiggyNativeApp.java`, `shouldOverrideUrlLoading`).
- The failed open on Linux was checked on this machine: with `XDG_DATA_DIRS` holding only links to `/usr/share/glib-2.0` and `/usr/share/mime`, `XDG_DATA_HOME` and `XDG_CONFIG_HOME` empty and `DBUS_SESSION_BUS_ADDRESS` pointing at no bus, `gio open https://fail.example.com/x` exits 2 with "Operation not supported"; with a recorder desktop file added under `XDG_DATA_HOME` and a `mimeapps.list` naming it, the same environment records the address; and the test app, built with `bun run build:linux` and run under `xvfb-run` in that environment, ran for 20 s and its frontend answered (`[Frontend] the page sent a ping`).
