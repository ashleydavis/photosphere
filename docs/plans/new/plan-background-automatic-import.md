# Automatic import while the app is in the background

## Overview

Automatic import only runs while the app is on screen. Two separate things stop it the moment it is not: the loop is driven by a `setInterval` inside the WebView (`packages/mobile-frontend/src/lib/platform-provider-mobile.tsx`), which the operating system throttles and then stops when the app is backgrounded and the screen goes off, and the settings that say whether to run at all live in `window.localStorage`, which nothing outside the WebView can read. Fixing the first without the second gets nowhere: a native service that wakes up has no way to find out whether automatic import is switched on or what it should be reading. This plan moves the settings somewhere the embedded engine can read, then drives the import from the native side: an Android foreground service that keeps working with the screen off, and on iOS the most the platform allows, which is an opportunistic background task rather than continuous work. What each platform can honestly do differs enormously, and the plan says so rather than implying parity.

## Issues

## Steps

1. **Move the automatic import settings out of the WebView's localStorage.** They are read and written through `packages/user-interface/src/lib/auto-import-config.ts` against an `IConfig`, and on mobile that is backed by `window.localStorage` (`platform-provider-mobile.tsx:97`). Add `packages/mobile-frontend/src/lib/mobile-auto-import-file.ts` holding `readAutoImportFile(configFile: IDatabasesConfigFile): Promise<IAutoImportFile>` and `writeAutoImportFile(configFile: IDatabasesConfigFile, contents: IAutoImportFile): Promise<void>`, where `IAutoImportFile` carries the settings and the default database path. Follow `mobile-config-store.ts` exactly: the WebView cannot touch the filesystem, so the read and the write go through the embedded worker's config-file tasks, and the module stays unit-testable with a fake. Store it beside `databases.toml` in the app's sandbox.

2. **Point the mobile provider at the file instead of localStorage.** In `platform-provider-mobile.tsx`, the automatic import effect reads its settings through the new module rather than `configStore`. Everything else it does stays as it is. The desktop is untouched: it already keeps these in `desktop.toml`.

3. **Add a worker task that decides what a background run should do.** Register `plan-auto-import` in `packages/mobile-worker/mobile-worker-entry.ts`, handled by a new `packages/mobile-worker/src/lib/plan-auto-import.worker.ts`. It reads the file from step 1 and returns the result of the existing `planMobileAutoImport` (`packages/mobile-frontend/src/lib/mobile-auto-import.ts`): whether to run, the database path, whether that database has to be created, and the settings. The native side must not parse the settings file itself; it asks this task, so the format stays in one place and stays TypeScript.

4. **Declare the Android service.** In `apps/android-frontend/android/app/src/main/AndroidManifest.xml`, add `android.permission.FOREGROUND_SERVICE`, add `android.permission.POST_NOTIFICATIONS` (Android 13 will not show the service's notification without it), and declare a `service` element for `AutoImportService` with `android:exported="false"` and `android:foregroundServiceType="dataSync"`.

5. **Write the Android foreground service.** Add `apps/android-frontend/android/app/src/main/java/au/com/codecapers/photosphere/jsengine/AutoImportService.java`, and beside it `AutoImportDriver.java` holding the one entry point that runs a single pass, serialised so that asking for a pass while one is in flight returns the pass already running rather than starting a second. Everything that wants a pass goes through it, on both platforms, which is what makes two imports at once unreachable rather than merely unlikely. The service creates its notification channel, calls `startForeground` with a notification saying automatic import is running, and then loops: queue `plan-auto-import` on the shared `EnginePool`; if the plan says not to run, stop the service; otherwise queue `create-database` when the plan asks for it, then `import-assets` with `options.auto` set and the plan's settings, wait for it to finish, then wait the configured gap and go again. It holds a `PARTIAL_WAKE_LOCK` only while a run is in flight and releases it between runs, because a foreground service keeps the process alive but does not by itself keep the CPU awake once the screen is off.

6. **Keep the engine pool alive without the WebView.** `JsEnginePlugin.handleOnDestroy` currently shuts the pool down. Change it so the pool is only torn down when no background import is running, and have the service take a reference that stops the teardown while it works. Without this, backgrounding the app destroys the very engines the service needs.

7. **Let the interface start and stop it, and start nothing until it does.** Add `startBackgroundImport` and `stopBackgroundImport` plugin methods to `JsEnginePlugin.java`, and the matching entries in the `JsEngine` plugin interface in `packages/mobile-frontend/src/lib/js-engine-plugin.ts`. The provider calls start when automatic import is switched on and stop when it is switched off. Nothing starts on its own: no service at launch, no scheduled background task, and no notification permission request, until the user has opted in. The permission in step 4 is declared in the manifest but only requested at the moment the toggle goes on, beside the photo permission the same toggle already asks for.

8. **Stop the WebView driving the loop, on every platform.** The `setInterval` in `platform-provider-mobile.tsx` that queues `import-assets` goes. The WebView's job becomes writing the settings and telling the native side to start or stop, and nothing else: it never queues an import again on any platform. Two drivers running at once is the failure this avoids, and having one platform work differently from the others is the thing this plan will not do. Progress still reaches the interface through the same task messages whenever the app is on screen.

9. **iOS: drive it from the plugin while the app is foregrounded.** Add `apps/ios-frontend/ios/App/App/JsEngine/AutoImportDriver.swift`, the same one-pass entry point and the same serialisation as its Java counterpart, with a loop above it that asks for a pass, waits, pauses, and asks again, stopping when the plan says off. The plugin starts it on the same `startBackgroundImport` call the Android plugin answers, and stops it on `stopBackgroundImport`. This is what makes the two platforms behave the same while the app is open, which is the part iOS can do.

10. **iOS: register a background processing task for when it is not foregrounded.** In `apps/ios-frontend/ios/App/App/AppDelegate.swift`, register a `BGProcessingTaskRequest` identifier at launch, add that identifier to `Info.plist` under `BGTaskSchedulerPermittedIdentifiers`, and add `processing` to `UIBackgroundModes`. The handler runs exactly one pass through the same driver as step 9, with the task's `expirationHandler` cancelling the run through the existing cancellation path, and schedules the next request before returning. Keep it to one pass: the system decides when this runs, and a handler that tries to loop will be killed part way.

11. **iOS: one driver, asked by two callers.** There is exactly one `AutoImportDriver` instance for the life of the app, and one entry point on it that runs a single pass. That entry point is serialised: asked to run while a pass is in flight, it returns the pass already running rather than starting a second. The foreground loop asks it repeatedly; the `BGProcessingTask` handler asks it once. Neither knows about the other, and there is no handover to get wrong, because two passes at once is not a state the code can reach. The lifecycle notifications only decide who is asking: the foreground loop stops when the app resigns active and the background request is submitted, and the reverse when it becomes active. If a pass is still running as the app backgrounds, it is left to finish or to be cancelled by expiry, not raced against a second one.

12. **Say what each platform does, in the interface.** The automatic import settings card (`packages/user-interface/src/components/auto-import-settings.tsx`) gains one line under the toggle describing what happens when the app is not on screen: on Android it keeps importing, on iOS it catches up when the system allows. The text comes from the platform through the existing platform context rather than the component working out which platform it is on.

13. **Update the documentation.** `docs/automatic-photo-backup.md` gains a section on background execution and what differs between the platforms, and `docs/mobile-background-tasks.md` gains the service and its engine-pool implications. The wiki's `Configuration-Desktop.md` is not affected; whether the mobile manual needs it is a judgement to make at the time.

## Unit Tests

- `packages/mobile-frontend/src/test/mobile-auto-import-file.test.ts` covering `readAutoImportFile` and `writeAutoImportFile`: a file that does not exist reads as the defaults rather than throwing; a written file round-trips; a malformed file reads as the defaults and does not throw, because a settings file the user never sees must not be able to stop the app starting.
- `packages/mobile-worker/src/test/lib/plan-auto-import.worker.test.ts`: returns "do not run" when the settings say off, returns the default database path when none has been chosen, and passes the configured sources through. The planning itself is already covered by `mobile-auto-import.test.ts`, so this covers the task around it.
- A test for the gap between runs, wherever that is computed, including that a value of zero or a negative one falls back to the default rather than spinning.
- `AutoImportServiceTest.java` under `apps/android-frontend/android/app/src/test/java/...`: the loop's decisions, extracted from the service into a plain class so they can be tested without Android. It must cover: a plan that says off stops the service, a run that fails schedules the next one anyway rather than giving up, and cancellation between runs ends the loop.
- No unit tests for the React changes in steps 2, 8 and 12, per the repository rule. They are covered by the smoke tests below.

## Smoke Tests

- `apps/smoke-tests/tests/49-background-import/test.sh`, Android only, following `47-auto-import`:
  - Switch automatic import on, wait for the first photo to be imported, exactly as test 47 does.
  - Send the app to the background with `adb shell input keyevent KEYCODE_HOME`.
  - Seed a second photo into the device library while the app is backgrounded.
  - Wait for the import to take it in **by asking the device, not the app**. See the note below: `wait_for_log` cannot be used while the app is backgrounded. Poll the database directory with `adb shell run-as "$APP_ID" ls files/...` until the asset count rises, the way the Electron auto-import test counts files.
  - Assert the service is actually running while this happens: `adb shell dumpsys activity services | grep AutoImportService`.
  - Bring the app back with `adb shell am start` and check the gallery holds both.
- A second case in the same test, or a sibling test, for the screen being off: `adb shell input keyevent KEYCODE_POWER` to turn the screen off, seed a third photo, wait for the asset count to rise, then turn the screen back on and check the gallery. The test must restore the screen state however it ends, because a screen left off poisons every test after it on that emulator.
- **Do not wait on `app.log` while the app is backgrounded.** A mobile app has no in-process control server: log lines reach `app.log` over a WebSocket from the WebView to the host bridge (`apps/smoke-tests/lib/common.sh:8-14`), and a backgrounded WebView may have that socket suspended, which is exactly the moment this test cares about. A test that waited on it would time out and report a working feature as broken. The two signals that keep working are the database on disk, read through `run-as`, and `adb logcat`, which the native service can write to directly and which is unaffected by the WebView. Use the first for what was imported; use the second only for diagnosis when a run fails.
- Extend `47-auto-import` only if step 8 changes what it observes; the intent is that it keeps passing untouched.
- **iOS: the foreground driver is covered, the background task is not.** After step 9 the same driver runs in both cases, so `47-auto-import` covers its logic on the simulator once that suite runs there. What cannot be tested is the part iOS reserves to itself: `BGProcessingTask` is scheduled by the system, and the only way to force one is an lldb command against a running app, which this harness has no way to issue on Xcode 14.2. Put a file at `apps/smoke-tests/tests/49-background-import/IOS-NOT-COVERED.md` saying that in as many words, so the gap is visible to whoever looks for it rather than being an absence nobody notices.

## Verify

- `mise exec -- bun run compile` is clean.
- `mise exec -- bun run test` passes, including the new unit tests.
- `mise exec -- bun run test:everything -- --force` passes, all thirteen scripts.
- `49-background-import` passes on a device, and `47-auto-import` still passes.
- With the app backgrounded and the screen off, a photo added to the device library is imported, measured by the database on disk rather than by anything the app says, and `adb shell dumpsys notification` shows the notification the service posts while it works.
- Switching automatic import off stops the service: `adb shell dumpsys activity services | grep AutoImportService` finds nothing, and the notification is gone.

## Notes

- **The settings living in `window.localStorage` is the real blocker**, not the loop. Anything that runs while the WebView does not is blind until step 1 is done, which is why it is first.
- **iOS cannot do what Android can, and the plan does not pretend otherwise.** A `BGProcessingTask` runs when the system decides, typically while charging and idle, and can be killed at any moment. A phone in a pocket all day may import nothing until the app is opened. The honest description for iOS is "catches up in the background when the system allows", and step 12 exists so the interface says that rather than implying continuous backup.
- **What can be proven and what cannot.** Android is testable end to end: backgrounding, the screen going off, seeding a photo and reading the result all happen through adb and none of them need the app to answer. iOS is testable up to the point the platform takes over, and no further. The plan does not pretend otherwise, and the marker file in the smoke tests is there so the untested part stays visible.
- **All of this is opt-in and stays opt-in.** Automatic import is off until the user switches it on, and everything here follows that: no foreground service, no background task request, no wake lock, no notification and no permission prompt exist until the toggle goes on. Switching it off has to leave nothing behind, which is why the Verify section checks for the service and the notification being gone rather than only for imports stopping. A phone that never opts in must be indistinguishable from one running a build without any of this.
- **Two passes at once must be unreachable, not unlikely.** The one serialised entry point in steps 5 and 9 is there for that reason. Anything that reads as "stop this, start that, and hope the timing works" is a defect being planned rather than a design, and does not belong in this work.
- **One driver, one loop, both platforms.** The loop lives on the native side on Android and iOS alike, and the WebView never queues an import on either. What differs is only what keeps the driver alive when the app is not on screen: a foreground service on Android, and on iOS a background processing task the system schedules. That difference is the platform, not a design choice, and it is confined to who starts a pass rather than to what a pass does.
- **That iOS limitation is accepted, not an open question.** It was put to the human as the best the platform allows and taken as the answer: iOS gets opportunistic catch-up, Android gets continuous import. Do not spend time looking for a way round it, and do not hold the Android work back for parity. The only real alternative is doing the work on a server rather than on the phone, which is a different feature.
- **No new dependencies.** WorkManager would be the conventional Android answer and is deliberately not used here: it is a library the project does not have, and adding one needs asking first. A foreground service needs nothing beyond the framework. If the periodic-work guarantees of WorkManager turn out to be wanted, that is a conversation, not a decision to make while implementing.
- **The notification is not optional.** A foreground service must show one. That is a visible product change: an ongoing notification whenever automatic import is on.
- **`targetSdkVersion` is 33** (`apps/android-frontend/android/variables.gradle`). At 34 and above a `dataSync` foreground service must also declare `FOREGROUND_SERVICE_DATA_SYNC` and is subject to a time limit, so raising the target later is a change that has to revisit this.
- **Battery.** A pass costs a listing plus a hash cache lookup per item, and the pacing already limits how fast photos are taken in, but the wake lock in step 5 is the part to watch: held wrongly it flattens a phone overnight. It is deliberately scoped to a run rather than to the service's lifetime.
- **The engine pool is shared** with the asset server and everything else the app runs. A background pass takes slots exactly as a foreground one does, so nothing about `EnginePool.POOL_SIZE` changes, but step 6 changes when the pool is torn down and that is the part most likely to break something else.
