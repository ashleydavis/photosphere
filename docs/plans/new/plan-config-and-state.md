# Config and state files in Ziggy, and Photosphere moved onto them

## Decisions not approved by a human

- The TOML library is `sam701/zig-toml`, taken at commit `8685923e32e8b8a795eb2715684236975a70faed`, the head of its `zig-0.16` branch.
- The library is kept in Ziggy's repository under `third-party/toml`, with one patch that adds writing a table of dynamic values (see the open question).
- Ziggy's config and state code is a new package, `packages/ziggy/config-state`, reached as `@import("ziggy").config_state`, which needs no core, so Photosphere's CLI uses it too.
- Config and state values cross Ziggy's API as `std.json.Value`, keyed by top-level key; a table is one value under its key.
- Every read and write goes to the file: no copy of the config or the state is kept in memory between calls.
- A write rewrites the whole config file with its keys in sorted order and without its comments.
- A `null` value inside a table is written as the key being absent, and a `null` inside an array fails the write.
- TOML dates and times are given to the app as strings holding the text from the file.
- The temporary file of a write is `.<file name>.tmp-<32 hex digits>` in the directory of the real file, after following any symbolic links.
- Symbolic links are followed up to 40 deep; deeper fails the read or write.
- The config file is read up to 1 MiB and the state file up to 16 MiB; a larger file is a problem reported like a bad line.
- On Android and iOS both files live in the app's data directory (`config.toml` and `state.json`).
- macOS takes the home directory from `CFFIXED_USER_HOME`, then `HOME`, as the data directory code already does.
- `<NAME>_CONFIG_DIR` and `<NAME>_STATE_DIR` (the app's name in capitals, dashes as underscores) move the two files, on the pattern of the existing `<NAME>_LOG_DIR`, and every smoke test sets them.
- The main thread reads both files once as it starts, before `on_create`, and writes a log line for a bad config line, a missing state file and an unreadable state file.
- A write to a config file with a bad line fails with `error.ConfigFileInvalid` and leaves the file alone; a write to an unreadable state file starts from an empty state.
- The frontend reaches the files through Ziggy system messages run on the main thread: `getConfig`, `setConfig`, `getState`, `setState` and `getConfigProblem` on `window.ziggy`.
- The backend reaches the paths through `HandlerServices.configPath()` and `statePath()`, task handlers through `TaskContext.config_path` and `state_path` and queue handlers through `ITaskContext.configPath` and `statePath`.
- A core built with no app name (Ziggy's own tests) has no config or state file unless the test sets `RegisteredApp.name`.
- The test app gets buttons, a message, a task and a menu item that read and write the files; the template gets no feature code.
- Two new Ziggy smoke scenarios: one for every platform and one desktop-only for the files on disk.
- Photosphere's `config.yaml` becomes Ziggy's `config.toml`, its `state.yaml` becomes Ziggy's `state.json` and its `databases.toml` becomes the `databases` key of `config.toml`.
- Photosphere moves the plain-text vault's default directory to `vault` beside the state file.
- Photosphere leaves existing users' old files where they are and does not read or move them.
- Photosphere's "reset device" empties the config file through any symbolic link, deletes the state file and empties the plain-text vault's default directory, in place of emptying the old config directory.
- Photosphere keeps its own `get-config`, `set-config`, `get-state` and `set-state` app messages and changes only the file code under them.
- Photosphere's CLI and its plain-text vault work out the paths with `ziggy.app_files.desktopAppFileLocations`, from the app names the core is built with.
- Photosphere takes Ziggy from the sibling checkout `../ziggy` by path for this work.
- The example repositories are not changed by this plan.

## Open questions

1. **How is the config file written?** `sam701/zig-toml` parses into a dynamic table (`toml.Table`, a `std.StringHashMap(toml.Value)`) and into typed structs, but its `serialize` handles only typed structs: given a `toml.Table` it writes each value as `{ string = "..." }`, and it crashes on an empty map (`key_iter.next().?`). Ziggy and the app share one file (Ziggy owns `theme`, the app owns its own keys), so a write has to keep keys it does not know. Ziggy's `CLAUDE.md` bans hand-writing what a library does, and the global rules ban patching a library, without approval.
    - A: Typed whole-file writes with the library as it is. The app declares its whole config as one Zig struct, Ziggy's settings included, and every write serializes that struct. Keys the struct does not name are lost on every write, the frontend cannot reach a key by name without comptime reflection and slice fields are reported (by one guide, not checked here) not to compile in `serialize`.
    - B: Ziggy writes TOML itself: a writer of a few hundred lines in `packages/ziggy/config-state`, from `std.json.Value` to TOML text. The library only parses. Needs your approval under Ziggy's `CLAUDE.md`.
    - C: Ziggy patches the library, keeping it in `third-party/toml` with a patch (`patches/0001-serialize-table.patch` and its `.md`) that adds `serializeTable`, a writer for `toml.Table`, as `third-party/websocket` is kept today. The writing stays in the library and the patch can be offered upstream. Needs your approval under the global rules.
    - Every option rewrites the whole file, so comments and key order are lost on each write. Keeping them needs a writer that edits the text in place, which is option B grown much larger.
    - Recommendation: C. The plan below is written for C. Under B, step 1 drops the patch and the vendoring (the library is fetched with `zig fetch --save` instead) and step 3 gains the writer and its tests. Under A, steps 3, 6 and 13 change to typed reads and writes.

## Overview

Graft and Photosphere each keep settings and remembered state in files of their own, read and written by code of their own. This plan gives every Ziggy app two standard files: a TOML config file, holding what the user chose, and a JSON state file, holding what the app remembers on one computer. Ziggy works out where they live on each platform, writes them atomically (read again just before the write, apply only this instance's change, write to a temporary file in the same directory, rename it over the old one), writes through a symbolic link so a config file kept with stow keeps working, and gives the frontend, the main thread (message handlers, menu handlers and `on_create`), task handlers and programs with no native app (a CLI) the same access. A missing config file means every setting has its default; a config file with a bad line is reported by line and reason, the app starts with the defaults and the file is left alone; a missing or unreadable state file means an empty state, and the log says so. Photosphere then moves its `config.yaml`, `state.yaml` and `databases.toml` onto these two files and stops keeping any other file in its config directory. The work covers the `ziggy` repository (Ziggy, its test app and the template's smoke tests) and the `photosphere` repository. The theme plan (`plan-theme.md`) stores its setting in this config file through the API in Notes, and the reload plan (`plan-config-reload.md`) watches these files.

## Notes

- The API the theme plan and the reload plan build on:
    - Zig, any thread: `ziggy.config_state.config.getValue(arena, io, config_path, key) !?std.json.Value`, `setValue(arena, io, config_path, key, ?std.json.Value)`, `update(arena, io, config_path, mutator)`, `read(arena, io, config_path) !ConfigRead` (`values`, `problem`), and the same in `ziggy.config_state.state` with `state_path`.
    - Where the paths come from: `HandlerServices.configPath()`/`statePath()` on the main thread (message handlers, menu handlers, `on_create`, timers), `TaskContext.config_path`/`state_path` in a task handler, `ITaskContext.configPath`/`statePath` in a queue handler, `ziggy.app_files.desktopAppFileLocations(arena)` in a program with no native app.
    - Frontend: `window.ziggy.getConfig(key)`, `setConfig(key, value)`, `getState(key)`, `setState(key, value)`, `getConfigProblem()`.
    - Ziggy's own settings are top-level keys of the same file. The theme plan adds `theme` and lists it in `docs/user-guide/config-and-state.md`; an app uses no reserved key for its own settings.
- The write follows Photosphere's update in what it re-reads and replaces, and drops its lock file and its fingerprint retry: the feature list settles that the last write wins, and a lock file is a second file in the config directory, which stow rules out. The temporary file sits in the directory of the real file only for the length of one write.
- Zig 0.16's `std.Io.Dir.rename` replaces an existing file, and its Windows file opens share `DELETE` (`share_access = .VALID_FLAGS`), so a rename over a file another process has open goes through.
- `<NAME>_CONFIG_DIR` matches the variable Photosphere's tests already set (`PHOTOSPHERE_CONFIG_DIR`), so its tests keep their isolation with one variable added. Photosphere's Android activity turns every `PHOTOSPHERE_` Intent extra into an environment variable (`MainActivity.java` line 64), so the extra reaches Ziggy's core.
- The app's names come from `app.zon` through the core's build options; Photosphere's CLI links the same core module, so it reaches the same paths without naming the app itself.
- Ziggy's Windows data directory uses the app id (`au.com.codecapers.photosphere`, `dev.ziggy.testapp`) and the state directory uses the title, so they never coincide.
- Rejected: keeping the config in memory on the main thread (a copy on two threads is shared state, which Ziggy's `CLAUDE.md` bans); a `get-config` task in place of a system message (the files are small and every other system message runs on the main thread); a typed config struct (see the open question).
- The Photosphere frontend's `ziggy` package and the Zig dependency point at the sibling checkout for this work; moving them back to a release tag is part of the next Ziggy release, outside this plan.
- Photosphere's TypeScript `packages/node-api` and `packages/node-utils` still name the old files; only the old TypeScript apps use them, and `plan-strip-superseded-typescript.md` removes them.
- Each step that changes code ends with the build and tests that cover it; the Android and iOS suites run in CI.
