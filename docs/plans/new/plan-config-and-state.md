## Overview

Ziggy apps keep settings and remembered state in files of their own, read and written by code of their own. This plan gives every Ziggy app two standard files: a config file, holding what the user chose, and a state file, holding what the app remembers on one computer. The config file is stored as TOML and the state file as nested JSON, but those are file formats only: no TOML or JSON type reaches an app's code. The app reads and writes both files through one typed key-path API: `get(T, "sidebar.left.open")` returns a value of the type the caller names, and `set("sidebar.left.open", value)` writes only that key path and keeps the rest of the file, the config file's comments included. Ziggy works out where the files live on each platform, writes them atomically (the way Photosphere does: take a lock file beside the file, read the file again, apply only this call's change, write to a temporary file in the same directory, rename it over the old one if the file has not changed since the read, release the lock), so two writers in different threads or processes that change different keys both keep their change and no reader ever sees a half-written file, and gives the frontend, the main thread (message handlers, menu handlers and `on_create`), task handlers and programs with no native app (a CLI) the same access, the frontend only to the keys the app opens to it. A missing config file means every setting has its default; a config file with a bad line is reported by line and reason, the app starts with the defaults and the file is left alone; a missing or unreadable state file means an empty state, and the log says so. Photosphere then moves its `config.yaml` and `state.yaml` onto these two files and reads and writes them through the typed API; its `databases.toml` and its plain-text vault stay where they are. The work covers the Ziggy checkout `~/projects/photosphere/ziggy` (Ziggy, its test app and the template's smoke tests), the Photosphere checkout `~/projects/photosphere/photosphere` and Photosphere's wiki checkout `~/projects/photosphere/photosphere.wiki`. The theme plan (`plan-theme.md`) stores its setting in this config file through the API in Notes, and the reload plan (`plan-config-reload.md`) watches these files.

## Notes

- The new Zig code in Ziggy follows Ziggy's existing code style, as `rules/general.md` says for a project that does not follow the rules' style: camelCase function names (`readLimited`, `appFileLocations`), kebab-case file names (`atomic-file.zig`) and positional string arguments (`get(T, arena, io, config_path, key_path)`) in place of an options struct. Every existing Ziggy file is written this way, and `plan-theme.md` and `plan-config-reload.md` are written against these names. Internal functions where two arguments of one type can be swapped take a struct or an enum instead, as each step says.

- Choices the human has made: the write mechanism is copied from Photosphere's `fs.zig` (the lock file `<file>.lock`, breaking a stale lock, the fingerprint check, and the Windows rename with its retry, `renameWindows` included); stow is dropped; the vault and `databases.toml` stay where they are; apps use a typed key-path API (`get(T, path)`, `set(path, value)`) and no TOML or JSON type reaches them; the TOML library is `sakakibara/toml-zig` v0.6.0. The lock file is the one exception the human made to Ziggy's rules against locks and shared state between threads: two writers share nothing in memory, only the lock file on disk.
- Ziggy hides the file formats: no TOML or JSON type (`toml.Value`, `std.json.Value`, `json.Raw` or the like) ever reaches a Ziggy app's code. The app uses a typed key-path API, the same shape for config and for state. `get(T, "sidebar.left.open")` returns a value of the type the caller names: bool, integers, floats, strings, enums, optionals, slices and arrays, and structs (a struct reads a whole table or object, nested to any depth). An absent key returns null when `T` is optional and is otherwise an error naming the key. A value in the file of the wrong type is `error.SettingWrongType`, its message naming the key, the type asked for and the type found. `update(change)` runs the app's change on the file's values under the update lock, through `Values.get` and `Values.set` and writes every `set` it made in one rename, so reading a key and writing it back, or writing several keys, cannot lose another writer's change or show a reader part of it. A `T` that cannot be stored is a compile error. `set("sidebar.left.open", value)` takes any such value (`anytype`), writes only that key path and keeps the rest of the file (for config, comments included, through the TOML library's lossless document editing). Keys are dotted paths into the nesting. Config is stored as TOML and state as nested JSON; those are file formats only. The frontend keeps `window.ziggy.getConfig(path)`, `setConfig(path, value)`, `getState(path)`, `setState(path, value)` and `getConfigProblem()`, taking and returning plain JavaScript values, also by dotted path; the bridge carrying JSON is an internal detail.
- The config and state files live in each platform's usual place for settings and for remembered state (XDG on Linux, `~/.config` and Application Support on macOS, `%APPDATA%` and `%LOCALAPPDATA%` on Windows), and in the app's data directory on Android and iOS.
- The typed API the theme plan and the reload plan build on:
    - Zig, any thread: `ziggy.config_state.config.get(comptime T: type, arena: std.mem.Allocator, io: std.Io, config_path: []const u8, key_path: []const u8) !T`, `ziggy.config_state.config.set(arena: std.mem.Allocator, io: std.Io, config_path: []const u8, key_path: []const u8, value: anytype) !void`, `ziggy.config_state.config.update(arena: std.mem.Allocator, io: std.Io, config_path: []const u8, change: anytype) !void` (with `change.run(arena, values: ziggy.config_state.config.Values) !void`) and `ziggy.config_state.config.problem(arena, io, config_path) !?ConfigProblem`; `ziggy.config_state.state.get`, `set` and `update` the same with `state_path`, and `ziggy.config_state.state.status(arena, io, state_path) !StateStatus`.
    - Where the paths come from: `HandlerServices.configPath()`/`statePath()` on the main thread (message handlers, menu handlers, `on_create`, timers), `TaskContext.config_path`/`state_path` in a task handler, `ITaskContext.configPath`/`statePath` in a queue handler, `ziggy.app_files.desktopAppFileLocations(arena)` in a program with no native app.
    - Frontend: `window.ziggy.getConfig(path)`, `setConfig(path, value)`, `getState(path)`, `setState(path, value)`, `getConfigProblem()`, each get and set limited to the key paths the app lists in `App`'s `.frontend_config_keys` and `.frontend_state_keys` (none by default), so a plan that has the frontend read or write a key adds it to the app's list.
- The arguments of `get` and `set` follow Ziggy's threading rules: the arena and the `Io` are passed on each call and never stored, the file's path is a string the caller holds (copied to each thread with the services and contexts), and no value is kept between calls, so two threads share no memory.
- Inside the package the files are read into `std.json.Value` (the TOML through `json-toml.zig`) so one key-path walk and one typed conversion serve both files. The core's system messages use that JSON layer to carry the frontend's values; `core/src/index.zig` exports only the typed API, so an app cannot reach the JSON layer.
- A key path cannot hold a key containing a dot and cannot index into a list; a list is read or written whole. Photosphere's interface keys, which may hold a dot, are encoded by `stateKeyPath` (step 11) so each stays one key.
- A struct field absent from the file takes its default value when it has one, so an app's settings struct can name its defaults once.
- TOML has no null: `set` of null removes the key, a null field of a struct is left out, and a `null` inside a list fails the write. JSON has no NaN or infinity, so writing one to the state file fails naming the key.
- JSON has no date: TOML dates and times are read as strings holding their text from the file. A date the write does not change stays a date in the file.
- Integers are stored as `i64`, the widest TOML holds; an integer the app writes outside that range fails naming the key.
- Rejected: keeping the TOML library in `third-party/toml` with a patch. Patches are banned.
- The TOML library is `sakakibara/toml-zig` at tag `v0.6.0` (commit `5706d29906d73d7c4f58a8a4b913c6e93251aa4e`), the release line its README gives for Zig 0.16, fetched with `zig fetch --save`. It is MIT, pure Zig with no libc and no dependencies, has no global state and its README says CI builds it for over 20 targets. It parses into a dynamic `toml.Value` (tables are `std.array_hash_map.String(Value)`, which keeps insertion order), writes a dynamic table with `toml.encode(w: *Io.Writer, value, options)` (sub-tables as `[a.b]`, arrays of tables as `[[a]]`, `sort_keys` option), reports errors as `Diagnostic`s with a `Span` and `span.lineCol(text)`, records value spans with `.spans`, compares values with `Value.eql` and edits a file losslessly with `toml.Document` (`parse(arena, text, options)`, `empty(arena, options)`, `setValue`, `setValueSegments`, `remove`, `removeSegments`, `emit(w: *Io.Writer)`), which keeps comments, blank lines and key order. Checked by reading its README and `src/toml.zig`, `value.zig`, `parser.zig`, `encoder.zig` and `document.zig` at `v0.6.0` on GitHub.
- Compared and not chosen: `eneskemalergin/z-toml` (v0.4.1, Zig 0.16 and 0.17, writes a dynamic tree with profiles that may keep bytes, but its README does not say comments are kept or give the writer's signatures) and `baskingspot/toml` (v0.2.1, Zig 0.16 and 0.17, writes a dynamic tree with `stringify` but drops comments, and is installed from a tarball on its own site).
- Rejected: `sam701/zig-toml`. Its `serialize` writes only typed structs, so it cannot write a table holding keys Ziggy does not know, and Ziggy and the app share one file with different keys.
- How a config write keeps comments: `set` works out the file's values with the one key path changed and hands the old and new values to `edit`. `toml.Document.setValue` writes a table value as an inline table, so `edit` writes a new table leaf by leaf, which the library places under a new `[a.b]` header at the end of the document (its module comment, `document.zig` lines 41-44). The library refuses every edit at or through an array of tables, and `removeSegments` refuses a table holding one (`document.zig` lines 548-571), so a write that changes an array of tables takes the whole-file path. `edit` checks every document result by parsing it back. On the whole-file path the file is written with `toml.encode`, in sorted key order and without comments, and any date in it becomes a string. The check makes every write correct whatever the document does with a case the tests do not cover.
- Ziggy's code is a new package, `packages/ziggy/config-state`, reached as `@import("ziggy").config_state`. It needs no core, so its tests run without one, and Photosphere's CLI reaches it through the same core module.
- Every read and write goes to the file and no copy is kept in memory between calls: a copy on two threads is shared state, which Ziggy's `CLAUDE.md` bans.
- The temporary file of a write is `<file>.tmp-<uuid>` beside the file, as in Photosphere, so the rename stays on one file system.
- The config file is read up to `config.read_limit_bytes` (1 MiB) and the state file up to `state.read_limit_bytes` (16 MiB); a larger file reads as a config problem or an unreadable state file, and a write to it fails with `error.FileTooLarge`, so a wrong file cannot exhaust memory and is never replaced.
- On Android and iOS both files live in the app's data directory, the only place the app's sandbox lets it write. macOS takes the home directory from `CFFIXED_USER_HOME`, then `HOME`, as the data directory code already does.
- `<NAME>_CONFIG_DIR` and `<NAME>_STATE_DIR` (the app's name in capitals, dashes as underscores) move the two files, on the pattern of the existing `<NAME>_LOG_DIR`. Every smoke test sets them, because the rules ban a fixed config path shared between test runs. A read of a config file with a bad line finds every key absent, so the app runs on its defaults.

- Photosphere today (`packages-zig/node-utils-zig/src/lib/fs.zig`, reached through `updateYaml` from `config-file.zig` `updateConfigFile` and `state-file.zig` `updateStateFile`, and through `updateToml` from `databases-config.zig` `updateDatabasesConfig`): `updateFileRawOptimistic` takes a lock file `<file>.lock` created with `.exclusive = true` (`tryTakeUpdateLock`), polled with a random growing back-off up to 50 times (`takeUpdateLock`) and broken when older than 30 seconds; under it `updateFileRawAttempt` reads the file, runs the mutator, writes `<file>.tmp-<uuid>` and, only when the file's size and modification time (`fileFingerprint`) are unchanged, renames it into place with `renameIntoPlace`, which retries a rename Windows refuses; otherwise it starts again, up to the caller's retry count.
- Without a lock, two writers can both read the file, each change a different key, and the second rename throws away the first writer's change. Only two changes to the same value may have the last write win, so Ziggy's `atomic_file.update` is Photosphere's mechanism above, copied as it is: a writer reads the file only while it holds `<file>.lock`, which the previous writer removes only after its rename, so two writers changing different keys both keep their change, and the fingerprint check starts a write again when something that did not take the lock changed the file.
- Readers take no lock: the file at the path is only ever replaced whole by a rename, which is atomic on POSIX and, through `FileRenameInformationEx` with POSIX semantics, on Windows, so a reader gets the old file or the new one and never a half-written one.
