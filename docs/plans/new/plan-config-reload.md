## Decisions not approved by a human

- A library notice is not acted on directly: it marks its file pending and the main thread checks the pending files once, 100 ms after the first notice of a burst (step 3). This bounds the work to one read of each file per 100 ms however many notices arrive (`general.md`: do not act directly on external events; put a limit on everything). 100 ms is chosen as shorter than a person notices and longer than the few milliseconds an editor's save or a rename burst takes.
- Running out of memory while reloading panics, as `init`, `frontend.deliver` (`core.zig` line 138) and the core's other main-thread paths do, so no out-of-memory path is reported as a settings file error.
- The change notice is the core message `{"type":"settings-file-changed","file":"config"}` (or `"state"`), posted with the sender id `from_core`, as the core's other threads post `files-dropped` (step 3).
- The `file-watcher` library lives in a checkout at `../../file-watcher`, which is `~/projects/file-watcher`, beside the `~/projects/photosphere` directory that holds the `ziggy` and `photosphere` checkouts. Ziggy takes it as a local dependency in `build.zig.zon`'s `.dependencies`, beside `.websocket`, with `.path = "../../file-watcher"`. The checkout's own commit is the version used, so no version is locked.
- The `file-watcher` library is deemed ready when its own code and documentation meet every need in "The `file-watcher` library" and step 3's tests and the smoke tests prove each one on every platform. A need it does not meet is added to the library rather than worked around in Ziggy: Ziggy keeps one watcher and no polling.
- A `--theme` on the command line wins over a `theme` in the config file: `ThemeState` records where the setting came from, so a config change to `theme` sends neither the native call nor the `theme-changed` event when the core was started with `--theme`.

## Overview

Ziggy keeps the app's config file (TOML, what the user chose) and state file (JSON, what the app remembers on this computer), as `plan-config-and-state.md` adds them. This plan makes Ziggy notice when either file changes on disk, whoever changed it: the user in an editor, another instance of the app (see `plan-new-window.md`), a task of this instance or this instance itself. The `file-watcher` library tells the main thread that a file changed; the main thread reads it, compares it with what it read last and, when it differs, sends the app an event: a system event to the frontend carrying the new contents, and a call of the app's backend callback. A theme set in the config file is applied too. When a changed file cannot be read, Ziggy logs the error with its logger, sends the frontend a `settings-file-error` system event naming the file, the line and the reason, so the frontend can show an error message, and keeps the settings it last read.

The work covers the `ziggy` repository (the core, the injected script, the frontend types, the test app, a smoke scenario and the docs) and the `photosphere` repository (the config store, the three contexts that hold settings, and a smoke step). The example repositories need nothing: they lock Ziggy to a release tag, and this plan adds calls they do not have to use.

## Notes

- The documentation is written after the code and before the Clean up step, and the plan has no review stop.
- The human chose the `file-watcher` library for finding changes, with no polling, and put the plan on hold until the library is ready. The steps name only what the plan needs from it; its calls are written from its documentation in step 3.
- The feature list settles that Ziggy watches the config file, refreshes on its own and gives the app an event when the config or the state changes, whoever changed it. The event names and calls follow the existing system events (`systemEvent("core-error")` with `onCoreError` and `removeCoreErrorListener`) and the existing optional app field `on_task_event`.
- The frontend gets `config-changed` and `state-changed` system events carrying the whole new file as a plain JS object, and the backend gets optional `on_config_change` and `on_state_change` fields in `ziggy.core.App`, which are given no values and read the settings they need with `get(T, "a.b.c")`. The human confirmed this design.
- The human's instruction for a config or state file that cannot be read while the app runs: the error is logged with the logger, and a `settings-file-error` event goes to the frontend so it can show an error message if it wants. Ziggy keeps the settings it last read and sends only that event.
- The error event carries `path` beside `file` so a frontend can show where the file is without asking for its location. `line` is given for a config file problem, an oversized config file being on line 1 as `plan-config-and-state.md` reports it at start-up; it is left out of the JSON otherwise, so the TypeScript field is optional (`typescript.md`: `undefined` for absent values).
- The backend gets no callback for a file error: the human's instruction names the logger and a frontend event only.
- A notice is followed by a read and a comparison with the text kept from the last read, because a notice says only that something happened to the file: a save of the same bytes, a touch, or two notices for one rename send nothing. The comparison is of the bytes, because HFS+ and FAT keep modification times only to a second or two.
- A file that stays unreadable is reported once: `check` returns `.read_failed` only when the error differs from the last one, and a parse problem keeps the bad text, so a notice for the same bytes sees no change.
- A file that cannot be read at start-up is reported by start-up's own log line and `getConfigProblem` from `plan-config-and-state.md`; the watch reports problems that appear while the app runs.
- The reads use `config_state.atomic_file.readLimited` and the named limits `plan-config-and-state.md` declares, so the watch refuses no file the app can read and the three reads of each file share one limit.
- Every test and smoke helper writes a file (Photosphere's `put_config_file`, `ios_put_config_file` and `android_put_config_file` once step 11 changes them) the way `atomic_file.update` and many editors do, to a temporary name renamed over the file, so a notice never finds a half-written file and the counts of events are exact.
- The main-thread tests do not rely on the order of notices: each check reads the file as it is then, so merged, reordered or repeated notices give the same events, and "sent once" for unchanged bytes is proved by `config-watch.test.zig` without the library.
- `config-watch.test.zig` is found by `build.zig`'s `addFilteredDirectoryTests`, which runs every `src/test/*.test.zig`, as for `remote-control.test.zig`; Ziggy's code files carry no test import block, so `zig.md`'s import of the test file is met by the build.
- `readLogFile` moves into `src/test/log-files.zig`, a test helper beside `test-app.zig`, because product code holds no test-only code (`testing.md`).
- Photosphere does not listen for `settings-file-error`: the human's instruction leaves showing a message to the frontend's choice, and Ziggy's log line records the problem. `FakeZiggy` still adds the listener pair, because it implements `IZiggyBridge`.
- The settings reload guard exists because a context's own write announces itself: a toggle clicked twice can have the first write's change event read the file before the second write lands, which would set the old value back for a moment and push a stale "Sync gate set to" line. Discarding reads that overlap a write, and reading once after each write ends, keeps the context at the user's value and still picks up another writer's change.
- The Photosphere smoke step turns syncing on from the file, because the default and an empty file both mean off, so the "true" line can come only from the edited file.
- The app's own writes are announced through the same notice as any other writer's: `plan-config-and-state.md` writes from any thread straight to the file, through functions that know nothing of the watch. One path for every writer keeps the watch on the main thread alone.
- No thread shares state: the watch, the comparison and the callbacks are all on the main thread, the library's notices reach it as messages, and every read of the settings goes to the file.
- The test app's `config-log` area, the `settings-file-error` lines it shows and its `config-changed-backend` and `state-changed-backend` events are the test app's own UI, which exists to show Ziggy's features to the smoke tests; nothing is added to Ziggy or to an app that ships.
- On a connected iPhone or iPad the scenario writes the files through lldb, as `ziggy_platform_data_dir` reads them there, so it runs every check on every platform.
- Photosphere reacts to config changes only. Its state readers (`asset-view.tsx`'s summary, `collapsible-section.tsx`, `search-context.tsx`'s recent searches, `developer-context.tsx`'s developer tools, `gallery-context.tsx`'s sort) hold what one window remembers, and another window's change should not move them in this one. The state's `createConfig` still gets its `subscribe`, which the new third argument requires.
- Photosphere's automatic import already reads its settings on every tick of its own check (`ensure-auto-import`, `main-process.zig`), so its backend needs no `on_config_change`.
- `IConfig.onChange` and `createConfig`'s third argument are inside Photosphere's shared UI package, between its own modules.
- `plan-theme.md` leaves a theme change that arrives in the config file while the app runs to this plan, which step 4 covers. Starting another instance is `plan-new-window.md`'s; this plan makes every instance follow the others' writes.
- The example repositories (`ziggy-example-vite`, `ziggy-example-rsbuild`) need no change: they lock Ziggy to a release tag, and this plan adds only optional calls. Moving them to the release that holds it is release work.
