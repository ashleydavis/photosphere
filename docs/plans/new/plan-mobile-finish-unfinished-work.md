# Finish the unfinished mobile (Android / iOS) work

## Overview

An audit (`docs/mobile-unfinished-work.md`) found ~45 gaps in the mobile platform, of which the worst class is stubs that return the exact value the shared UI reads as success: `importSharePayload` is an empty function whose caller unconditionally shows "Database imported successfully!", `pickFolder` returns the literal string `"downloads"` to six callers, `checkDatabaseExists` returns `true` so the "Database not found" guard is unreachable, `listS3Dirs` returns `[]` so an S3 bucket looks empty rather than unsupported, and `setSyncAllowed` writes to a module variable nothing reads while the Settings UI presents working sync toggles. Underneath these the mobile platform is genuinely strong: the `NOT IMPLEMENTED` host-bridge machinery in `packages/mobile-worker/src/lib/host-functions.ts` works, all 30 host functions are implemented on both platforms, outbound cert-pinned HTTPS already exists via `node-https.ts` over `tlsConnect`, and native ImageMagick/ffmpeg are real. The rot is concentrated in one unfenced, untested file (`packages/mobile-frontend/src/lib/platform-provider-mobile.tsx`) and in a smoke-test harness that structurally cannot fail: `check_no_errors` signals failure by `return 1`, no `test.sh` sets `-e`, and every test ends with an `echo` returning 0, so a test prints `[FAIL] Errors found in app.log` and then prints `[PASS]` and exits 0. It is unguarded at 17 of 24 mobile call sites (24 calls across 24 of the 25 test dirs; `15-duplicate-name` has none; 7 are guarded with `|| exit 1`) and at all 25 desktop call sites (25 calls across 23 of the 24 test dirs; `15-duplicate-name` has none; `7-share-secret:117,118` and `8-share-database:163,164` have two each). How many tests are silently failing today is not knowable until the harness can fail, which is what Part 1 establishes. This plan fixes the harness first (so every later gate means something), then closes every gap, one step per item, each left uncommitted in its own worktree for review.

## Working agreement

Rules for how the steps are worked. These override any looser reading of the steps below.

- No changes are to be made in the main repo. Changes you make to the main repo will be summarily reverted without telling you.
- **Any order, no cherry-picking of the easy ones.** The steps are independent and may be worked in any order and in parallel: there are no between-step ordering dependencies to respect. The only sequencing is *inside* a merged step, whose lettered substeps run in their stated order because one subagent does them in one worktree (7a before 7b; 12a before 12b; 14a before 14b before 14c before 14d and 14e). Do not skip a step because it is hard, native-only, or cannot be fully verified on this machine.
- **One subagent per step.** Each step (or an explicit merge group, e.g. 7+8) is implemented by its own dedicated subagent. The subagent does that step and only that step, so each step can be reviewed as one self-contained unit of work.
- **Do not commit. Leave each step in its own worktree for review.** Each step's subagent works in that step's own git worktree, branched independently from the current branch, and leaves it there, uncommitted, for the reviewer to inspect and merge. No subagent commits, stages, or merges anything. Steps are independent, so no worktree builds on another's changes; the reviewer integrates them. Tick the step's box in the Progress checklist (in the main-repo copy of this plan) once its worktree is ready for review.
- **Every step collects its evidence under `evidence/` in its worktree.** Each subagent creates an `evidence/` subdirectory at the root of its worktree and gathers there whatever proves its change works and breaks nothing else: the captured output of `bun run compile`, `bun run test:all`, `bun run test:and` and `bun run test:and:unit` (redirect each to a file under `evidence/`, for example `evidence/test-and.log`); any `FAILS-WITHOUT-THE-FIX.md` note the step requires; and any screenshots, logs, or command output the step's gate rests on. It must also write `evidence/summary.md` in plain bullet points covering, in this order: what changed, why it changed, how it was tested, and a summary of the evidence collected (naming the files under `evidence/` and their result). `evidence/summary.md` is the step's cover sheet that the reviewer reads first, not an afterthought. The `evidence/` directory is a review artifact and is not intended to be merged into the branch; the reviewer discards it after review.
- **Run 5 subagents in parallel at a time, in batches.** Launch 5 subagents at once, each step on its own independent worktree. The moment all 5 in a batch are done, immediately start the next 5, and so on, until every step is finished. Batch membership is free: the steps are independent, so any step may share a batch with any other. Two constraints remain, and neither is a between-step dependency: the lettered substeps of a merged step (the 14a→14b→14c→14d/14e chain, and 7a→7b, 12a→12b) run in sequence within their one subagent and worktree, not split across the batch; and any verification that needs the single Android emulator or device is serialized across subagents, not run at once. Steps that edit the same file (for example 31, 35 and 36 all touch `apps/ios-frontend/ios/App/App.xcodeproj/project.pbxproj`) do not conflict while worked, because each worktree is a separate checkout; the reviewer resolves any overlap at merge.
- **Keep changes minimal and easy to diff.** Touch only the lines a step needs. Do not reformat, re-order, or rewrite surrounding code. A small diff is a reviewable diff.
- **New functionality gets new smoke tests.** Every step that adds behaviour adds a smoke test that drives that behaviour through the real path and asserts real state (per the step-3 helpers), not a log line.
- **Existing unit and smoke tests keep working.** A green suite stays green. If an existing test newly fails, that is a bug the step surfaced: fix the code, never the test.
- **Only ever strengthen a test.** Do not modify a unit or smoke test unless the change makes it stronger (adds an assertion, tightens a match, removes a false-pass path). Never loosen, delete, or weaken an assertion to make a run go green. Removing a guard that a helper change made unreachable (step 1's `|| exit 1` cleanup, redundant once the helper itself calls `exit 1`) is allowed because it is a no-op, not a weakening; nothing else is.
- **Test edits must be minimal and obviously-strengthening.** Keep every unit/smoke test change as small as possible so the diff shows, at a glance, that assertions were added and none removed. Do not restructure a test file while editing it.
- **Blocked is not done, and not skipped.** If a step's gate genuinely cannot be met here (macOS-only iOS build/test, an opt-in S3 endpoint with no credentials), implement it in full anyway, mark it `blocked: <reason>` in the checklist rather than `[x]`, and continue. Never mark a step done without meeting its gate, and never report an iOS step as verified.
- **Do not stop until all steps are complete.** Work through to the end of the checklist.
- **Run unattended. Do not ask questions.** Do not pause for confirmation, clarification, or a reviewer decision. Make the best call and keep going until the plan is 100% complete. Record any decision or blocker in the Progress checklist (`blocked: <reason>` or a note) rather than stopping to ask.
- **Do not break the emulator-to-host LAN bridge.** `apps/android-frontend/scripts/emulator-lan-bridge.sh` puts the Android emulator on a real layer-2 segment shared with the host, which is what lets LAN sharing work between the host and the emulator: QEMU's default user-mode NAT isolates the guest, so the receiver's `255.255.255.255:54321` discovery broadcast never leaves the emulator and the host cannot open the return HTTPS connection. This bridge is 100% necessary and must keep working. No step may change the emulator's network mode, the bridge script, or `android_launch`'s host-address handling (`apps/smoke-tests/lib/android.sh`, which defaults to `127.0.0.1` over `adb reverse` and must stay overridable via `PHOTOSPHERE_ANDROID_TEST_HOST`) in a way that regresses host-to-guest LAN sharing. Treat it as a fixed dependency; a dedicated smoke test guards it (`apps/smoke-tests/tests/28-host-emulator-comms/`), which asserts the emulator is on the bridge subnet and host and guest can reach each other, and skips cleanly when the bridge is not up.

## Orchestration runbook (operational learnings from execution)

This section is hard-won operational knowledge for running this plan with parallel subagents. Read it before restarting the process. It is about HOW to drive the agents, not about the code.

TWO-PHASE EXECUTION (the chosen strategy — decouples fast implementation from slow verification):
- PHASE 1 — get EVERY step to review-ready, in parallel, fast. Each step's agent: fully implements the code (both platforms; iOS written not run), writes the smoke/native tests as files, runs ONLY `bun run compile` (clean) and `bun run test` (unit, pass), writes evidence/summary.md, and reports STATUS=REVIEW. It does NOT run test:all / test:electron / test:and / test:and:unit / stories / stories:and. This takes minutes per step instead of ~30-40 min, so all steps reach review-ready quickly and the reviewer can start reading them. Run many Phase-1 agents in parallel (the machine is idle; compile+unit are CPU-parallel).
- PHASE 2 — verify each step's full gate afterwards, one worktree at a time, unattended (overnight). A dedicated verification agent per step runs the full heavy suite (`test:all` via the Electron semaphore, `test:and`/`test:and:unit` via the emulator lock/aslot) on that step's already-implemented worktree, fixes any failure it finds, and records the results in that worktree's evidence/. Run these strictly sequentially: ONE step's suite at a time, never two at once. A step is only fully COMPLETE once Phase 2 is green; Phase 1 REVIEW means "code ready to read, full verification pending".
- ALL tests must pass — `test:all`, `test:and`, `test:and:unit` all green, every step, no exceptions. A step is not COMPLETE while any of them fails.
- `stories:and` is NOT part of the Phase 2 gate and must NOT be run for any step (dropped per direction). Any per-step requirement text below that mentions `stories:and`/`stories` is superseded by this: do not run it.
- AND `test:and` IS THE WHOLE REASON WE ARE DOING THIS. This plan fixes mobile gaps, and `test:and` (the mobile smoke suite running on a real emulator/device) is the ONLY thing that actually exercises those fixes on-device. So while every suite must pass, `test:and` is the point of the exercise: never defer, skip, downgrade, or substitute it, and if anything has to run first it is `test:and`. The others being green does not make a mobile step done, its `test:and` being green is what proves the gap is actually fixed.

PHASE 2 EXECUTION - RUN test:and IN THE FOREGROUND (proven; this overrides the earlier "background long commands" guidance):
- A full `test:and` completes in UNDER 10 MINUTES and passes clean when run in a normal foreground shell (proven: step 20 ran 27/27 in <10 min). It fits inside the foreground command limit, so RUN IT FOREGROUND. Do NOT background it.
- Backgrounded `test:and` runs were getting an intermittent `killed` status (mostly during the build phase). The exact cause was NEVER proven (OOM was ruled out - 43 GB RAM free at the time; the kill signal source was never captured via dmesg/journalctl). Do not theorize about it or design around a guessed cause. The proven fix is simply: run foreground.
- Fast path when an emulator is already up and the app APK is already built (e.g. from a prior run, at apps/android-frontend/android/app/build/outputs/apk/debug/app-debug.apk): `adb install -r -g <apk>` then run a SINGLE test directly foreground: `PLATFORM=android ANDROID_SERIAL=<serial> mise exec -- bash apps/smoke-tests/tests/<n>-<name>/test.sh` (with `adb logcat` capturing in parallel if you need the app side). This skips the heavy rebuild entirely and is fast and reliable.
- The control bridge itself is fine (proven: run standalone it binds an OS-assigned port, writes that exact port to <tmp>/bridge.port, and serves /ready with HTTP 503). A "Control bridge did not start on port X within 40s" / "app not ready" is the app's WebView not connecting on a cold/loaded emulator (the harness's own comment notes this and its retry usually recovers it); it is a transient, not a bridge bug.
- KEEP ONE EMULATOR WARM ACROSS STEPS. Do not kill/reboot the emulator between steps. Per step: (1) build+install that worktree's app ONCE - foreground, e.g. `cd apps/smoke-tests && PLATFORM=android ANDROID_SERIAL=<serial> mise exec -- bash -c 'source lib/common.sh; android_prepare; android_build; android_install'` (completes in <10 min); (2) optionally run a single `tests/<n>/test.sh` foreground as a fast sanity check; (3) run the full `test:and` foreground (an 11 min run must be backgrounded because the foreground cap is 10 min, but a warm/cached run completes without being killed - proven on step 20). The only heavier part is the first build in a cold worktree; the warm emulator + shared gradle/bun/vite caches keep it fast. This is the whole reliable loop - build once, sanity-check one test, then full run.
- STEP 20 test:and: TESTED GREEN (27/27 passed, confirmed by the developer's foreground run and a warm background run). Its test:all + test:and:unit remain to fully complete it.

NEVER USE A SHARED LOCK TO CONTROL THE EMULATOR. Do NOT use `flock` (or any other lock) to coordinate emulator access. EMULATOR TESTS MUST BE RUN IN THE FOREGROUND, one at a time, by the coordinator. That means `test:and` and any single `apps/smoke-tests/tests/<n>-<name>/test.sh` run: foreground Bash call, explicit timeout, nothing else touching the emulator.
- THE DIVISION OF LABOUR: each step MAY have its own fix-agent, and those fix-agents RUN IN PARALLEL - but they FIX CODE ONLY. SUBAGENTS MUST NOT RUN EMULATOR TESTS AT ALL: never `test:and`, never a single on-device `test.sh`, never any adb/emulator work. An agent's verification is limited to `bun run compile` and `bun run test` (unit). THE COORDINATOR runs every emulator test itself, SEQUENTIALLY, in the FOREGROUND, one step at a time, and feeds each result back to that step's agent, which fixes again. Loop fix -> coordinator-verifies -> fix until the step passes.
- A lock is NOT a substitute for foreground serialization. Lock-based sharing hides contention, lets background runs pile up behind each other, and background/locked emulator runs were repeatedly killed or interfered with each other. Foreground + one-at-a-time is the only reliable way.

ALWAYS SET AN EXPLICIT TIMEOUT ON EVERY Bash CALL. The Bash tool's DEFAULT timeout is only 2 minutes and will cut a test run short (a foreground run misread as a failure). A foreground warm `test:and` run must pass `timeout: 600000` (the 10-minute max). Never rely on the default.

THE ITERATION LOOP (developer-directed sweep over every remaining step):
- Run each step's `test:and` FOREGROUND (background commands get killed intermittently; foreground does not). Foreground caps at 10 min, and a warm run finishes well under that. Pass `timeout: 600000` on the Bash call.
- Keep ONE emulator warm across ALL steps (never kill/reboot it mid-sweep).
- For each remaining step in turn: run its `test:and` with an 11-MINUTE timeout (the build is part of test:and). The WHOLE step also runs under a 20-MINUTE hard cap.
- Classify the result:
  - RC=0 AND "All N tests passed" AND it did NOT hit the timeout / crash / error  ->  mark the step PASSED.
  - Anything else (any test failure, an 11-min timeout, a crash, an error)  ->  mark the step NEEDS-ATTENTION. Do NOT fix it now; just record it and move on.
- Then move to the next step and repeat.
- HARD STOP: if ANY step hits the 20-MINUTE cap, STOP EVERYTHING, report to the developer, and await instructions (do not continue the sweep).
- When every step has been passed over this way, report the full PASSED / NEEDS-ATTENTION summary. Do not fix NEEDS-ATTENTION steps during the sweep; that is a later, separate pass.

## FIX-AGENT RULES

- Fix-agents run in PARALLEL, one per step needing attention, and they FIX CODE ONLY. They must NEVER run `test:and`, any on-device smoke test, adb, logcat, or touch the emulator. The coordinator runs every emulator test itself, SEQUENTIALLY, in the FOREGROUND, with an explicit Bash timeout.
- IF AN AGENT CAN PREDICT A FAILURE, IT MUST FIX IT, NOT REPORT IT. A predicted-but-unfixed failure burns a whole ~10-minute serial emulator round for nothing. Agents must chase a failure all the way down and fix everything they can see coming, not just the currently-red thing. Defensive fixes across all plausible causes beat waiting for evidence to pick one. "I predict X will fail next" and "here is a decision tree for the next run" are NOT acceptable stopping points: either fix X, or state specifically why it cannot be fixed without a run. This rule has already cost real rounds (step 14 predicted `gallery-asset-count` and shipped anyway; step 10 predicted the MUI Joy `defaultMode`/`setMode` path and shipped anyway).
- Every step needing attention should have an agent attending it. Do not leave a failing step unattended while the emulator is busy with another.
- Agents verify with `mise trust`, `mise exec -- bun run compile` (RC=0) and `mise exec -- bun run test` (RC=0). They may freely read `evidence/test-and.log` and per-test `tmp/app.log` files.

PRODUCT BUGS FOUND VIA test:and (not test bugs - these would have shipped):
- **6b**: `EncryptedSharedPreferences` stores its Tink keyset in the same prefs file as the data, but the keyset is written by `AndroidKeysetManager` with `apply()` (async background flush) while our secret used `commit()` (synchronous). A force-stop SIGKILLs the process without Android's normal `QueuedWork.waitToFinish()`, so the KEYSET was lost while the secret row survived; on the next launch Tink generated a NEW keyset, and because key names are encrypted deterministically (AES256_SIV) the lookup computed a different ciphertext key, MISSED, and returned null with no exception. That silent null is the only path yielding "loaded 0 of 1" rather than a throw, and it is load-dependent because it is a race between the background flush and the force-stop. Fixed by committing a sentinel key synchronously after building the store (Android rewrites the whole prefs file on any commit, forcing the keyset to disk); the sentinel is filtered out of `keys()`. This is a real data-loss bug on any hard kill, not just under test.
- **19**: `EnginePool.cancelTasks(source)` added the source to a `cancelledSources` set that was never cleared except on full pool shutdown, so `addTask` silently DROPPED every later task for that source, with no run and no completion event (the awaiting promise hung forever). The frontend creates and shuts down a `TaskQueue` keyed on the database path for nearly every operation, so on mobile the FIRST such shutdown permanently killed all further tasks for that database. Desktop/CLI `WorkerPoolBun` never had this; the mobile pools had diverged. Fixed on both Android and iOS (iOS additionally needed a `cancelledTaskIds` set, since it derived running-task cancellation from the source set alone).
- **14**: the wedged `isSyncRunning` flag described above.
- **6ab**: the `loadFailed` latch retained from an earlier attempt - an empty cache could overwrite real secrets (data loss).

Preventing another multi-hour stall (this is the rulebook that stops the one big failure recurring):

- Do NOT judge "stalled" from a process snapshot. ## Implementation notes

Concrete findings from a first implementation pass, recorded to save the next one time. Technical only.

- **The Android emulator boots itself.** `android_prepare` (`apps/smoke-tests/lib/android.sh`) starts an AVD if none is attached, so `bun run test:and` runs on Linux with only the Android SDK installed. An empty `adb devices` is not a blocker, so do not treat Android as unverifiable. `/dev/kvm` is reachable via ACL even when the user is not in the `kvm` group.
- **Add a single-test filter to the mobile suite and use it.** A full `test:and` is a build, an install, and 27 sequential device tests. `run.sh` should accept a number or name (`bun run test:and -- 12`) so one failing test can be iterated in a couple of minutes instead of twenty. This is worth doing early; it pays for itself immediately. **Owned by step 6a** (which already restructures the suite and runs early); it carries the `run.sh` change, its `harness-guard.test.ts` coverage, and its doc update, so it is not floating.
- **There is a load-dependent typed-input race, and it is the most important thing to know.** `doType` sets the input value with the native setter and dispatches `input`; React's `onChange` then updates state and re-renders. Two failure modes appear only under full-suite load, never when a test runs alone: (1) a competing async state update already in flight (for example `openEditDialog` awaiting `getSecretValue` then `setForm`) lands *after* the typing and re-renders the controlled input back to its old value, silently losing the typed text; (2) the next command runs before React has committed, so it sees the pre-typing state. Symptom seen: `12-edit-api-key` and `13-edit-s3-credentials` saved the *old* value under load while passing in isolation, which is the worst shape a test can have. Fix in the driver: after typing, read the value back and retry until it sticks, failing loudly if it never does. This makes `type` deterministic and turns a silent revert into a real failure. Do this in step 4's territory (the test driver), and it de-flakes every later test that types into a dialog.
- **Joy `Select` popups cannot be driven by `data-id`** (the listbox renders in a portal). The add-secret dialog defaults to the `s3-credentials` type, so the api-key field (`secret-value-input`) is not on screen at open; the region field (`secret-s3-region-input`) is. For a value round-trip that does not need to change the type, drive the default-type field and read it back via `revealed-secret-region`, rather than trying to operate the Select.
- **`ResponsiveDialog` is a Joy `Drawer` on a phone and does not unmount when closed** (it sets `visibility: hidden` so it can animate); the desktop form is a Joy `Modal`, which returns null when closed. Two consequences for tests and the driver: the driver must filter `data-id` matches to *visible* elements, or a closed dialog's fields shadow the open one in DOM order; and after a receive/save flow the dialog sits open on its success step over the page, so a test must click the dialog's close button before it can touch the page behind it.
- **`configStore.addSecret` throws on a duplicate name** (matching desktop). Any code path that overwrites a secret (a share-import 'replace' resolution) must `deleteSecret` first; it cannot rely on `addSecret` upserting.
- **Assertion-helper contract.** A bash helper that is meant to abort the test must `exit`, and must not also print a value, because `x=$(helper ...)` runs it in a subshell where `exit` only kills the subshell and the failure is swallowed. Keep value-returning helpers (`read_value`) separate from asserting helpers (`assert_value`/`wait_for_value`/`wait_for_no_value`), and have the asserting ones exit and print nothing capturable. `wait_for_no_value` needs a present-first precondition, or a mistyped `dataId` reads as absent and passes.
- **`spawnSync` deadlocks a Jest test that needs an in-process server.** The `harness-guard` test drives bash, which `curl`s a fake `/get-value`. `spawnSync` blocks Node's event loop for the child's whole life, so an in-process HTTP server can never answer and the test hangs. Use async `child_process.spawn` for that pattern.
- **The WebView bundle contains no vault code** (Vite tree-shakes it; grep the built `index-*.js` for `getDefaultVaultType` / `MacOSKeychainVault` and get zero hits). So importing `api`'s `lan-share-import` (which imports `vault`, which pulls in `fs`/`os`/`path` and keychain CLIs) into `mobile-frontend` really would drag `vault` into the bundle. The separate `mobile-share-import` module over `configStore` is necessary, not a stylistic choice.
- **`check-database-exists` should reuse `checkConnectivity`/`merkleTreeExists` from `node-api`** (the same call desktop's IPC handler ends in), not a raw `fsAccess` path probe, so "the database exists" means the same thing on both platforms: a directory that exists but holds no database reads as absent on both.
- **Step 20 needs a companion fix in the same change.** Giving the Android timer pump a real elapsed budget (matching iOS) means `__pumpTimers` returns false whenever the earliest timer is not yet due, so `pumped` is often false. The idle-attempt counter then fails a legitimately-waiting long-running task as "did not settle". Add a branch: when a timer is pending but not due, sleep (bounded) instead of counting an idle attempt.
- **The `17-` test-number collision resolves itself** when `17-news-notifications` is deleted in step 22 (as step 6a predicts); do not separately renumber `17-replicate-database`.
- **`resetConfig` clearing the config namespace needs key enumeration.** The config keys have caller-chosen suffixes under a prefix, so `IKeyValueStore` must expose `length` and `key(index)` (both already on `window.localStorage`, so it still satisfies the interface). Collect the matching keys before removing any; removing while iterating shifts the indices of the unvisited keys and skips half of them.

## Steps

Each step is one self-contained unit of work, left uncommitted in its own worktree for review.

**Two numbering namespaces, and they overlap.** Plan step numbers (`31`, `32`, `33`, `34`, `35`, `36`) and smoke-test directory numbers (`31-create-database-no-collision`, `32-encrypted-database`, `33-s3-database`, `34-sync`, `35-database-summary`, `36-lan-share-timeout`) run over the same integers with unrelated meanings: plan step 31 is the ImageMagick Q16 reconciliation, while `31-create-database-no-collision` is a test dir created by substep 12a. **A bare number always means the plan step; a smoke-test dir is always written with its name suffix (`33-s3-database`), never as a bare `33`.** Every `Requires:` line and the Smoke Tests section already follow this, so a `33` with no name is a step and a `33-s3-database` is a directory. When scanning a Requires line, read the suffix, not just the number.

**The standing review gate.** An agent may not leave a step at `REVIEW` until: the named gap is fully implemented (not stubbed, not fenced) with unit tests and smoke tests as appropriate for each platform; `bun run compile` is clean across the repo; and `bun run test:all`, `bun run test:and` and `bun run test:and:unit` all pass. A step that cannot meet that gate is not done.

**iOS is written by the agent and run by the developer.** The dev machine is Linux; `bun run test:ios` needs macOS with Xcode (`apps/smoke-tests/lib/ios.sh:27-28` requires `xcrun`, `simctl` and `xcodebuild`), as do `bun run test:ios:unit` and `apps/ios-frontend/ios/build-imagemagick.sh`. So `test:ios` is **not** in the per-step gate: it cannot be, and pretending otherwise blocks all 36 steps at step 1. Every step still writes the iOS half in full: the Swift code, the XCTest cases, and the smoke tests (which are platform-neutral, run from the same `test.sh` under both `test:and` and `test:ios`, and therefore get real coverage on Android). What an agent cannot do is execute the iOS side. Each step that touches iOS therefore adds its check to the **iOS Verification Pass** in the Verify section, which the developer runs on the macOS box (macOS 12.7.6 / Xcode 14.2, per CLAUDE.md) as part of reviewing that step, before the step is marked `COMPLETE`, not batched to the end of the plan. So the rule for iOS is: the agent makes its best effort to implement and test the iOS half of every step (the Swift code, the XCTest cases, and the platform-neutral smoke tests), and the developer runs that step's iOS tests during the step's review, treating a failure as reopening the step. Two rules follow: an agent must never report an iOS step as verified, and an agent must never weaken, skip or fence an iOS implementation on the grounds that it cannot run it. Steps 6b, 12, 14, 20, 23, 29, 31, 32 and 33 carry iOS-only native code and are the ones this bears on.

**Proving a test can fail, without a revert.** Several steps fix a stub and add the test that catches it, so once the fix is in the worktree "run the new test against the old stub" is no longer available. Capture the evidence at the only moment it exists: write the test **first**, run it against the stub still in the working tree, confirm it goes red, and record the observed failure output in `evidence/FAILS-WITHOUT-THE-FIX.md` in the step's worktree (and quote its gist in `evidence/summary.md` and in the step's Progress entry). Then write the fix. Wherever a step below says "prove it fails", this is the mechanism, and the `evidence/FAILS-WITHOUT-THE-FIX.md` note is the deliverable. There are no commits, so the evidence lives in the worktree beside the change, not in a commit message.

The one exception to the gate is Part 7 (correcting inaccurate comments and docs), which changes only comments, docs and READMEs and gates on `bun run compile` alone. Booting an emulator to prove a README edit is inert buys nothing.

### Part 6: The divergences

31. **Reconcile the ImageMagick quantum depth.** iOS builds Q8 HDRI from source (`apps/ios-frontend/ios/build-imagemagick.sh:82` `--with-quantum-depth=8`); Android uses the prebuilt MolotovCherry Q16 HDRI libs (`apps/android-frontend/android/app/src/main/cpp/CMakeLists.txt:42` `MAGICKCORE_QUANTUM_DEPTH=16`). iOS thumbnails are therefore 8-bit per channel with visible banding versus Android. This matters beyond appearance: thumbnails and display assets are hashed and stored (`upload-asset.worker.ts:218,247`) and hashes drive sync comparison (`sync.ts`), so the two platforms generating different bytes for the same source photo is a real divergence.

    Standardise on **Q16**, matching Android's prebuilt libs, so iOS changes a build flag rather than Android swapping libraries.

    **This renames the built libraries; it is not one flag.** ImageMagick's autotools build encodes the quantum depth and HDRI setting into the static-library filename, so `--with-quantum-depth=8` → `--with-quantum-depth=16` turns `libMagickWand-7.Q8HDRI.a` into `libMagickWand-7.Q16HDRI.a`. An earlier draft named only `OTHER_LDFLAGS`. The full set is six edits across four files, and missing any one of the first three fails at link while missing the fourth fails **silently**:

    - `apps/ios-frontend/ios/build-imagemagick.sh:82`: the `--with-quantum-depth=8` configure flag itself.
    - `apps/ios-frontend/ios/build-imagemagick.sh:12`: a comment documenting the resulting ldflags by name.
    - `project.pbxproj:642` and `:679`: `OTHER_LDFLAGS`, which hard-code `-lMagickWand-7.Q8HDRI -lMagickCore-7.Q8HDRI`.
    - `project.pbxproj:640` and `:677`: `MAGICKCORE_QUANTUM_DEPTH=8` in the preprocessor defines. **This is the silent one.** The define tells the compiler how wide a quantum is; the library decides how wide it actually is. Leave it at 8 while linking Q16 libs and nothing fails to build: the app misreads every pixel struct. It must move to 16 with the rest.
    - `scripts/fetch-mobile-media-tools.sh:157-158`: `ios_already_fetched()` probes for `$vendor/{device,sim}/lib/libMagickWand-7.Q8HDRI.a`. Miss this and the file it probes for never exists again, so the idempotency check always returns false and every run does a full from-source ImageMagick rebuild. Slow, not broken, and therefore easy to live with for months without noticing.

    **Android's Q16 is asserted by a define, not by the binary, and nothing checks it.** The prebuilt MolotovCherry libraries are `libmagickcore-7.so` / `libmagickwand-7.so` (`fetch-mobile-media-tools.sh:120-126`) with **no quantum suffix in the filename**, so unlike iOS there is nothing in the artifact that says what depth it is. `CMakeLists.txt:42`'s `MAGICKCORE_QUANTUM_DEPTH=16` is a claim about the upstream binary, and its comment at :40-41 ("This build is Q16 HDRI, matching the prebuilt .so") is the only thing holding it true. If MolotovCherry ever ships a Q8 build at the pinned `IM_VERSION`, or the version is bumped to one that does, Android misreads every pixel and nothing anywhere fails. Standardising on Q16 makes both platforms depend on that claim, so this step must add the check that is missing today: after fetch, assert the depth reported by the fetched library (`identify -version`, or `MagickGetQuantumDepth` via the shim) equals 16, and fail the fetch loudly if not. Without it, "standardise on Q16" means iOS is verifiably Q16 and Android is Q16 by assumption.

    Do **not** require byte-identical output as the gate. iOS builds ImageMagick from source and Android uses prebuilt binaries, so identical bytes would also need identical libjpeg/libpng versions on both, which matching the quantum depth does not deliver. Assert the properties that matter and are achievable: same dimensions, same channel depth, no banding on a gradient fixture. Byte-equality becomes a reasonable gate only if the encoders are later pinned to one version on both platforms; record that as the open question it is.

    Requires: the Android quantum-depth assertion fails the fetch when the library is not Q16; the gradient-fixture properties hold on Android. iOS Verification Pass: `bun run vendor:imagemagick:ios` rebuilds and links at Q16 (this is the step that most needs the macOS run, since the agent can change every flag above but cannot link once).

## Security

Every security issue this plan surfaces, and where it is fixed. The rule for this section: fix it in this plan unless the fix would break existing functionality or make the app harder to use. All of them are fixed within the plan.

- **Secrets stored in plaintext on mobile → FIXED (step 6b).** Mobile secrets were kept plaintext in WebView localStorage; desktop uses the OS keychain. Step 6b moves every mobile secret (UI-added or LAN-received) to the device keychain (iOS Keychain Services, Android Keystore-backed secure storage). The store's method signatures are unchanged and access is transparent (no per-access prompt), so nothing breaks and the app is no harder to use.
- **No user consent/warning for the plaintext downgrade → RESOLVED by 6b, not by a warning.** With secrets in the keychain there is no downgrade from desktop to disclose, so the earlier in-app-warning decision point is gone. The better fix (remove the exposure) replaced the weaker one (warn about it).
- **Secrets leaking into logs → FIXED (steps 6b, 14b).** The worker vault reads secret values from the keychain natively via step 6b's `secureStoreGet` host function, so raw secret values never enter task payloads or `app.log`. A `[redacted]` allowlist at the serialisation boundary (built in 14b, reused by 14c) covers derived request material that is computed in the worker (the SigV4 signing key and the `Authorization` header), with a test asserting no secret material appears in `app.log`.
- **S3 TLS silently downgrading to no certificate validation → FIXED (substep 14c).** The validated-vs-trust-all connect mode is a required explicit argument with no default; a bad-certificate connection must fail, asserted at the unit level and in `33-s3-database`. The pre-existing trust-all mode stays only for LAN share, which pins the certificate itself in JS and fails closed; substep 14c does not weaken it.
- **Plaintext temp files left after asset export → FIXED (substep 12a).** The decrypted temp copy is deleted on all three sheet exits (shared, cancelled, error) plus a start-up sweep for a kill mid-sheet.
- **A real private key committed as a test fixture → ADDRESSED (substep 14a).** Named unmistakably test-only, documented in a fixture README, and checked against any secret scanner / pre-commit hook with an allowlist entry if one exists.

## Notes

- **Ordering is load-bearing.** Part 1 comes first because every later step's gate is "all smoke tests pass" and that gate is currently vacuous: `run.sh:52` invokes `bash "$test_path"` in a fresh non-`-e` shell, no `test.sh` sets `-e`, `check_no_errors` signals failure by `return 1`, and every test ends with `log_success` (an `echo`, exit 0), so a test prints `[FAIL] Errors found in app.log`, then prints `[PASS]`, and exits 0. Expect step 1 to surface tests that have been failing silently; fixing them is inside step 1.
- **Substep 14c (S3) gates substep 14e (sync) for real value.** `sync-database.worker.ts:34` reads `config.origin` and calls `openStorage`; on mobile an `fs:` origin is another directory on the same device. Sync works without S3 but syncs nothing useful.
- **Substep 14a's OAEP padding is the single highest-risk detail in this plan, and the native RSA split is how it is managed.** `encrypt-buffer.ts:24` calls `publicEncrypt(publicKey, key)` with no explicit padding, which is Node's `RSA_PKCS1_OAEP_PADDING` with a **SHA-1** hash; `:107`'s matching `privateDecrypt` takes the same default. Get it wrong and every existing encrypted database silently becomes unreadable, and the format is on-disk with a version header, so it cannot be migrated away from. Using each platform's crypto library for RSA rather than hand-rolling OAEP in JS removes the opportunity to get it wrong, and it follows the precedent already set by `cryptoGenerateRsaKeyPair`/`cryptoSignSha256`. Still test against desktop-generated fixtures, never against the implementation itself: substep 14a checks them in and forbids regenerating them from mobile, because a fixture regenerated from the code under test asserts nothing.
- **Substep 14c must not weaken the pinned TLS path.** `TlsHost.java:147` `buildTrustAllClientContext()` installs a no-op `X509TrustManager` and iOS matches (`TlsHost.swift:177`). This is deliberate and correct: LAN share pins the certificate itself in JS (`lan-share-sender.ts:139-152`, `lan-share-receiver.ts:64`) and fails closed. Add a **second** validated connect mode for S3; do not make the existing one validate.
- **Step 11 takes the task path, not a new native plugin method.** `fsAccess` already exists as a host function and already routes through `PathSandbox`; `addTask` already carries WebView-to-worker calls. One TypeScript handler beats a plugin method in both `JsEnginePlugin.java` and `JsEnginePlugin.swift` plus native tests on two platforms. The check queues behind a running task, which is acceptable for a tap-time check. If that latency ever bites, a plugin method is the escalation.
- **Substep 12a takes the sandbox, not a multi-root rewrite. This is a design decision, record it.** A user-chosen folder is an absolute security-scoped `file://` URL (iOS) or an opaque `content://` tree URI (Android, not a filesystem path at all: no `File`, no POSIX ops, only `DocumentFile`/`ContentResolver`). `PathSandbox.resolveWithin` rejects absolute paths (`PathSandbox.swift:60`, `PathSandbox.java:38`) and every path-taking host function goes through it. Sandbox-relative paths are the mobile storage layer's universal currency all the way up: `node-path.ts:88` deliberately does not prepend a cwd, so `storage-factory.ts:59` yields a relative string on mobile. Supporting real folders means a multi-root sandbox (root-scoped `{rootId, relativePath}` paths rippling through both `PathSandbox`es, every host function, the `fs` shims, `node-path`, `storage-factory`, and every stored database path) **plus** a `content://`-backed `IStorage` on Android, because `DocumentFile` is not `File`. The existing photo picker already chose the other design: it copies bytes in and returns a sandbox-relative path (`JsEnginePlugin.swift:166`, `JsEnginePlugin.java:291`). Substep 12a follows that. If real folder semantics are wanted later, that is its own plan and it is a storage-layer change, not a picker feature.
- **`get-database-summary` needs an entry point, not just a handler.** Step 19 registers the handler and adds a sidebar link. The route's only existing real entry point is a native desktop menu item (`apps/desktop/src/main.ts:1463`) delivered through `platform.onNavigate`, and mobile has no menu, so step 22 deletes `onNavigate` on mobile rather than inventing a trigger for it. `nav-pages.ts:56-60` supplies only a temporary breadcrumb, and neither the navbar (`navbar.tsx:138`) nor the sidebar (`left-sidebar.tsx:90`) links to it today.
- **Step 31 matches the quantum depth but does not chase byte-identical output.** The divergence is real and it is not cosmetic: thumbnails and display assets are hashed (`upload-asset.worker.ts:218,247`) and hashes drive sync comparison. But iOS builds ImageMagick from source while Android uses prebuilt libraries, so byte-equality needs matching libjpeg/libpng versions too, which the depth fix does not deliver. Asserting it would write a gate the step cannot pass for reasons the step cannot fix. Pin the encoders on both platforms first if byte-equality is wanted; that is a separate piece of work.
- **Bundle id defaulted, not decided.** Step 35 defaults to `com.codecapers.photosphere` to match desktop's electron-builder appId, on the reasoning that desktop shipped first and the mobile value labels itself a placeholder. The alternative (`au.com.codecapers.photosphere`, changing desktop to match) is the more conventional Australian reverse-DNS form. This is a product identity decision and it is permanent after the first Play upload. Override the default if the `au.` form is wanted.
- **Artwork is out of scope and is not a mobile defect.** Both mobile apps ship the stock Capacitor logo as icon and splash (verified by rendering them; all dated Aug 2024, the scaffold date). But no Photosphere artwork exists anywhere in the repo, and `apps/desktop/package.json` has no electron-builder icon config either, so desktop runs the default Electron icon too. The product has never had branding on any platform. This is owed before any store build and needs a designed asset, not a code change. It is also why step 36 does not build version-derivation tooling: there is no store build to derive for.
- **`useIsMobile()` is not a capability check and must not be used as one.** `packages/user-interface/src/lib/use-is-mobile.ts:16-33` is a viewport media query whose own docstring says "This reflects form factor only; it does not indicate the native platform", and none of its ~100 usages fence a capability, they all adjust padding and font sizes. The platform context has exactly one capability flag, `supportsDragAndDropImport` (`platform-context.tsx:409`), correctly checked at `import-page.tsx:285`. This plan implements the gaps rather than fencing them, so no new flags are needed; if any step turns out to be deferred, it gets a flag on `IPlatformContext` set in all four providers (Electron, web, mobile, stories mock) and checked by the caller, following that precedent. Note `plan-mobile-asset-import.md:98` records that `supportsDragAndDropImport` is true on web, not false; heed that if adding flags.
- **The estimates in an earlier draft of this analysis were wrong and are not repeated here.** They were human-developer sizings (3-4 weeks for S3, weeks for pickers) applied to AI-executed work in a repo whose history refutes them: the entire mobile platform (Capacitor shells on two platforms, embedded JS engines (QuickJS + JavaScriptCore), a 30-function host bridge, native TCP/UDP/TLS, ImageMagick and ffmpeg on both platforms, LAN share, the asset server, import, and the smoke suite) landed between 2026-06-24 and 2026-07-17, with `a5a02308` alone contributing 27,697 insertions across 95 files in a single commit.
- **The whole-file memory model is deliberately not fixed.** `node-fs.ts:16-23` reads entire files as base64, `node-http.ts:498-517` buffers whole responses, the bridge adds roughly 1.33x for base64, and `node-stream.ts:153`/`node-net.ts:186`/`node-http.ts:479` all unconditionally `return true` so there is no backpressure anywhere. This is a real OOM risk for large videos on low-end devices, but it is a performance architecture question deserving its own plan. It is why substep 14c defers multipart upload (chunking the upload without fixing the read path buys nothing) and why step 28 leaves the no-op stream constructors alone (they are inheritance bases, and the real stream problem is not that they exist).
- **Neither platform builds from a fresh clone.** Android `jniLibs/*.so` and `cpp/imagemagick/` are git-ignored and need `scripts/fetch-mobile-media-tools.sh`; iOS `vendor/im` is git-ignored and needs the macOS-only `ios/build-imagemagick.sh`, while `OTHER_LDFLAGS` hard-codes `-lMagickWand-7.Q8HDRI` so a fresh clone fails at link (step 31 changes that flag to Q16). That is an onboarding cliff, but it fails loudly and is a deliberate vendoring choice.
- **Two steps are unavoidably one large, high-blast-radius change each; track them as such.** Step 1 (flip the mobile harness helpers to fatal, plus all the silently-failing-test fallout, in one green suite) and step 35 (a 37-file Java package move plus ~10 cross-platform config edits, including the smoke-harness constants at `common.sh:31-32`) each cannot be split without leaving the suite red mid-way, and the plan justifies why at each step. The cost is that both are hard to review as a single worktree diff. Mitigate at review time rather than by splitting: for step 1, review the helper flip separately in your head from the per-test fixes (the diff groups them: `lib/common.sh` versus each `tests/<n>/test.sh`); for step 35, review the mechanical package move (the working diff with rename detection shows it as renames plus `package`/`import` line rewrites) separately from the config edits, and confirm `common.sh:31-32`, the pbxproj test-target ids (`:500,700`) and `custom_url_scheme` are all present, since those are the three the earlier draft missed. Neither may be made green by weakening a test or reducing parallelism. This note exists so the review risk is tracked, not discovered.
