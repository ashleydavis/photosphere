# Review How Configuration Is Stored On Mobile

## Overview

On desktop, application configuration lives in two TOML files under `~/.config/photosphere/`: `desktop.toml` (handled by `packages/node-api/src/lib/desktop-config.ts`, typed as `IDesktopConfig`) and `databases.toml` (handled by `packages/node-api/src/lib/databases-config.ts`). The Electron main process owns both, and the renderer reaches them through the `get-config` / `set-config` IPC handlers (`apps/desktop/src/main.ts:711` and `:728`), which the shared `createConfig` helper (`packages/user-interface/src/context/config-context.tsx`) wraps into the `IConfig` interface the UI consumes. On mobile the equivalent state lives in WebView `localStorage`: `packages/mobile-frontend/src/lib/mobile-config-store.ts` holds every read and write, and `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx:75` binds `window.localStorage` as the backing store. Secrets have already been moved out of `localStorage` and into the device keychain via the `SecureStore` Capacitor plugin (`packages/mobile-frontend/src/lib/mobile-secure-store.ts`, `packages/mobile-frontend/src/lib/secure-store-plugin.ts`, with native Swift and Java implementations in `apps/ios-frontend` and `apps/android-frontend`), so a durable native key/value pattern already exists in the codebase for non-secret config to follow if the review concludes it should.

This plan produces a written, evidence-backed assessment of whether the mobile approach is appropriate, and fixes the defects the assessment confirms. The main open questions are durability (WebView storage is website data and can be evicted or cleared by the OS or by the user clearing app storage, which would silently lose every configured database entry), failure handling (writes can throw and reads silently discard malformed data), unbounded growth of the stored lists, parity with the fields `IDesktopConfig` defines, and the total absence of any schema version or migration mechanism. The review is the deliverable; the fixes in the later steps are the subset of findings that are clear-cut enough to correct without a further design decision. Anything requiring native work on both platforms is recorded as a recommendation and turned into a follow-up plan rather than implemented here.

## Steps

Steps 1 to 9 are the audit. They write findings into a single new document, `docs/mobile-config-storage-review.md`, which the agent creates in step 1 and appends a section to in each subsequent audit step. No production code changes in steps 1 to 9. Steps 10 to 14 implement the confirmed fixes; each must compile cleanly and leave all unit tests passing before it is considered complete.

1. **Create the review document and record the current architecture.** Create `docs/mobile-config-storage-review.md` with a title, a one-paragraph statement of scope, and a section "Current architecture". In that section record, with `file:line` references: the desktop config surface (`IDesktopConfig` and every exported function in `packages/node-api/src/lib/desktop-config.ts`, plus the `databases.toml` surface in `packages/node-api/src/lib/databases-config.ts`); the IPC bridge (`get-config` / `set-config` in `apps/desktop/src/main.ts`); the shared `IConfig` interface and `createConfig` in `packages/user-interface/src/context/config-context.tsx`; and the mobile surface (every exported symbol in `packages/mobile-frontend/src/lib/mobile-config-store.ts`, the `persistentStore` binding in `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx`, and the `createConfig` wiring at the bottom of that same file). Include the full list of `localStorage` keys the mobile store uses: `DATABASES_KEY`, `RECENT_DATABASES_KEY`, `LEGACY_PLAINTEXT_SECRETS_KEY`, `NEWS_KEY`, `SHOWN_NEWS_KEY`, and the `CONFIG_KEY_PREFIX` namespace.

2. **Audit field parity between `IDesktopConfig` and mobile.** Add a section "Field parity" to the review document containing a table with one row per field of `IDesktopConfig` (`lastFolder`, `theme`, `recentSearches`, `lastDownloadFolder`, `lastDatabase`, `showFpsIndicator`, `developerMode`, `devToolsOpen`, `syncEnabled`, `syncOnlyOnWifi`). For each field record: whether the shared UI reads or writes it through `IConfig` (grep `packages/user-interface/src` for the key literal), whether it is meaningful on mobile, and where it ends up on mobile (the `photosphere.config.<key>` namespace, somewhere else, or nowhere). Then grep `packages/user-interface/src`, `packages/mobile-frontend/src` and `apps/desktop-frontend/src` for every distinct key literal passed to `config.get`, `config.set`, `config.add`, `config.remove` and `config.clear`, and list any key used by the shared UI that `IDesktopConfig` does not declare. Record each mismatch as a finding, classified `must fix`, `should fix`, or `acceptable`, with a one-line justification.

3. **Audit durability of WebView `localStorage` on both platforms.** Add a section "Durability" to the review document. Determine and record, with references to the native configuration in the repository: whether the Android WebView's `localStorage` for this app survives the user clearing app storage or cache from Android settings; whether iOS `WKWebView` website data for this app can be evicted by the system under storage pressure or reset on app update or reinstall; and whether either store is included in device backup (iCloud / iTunes on iOS, Android auto-backup). Check `apps/android-frontend/android/app/src/main/AndroidManifest.xml` for an `android:allowBackup` setting and any backup rules XML, and check `apps/ios-frontend/ios/App/App/Info.plist` and the Capacitor configuration for anything relevant. State plainly what is lost if the store is cleared: the entire configured-databases list, the recents list, and every generic config value, while the secrets survive in the keychain, leaving a device with orphaned secrets and no databases. Rate this finding.

4. **Audit read and write failure handling.** Add a section "Failure handling" to the review document. Record that `readArray` in `packages/mobile-frontend/src/lib/mobile-config-store.ts` returns `[]` when `JSON.parse` throws, so a single corrupted value silently discards the user's whole configured-databases list with no log line and no user-visible signal, and that `getConfigValue` does the same for a single value. Record that `writeArray` and `setConfigValue` call `store.setItem` with no handling of the `QuotaExceededError` the Web Storage API throws when the quota is exceeded or when the WebView is in a mode that rejects writes, and trace what happens to that exception: follow the call chain up through the `useCallback` wrappers in `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx` (for example `addDatabase`, `updateDatabase`, `removeDatabaseEntry`) and into their callers in the shared UI (`packages/user-interface/src/components/edit-database-modal.tsx`, `packages/user-interface/src/pages/secrets/secrets-page.tsx`) and record whether any caller catches it or whether it becomes an unhandled promise rejection that leaves a modal open with the edit lost. Rate each finding.

5. **Audit unbounded growth of the stored lists.** Add a section "Growth" to the review document. Record for each stored list whether it has an upper bound and where that bound is enforced: `addRecentDatabase` and `seedRecentDatabases` (`RECENT_DATABASES_KEY`), `addShownNewsId` (`SHOWN_NEWS_KEY`), `addDatabase` (`DATABASES_KEY`), and the `IConfig.add` path in `packages/user-interface/src/context/config-context.tsx` which caps only when the caller passes `maxItems`. Compare against desktop, where `MAX_RECENT_SEARCHES` in `packages/node-api/src/lib/desktop-config.ts` caps recent searches and `packages/node-api/src/lib/databases-config.ts` caps the recents list, and record any list that grows without limit on mobile but is capped on desktop. Rate each finding.

6. **Audit write atomicity and concurrent writers.** Add a section "Concurrency" to the review document. Record that desktop serialises its read-modify-write through `updateDesktopConfig`, which uses `updateToml` so two overlapping updates cannot lose each other's changes, and that every mobile mutator (`addDatabase`, `updateDatabase`, `setDatabaseOrigin`, `removeDatabase`, `addRecentDatabase`, `removeRecentDatabase`, `addShownNewsId`) performs an unserialised read-modify-write over the whole list. Then establish whether that can actually interleave on mobile: grep `packages/mobile-worker/src` and the `host.*` bridge surface for any read or write of the config `localStorage` keys or the `photosphere.config.` prefix, and check whether `packages/mobile-frontend/src/lib/mobile-share-receive.ts` and `packages/mobile-frontend/src/lib/mobile-sync-scheduler.ts` write config from a context that can run concurrently with the UI. Record whether the WebView's single-threaded synchronous `localStorage` access makes the lack of serialisation harmless, or whether a genuine second writer exists. Rate the finding.

7. **Audit schema versioning and migration.** Add a section "Versioning and migration" to the review document. Record that the mobile store has no version key and no migration mechanism, and that the one shape change made so far (moving secrets from the plaintext `photosphere.secrets` blob into the keychain) was handled by a hand-rolled one-off purge at `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx:90` plus the retained `LEGACY_PLAINTEXT_SECRETS_KEY` constant. Contrast with desktop's explicit JSON-to-TOML migration inside `loadDesktopConfig`. State what a second shape change would cost under the current design, and recommend either a stored schema version key or an explicit statement in the document that migrations will keep being one-off purges. Rate the finding.

8. **Audit the separation between config and secrets.** Add a section "Config versus secrets" to the review document. Confirm by reading `packages/mobile-frontend/src/lib/mobile-secure-store.ts` and grepping `packages/mobile-frontend/src` that no secret value or secret type is written to `localStorage` on any current path, that `resetConfig` clears only `localStorage` keys and the platform provider separately clears the keychain, and that `IDatabaseEntry` fields persisted in `DATABASES_KEY` (in particular `s3Key`, `encryptionKey`, `geocodingKey`) hold secret *names* and never secret values. Record any place where a secret value could reach `localStorage`. Rate the finding.

9. **Write the verdict and the recommendation.** Add a final section "Verdict" to `docs/mobile-config-storage-review.md`: one paragraph stating whether the current mobile approach is appropriate as it stands, followed by a table of every finding from steps 2 to 8 with its rating and its disposition (`fixed in this plan`, `follow-up plan`, or `accepted`). Every finding rated `must fix` that is not addressed by steps 10 to 14 must be assigned to a follow-up plan. In particular, if the durability finding from step 3 is rated `must fix`, write a separate follow-up plan file `docs/plans/new/plan-mobile-durable-config-store.md` describing moving the non-secret config off WebView `localStorage` onto a native key/value store following the existing `SecureStore` plugin pattern (a new Capacitor plugin interface in `packages/mobile-frontend/src/lib`, native implementations under `apps/ios-frontend/ios/App/App/JsEngine` and `apps/android-frontend/android/app/src/main/java/au/com/codecapers/photosphere/jsengine`, and an async `IKeyValueStore` variant). Do not implement that move in this plan.

10. **Make a corrupted stored value loud instead of silent.** Change `readArray` and `getConfigValue` in `packages/mobile-frontend/src/lib/mobile-config-store.ts` so a value that fails to parse is reported rather than silently replaced by an empty result. Add a required `onCorrupt` callback parameter to both functions carrying the key and the raw string, threaded through from a single new parameter on the exported functions that reach them, or introduce a small store wrapper that carries the callback so the exported signatures do not all change; choose whichever keeps the diff smaller and state the choice in a comment. The mobile platform provider supplies a callback that writes a `log.error` line naming the key. The parsed-successfully path is unchanged. Compile must be clean and all unit tests must pass.

11. **Cap the lists that grow without limit.** For each list step 5 recorded as unbounded on mobile but capped on desktop, add the matching cap in `packages/mobile-frontend/src/lib/mobile-config-store.ts` using an exported named constant per list (following the `MAX_RECENT_SEARCHES` naming in `packages/node-api/src/lib/desktop-config.ts`) and matching desktop's cap value where desktop has one. At minimum this covers `addRecentDatabase` trimming `RECENT_DATABASES_KEY` and `addShownNewsId` bounding `SHOWN_NEWS_KEY`. Do not cap `DATABASES_KEY`: that list is user-created and must not silently drop entries. Compile must be clean and all unit tests must pass.

12. **Surface a failed config write.** Wrap the `store.setItem` call in `writeArray` and in `setConfigValue` so a thrown storage error is re-thrown as an `Error` naming the key and stating that the setting could not be saved, rather than propagating the raw `QuotaExceededError`. Then fix the caller chain step 4 identified as producing an unhandled rejection: in `packages/user-interface/src/components/edit-database-modal.tsx`, `handleSave` must not leave the modal open with no feedback when the platform call rejects. Follow the pattern the file already uses for name collisions (`setNameError` with an inline message) rather than adding a new error-display mechanism. Compile must be clean and all unit tests must pass.

13. **Close the field-parity gaps rated `must fix`.** For each gap from step 2 rated `must fix`, make the smallest change that closes it: a key the shared UI reads that mobile never persists gets wired through the existing `photosphere.config.` namespace in `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx`; a key the shared UI uses that `IDesktopConfig` does not declare gets declared in `packages/node-api/src/lib/desktop-config.ts` with its TOML snake_case mapping added to both `tomlToDesktopConfig` and `desktopConfigToToml`. If step 2 found no `must fix` gaps, record that in the review document and skip this step. Compile must be clean and all unit tests must pass.

14. **Update the mobile documentation.** Add a short section to `docs/mobile-unfinished-work.md` (or the closest existing mobile document) linking to `docs/mobile-config-storage-review.md` and listing the findings left open, so the durability decision is visible from the mobile documentation rather than only inside the review. Do not restate the review; link to it.

## Unit Tests

All mobile config-store tests go in `packages/mobile-frontend/src/test/mobile-config-store.test.ts`, alongside the existing tests, using the in-memory `IKeyValueStore` fake already defined there. Steps 1 to 9 add no code and therefore no tests.

- `readArray` corruption reporting (step 10): a stored value that is not valid JSON invokes the `onCorrupt` callback with the key and the raw string, and still returns an empty array. Cover through a public entry point such as `getDatabases`.
- `readArray` valid path unchanged (step 10): a well-formed stored array parses and does not invoke `onCorrupt`.
- `getConfigValue` corruption reporting (step 10): a malformed generic config value invokes `onCorrupt` and returns `undefined`; an absent key returns `undefined` without invoking it.
- `addRecentDatabase` cap (step 11): adding more than the cap keeps the most recent entries, drops the oldest, and preserves most-recent-first ordering; the existing de-duplication by path still holds at the cap boundary.
- `addShownNewsId` cap (step 11): adding more than the cap bounds the stored list, and an id already present is still a no-op.
- `writeArray` write failure (step 12): a store whose `setItem` throws causes the mutator to throw an error whose message names the key; assert on the message, and assert the caller sees a thrown error rather than a silent success.
- `setConfigValue` write failure (step 12): same assertion through `setConfigValue`.
- Any new pure function introduced by step 13 gets a unit test. Changes confined to `platform-provider-mobile.tsx` and `edit-database-modal.tsx` are React components and providers and are not unit tested; they are covered by the smoke test below.
- `desktop-config.ts` round-trip (step 13, only if a field is added there): `tomlToDesktopConfig` and `desktopConfigToToml` round-trip the new field, and an absent field stays absent. Add to the existing node-api test file covering `desktop-config.ts`, or create `packages/node-api/src/test/desktop-config.test.ts` if none exists.

## Notes

- The review is the primary deliverable. Steps 10 to 14 deliberately cover only findings that need no design decision. Moving config off WebView `localStorage` onto a native store is the one change likely to be rated `must fix` that this plan does not implement, because it needs Swift and Java work on both platforms and should be planned separately.
- The `SecureStore` plugin is the precedent to follow if that move happens: `packages/mobile-frontend/src/lib/secure-store-plugin.ts` for the plugin interface and the adapter shape, `packages/mobile-frontend/src/lib/mobile-secure-store.ts` for the pure store logic over an injected interface, with the native halves under each app. The same split keeps the store unit-testable against an in-memory fake.
- Note that moving to a native store makes every read async, whereas `IKeyValueStore` is synchronous today and `mobile-config-store.ts` is written against that. The follow-up plan must account for the ripple through `platform-provider-mobile.tsx`, which already returns promises from its platform methods, so the seam is narrower than it first looks.
- The iOS environment is fixed at macOS 12.7.6 and Xcode 14.2 and the project is pinned to Capacitor 5. Any recommendation that needs a newer Capacitor or a third-party plugin is out of bounds; the existing hand-written plugin pattern is the only route.
- Do not add exception handling beyond what steps 10 and 12 specify. Those two are explicitly requested by this plan; speculative guards elsewhere are against the project's style.
- Step 6 may well conclude the missing write serialisation is harmless because the WebView is single-threaded and `localStorage` access is synchronous. If so, record that as `acceptable` with the reasoning rather than adding locking nobody needs.
- **Widen the comparison to all three platforms and normalize if possible.** This plan as written compares mobile against desktop only. It should also cover the CLI, and the goal is not just to document the differences but to make the three work the same way wherever there is no good reason for them to differ: one file format, one set of operations, one place the format is defined. `61ac4cee` already did this for the databases list, moving mobile onto the same `databases.toml` format as desktop and pulling the entry type and TOML conversions into a shared `packages/node-api/src/lib/databases-config-format.ts` imported by both, precisely so the two could not drift apart again. That is the pattern to extend to the rest of the config surface and to the CLI.
- **Two premises in this plan are out of date, both because of `61ac4cee`.** Mobile config no longer lives in WebView `localStorage`: the databases list and recents are now `databases.toml` at the root of the storage sandbox, read and written through embedded-worker tasks. That also settles step 6 the opposite way to the guess above: with the reads and writes now async round-trips rather than synchronous `localStorage` access, the unserialised read-modify-write became a real lost-update bug (two back-to-back seeds each read the same config and the second write dropped the first's list), and it has been fixed with a promise-chain lock in `mobile-config-store.ts`. Re-derive the current state from the code rather than trusting the file references in the steps above.
