# Ziggy: a Zig and system web view application shell for Photosphere

## Overview

Ziggy is a Capacitor-style application shell built only for Photosphere. Its code is kept apart from Photosphere's so it is always clear which is which, and a small permanent example app, the Ziggy example, sits beside Photosphere to show how an app is built on it. The example proves Ziggy's design before the rest of the work starts, and keeps proving that Ziggy stays separate from Photosphere. Ziggy replaces the Electron desktop app and the Capacitor mobile apps with the Photosphere App, which builds, bundles and delivers Photosphere to Windows, MacOS, Linux, Android and iOS. Where Ziggy, the example and Photosphere live on disk is the human's decision, made at step 2. The user interface stays TypeScript, CSS and HTML (the existing `packages/user-interface`, with the minimum set of changes needed) running in the system web view of each platform. Everything else (backend, background tasks, the asset HTTP server, shared code) is Zig, and every platform has a native shell that does nothing except host the system web view, load the Zig library, pass messages between the two, and provide the few things that must be native code. The existing `psi` port (`apps/cli-zig` and `packages-zig/*`) is the base: the rest of the non-UI TypeScript is ported to Zig as faithfully as possible, so each Zig file can be read beside the TypeScript it came from. Ziggy lives beside `apps/desktop` and the Capacitor apps until it reaches feature parity, and then the human removes those, and the other apps and packages the Zig port supersedes, using the reminder in step 35. The UI stories keep working in the new app on every platform. The work starts with Phase A, Ziggy and the Ziggy example, the smallest complete app that shows TypeScript, HTML and Zig working together on every platform, and stops there so the human can try it on real platforms before the remaining phases begin.

Ground rules that apply to every step:

- Languages: TypeScript, shell and Zig. The native shells use these languages, approved by the human: Java for Android, Swift for iOS and MacOS, Zig for Windows and Linux, and only if Phase A shows Zig cannot host the web view on Windows then C++, and on Linux then C. No other language is used for any shell. Native code stays as small as the platform allows.
- Build systems: `build.zig` builds everything it can, including the core library for every target, the Windows and Linux shells (each is its own Zig package under `apps/photosphere/shells/` with its own `build.zig`), any C or C++ fallback shell (compiled by Zig), and the Android shared library. A second build system is used only where the platform forces it: Gradle to package the Android APK, `xcodebuild` for the Swift iOS and MacOS apps, and Vite for the UI. No Makefiles, no CMake, no other build systems, and the shell scripts in `apps/photosphere/scripts/` only call these tools in order.
- Compatibility with the existing apps: everything in Ziggy is done in a way that is recognisably compatible with the standards of the existing Electron and Capacitor projects, so someone who knows those can read Ziggy without relearning anything. That means the same channel names and message payloads, the same task types, task messages (`job-progress` included), task context (`sendMessage`, `isCancelled`, `maxConcurrentChildTasks`, child tasks queued and awaited), priorities and cancellation by source, the same `IPlatformContext` and `IQueueBackend` interfaces, the same file, folder and script naming and layout (`<n>-<name>/test.sh` scenarios, `sync`, `open`, `run` scripts, `*.worker` handler files), and the same code style and documentation habits. Where Ziggy must differ, the difference is limited to what Zig or the platform forces, and it is recorded where the code is.
- What belongs in Ziggy: a feature that Electron or Capacitor provides to an app can be a feature of Ziggy, because Ziggy replaces them. A feature that neither provides is added to Ziggy only when there is no other choice, and the reason is recorded where it is added. Anything else an app needs stays in the app. The bridge's `getPathForFile` is Electron's `webUtils.getPathForFile`, so it qualifies.
- No third-party SDK or library is reimplemented, shimmed or faked. If a real library does not work somewhere (a web view library, the AWS SDK, ffmpeg), STOP and ask.
- No globals: no module-level mutable variable, no `threadlocal`. The native shells hold an opaque handle returned by the Zig library and pass it back on every call.
- Ziggy, the Ziggy example and Photosphere are kept apart on disk, so it is always clear which code is the framework and which is an app.
  - Ziggy is the C interface, the dispatcher, the task runner, the origin check, the native host callback plumbing and the test hooks (Zig), the `window.ziggy` script and its types (TypeScript), and the framework code of each platform's shell (the Zig, Swift and Java that hosts the web view and talks to the core).
  - The Ziggy example is a complete small app built on Ziggy, kept permanently as the reference for building an app on it: its handlers, its page, its native projects and its smoke tests.
  - Photosphere is built the same way as the example. Its code holds only what is Photosphere's (its channels and task handlers, the asset server, the photo library, pickers, menu content, permission strings and background work), on top of Ziggy.
  - Where all of this lives on disk is not decided. Step 2 proposes a layout (packages, folders, workspace names and command names) and waits for the human to approve it. Until then no folder, package or command name for Ziggy, the example or Photosphere is final.
  - The example exists for two reasons that last as long as the repository does. First, it proves Ziggy's design on every platform before the rest of the plan starts. Second, it keeps Ziggy clean: Ziggy must work for an app that is not Photosphere, so the example is a standing test that Ziggy code has not become tangled with Photosphere code. The example is simple, has simple smoke tests, and is never allowed to use anything of Photosphere's. Any change to Ziggy is made with the example building and its smoke tests passing. If Photosphere needs something from Ziggy that the example cannot also use, or needs Ziggy to know about Photosphere, the design is wrong and the work goes back to the human instead of being worked around.
  - Dependencies point one way: an app uses Ziggy, and nothing in Ziggy names an app or imports an app's package. An app's code reaches Ziggy only through its interfaces: the C interface, `window.ziggy`, the dispatcher and task handler registration, and the host callbacks. Photosphere never imports anything from the example, nor the example from Photosphere.
- No default or optional parameter values. No `any`, no `unknown`, no anonymous object types, no `ReturnType<typeof ...>` in TypeScript.
- Faithful ports: each ported Zig file sits beside the Zig package that already mirrors its TypeScript package (`packages-zig/<name>-zig`), keeps the TypeScript file name and function names (converted to Zig naming), keeps the same order and the same control flow. Where Zig forces a difference, say so in a comment above the function.
- The existing UI TypeScript and HTML (`packages/user-interface` and the Electron and Capacitor frontends) is used almost exactly as it is. The only changes permitted are the minimum needed to start the current UI on Ziggy: the platform layer in `apps/photosphere-frontend` (queue backend, platform provider, entry point) and, where the existing code truly cannot run unchanged, a recorded one-line-scale edit. No redesign, no refactor, no restyling, no behaviour changes, no cleanup, no renaming. Every edit to a file outside `apps/photosphere` and `apps/photosphere-frontend` is listed in the "UI changes" section of `packages/ziggy/docs/architecture.md` (a section that exists only if such an edit is made) with the reason it could not be avoided, and the final audit reviews every one of them.
- The UI reaches Zig only through the two routes the existing apps already use. Request and event messages are JSON, carrying the same channel names and payloads as the Electron IPC channels and the mobile `JsEngine` plugin methods. Images, video and asset writes use the same three loopback HTTP routes as the existing asset server (`GET /asset`, `POST /asset`, `POST /apply-database-ops`). No new routes and no new HTTP usage are added. Platform-specific code stays out of `packages/user-interface`.
- The page talks to native code the way Electron's preload does: each shell injects a small script before the page loads that exposes only `window.ziggy` (`invoke`, `send`, `onMessage`, `removeAllListeners` and, on desktop, `getPathForFile`). The web view's own native handle (`window.chrome.webview`, `window.webkit.messageHandlers`, the Android interface object) is never used directly by UI code and nothing wider than those methods is exposed. The script is embedded in the core library and every shell takes it from there, so neither an app nor a shell project supplies or carries a file for it.
- Each platform's app is one binary that holds everything needed to run it. No loose file sits beside it: no folder of page files, no script, no DLL. The page and the injected script are embedded in the executable on Linux and Windows, and in the core library inside the app on MacOS, iOS and Android, whose bundle or APK is the platform's own container for that binary and holds nothing else of the app's. Nothing is written out at run time to get around this, and nothing is loaded from a file the app puts down. A platform that cannot meet this goes back to the human.
- Every shell accepts messages only from the app's own bundled page. It blocks navigation to anything else and opens external links in the system browser, as `apps/desktop/src/main.ts` does with `setWindowOpenHandler` and `will-navigate`. The decision of whether an address is the app's own is a Zig function in the core, called by the shell, so it is written and tested once.
- Test-only scaffolding in the app (a test mode, a test driver connection, test commands) needs the human's approval first. The existing apps ship a test mode switched on by `PHOTOSPHERE_TEST_MODE` that connects the shared `test-driver.ts` to a host-side control bridge. The exact hooks Ziggy proposes to ship are listed in the documentation drafted in step 1 and approved with it; nothing outside that list is added. Hooks are compiled in only by the core's `test_hooks` build option, which is off by default and never set for a release artifact, so a released app cannot be driven for testing. Set test state up from outside the app wherever possible (config files and data placed on disk).
- Every function new or changed gets a unit test, every test is run and watched failing before it is accepted, and every test must survive running beside copies of itself and beside every other suite (free ports, per-test temp directories, pids recorded and killed through `kill_process_tree`). Nothing in a shell script embeds another language, and no tests are written for shell scripts. Every new script has a markdown file beside it.
- Never commit, stage or push. Never edit `.githooks/pre-commit` or `scripts/install-hooks.sh`.

### What building the example taught

- One binary per platform, no loose files. The page and the script that creates `window.ziggy` are embedded: in the executable on Linux and Windows, and in the core library on MacOS, iOS and Android, where the shell asks the core for each file (`ziggy_ui_file`, `ziggy_inject_script`). An app supplies nothing for the script. The page is served from an address of its own, never `file://`: `ziggy-app://app/` on Linux, MacOS and iOS and `https://ziggy-app.invalid/` on Windows and Android. The apps' build files embed whatever the page build produces, through `embedPage`, which fails the build when the page was not built first.
- Photosphere's page is far larger than the example's (fonts, a multi-megabyte script and source maps). The release page build must not produce source maps, or `embedPage` must skip `.map` files, and the content type table in `ui-files.zig` needs the font types the page uses (it has `.woff` and `.woff2` but not `.ttf` or `.otf`).
- Windows needs Microsoft's C++ toolchain to build. A single executable with no `WebView2Loader.dll` means linking the SDK's static loader, which is built with Microsoft's compiler and needs its runtime, so Zig must target `x86_64-windows-msvc`. That needs Visual Studio's C++ tools (and the Windows SDK) on every Windows build machine and on the Windows CI runner. Setup installs the Visual Studio 2022 Build Tools with the C++ workload through winget when they are missing, and the build and package scripts check for the toolchain, the WebView2 SDK with its static loader and WiX before building, and say what to run instead of failing part way with `WindowsSdkNotFound`. Zig cannot link that target from Linux, so Linux only type-checks the Windows shell (a compile-only step against the MinGW headers). Windows arm64 is refused because Zig 0.16's standard library does not compile for `aarch64-windows-msvc`. Three build facts took a Windows machine to find and are now in the example's build files: `translate-c` must read the `-gnu` ABI's headers of the same architecture, because Zig 0.16's C front end cannot parse the Windows SDK's own headers (the two ABIs agree on calling convention and layout on x64, and the executable is still built and linked for `-msvc`); the shell links `advapi32`, which `WebView2LoaderStatic.lib` needs; and the entry point is `mainCRTStartup`, because the MSVC runtime's GUI startup otherwise looks for a `WinMain` the app does not define.
- The Windows installer is an MSI built with WiX Toolset 3.14.1 and a zip, replacing the NSIS installer the first draft used. WiX 3 is licensed MS-RL alone, while WiX 6 and later put their binaries under the Open Source Maintenance Fee agreement and ship only as an admin MSI or a .NET tool. The MSI installs per user into `%LOCALAPPDATA%\Programs\<app name>` with a Start menu shortcut and needs no administrator rights. Setup fetches a pinned WiX zip and checks its sha256, the same way it fetches the WebView2 SDK. The Electron desktop app's `electron-builder` target is NSIS plus zip, so Photosphere's Windows artifact changes kind from an NSIS installer to an MSI, and the build is removed with the old desktop app.
- The Linux deb installs the one executable under `/opt`, a link in `/usr/bin` and a `.desktop` menu entry (whose `StartupWMClass` is the app id the shell sets), so the app appears in the applications menu and search. Without the entry the app could only be started from a terminal. The example has no icon, so the entry shows the generic one: Photosphere needs its icon in the deb, the MSI shortcut, the macOS bundle, the iOS app and the Android app, and the shells must set the window icon.
- Several builds embed `dist` at the same moment (the lanes of `bun run tev`), so `bundle:ui` builds the page in a directory of its own and leaves `dist` untouched when nothing changed. Anything new that reads `dist` must go through it.
- The release-has-no-hooks check must search a release binary for text only the core contains. The page is embedded in the binary now, and the page contains the names of events the core also sends, so searching for those names finds the page and proves nothing. The Phase K check on test hooks in release artifacts needs the same care.
- The example's packaging scripts take their version from the `package.json` of the example, a fixed number. Photosphere's release workflow versions everything from the release tag, so Photosphere's `package:*` scripts take the version as an argument (see steps for packaging below), and no `package.json` version is ever the source of a release version.
- WebKitGTK cannot start its sandbox on some Linux setups (Ubuntu's restriction on user namespaces). The Linux shell checks for it and turns the sandbox off for that run, saying so.
- The example's shells each compose the page address and the `?testMode=1` query themselves. Photosphere's page needs more in its address (see below), so that moves into the core.

### What the platform runs taught

The human ran the example on Windows, MacOS and iOS (simulator and a real iPhone) and fixed what broke. Photosphere's shells, core and scripts are copied from the example, so each of these applies to it too:

- MacOS and iOS, Xcode 14.2 (the pinned version): the projects must not use `XCLocalSwiftPackageReference` for the shared `ZiggyShellApple` package, which only Xcode 15 reads and which fails with "Missing package product". They use the older form, a folder reference to the package plus the product dependency. Xcode's linker does not supply Zig's compiler runtime, so a static library built for Xcode must bundle it (`bundle_compiler_rt`), or linking fails on `___zig_probe_stack`. Photosphere's core library, and every C library it pulls in, links the same way.
- iOS: Zig's MachO stack-trace symbolizer calls `_dyld_get_image_header_containing_address`, which the iOS SDK does not export, so the library root switches Zig's `SelfInfo` off on iOS (a Zig stack trace on iOS prints addresses only). Photosphere's library root needs the same switch or it will not link.
- MacOS undo: the web view groups edits into one undo step until a real mouse click or key press, and the test control connection supplies neither, so `ZiggyMenu` closes the open undo group before each edit menu action and opens a new one (except for undo and redo). The real click path was not exercised by hand.
- Windows quitting: on Windows `shutdown()` on a socket does not wake a pending read in Zig's `std.Io`, and closing the handle completes the read as `CANCELLED`, which `std` treats as unreachable, so quitting hung. Each control connection is now a task on the control server's own threaded `Io` and `stop()` cancels it. The core's single-threaded `Io` ignores cancel requests, hence the separate one. Cancel state is per thread and shared across `Io` instances, so cancellation is blocked while a command runs and allowed only while waiting for the next line. Photosphere's asset server and any other thread that blocks on a socket read will meet the same behaviour, so this is the pattern to follow for each, and every one must be shown to stop when the app quits on Windows.
- Windows developer tools: WebView2 has no call to close the DevTools window. The shell looks for a visible window titled "DevTools" owned by the web view's browser process and sends it `WM_CLOSE`, otherwise it opens one. It checks every time instead of remembering, so the toggle stays right when the user closes the window.
- Windows paste: emulating the clipboard with `execCommand('insertText')` merged with the typing before it, so one undo removed both. Paste now runs Chromium's own paste command, sent as `Input.dispatchKeyEvent` with `commands: ["paste"]` through `CallDevToolsProtocolMethod`.
- Windows smoke tests run under Git Bash. `tasklist /v` over every process takes about eighteen seconds a call, so ask only about `msedgewebview2.exe`. `grep -iF` crashes Git Bash's grep. The scripts need `bun` and `zig` on PATH, which means mise's shims.
- iOS on a device: device builds are signed by the team of the account signed in to Xcode, or by `ZIGGY_IOS_TEAM` when there are several. Xcode 14 cannot install or launch on a device from the command line, so `scripts/ios-device.ts` uses native-run's device library (already in the repo for Capacitor) to install, launch paused under the device's debugserver and forward a port over USB. It runs under Node because Bun's sockets cannot carry the TLS session native-run opens. `run-ios.sh` has lldb detach so the app keeps running. iOS ignores the working directory a debugserver launch asks for, so the app pauses at `ziggy_create` and calls `chdir` into its data container before the core starts. The data container outlives the app, so every scenario uses its own port file name. A device runs one copy at a time, so a scenario claims it under a lock. The scripts use a fixed file descriptor for lldb's input, because the bash 3.2 that ships with MacOS has no `{name}` form. There is one `run` and one `test` command for iOS, which use a device when one is connected, otherwise the simulator, otherwise fail.
- Packaging: every platform's packages go to `out/<platform>` and nothing else goes there. Build files (Xcode's derived data, the synced native library, dmg and ipa staging, the Windows install prefix) stay in the shell's own build folder. `--output-dir` on the packaging scripts sets only where the packages go. CI uploads `out/<platform>/*`, so only finished packages reach the release. The clean scripts delete their packages one file at a time.
- Without `-Doptimize` a Zig build is `Debug`, and the Linux example's executable was 26 MB against 6.9 MB for `ReleaseSafe`. Every sync script now defaults to `ReleaseSafe`, and the release is built the same way as a test build except for the test hooks. The Android package build is the exception: it passes `ReleaseSmall` explicitly, and nobody has recorded why.

### Fitting the existing TypeScript UI with the fewest changes

What the code shows:

- `packages/user-interface` never touches the bridge. It is configured only through `IPlatformContext` and `IQueueBackend`. The only code that touches `window.electronAPI` is the platform layer in `apps/desktop-frontend` (its entry, its platform provider, its queue backend, its renderer log and its MCP tool handler), and it uses exactly `invoke`, `send`, `onMessage`, `removeAllListeners`, `log` and `getPathForFile`.
- So no change to `packages/user-interface` is needed, and the platform layer in the new app is a copy of the desktop one with `window.electronAPI` replaced.

What the bridge and Zig should do so those copies change as little as possible:

- Keep `window.ziggy` with Electron's semantics, which it already has: `invoke(channel, data?)` returns a promise that rejects with an `Error`, `send`, `onMessage` adds a callback and keeps earlier ones, and `removeAllListeners(channel)` removes them all (the desktop provider relies on that in its effect cleanup).
- Add one member to the bridge: `getPathForFile(file)`, on desktop. The UI calls it synchronously inside a drop handler, and only native code knows the path of a dropped file, so the bridge cannot leave it to the page. The shells record the paths of dropped files and the bridge looks the dropped `File` up. How each web view makes that possible has to be proven in the example before Phase F, because a dropped `File` carries no path on WebKitGTK and WKWebView.
- Do not add `log` to the bridge. It is `send('renderer-log', message)`, and `renderer-log` is Photosphere's channel, which Ziggy must not know. Photosphere's platform layer builds an object with the same members as `IElectronAPI` from `window.ziggy` plus its own `log`, so the copied files change only where they name the global.
- Let the app supply the page address's query, and keep Ziggy ignorant of what is in it. `app.tsx` throws on its first render without the `restApiUrl` query parameter, and also reads `theme` and `testMode` from the query, so the shell must navigate to an address that already carries them. All three are Photosphere's: `restApiUrl` is the address of Photosphere's asset server, which binds its port inside Photosphere's core. Ziggy offers only an opaque hook: the app's core supplies a function that returns the query text, a new C function (`ziggy_page_query`) hands that text to the shell unread, and the shell appends it to the page address. No shell composes the query itself and Ziggy names none of its parts. The test mode switch is Ziggy's, so the hook is told whether it is on, and the app decides how to say so in the query. The example's hook returns `testMode=1` in test mode, and Photosphere's returns `restApiUrl`, `theme` and `testMode=1`, which is the flag its existing UI already reads. The same rule holds for everything else the existing UI uses that is Photosphere's and not Ziggy's (the asset server and its routes, `renderer-log`, `main-command`, the database channels): it lives in the app's core and platform layer, never in Ziggy.
- JSON replaces structured clone. Electron carries `Date`, `Map`, `Set`, binary and `undefined`, while Ziggy sends JSON. The payloads read in the desktop provider are plain objects and arrays, but step 10 must check every channel's payload for these before the protocol is written, and anything that does not survive JSON is changed on the Zig side (a `Date` is sent as the same text the UI already parses), not in the UI.
- Keep the existing frontend's Vite output unchanged. It emits an ES module script with `crossorigin`, and the example's page works around file addresses with a classic script and relative paths, which is no longer needed. Module scripts and `crossorigin` from an embedded origin are expected to need a permissive CORS header on the page's own responses, so every shell answers page requests with `Access-Control-Allow-Origin: *`. The example then drops its classic-script build and proves the default module output loads on all five platforms.
- The asset server's CORS header must allow any origin, because the page's origin is `ziggy-app://app` or `https://ziggy-app.invalid`, never `file://`. `localStorage` and IndexedDB are kept per origin, so the origin must stay the same from run to run, and the example must prove they persist on each platform.

### Not yet proven by the example

The Phase A list names proofs that the example does not have yet. Each is built into the example, on every platform it applies to, before the phase that depends on it starts:

- A Zig loopback HTTP server reachable from each web view, including cleartext loopback on Android and iOS, fetched from the embedded origin with a range request, with the page loaded from the unchanged module build.
- Zig calling the bundled ImageMagick and FFmpegKit libraries on Android and iOS.
- The AWS SDK and keychain code from the existing Zig packages linking into the core library on each platform.
- What happens to a running task when the app goes to the background and returns on Android and iOS, and when the window closes on desktop.
- Drag and drop of files returning paths through `getPathForFile`, on each desktop platform.
- `localStorage` and IndexedDB persisting across runs from the embedded origin.

### Decisions the human made or reacted to

- Ziggy is built only for Photosphere, but its docs are written for someone learning to build an app on it, with Photosphere's specifics in one closing section.
- The asset server and its routes are Photosphere's, not Ziggy's. `main-command` is Photosphere's. `get-platform`, `add-task`, `cancel-tasks`, `task-message` and `task-completed` are Ziggy's.
- Channels and native host callbacks are separate mechanisms and each has its own section. The human said both are fine if documented clearly.
- The Windows and Linux shells are their own Zig projects, with `sync`, `build` and `open` scripts like the others.
- Stories must keep working in the new app on every platform. The stories README in `packages/user-interface` must not mention Ziggy or Photosphere's app; the stories commands are documented elsewhere.
- Packaging for distribution is in the plan and is proven in Phase A. Step 35 is a reminder for the human only, listing what to delete and what to move first.
- `docs/development.md` marks everything the Zig port supersedes as "(deprecated)".
- An app is one binary per platform with nothing beside it: no `ui` folder, no `WebView2Loader.dll`, no script or page files. The human banned separate DLLs and loose files outright, and wanted the framework to need nothing supplied by the app (the Capacitor way). Do not add an exception.
- The Windows installer is an MSI (WiX 3), per user, and every package is written to `out/<platform>`.

### Traps

- The test hooks design (a `test_hooks` build option that is off for every release artifact and a loopback-only control connection) is my answer to the human's security objection. The human reacted to the problem, not to this fix, so treat it as not approved.
- The host callback design (function pointers in the `callbacks` struct, called from a worker thread, result as JSON) and the example's `os-version` proof are mine and not approved.
- The Edit tool can swallow the newline when `old_string` ends at the end of a line, joining two lines. Check bullets after such edits.
- In this worktree, shell commands that use a variable where an option could go are refused. Use literal arguments.
- The human is sensitive to unrequested changes. Answer questions as questions, and do what is asked and no more. A question from the human usually points at something wrong, but ask before making a large change. A question about the docs is not a request to change code: in the example a question about how to build a release led to an unasked edit of a build script, which the human questioned.
- The human wants the five platforms to behave the same. A default, a folder, an option or a document that differs between platforms needs a recorded reason or it is a bug, and a fix to one platform's script means checking the other four. The answer to "do the docs say how to do X" should be yes, so when the answer is no, say so and write the missing piece, for every platform.
- A word like "mostly" or "should" about something that was not run is a wrong answer. Say what was run and what was read, and name what was not checked. Windows, MacOS and iOS cannot be run from the Linux machine, so every change to them is unrun until the human reports.
- Anything a tool writes is ignored before the tool first runs, or it gets committed. ## Notes

- The human expects no hacks and no workarounds: everything is done properly, the first time, at the cause. The human equally does not want over-engineering or overreach: build what the feature checklist needs and nothing more, no extra framework features, no generality for other apps, no abstractions with a single user. Phase K audits both.
- Compatibility with the existing Electron and Capacitor projects is a requirement, not a preference: Ziggy follows their standards and names wherever it can (see the ground rules), and Phase K checks it as part of the faithful port and no-hacks audits.

- The previous plan the human mentioned was not shown, so this plan was built from the code. The files `docs/plans/new/plan-zig-core-port.md` and `plan-zig-cli-port.md` are different work (a port into a new repository) and were not used.
- The bridge follows the existing apps instead of inventing a protocol: Electron's `invoke/send/onMessage` surface and channel names, and the mobile `JsEngine` plugin methods, with the same three HTTP routes for media. The asset server is already shared between desktop and mobile in TypeScript, so one Zig port covers both.
- Linux is a delivered desktop target, as the human decided, in addition to Windows, MacOS, Android and iOS.
- The desktop shells: MacOS is Swift. Windows and Linux are Zig first, with C++ and C as approved fallbacks if Phase A shows Zig cannot host WebView2 or WebKitGTK. Phase A records which was used in the shell READMEs.
- The Bun workspace names for Ziggy, the example and Photosphere are set by the layout approved at step 2. `photosphere` is already the name of `apps/desktop`, so it cannot be reused.
- iOS stays on Capacitor-era tooling constraints: Xcode 14.2 and macOS 12.7.6. Whether Zig 0.16 can produce an iOS static library that links under Xcode 14.2 is a Phase A question, and a negative answer goes to the human.
- Embedded JavaScript engines, the Node shims and the `host.*` bridge are dropped because Zig runs the handlers natively. Only the behaviours behind them are carried over.
- `apps/dev-server` and `apps/dev-frontend` are not ported; they serve the web-only developer loop, not a delivered app, and are marked "(deprecated)" in `docs/development.md`.
- The documentation describes Ziggy on its own terms, as finished and as if the plan were complete.
