# Make the HashCache safe for concurrent writers

## Overview
Running multiple Photosphere instances at once can corrupt the shared hash cache. The corruption has two causes in `packages/node-api/src/lib/hash-cache.ts`: `save()` writes every instance's temporary file to the same fixed path (`hash-cache-x.dat.tmp`), so two concurrent saves interleave their bytes into one temp file and the following `rename` publishes a byte-mixed file that fails the checksum and gets discarded on the next load; and even without that, each `save()` writes the instance's full in-memory snapshot over whatever is on disk, so two instances that both loaded the cache and each added entries clobber each other (last writer wins, the other's additions are silently lost). The codebase already has the correct machinery for this in `packages/node-utils/src/lib/fs.ts`: `updateFileOptimistic` performs an optimistic read-modify-write with a unique per-write temp file (`outputFile`) and a fingerprint compare-and-swap that retries when the file changed underneath it. That helper is string-only. This plan first extracts a raw-`Buffer` underlying function from it (no behaviour change for existing callers), then rewrites `HashCache.save()` to use that function and merge its own changes onto the freshly-read on-disk contents rather than overwriting them. A final optional phase adds an in-memory mode so the unit tests stop depending on a real `cacheDir`.

## Steps

1. **Add `updateFileRawOptimistic` to `packages/node-utils/src/lib/fs.ts`.** Add an exported async function `updateFileRawOptimistic(filePath: string, mutator: (current: Buffer | undefined) => Buffer, retries: number): Promise<void>`. Its body is the existing `updateFileOptimistic` loop with parse/serialize removed: take a `fileFingerprint` before the read, read the current file as raw bytes (a new private `readRawFileBytes(filePath): Promise<Buffer | undefined>` that returns `undefined` when the file is absent, mirroring `readRawFile` but without the utf8 decode), compute `next = mutator(current)`, `ensureFileDir`, write `next` to `${filePath}.tmp-${randomUUID()}`, re-fingerprint, and on `fingerprintsMatch` `rename` into place and return, otherwise `fs.rm` the temp and retry. Throw the same "kept changing under concurrent writers" error after `retries`. Reuse the existing `fileFingerprint`, `fingerprintsMatch`, and `ensureFileDir` helpers unchanged. Requires: compiles, and the new unit tests plus all existing `fs.test.ts` tests pass.

2. **Refactor `updateFileOptimistic` in `packages/node-utils/src/lib/fs.ts` to wrap `updateFileRawOptimistic`.** Keep the exact same exported signature. Replace its body with a single call to `updateFileRawOptimistic(filePath, rawMutator, retries)` where `rawMutator(current: Buffer | undefined)` computes `const parsed = current === undefined ? fallback : parse(current.toString('utf8'))` and returns `Buffer.from(serialize(mutator(parsed)), 'utf8')`. This must preserve current semantics exactly, so the existing `updateFileOptimistic`, `updateToml`, and `updateJson` tests pass unchanged and act as the regression guard. Remove the now-unused private `readRawFile` only if nothing else references it (grep first; `updateFileOptimistic` was its sole caller). Requires: compiles, all existing `fs.test.ts` tests pass with no edits to them.

3. **Export `updateFileRawOptimistic` from `packages/node-utils/src/index.ts`.** It is already re-exported via `export * from "./lib/fs"`, so confirm no explicit list needs updating; add nothing if the wildcard already covers it. Requires: `import { updateFileRawOptimistic } from "node-utils"` type-checks from `packages/node-api`.

4. **Factor pure encode/decode helpers out of `HashCache` in `packages/node-api/src/lib/hash-cache.ts`.** Introduce two private, side-effect-free helpers so the merge path and the normal load share one implementation: `private static decodeEntries(fileBytes: Buffer | undefined): IHashCacheEntry[]` and `private static encodeEntries(entries: IHashCacheEntry[]): Buffer`. `decodeEntries` performs the version check, checksum verification, and per-entry walk currently spread across `load` and `createLookupTable`, returning `[]` for an absent, too-small, wrong-version, or checksum-failed buffer (matching today's "discard and start fresh" behaviour, but without logging inside the pure helper — callers log). `encodeEntries` builds the `[version][entryCount][sorted entries][sha256]` layout currently inlined in `save`. Define a named interface `IHashCacheEntry { filePath: string; hash: Buffer; length: number; lastModified: number }` (store `lastModified` as epoch ms to match the on-disk format). Rewrite `load` to call `decodeEntries` and rebuild the in-memory buffer/lookup from the result. Requires: compiles, all existing `hash-cache.test.ts` tests pass.

5. **Track a per-instance changeset in `HashCache`.** Add private fields recording what this instance changed since the last `load`/`save`: `private pendingUpserts: Map<string, IHashCacheEntry>` and `private pendingRemovals: Set<string>` (keyed by the normalized file path). Update `addHash` to record the entry in `pendingUpserts` (and clear any matching `pendingRemovals`) in addition to its current in-memory mutation, and `removeHash` to record the path in `pendingRemovals` (and drop any matching `pendingUpsert`). Clear both in `load` and after a successful `save`. Keep the existing in-memory buffer behaviour so `getHash`/`getEntryCount`/`getAllEntries` are unchanged for the common single-process path. Requires: compiles, existing `hash-cache.test.ts` tests pass.

6. **Rewrite `HashCache.save()` in `packages/node-api/src/lib/hash-cache.ts` to merge via `updateFileRawOptimistic`.** Keep the early-out guards (`!initialized`, `!isDirty`, `isReadonly`). Replace the hand-rolled temp-write/rename with a call to `updateFileRawOptimistic(path.join(this.cacheDir, "hash-cache-x.dat"), mergeMutator, retries)` where `retries` is a small constant (e.g. 5). `mergeMutator(current: Buffer | undefined): Buffer` must: `decodeEntries(current)` into a `Map<string, IHashCacheEntry>` keyed by path; apply this instance's `pendingRemovals` (delete) and `pendingUpserts` (set, this instance wins); sort the resulting entries by path with the same `localeCompare` ordering `findEntryOffset` relies on; and return `encodeEntries(sorted)`. After the call returns, clear the changeset, mark `isDirty = false`, and rebuild the in-memory buffer/lookup from the merged entries so the instance reflects the merged state. Delete the old shared `${cachePath}.tmp` write, the manual `fs.writeFile`/`fs.rename`, and the inline header/checksum construction now living in `encodeEntries`. Requires: compiles, existing and new `hash-cache.test.ts` tests pass.

7. **(Optional, Phase 3) Add an in-memory mode to `HashCache` to decouple tests from `cacheDir`.** Add an optional construction path (e.g. a `HashCache.inMemory()` static factory or an `IHashCacheStorage` injected dependency with a file-backed default and an in-memory implementation) where `load`/`save` operate on an in-process byte store instead of the filesystem. Update the non-concurrency tests in `hash-cache.test.ts` to use the in-memory mode so they no longer create a real directory, and remove the `Date.now()`-plus-counter `cacheDir` uniqueness workaround added in `beforeEach`. Keep at least the concurrency test (Step 8's second item) on a real shared directory. Requires: compiles, all `hash-cache.test.ts` tests pass. This phase is optional and can be deferred; leaving the counter workaround in place is acceptable if this phase is skipped.

## Smoke Tests

- No new smoke test is required: `HashCache` is a plain library class fully exercisable by unit tests, and concurrency is deterministically reproducible in-process (Step below). If an end-to-end signal is wanted, add a Node-driven concurrency check under `packages/node-api/src/test` (not a shell smoke test): spawn N async writers against one shared `cacheDir`, each loading, adding a disjoint set of entries, and saving with retries; after all settle, load once and assert the union of every writer's entries is present with none lost. ## Notes

- The hash cache is a performance optimization: a miss just recomputes a file hash, so occasional recomputation is acceptable but silent data loss and whole-cache wipes are not. This is why merge-on-save (not just a unique temp file) is worth the extra work — a unique temp alone fixes the byte-interleaving corruption but still loses concurrent writers' entries.
- Merge semantics are well-defined because entries are keyed by normalized file path and are independent; "this instance wins" on an upsert conflict is a safe choice since a freshly computed hash for a path is as valid as any other.
- `updateFileRawOptimistic`'s conflict detection uses the existing size+mtime `fileFingerprint`, which cannot distinguish two writes producing an identical size in the same millisecond. That residual race is already accepted by `updateFileOptimistic` and is tolerable for a cache; the retry loop plus merge makes a genuinely lost update very unlikely and never corrupting.
- Keep `updateFileOptimistic`'s public signature intact — `updateToml` and `updateJson` (both in `fs.ts`) depend on it, and only `fs.test.ts` calls it directly.
- Step 7 (in-memory mode) is optional and separable. If skipped, the `Date.now()`-plus-counter `cacheDir` workaround already committed stays; it is harmless, just less clean than filesystem-free tests.
- Open question for `plan:check`: whether to also rebuild the in-memory buffer after every `save` merge (Step 6) or lazily on next access — rebuilding keeps `getHash` correct immediately after a save that merged in other instances' entries, at the cost of one re-encode per save.
