# Merge The Configuration Files Into One config.yaml

## Overview

Settings are spread across several files in several formats, and which file a setting lands in depends on which platform wrote it rather than on what the setting is. On desktop, `~/.config/photosphere/desktop.toml` holds everything from the theme to the automatic import sources (`packages/node-api/src/lib/desktop-config.ts`), and `~/.config/photosphere/news.yaml` holds the news state (`packages/node-api/src/lib/news-state.ts`). On mobile the same settings are split across `auto-import.toml` and `sync.toml` at the root of the app's storage sandbox (`packages/api/src/lib/mobile-config-paths.ts`), read and written through two near-identical worker task pairs and two near-identical frontend accessors. The result is four on-disk formats to keep in step, two of which describe the same features on different platforms, and a user who wants to change a setting by hand has to know which file it lives in.

This plan replaces `desktop.toml`, `auto-import.toml`, `sync.toml` and `news.yaml` with a single `config.yaml`: at `~/.config/photosphere/config.yaml` on desktop and CLI, and at the root of the storage sandbox on mobile. `databases.toml` is explicitly out of scope and is left exactly as it is. The merged file is one shared TypeScript type with one shared reader and writer, so a setting means the same thing on every platform and there is one format definition rather than four. YAML is chosen because it is already in use for `news.yaml`, `js-yaml` is already a dependency of `api`, `node-api` and `apps/cli`, and nested sections let the file group settings by feature rather than flatten everything into prefixed keys.

The work also closes a parity gap: today the mobile app has no home for the desktop-only fields (theme, developer mode, recent searches) and the desktop app carries no notion of the mobile sync pacing. One type covering both means adding a setting reaches every platform at once.

## Steps

Step 1 is documentation and stops for human approval. Step 2 is a feasibility check that can stop the plan. Every step from 3 onwards must leave `bun run compile` clean and `bun run test` passing before it is considered complete, and each step that changes mobile or desktop behaviour must leave `bun run tev` passing before the next step starts.

1. **Write the documentation for the merged file, then STOP.** Create `docs/configuration.md` describing: where `config.yaml` lives on each platform (`~/.config/photosphere/config.yaml` on Linux/macOS/Windows for the CLI and desktop app, and the storage sandbox root on Android and iOS), the full set of sections and keys with their types, defaults and meanings, which settings apply to which platforms, and the explicit statement that `databases.toml` is a separate file and stays that way. Include a complete worked example of the file. Add a "Configuration" row to the guides table in `docs/development.md` linking to it. Update the two places that currently describe the split files so they point at the new document rather than restating it: the config-file paragraphs in `docs/automatic-photo-backup.md` and `docs/syncing.md`. **STOP here. Do not begin step 2.** Wait for the human to read and approve the documentation. If the human revises it, revise steps 3 to 14 of this plan to match before implementing anything.

2. **Prove `js-yaml` runs inside the embedded mobile JS engine before changing anything.** The mobile worker bundle is built by `packages/mobile-worker/scripts/bundle.ts` and runs under QuickJS on Android and JavaScriptCore on iOS, and today it parses TOML with `smol-toml`. Add `js-yaml` to the `dependencies` of `packages/mobile-worker/package.json`, add a temporary handler to `packages/mobile-worker/mobile-worker-entry.ts` that parses a small YAML document and dumps it back out, build the bundle with `bun --filter=mobile-worker build:bundle`, and run it on a device or emulator to confirm both directions work and that the bundle size is still acceptable. Record the measured result. **If `js-yaml` does not work in the embedded engine, STOP and ask the human**, stating plainly what fails and what the options are (a different YAML library, keeping TOML and merging into one `config.toml` instead, or hand-writing a parser, which is banned without explicit approval). Do not write a substitute for the library. Remove the temporary handler once the answer is known.

3. **Define the merged config type and its YAML conversions.** Create `packages/node-api/src/lib/config-format.ts`, following the existing pattern of `packages/node-api/src/lib/sync-config-format.ts` and `packages/node-api/src/lib/auto-import-config-format.ts`: it must touch no filesystem, so it can be bundled into the mobile worker, and it must be the only definition of the file format so a reader and a writer cannot drift. Export `IPhotosphereConfig` as the in-memory type with camelCase fields, `IYamlPhotosphereConfig` as the on-disk type with snake_case keys and nested sections (`auto_import`, `sync`, `desktop`, `news`, plus top-level fields that are genuinely global such as `theme` and `developer_mode`), and the two conversion functions `yamlToConfig` and `configToYaml`. `yamlToConfig` must accept `undefined` and return the defaults, exactly as `tomlToSyncFile` does now, because a phone that cannot read its settings must not start syncing over a metered connection. Reuse the existing normalisers rather than reimplementing them: `normaliseSyncSettings` and `resolveSyncPauseMs` from `api/src/lib/sync-settings`, and `normaliseAutoImportSettings` and `resolveAutoImportPauseMs` from `api/src/lib/auto-import-settings` and `api/src/lib/auto-import-mobile`. Keep `sync.database_path` and `auto_import.default_database_path` as separate fields: `packages/mobile-worker/src/lib/plan-sync.worker.ts` treats the first as the last database the user opened and the second as the fallback the background import writes to, so they are not the same value.

Model `updateConfig` on the optimistic read-modify-write `updateToml` in `packages/node-utils/src/lib/fs.ts` provides, adding `readYaml`, `writeYaml` and `updateYaml` beside the existing TOML helpers in that file rather than open-coding YAML I/O here. `writeYaml` must write through the same temp-file-and-rename path `writeToml` uses, for the reason recorded in the comment at `packages/node-utils/src/lib/fs.ts:65`.

## Unit Tests

- `yamlToConfig` (step 3): an absent document returns the defaults with syncing and automatic import switched off; a document with only a `sync` section leaves the other sections at their defaults; unknown keys are ignored rather than throwing; a malformed section falls back to that section's defaults without discarding the sections that parsed.
- `configToYaml` (step 3): every field round-trips through `configToYaml` then `yamlToConfig` unchanged; an absent optional field stays absent rather than being written as null; an empty `auto_import.sources` list round-trips as an empty list and not as absent.
- `configToYaml` nesting (step 3): the emitted document puts auto-import keys under `auto_import` and sync keys under `sync`, so the file matches what `docs/configuration.md` documents.
- `readYaml`, `writeYaml`, `updateYaml` (step 4): a file that does not exist reads as undefined; a written file reads back identically; `updateYaml` applies the mutator and retries on a concurrent modification, mirroring the existing `updateToml` tests.
- `loadConfig`, `saveConfig`, `updateConfig` (step 4): loading with no file returns defaults; saving then loading round-trips; `updateConfig` changes one field and leaves the rest.
- `readConfigHandler` and `writeConfigHandler` (step 7): reading a sandbox with no config file reports `exists: false` and returns defaults; writing then reading round-trips both sections; a read of a corrupt file throws rather than silently returning defaults, so the caller surfaces a real error.
- `buildConfigYaml` (step 7): produces a document `yamlToConfig` parses back to the input, which is what stops the smoke-test harness drifting from the app.
- The migration merge function (step 12): each old file alone produces the right merged config; all of them together merge without a field from one overwriting a set field from another; absent old files contribute nothing.
- `loadNewsState` and `saveNewsState` (step 10): state round-trips through the `news` section; a config file with no `news` section loads as empty state.
- Existing tests to update rather than delete: `packages/mobile-frontend/src/test/mobile-config-store.test.ts`, `packages/mobile-worker/src/test/lib/plan-sync.worker.test.ts`, `packages/mobile-worker/src/test/lib/plan-auto-import.worker.test.ts`, `packages/mobile-worker/src/test/lib/record-default-database.worker.test.ts`, `packages/node-api/src/test/lib/desktop-config.test.ts`, `packages/node-api/src/test/lib/auto-import-desktop.test.ts` and `packages/node-api/src/test/lib/news-state.test.ts`. Every one of these must keep testing the behaviour it tests today against the merged file.

## Notes

- `databases.toml` stays TOML and stays separate, as asked. That means `smol-toml` remains a dependency and the repository carries two config formats. That is the deliberate trade: merging the database list in as well would be a bigger change and was excluded.
- `news.yaml` is state rather than a setting, so folding it into `config.yaml` is a judgement call. It is included because the request excluded only `databases.toml`, and because leaving it out would mean the config directory still holds three files. If the human would rather keep news state separate, drop step 10 and the news parts of steps 12 and 14; nothing else in the plan depends on it.
- Step 2 is the real risk. `js-yaml` is a much larger library than `smol-toml` and the embedded engines are not Node. If it does not run there, the merge can still happen as `config.toml` instead, keeping `smol-toml` throughout, which would be a smaller change than this plan describes but loses the nesting that makes the file readable. That decision belongs to the human, which is why step 2 stops rather than choosing.
- The mobile app has never had the desktop-only fields and the desktop app has never had the mobile pacing fields. One shared type gives every platform every field, which closes the parity gap `docs/plans/new/plan-review-mobile-config-storage.md` records. This plan does not depend on that one and does not replace it: that plan is about durability of the mobile store, which is untouched here.
- Nothing in this plan changes where secrets live. They stay in the vault and the device keychain, and `config.yaml` holds secret names only, exactly as `databases.toml` does today.
- The two mobile worker task pairs being replaced by one means one fewer file read per background sync pass, since `plan-sync.worker.ts` currently opens both `sync.toml` and `auto-import.toml` to resolve which database to push.
