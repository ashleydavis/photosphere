# Get the Release run under 10 minutes by sharding the long suites

## Overview

The Release workflow's wall clock is whatever its slowest single job takes. In run `31282883315` seven jobs were over 10 minutes: `ios-smoke-tests` 1154s, `build-windows` 1151s, `build-desktop (windows-latest)` 1140s, `build-macos-x64` 1109s, `android-smoke-tests` 989s, `build-desktop (macos-15-intel)` 818s, `stories-ios` 757s and `stories-android` 628s. In every one of them the time is a single long test suite run end to end on one machine, and none of those suites can be made much faster. They can be made narrower: each suite gets a `--shard <index>/<total>` selector, and the workflow runs the shards as legs of a matrix so the segments run on separate machines at the same time. The selector goes in one shared shell library so the CLI, Electron and mobile suites all select the same way, and it is round-robin over the discovered test list so a new test lands in a shard automatically and the expensive tests spread rather than pile into one leg.

## Steps

1. **Create `scripts/lib/select-test-shard.sh`.** A new sourced shell library beside the existing `scripts/lib/allocate-test-temp-dir.sh` and `scripts/lib/process-control.sh`, which all three suites already source. It defines two functions, each with a `//`-style comment block above it describing intent and usage (match the comment style of `process-control.sh`):
   - `parse_shard_spec <spec>` - accepts `N/M`, sets the globals `SHARD_INDEX` and `SHARD_TOTAL`. It must reject and exit non-zero, with a message naming what was passed, when: the spec does not match `<digits>/<digits>`, `M` is 0, `N` is 0, or `N` is greater than `M`. A silently misread spec would run the wrong subset and still report success, so this refuses rather than defaults.
   - `select_shard_tests <index> <total> <test-path>...` - prints the selected test paths, one per line, keeping the input order. Selection is round-robin: the test at zero-based position `p` belongs to shard `(p % total) + 1`. It exits non-zero if the selection is empty, because an empty shard means the shard count exceeds the number of tests and the leg would report a pass having run nothing.
   - Both functions must work under the bash macOS ships (3.2): no `${var,,}`, no associative arrays, no `mapfile`. `apps/smoke-tests/lib/runner.sh:676` already carries this constraint for the iOS runs.

2. **Wire the shard selector into `apps/cli/smoke-tests.sh`.** Source the new library next to the existing sources at lines 56 and 67. Add `--shard <spec>` to the option loop in `main()` (the `while [[ $# -gt 0 ]]` block near line 914), calling `parse_shard_spec`. Add a `--list` command that prints the selected tests (number and name, the same format as the `RUN` lines) and exits 0 without running anything, so the shard split can be checked in a second rather than by running the suite. In `run_all_tests()` (near line 713), after the loop that excludes `*keychain*` directories builds `all_scripts`, replace it with the output of `select_shard_tests` when `SHARD_TOTAL` is set. Change the existing `log_info "Running ${#all_scripts[@]} tests in parallel (batch size ...)"` line to also state the shard, e.g. `shard 2 of 3: 26 of 79 tests`. Update `show_usage()` (line 857) with both new options.

3. **Wire the shard selector into `apps/desktop/smoke-tests.sh`.** Source the new library next to lines 9 and 14. The pre-pass `for arg in "$@"` loop at line 378 already strips `--binary`; extend it to strip `--shard <spec>` and call `parse_shard_spec`. Filter `all_tests` through `select_shard_tests` after the `discover_tests` loop near line 437 and before `bundle_app`, and make `list_tests()` honour the shard so `./smoke-tests.sh --shard 1/2 ls` prints exactly what that leg would run. 4. **Wire the shard selector into `apps/smoke-tests/run.sh`.** Source the new library after the `source "$SCRIPT_DIR/lib/common.sh"` at line 30. `main()` currently takes a bare positional filter as `$1`; add a `--shard <spec>` option parsed before that filter is read, so `run.sh --shard 1/3` and `run.sh --shard 1/3 34-sync` both work. ## Unit Tests

None, and this is deliberate. Every change in this plan is shell script or workflow YAML. `CLAUDE.md` states plainly: do not write tests for shell scripts, do not create `*.test.sh` files, and the rule requiring a unit test for every new or changed function does not apply to shell. `scripts/lib/select-test-shard.sh` therefore gets no test file of its own, and no test is added beside the existing `apps/smoke-tests/runner.test.sh`, `android-lock.test.sh` or `timeout.test.sh`. What proves the selector works is the real suites running through it, which is what the Verify section does.

## Smoke Tests

The suites being sharded are themselves the end-to-end coverage, and they already exist. What the sharding adds is one property that has to be checked directly: the shards of a suite must together be exactly the whole suite, with nothing dropped and nothing run twice. The `--list` flag added in steps 2, 3 and 4 makes that a fast, repeatable check for each of the four suites:

- `apps/cli/smoke-tests.sh`: the concatenation of `--shard 1/3 --list`, `2/3` and `3/3` sorted equals `--list` with no shard, and every test appears exactly once.
- `apps/desktop/smoke-tests.sh`: same check with `--shard N/2 ls` against bare `ls`.
- `apps/smoke-tests/run.sh` for both `PLATFORM=android` and `PLATFORM=ios`: same check with `--shard N/3 --list`.
- A bad spec (`--shard 0/3`, `--shard 4/3`, `--shard 3`, `--shard 1/0`) exits non-zero with a message naming the spec, on each of the four entry points.
- A shard count above the test count (for example `--shard 9/9` on a suite with fewer tests in a shard) exits non-zero rather than reporting a pass over an empty selection.

## Notes

- **Measured, not estimated.** Everything below comes from run `31282883315`'s job timings and logs.
- **Why these shard counts.** Android: 340s of fixed cost per leg (83s job setup, 58s emulator install, 43s boot, 155s `cap sync` plus Gradle) and 625s of tests, so 2 legs land at 653s and 3 legs at 548s. CLI on Windows: 160s setup (86s bun cache restore, 38s install, 25s choco) and 964s of tests, so 2 legs land at 650s and 3 at 490s. CLI on Intel macOS: ~100s setup and 978s of tests, so 2 legs land at ~590s; 2 rather than 3 because `macos-15-intel` runners are scarce and a queued leg costs more than the split saves. Electron on Windows: 610s of sequential tests halves to ~305s plus ~150s setup and ~90s artifact download.
- **iOS is the one that may not make it, and sharding is not the whole answer.** Its 1098s step splits into 44s prep, 98s xcodebuild and simulator boot, and 956s of tests. Of those tests, `0-launch-and-navigate` alone takes 206s, against 7s for the same test on Android, and every shard pays that first-launch cost. Three shards therefore land at roughly 609s, right on the bar. If that 206s were brought near Android's, two shards would reach ~530s comfortably. Finding out what those 206 seconds are is worth doing before or alongside this plan; it is not in scope here.
- **The iOS ImageMagick cache gets riskier.** All three iOS legs share the cache key from `hashFiles('apps/ios-frontend/ios/build-imagemagick.sh')`. On a hit the build is 1s. On a miss, all three legs now build ImageMagick from source concurrently, and that build has taken 37 minutes on a slow runner. The alternative, a small priming job that the legs depend on, would add its own latency to the critical path on every run, including the common cache-hit case. Accepting three concurrent rebuilds on the rare miss is the better trade, but it is a trade and it is why step 9 keeps the 90-minute timeout.
- **This costs more runner minutes.** Each new leg repeats checkout, `bun install` and the media-tool install: roughly 100-160s per leg, across about 10 new legs. The workflow gets faster in wall clock and more expensive in total minutes. Moving the story jobs off the push path (step 11) gives back about 23 runner-minutes per run and covers most of it.
- **Two claims in `ci-run-time.md` are wrong and the doc should be corrected separately.** Its job table omits `build-desktop (windows-latest)` at 1140s, the third-slowest job in the run, so its plan leaves a 19-minute job in place. And it says the mobile suite "supports this today: `run.sh` takes test names": `run.sh` takes a single filter, one number or one substring (`apps/smoke-tests/lib/runner.sh:654`), which is why step 4 exists.
- **What this plan does not do.** It does not touch the batching inside the CLI suite. `run_parallel` (`apps/cli/smoke-tests.sh:524`) waits for every test in a batch of 5 before starting the next, and on Windows that idles slots for about 120s per run (measured: 947s of batch maxima against an 824s ideal work queue). Replacing fixed batches with a work queue, as `apps/smoke-tests/lib/runner.sh` already does, is a real but separate improvement, and sharding does not depend on it.
