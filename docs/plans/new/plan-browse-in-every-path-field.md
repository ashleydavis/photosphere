# The same Browse control on every database path field

## Overview

Six dialogs take a database path and they offer three different ways to fill it. New Database, Add Database and Replicate have a Browse button that opens the folder picker for a filesystem path and the S3 browser for an S3 path. Edit Database has a Browse button that always opens the folder picker, even when the path being edited is an S3 path. Receive Database's Path and Consolidate's Remote path have no Browse at all and must be typed. The three dialogs that do it right each carry their own copy of the same twenty-odd lines. This plan moves that code into one `PathField` component and uses it for every path field, so each one offers Browse for a folder and Browse S3 for a bucket.

## Issues

- `packages/user-interface/src/components/create-database-modal.tsx`, `add-database-modal.tsx` and `replicate-database-dialog.tsx` each hold a `handleBrowse`, an `s3BrowserOpen` state, an `Input` plus `Button` row and an `S3BrowserModal` block that are the same apart from names.
- `packages/user-interface/src/components/edit-database-modal.tsx` `handleBrowse` always calls `platform.pickFolder()`, whatever the path is.
- `packages/user-interface/src/components/receive-database-dialog.tsx` renders `receive-database-path-input` with no Browse.
- `packages/user-interface/src/components/consolidate-database-dialog.tsx` renders `consolidate-remote-path-input` with no Browse and has no way to name S3 credentials: the `consolidate-database` task (`packages-zig/node-api-zig/src/lib/consolidate-database.worker.zig`) opens the remote with `openStorage(..., data.remotePath, null, null, ...)`, so an S3 remote works only when a database record with exactly that path and an S3 key already exists.

## Steps

1. **A plain function for the storage type a path names.** Add `packages/user-interface/src/lib/path-storage-type.ts` exporting `PathStorageType` (`"filesystem" | "s3"`, with a comment) and `storageTypeOfPath(path: string): PathStorageType`, which returns `"s3"` when the trimmed path starts with `s3:` and `"filesystem"` otherwise, with a comment saying it is the same test the storage factory uses (`packages-zig/storage-zig/src/lib/storage-factory.zig` and `packages/storage/src/lib/storage-factory.ts` both branch on the `s3:` prefix). Write `packages/user-interface/src/test/lib/path-storage-type.test.ts` (see Unit Tests). `bun run test -- path-storage-type` passes.

2. **The shared control.** Add `packages/user-interface/src/components/path-field.tsx` exporting `IPathFieldProps` and `PathField`. Every prop has a `//` comment and none is optional:
    - `label: string`, `value: string`, `onChange: (path: string) => void`.
    - `storageType: PathStorageType`: which Browse the button offers.
    - `s3Key: string | undefined`: the vault secret the S3 browser lists with. Browse S3 is disabled when it is undefined.
    - `inputDataId: string`, `browseDataId: string`.
    - `placeholder: string | undefined`.
    It renders, inside one `FormControl sx={{ mb: 2 }}`, the `FormLabel`, then a `Box sx={{ display: 'flex', gap: 1 }}` holding the `Input` (`data-id={inputDataId}`, `sx={{ flexGrow: 1 }}`) and a `Button` (`data-id={browseDataId}`, `variant="outlined"`, labelled `Browse S3` for `s3` and `Browse` for `filesystem`, disabled when `storageType === 's3' && !s3Key`). The button calls `platform.pickFolder()` for `filesystem` and passes a chosen folder to `onChange`; for `s3` it opens `S3BrowserModal` with `s3Key`, whose `onSelect` passes the path to `onChange` and closes it. Browse errors go to `log.exception('Browse error:', err as Error)` as they do today. The `S3BrowserModal` is rendered after the `FormControl` inside a fragment, because Joy allows a `FormControl` one control (the comment in `edit-database-modal.tsx` above the origin picker records this). A comment block above the component says it is the one path field every database dialog uses, so Browse behaves the same in all of them. `bun run compile` passes.

## Notes

- Decided: one `PathField` component, because New Database, Add Database and Replicate already carry the same code three times and Edit, Receive and Consolidate would make it six. It lives in `components/` because more than one dialog uses it.
- The labels and data-ids of each field are left as they are. Making the labels the same is a separate change and keeping the data-ids keeps every existing scenario working unchanged.
- Dialogs with a Type choice (New, Add, Replicate, Consolidate) pass that choice. Dialogs without one (Edit, Receive) take the type from the path, so an S3 record's Browse offers the bucket.
- Consolidate needs a key of its own to browse S3 and passing it to the task makes the browse useful: the path the browser returns would otherwise work only if a record with exactly that path already held a key. The chosen key overrides the record's key, as `destS3Key` does for a replication (`resolveStorageCredentials` uses the given key before the record's).
- Consolidate uses `ConfigureSecretsModal` with only the S3 row, which is how Replicate and Edit choose secrets, rather than adding another way to choose one.
- Receive's Browse S3 uses a vault secret already present under the received credential's name and is disabled otherwise, because the S3 browser lists only through a vault secret and the received one is not in the vault until the import runs.
- A path chosen in the S3 browser ends with `/` (`s3:${bucket}/${prefix}`, with the prefix ending in `/`). The scenario types the remote path without it before consolidating, so it does not depend on how a trailing slash is treated by the storage layer; that is the S3 browser's behaviour today and not part of this change.
