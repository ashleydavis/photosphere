# The page queues the core's tasks itself

## Overview

Photosphere registers message handlers in `packages-zig/photosphere-core/src/lib` that do nothing but name a task and pass the page's data to it (`return .{ .task = .{ .task_type, .data } }`). The page sends each one with `window.ziggy.invoke(name, data)`, Ziggy's core queues the named task under the source `"request"` and the task's result comes back as the reply. The page can already queue tasks itself through `TaskQueue` and `ZiggyQueueBackend` and gets the same result and the same error text from the task's `task-completed` event.

This plan removes every handler that only starts a task and its entry in `.messages` of `apps/photosphere/core/src/app.zig`. The page queues those tasks itself through one new helper, `runCoreTask` (`apps/photosphere-frontend/src/lib/run-core-task.ts`), which queues the task at interactive priority under a source of its own, awaits it, resolves with its outputs and rejects with the task's error text, so every caller handles failure exactly as it did when `invoke` rejected. Two handlers stay messages, because they read main-thread state before they start their task. Five messages have no caller in the page, so they go together with the tasks behind them. The classification of every handler is in Notes.

The Zig tests of the removed messages are ported to queue the tasks directly, with two test helpers in `test-support.zig`. The MCP smoke scenario gains a `save_media_file` call, which is the only page caller of the `save-asset-request` task that no smoke scenario reached.

## Notes

- The human's answer: no documentation step first and no review stop. The plan runs start to finish.
- Order with the other plans in this directory: this plan is implemented first, then `plan-start-tasks-by-call.md`, then `plan-one-handler-form.md`. This plan changes nothing in Ziggy. After this plan, Photosphere's only `.task` users are the two kept handlers, set-config and get-log-details, which keep `.task` as they are today; `plan-start-tasks-by-call.md` converts them, and its conversion of the other Photosphere handlers finds them already gone. No Ziggy change is needed: `window.ziggy.addTask`, the `task-completed` event and `onTaskEnd` for page-queued tasks already exist in the locked Ziggy.
- Same result and same error: the core sends a `.task` reply as the task's result JSON, or an error of `Cancelled`, the task's error message or `Failed` (`emitReply` in Ziggy's `worker-pool.zig`) and `invoke` rejects with `new Error(text)`. A page-queued task's `task-completed` event carries the same JSON as `outputs` and the same texts as `errorMessage` (`emitTaskCompleted`). `runCoreTask` resolves and rejects with those, so callers keep their error handling.
- Main-thread effects: `onTaskEnd` in `main-process.zig` acts on `notify-database-opened`, `notify-database-closed` and `startBackgroundImport` by task type and Ziggy records the end of every task whoever queued it, so those effects are unchanged. The order of the page's event and the main thread's notice is the same as for a reply (both are sent in `finish` before the notice is handled).
- Validation: a removed message parsed the page's data into a struct first and replied `InvalidMessageData` for data that did not fit. Every task checks its own data and fails with a sentence (listed in steps 2 to 9). The page sends typed data, so only the error text for malformed data changes; the tests of the message's check go and tests of the task's check replace them.
- Source: one per call, `<taskType>-<uuid>`, as `runResetAppStorageTask` and `runConfigTask` already do. A shared source would let one call's `shutdown` cancel another in flight and the database path would let closing a database cancel a vault read. Child tasks (save-assets' writes) take the parent's source as they took `"request"`.
- Priority: interactive, as the core queued every message's task.
- Jobs: none of these tasks gets an `IJobTag`. Each is a call the user waits on in place (a dialog, a form, a list, a sheet), none reports progress and none can be cancelled from the interface today. save-assets keeps reporting through its own result and the toast the page shows for it.
- Mobile: the phone runs the same page and the same `ZiggyQueueBackend` (installed in `app.tsx` on every platform) and the phone tasks are registered in `app.zig` on every platform, so the phone needs no change of its own.
- `runCoreTask` lives in `apps/photosphere-frontend/src/lib/` because two files use it (`platform-provider-ziggy.tsx` and `mcp-tool-handler.tsx`). It rejects with an `Error`, like `invoke` did and like the existing task helpers, so every caller's `catch` stays as it is. `runDownloadTask` in `platform-provider-ziggy.tsx` stays as it is: it returns the whole `ITaskResult` to `saveDownloadsViaShareSheet`, which reads its status.
- set-config is one message for every key, because its handler cannot know before parsing whether the key is one of automatic import's.
- Rejected: moving set-config's main-state read into the task (a task cannot reach `MainState` and the reply has to wait for the automatic import check, which `35-auto-import` relies on); having the worker log report the log file path for get-log-details (a worker's log returns no path, see `QueueLog.logFilePath` in Ziggy's `thread-log.zig`); keeping the pick-file and secureStore tasks with no caller; giving the replaced tasks job rows.
