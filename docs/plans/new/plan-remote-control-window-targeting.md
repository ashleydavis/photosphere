## Overview

The remote control server (`tools/remote-control-server` in the Ziggy repository) takes one app connection at a time, and a new app replaces the one before it. This plan lets the server hold many app connections at once, gives each the lowest number from 1 that no connected app holds and sends each script line to the window its `"window": <n>` field names (window 1 when it has none). A line for a window that is not connected waits for it, as a line waits for the app today. The change is in the server and in the Ziggy test app's smoke tests and docs. The app's own code does not change: the server takes the `window` field off before the app sees the line.

The server numbers connections, so a window is one app connection to it: a window gets a number only while it has a WebSocket connection of its own to the server, opened when the window starts and ended when the window closes. Today an app process is one window with one connection. How an app hosts several windows (a process each, or many windows in one process, which plan-new-window.md is being reworked to do on macOS and Linux) is plan-new-window.md's to decide; this plan holds for either as long as each window opens its own connection and ends it when it closes, and plan-new-window.md has to provide that for its windows to be numbered.

Dependency: plan-new-window.md needs this plan for its smoke test of a second window. This plan does not need plan-new-window.md: its smoke test starts a second process of the test app itself, the way the test already starts the first, and that process is one window with one connection whatever plan-new-window.md does to windows inside a process. The second process runs as a second app on Linux because the native app creates its `GtkApplication` with `G_APPLICATION_NON_UNIQUE` (`packages/ziggy/native/linux/src/lib/native-app.zig` line 114), which holds when this plan is implemented, since plan-new-window.md comes after it. A later change that makes the Linux app unique hands a second process's start to the first process, so whichever plan makes that change also has to keep step 4's scenario starting a second app of its own; it runs in the whole suite, so such a change fails it. No sibling plan is needed by this one.

    - `export interface ILineTarget { window: number; text: string; }`: the window the line goes to and the text to send the app. Each field gets a comment block.
    - `export interface IInvalidWindowError { name: "InvalidWindow"; text: string; }`: a line whose `window` is not a whole number from 1 to `WINDOW_COUNT_MAX`, with the line as it came.
    - `type JsonValue = object | string | number | boolean | null;` (not exported), with a comment block saying it is what `JSON.parse` can return, named so the parsed value is typed without `any`, `unknown` or a cast.
    - `export function readTarget(text: string): Result<ILineTarget, IInvalidWindowError>` (using `Result`, `ok` and `err`, which the file already imports from `./result`). It parses the line with `JSON.parse` inside `try`/`catch` (see Notes for why the catch is allowed), into a variable declared `let parsed: JsonValue;`. The plain-object check is `typeof parsed === "object" && parsed !== null && !Array.isArray(parsed)`. The object's keys are read with `const fields: Map<string, JsonValue> = new Map(Object.entries(parsed));`, the window is `fields.get("window")` when `fields.has("window")`, and the text without it is `fields.delete("window")` then `JSON.stringify(Object.fromEntries(fields))`, which keeps the other keys in their order. This shape was type-checked with the package's `tsc` settings (`strict`) and run under Bun while the plan was checked. A line that does not parse, or parses to something other than a plain object (`null`, an array, a string or a number), is `ok({ window: 1, text })` with the text unchanged, so the app still answers it with `InvalidCommand` (scenario `7-control-reports-bad-commands`). An object without a `window` key is `ok({ window: 1, text })` with the text unchanged, byte for byte. An object with a `window` key that is a whole number (`Number.isInteger`) from 1 to `WINDOW_COUNT_MAX` is `ok({ window, text: JSON.stringify(<the object without its window key>) })`. That text is the parsed value written again, so it can differ from the script's bytes: an integer beyond 2^53 comes out rounded, a number spelling (`1.0`, `1e2`) comes out as `JSON.stringify` writes the number (`1`, `100`), a string escape comes out as `JSON.stringify` writes it, and a key given twice comes out once with its last value. Notes says why that is accepted. Say so in the comment block above `readTarget`. Any other `window` value (0, a negative number, a fraction, a string, `null`, a number above `WINDOW_COUNT_MAX`) is `err({ name: "InvalidWindow", text })`. Assert that the text has no newline, and that an `ok` window is a whole number from 1 to `WINDOW_COUNT_MAX`.

## Unit Tests

- `remote-control-server.test.ts`, `describe("readTarget")`: a line that is not JSON, a JSON array, a JSON string, a JSON number and `null` are window 1 with the text unchanged; an object without `window` is window 1 with the text unchanged byte for byte (including spacing); `window` 1, 2 and `WINDOW_COUNT_MAX` give that window and the text without the `window` key, other keys in their order; a line with `"window":2` and other fields `"a":1.0`, `"b":1e2`, `"c":"A\/"`, `"d":9007199254740993` and `"e":1,"e":2` gives window 2 and exactly `{"command":"x","a":1,"b":100,"c":"A/","d":9007199254740992,"e":2}` (the line and the expected text are the ones in Notes), so the re-written text is pinned; `window` 0, -1, 1.5, `"2"`, `null`, `true` and `WINDOW_COUNT_MAX + 1` are `InvalidWindow` carrying the line.
- `remote-control-server.test.ts`:
    - A line with `"window":2` reaches app 2 without the `window` key, and app 2's reply reaches the script.
    - Lines to window 1 and to window 2 sent before either replies: app 2 replies first and app 1 second, and the script gets each reply as it is sent, in that order.
    - A line for window 2 sent while only window 1 is connected waits, and app 2 receives it when it connects. The script sends the window 2 line and then a line with no `window`, and app 2 connects only after app 1 has received the second line, so the server has already put the first one in the waiting list (it reads one script connection's lines in order). App 1 receives only its own line.
    - An app connecting while lines for another window wait gets only its own window's lines, and the others keep waiting. App 1 connected. The script sends `{"command":"for-three","window":3}` and then `{"command":"one"}`; once app 1 has received `{"command":"one"}`, the window 3 line is in the waiting list.     - Windows 1 and 2 connected. Window 1 receives a line and closes without answering: the script gets `AppDisconnected`, and window 2 still relays a line and its reply. A third app then connects, and a line with no `window` reaches it, so it took number 1.
    - With `WINDOW_COUNT_MAX` apps connected (each through `connectApp`, one after another), one more app is closed by the server and the error naming the limit and the port is written.     - `lowestFreeWindow`, on a `Map<number, string>`: 1 for an empty map, 2 when 1 and 3 are held, `undefined` when every number from 1 to `WINDOW_COUNT_MAX` is held.

## Notes

- The app's core (`packages/ziggy/core/src/lib/remote-control.zig`), the native apps and the frontends do not change. The feature list has the server number the apps and route the lines, and the server takes the `window` key off before it sends the line, so the app never sees it and its handling of every command (`handleLine` parses the whole line and passes it on) is the same.
- The feature list settles that the server accepts more than one app, numbers them from 1 and sends a command with no `window` to window 1. Accepting many apps means a new app can no longer replace the connected one.
- Settled by the human, not to be reopened: a window that disconnects frees its number, and the next app to connect takes the lowest free number (the feature list's "in connect order" holds only while no window closes); there is no command that lists connected windows; a command to window N waits for it to connect.
- A line for a window that is not connected waits for it with the same timeout (`appWaitTimeoutMs`, which `APP_WAIT_TIMEOUT_MS` in `tools/remote-control-server/src/index.ts` sets for the smoke tests) and limit (`WAITING_LINES_MAX`) as a line waits for window 1 today, and then gets the existing `AppNotConnected`. So `wait_for_ready 2` straight after starting the second app waits for it to connect, with no list command and no polling for it.
- `readTarget` and its types go in `remote-control-server.ts`, the one file that uses them, with their tests in its existing test file: `rules/typescript.md` puts code in a new `src/lib/` file only when two or more files use it, and Ziggy's `CLAUDE.md` says not to make a new file only to test it.
- `readTarget` catches the exception `JSON.parse` throws. Ziggy's `CLAUDE.md` bans adding exception handling unasked, and `rules/typescript.md` allows catching a third-party exception where the code acts on it. `JSON.parse` has no form that does not throw, and a line that is not JSON is expected input (scenario `7-control-reports-bad-commands` sends one) that the catch sends to window 1 unchanged, as the existing `listen` catches what `server.listen` throws.
- The new scenario prints no usage when run with no arguments, though `rules/general.md` asks that of a shell script: the runner (`smoke-tests/run.sh` line 104) runs every scenario with no arguments, so usage on no arguments would stop every run. It takes no arguments, as every existing scenario does, and its `test.md` says so.
- `wait_for_ready` with a window fails at once on `AppNotConnected` instead of sending `ready` again, because a second `ready` would wait the server's whole timeout again for a window that has had that whole timeout to connect, and the global rules ask that failures be loud. With no window it keeps today's behaviour, so the first window of every scenario starts exactly as it does today. It is defined here, where the helper gains its window argument, so `plan-new-window.md` does not change it.
- `control`'s read timeout stays as it is. A window that never connects fails the scenario whichever comes first: `control`'s read timing out (it names the command) or the server's `AppNotConnected` reply reaching `wait_for_ready` (it names the window). Neither failure depends on which timeout is longer, so no check ties the read's timeout to `APP_WAIT_TIMEOUT_MS`.
- `readTarget` writes a line that names a window again from its parsed value, because taking the key out of the text needs a JSON parser and `JSON.parse` with `JSON.stringify` is the one the server has. The changed text was checked under Bun while the plan was fixed: `{"command":"x","window":2,"a":1.0,"b":1e2,"c":"A\/","d":9007199254740993,"e":1,"e":2}` became `{"command":"x","a":1,"b":100,"c":"A/","d":9007199254740992,"e":2}`. Number spellings and string escapes give the same JSON values, so no command changes. The app's commands in `handleLine` (`packages/ziggy/core/src/lib/remote-control.zig`) read no integer field, and a command the app passes to the frontend (`callUi`, which embeds the command's text in a `test-ui-command` message) becomes a JavaScript value there, whose numbers are doubles, so an integer beyond 2^53 is rounded the same way whichever text it came from. A key given twice is the one change a command can see: the app parses a line with Zig's `std.json` defaults, whose `duplicate_field_behavior` is `.@"error"` (`lib/std/json/static.zig`), so it answers such a line `InvalidCommand`, while after `readTarget` the line runs with the key's last value. That applies only to lines that name a window, which no existing script sends, and the README states it (step 7).
- `restart_test_app` starts a new remote control server with `stop_remote_control_server` and `start_remote_control_server`, which the harness already has. It follows from the human's settled numbering (a closed window's number is free only once the server sees its connection end) and the rules' ban on races and waits in tests: keeping the old server would make the restarted app's number depend on event order, and with no list command a script cannot wait for the old connection's end, so a new server is the race-free way, not a choice left open. The old server frees window 1 only in `releaseApp`, which runs when it sees the old connection end, and nothing orders that before the new app's connection: on Android the server's connection is held by `adb reverse` (`smoke-tests/lib/android.sh` lines 150 to 155), not by the app, so the app's process having exited does not mean the server has seen the connection end; on a desktop nothing in the server orders the old socket's close against the new app's upgrade in its event loop. A new server has an empty `state.apps`, so `lowestFreeWindow` gives the new app 1 whatever the old server does. `stop_remote_control_server` closes the server's stdin pipe and waits for its process group to exit (`kill_process_group` in `smoke-tests/lib/process-control.sh`). `start_remote_control_server` truncates `remote-control-server.log` when it launches (`launch_in_process_group` writes with `>`), so it reads the new server's ports, not the old ones, and it exports the new `ZIGGY_REMOTE_CONTROL`, which every platform's `ziggy_platform_start` reads when it starts the app (`linux.sh`, `windows.sh`, `macos.sh`, `ios.sh`, `ios-device.sh` and the `adb reverse` in `android.sh`). The first server's log is overwritten by the second's.
- The smoke scenario does not check that a closed window's number goes to the next app: without a list command a script cannot see when the server has seen window 1's connection end, so starting another app straight after would be a race. The server test that closes window 1 with a line unanswered checks it without a race, because the script gets `AppDisconnected` only from `releaseApp`.
- A `window` that is not a whole number from 1 to `WINDOW_COUNT_MAX` gets `InvalidWindow` at once, because no app can ever connect as that window and waiting the server's whole app wait would hide the mistake. It follows from the bound the rules require (below) and the rule that failures are loud, so it is not a choice left open. The name follows the server's and the app's existing errors (`AppNotConnected`, `InvalidCommand`).
- `WINDOW_COUNT_MAX` exists because `rules/general.md` in agent-config requires a fixed upper bound on every loop and queue, as `WAITING_LINES_MAX` already bounds the waiting lines.
- `WINDOW_COUNT_MAX` limits both the numbers a line may name and the apps the server holds, so every window number a line can name is one an app can have.
- The server keeps one script connection at a time, as it does today. A scenario drives all its windows from one script.
- The scenario runs on Linux, Windows and macOS only, because Android and iOS run one instance of an app on a device.
- Only the test app's `smoke-tests/lib/common.sh` gains `window_control`: the template's has no restart and none of the template's scenarios uses a second window.- Ziggy's `CLAUDE.md` requires an upgrade note for every change that makes an app change its code or files. `## v0.0.23` is the newest heading in `docs/upgrade-notes.md` and the tag the example repositories pin, so this change goes under a new `## v0.0.24`.
- Lines without `window` are sent byte for byte, so every existing scenario and the unit tests that send lines that are not JSON (`first`, `quit`) behave as before. A line that is not a JSON object goes to window 1, so the app still answers it with `InvalidCommand`.
- The scenario starts its second app with `ziggy_platform_start` in a test directory of its own, so it works before plan-new-window.md is done and stays a test of the server once it is. Each app's processes are recorded through `launch_in_process_group` and stopped by the trap.
- The Linux native app creates its `GtkApplication` with `G_APPLICATION_NON_UNIQUE` (`packages/ziggy/native/linux/src/lib/native-app.zig` line 114), so a second process of the test app runs as a second app. The Overview says what a later change to that has to keep.
- Photosphere starts one server for each app instance and sends no `window`, so it needs no change. The example repositories start one app on one server and never restart it, so they need no change. Each takes the new server when it moves to the Ziggy release that contains it, which is outside this plan.
- The Ziggy repository needs no dependency on Photosphere or the example repositories, and they take nothing from it in this plan, so no local path dependency is needed.
