## Overview
Photosphere currently performs all image/video asset operations (dimensions, EXIF, resize, format convert, orientation transform, dominant colour, video probe, video screenshot) by shelling out to system-installed ImageMagick and ffmpeg from `packages/tools`. On mobile there is no Node runtime and no system binaries, so the mobile worker bundle aliases the whole `tools` package to `packages/mobile-worker/src/shims/stub-tools.ts`, which throws NOT IMPLEMENTED. This plan wires real in-process ImageMagick and ffmpeg into the iOS and Android apps using the proven approach from the sibling prototype repo `capacitor-ffmpeg-imagemagick-prototype`, exposed to the embedded JS engine through three new `host.*` bridge functions, with a self-contained mobile `Image`/`Video`/`getFileInfo` replacement that builds the exact argv and parses the exact output. Electron and CLI are untouched and keep using their locally installed binaries. The mobile apps ship and call the built-in libraries.

## Approach and key decisions
- Reuse the prototype's command-string (argv) model exactly. The native side runs an in-process entrypoint that accepts argv: ImageMagick via the `MagickCommandGenesis(... MagickImageCommand ...)` C shim (`run_magick`), ffmpeg/ffprobe via the FFmpegKit fork's `executeWithArguments`. argv is built in shared TypeScript with the tool name omitted; the native runner prepends `magick`/`ffmpeg`/`ffprobe`.
- Integrate through the existing `host.*` bridge, NOT a Capacitor `MediaTools` plugin. Photosphere asset operations run inside the embedded JS engine (JavaScriptCore on iOS, QuickJS on Android) as background tasks, which reach native only via `globalThis.host`. The prototype's WebView Capacitor-plugin surface is therefore re-homed as three synchronous host functions.
- Keep desktop/CLI `packages/tools` completely unchanged (no refactor to make its execution pluggable). Instead replace the mobile-only `stub-tools.ts` with a real host-backed implementation that mirrors the public API the `node-api` consumers use. This duplicates the small amount of output-parsing logic but isolates all change to the mobile worker and removes any risk to the working desktop path. The alternative (refactor `tools` to inject a runner) was rejected as more invasive.
- Cross the bridge with the existing conventions: argv in as a JSON string, result out as a JSON string `{ exitCode, output }`, errors as the `@@HOSTERR@@<code>:<message>` envelope decoded by `callHost` in `packages/mobile-worker/src/shims/host-access.ts`. All file paths are real absolute filesystem paths (no base64), sandbox-checked by the existing `PathSandbox`, matching how `host.fs*` already works.
- The mobile `Image`/`Video` already know the output path they passed in argv, so success is validated with `host.fsAccess(outputPath)` and `exitCode === 0`; the prototype's last-argv-token output heuristic is not needed.

## Steps

### Phase A: TypeScript seam and host contract (no native dependency, fully unit testable)

1. Add argv builders to the mobile worker. Create `packages/mobile-worker/src/lib/media-commands.ts` porting the pure functions from the prototype's `tools/src/commands.ts`: `buildFfprobeInfoArgs`, `buildFfmpegScreenshotArgs`, `toFfmpegQuality`, `buildIdentifyDimensionsArgs`, `buildIdentifyExifArgs`, `buildGeometry`, `buildResizeArgs`, `buildSaveArgs`, `buildDominantColorArgs`, `buildDominantColorHistogramArgs`, `buildTransformArgs`, plus the `IScreenshotArgs`/`IResizeArgs`/`ISaveArgs`/`IHistogramArgs`/`ITransformArgs` interfaces. Match the repo code style (named interfaces with per-field `//` comments, 4-space indent, no single-char params). Each builder must compile and have a unit test before the step is complete.

2. Extend the host contract for media. In `packages/mobile-worker/src/lib/host-functions.ts`: add `imageMagick`, `ffmpeg`, `ffprobe` to the `IHost` interface (signature `(argvJson: string) => string`, each with a `//` comment), add the three names to `EXPECTED_HOST_FUNCTIONS`, and rely on the existing `buildHost`/`resolveHostFunction` so a platform that has not installed one still fails loudly with `notImplementedMessage`. Add a unit test asserting the three names are present in `EXPECTED_HOST_FUNCTIONS` and that `buildHost` stubs them when absent.

3. Add a media host-access helper. Create `packages/mobile-worker/src/shims/media-access.ts` with a named result interface `IMediaResult { exitCode: number; output: string; }` and a function `runMediaTool(hostFn: (argvJson: string) => string, argv: string[]): IMediaResult` that JSON-encodes argv, invokes the host function through `callHost` (so `@@HOSTERR@@` envelopes throw coded errors), and JSON-parses the result. Reuse `getFsHost`/`callHost` patterns from `host-access.ts`. Unit test it with a fake `globalThis.host` covering success, non-zero exit, and error-envelope.

4. Replace the stub with a real mobile tools implementation. Rewrite `packages/mobile-worker/src/shims/stub-tools.ts` (keep the filename so the bundler alias is unchanged, or rename to `mobile-tools.ts` and update `aliasMap`/`filter` in `build-bundle.ts`; prefer keeping the filename to minimise change) to export `Image`, `Video`, and `getFileInfo` whose public surface matches `packages/tools` as consumed by `node-api`:
   - `Image`: `constructor(filePath)`, `getInfo()`, `getDimensions()`, `getExifData()`, `resize(options, tempDir, uuidGenerator)`, `saveAs(outputPath, options?)`, `getDominantColor()`, `getDominantColorHistogram(colorCount?)`, `getDominantColors(colorCount?)`, `transform(options, tempDir, uuidGenerator)`, `getPath()`. Build argv with the Step 1 builders, run via `runMediaTool(getHost().imageMagick, argv)`, and parse `output` with the same parsing the desktop `Image` uses (dimensions split on space, EXIF `exif:Tag=value` lines, dominant `R,G,B`, histogram `%c` line regex). For file-producing ops, return the known output path after `host.fsAccess` confirms it exists.
   - `Video`: `constructor(filePath)`, `getInfo()`, `getDimensions()`, `getDuration()`, `extractScreenshot(outputPath, timeInSeconds?, options?)`, `getPath()`. `getInfo` runs `buildFfprobeInfoArgs` via `runMediaTool(getHost().ffprobe, ...)` and parses the JSON exactly like desktop `Video.getVideoInfo` (video/audio stream split, `r_frame_rate`, `duration`, `bit_rate`, `creation_time`, codecs). `extractScreenshot` runs `buildFfmpegScreenshotArgs` via `runMediaTool(getHost().ffmpeg, ...)`.
   - `getFileInfo(filePath, contentType)`: port `packages/tools/src/lib/file-info.ts` dispatch (`image/*` to `Image.getInfo`, `video/*` to `Video.getInfo`).
   - Keep the `AssetInfo`/`Dimensions`/`ResizeOptions`/`IImageTransformation` shapes identical to what `node-api` imports (re-import the types from `tools`/`utils` where they are type-only; types are erased so they do not pull native code into the bundle).
   - This file is the seam; it must compile and every method must have a unit test driven by a fake `globalThis.host`.

5. Confirm bundle wiring. Verify `packages/mobile-worker/build-bundle.ts` still aliases `tools` to this file, run `bun run build:bundle` in `packages/mobile-worker`, and ensure `mobile-worker-entry.ts` and the `node-api` `*.worker.ts` handlers compile against the new surface with no `tools` symbols missing. The committed `worker.bundle.js` and its copies into the iOS/Android asset dirs are regenerated by the existing `build:bundle`/`copy:bundle` scripts.

## Notes
- Source of truth for the native integration is the sibling prototype repo `capacitor-ffmpeg-imagemagick-prototype`, which already verified all nine operations (probe, screenshot, identify, exif, resize, convert, dominant, histogram, transform) on an iOS simulator and an Android emulator. This plan re-homes that code from a WebView Capacitor `MediaTools` plugin to three `host.*` bridge functions because Photosphere's asset work runs in the embedded JS engine, not the WebView.
- The single most important non-obvious technique to carry over verbatim: ImageMagick text output (`identify`/`info:`/EXIF/dominant/histogram) is captured by redirecting the process stdout file descriptor to a file around the `MagickCommandGenesis` call, then reading the file back. The `MagickCommandGenesis` metadata out-param was unreliable on device.
- Reentrancy: the stdout redirect is process-global, so concurrent ImageMagick calls across engine-pool slots must be serialised by a native lock (added in Steps 7 and 11). FFmpegKit captures per session and does not need this.
- All media paths are real absolute filesystem paths and must pass the existing `PathSandbox`; there is no base64 transfer for media (unlike `host.fsReadFile`). Inputs and outputs live under the same sandbox root the host fs uses.
- App size grows by roughly 18 MB (iOS static libs) and roughly 20 MB per ABI (Android `.so` plus ffmpeg). This is the expected cost of bundling the built-in tools and is what the user asked for.
- Licensing must be resolved and recorded (Step 16), not just noted: the upstream `arthenica/ffmpeg-kit` was retired and its binaries pulled in 2025, so this plan uses community forks (`ffmpeg-kit-full-spm` on iOS, `com.moizhassan.ffmpeg:ffmpeg-kit-16kb` on Android). The exact LGPL-vs-GPL status of each fork's ffmpeg build and any patent-encumbered codecs must be determined, and Photosphere's root `LICENSE`/third-party notices, the `README.md`, and the release-notes `body:` template in `.github/workflows/release.yml` updated to attribute and licence the bundled ImageMagick and ffmpeg builds (and ImageMagick's libjpeg/libpng/zlib delegates). ImageMagick itself is under its Apache-2.0-like licence. This is required before a public release but does not block implementation or testing.
- Desktop and CLI are intentionally not touched: `packages/tools` keeps shelling out to system-installed ImageMagick/ffmpeg, and the change is confined to `packages/mobile-worker` plus the two native app projects.
