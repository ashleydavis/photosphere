# Mobile Smoke Tests (Android and iOS Emulators, Driven From the Host)

## Overview
The desktop app has shell-driven smoke tests (`apps/desktop/smoke-tests/`) that launch the Electron app in test mode and drive it over HTTP through the `TestControlServer` (`apps/desktop/src/lib/test-control-server.ts`): the test scripts call `send_command <port> click '{"dataId":...}'` and the server forwards the command to the renderer over Electron IPC, where test handlers in `apps/desktop-frontend/src/index.tsx` manipulate the DOM by `data-id`. We want the same style of smoke tests for the Android and iOS Capacitor apps (`apps/android-frontend`, `apps/ios-frontend`), runnable on an emulator/simulator with the test scripts running on the host computer. This is feasible: the iOS simulator shares the host loopback, and the Android emulator is bridged to the host with `adb reverse` (app reaches host) and `adb exec-out` (host captures screen). The one structural difference from Electron is that a mobile app has no Node process, so the control server cannot run inside the app. Instead a small host-side control bridge presents the same HTTP command surface to the test scripts and relays commands to the app over a WebSocket that the app opens on launch in test mode. The DOM-driving logic is shared with the existing Electron renderer so the command behaviour is identical.

## Architecture
- Host control bridge: a Bun process started by the mobile `common.sh` `start_app`. It exposes the same HTTP endpoints as `TestControlServer` (`/ready`, `/navigate`, `/menu`, `/click`, `/long-press-click`, `/type`, `/screenshot`, `/get-value`, `/data`, `/create-database`, `/import-assets`, `/quit`) so the existing `send_command` helper and the test-script style are reused. It holds a WebSocket connection to the app, translates each HTTP command into a WebSocket message, awaits the app's reply, and returns the HTTP response.
- App test client: in test mode the WebView frontend opens a WebSocket to the host bridge (`ws://10.0.2.2:<port>` on Android, `ws://localhost:<port>` on iOS simulator). It runs the same DOM-driving test handlers the Electron renderer uses (click/type/long-press by `data-id`), now triggered by WebSocket messages instead of Electron IPC, and forwards console logs over the WebSocket. It posts a `ready` message once the app has loaded.
- Screenshots: the bridge's `/screenshot` shells out on the host (`adb exec-out screencap -p` on Android, `xcrun simctl io booted screenshot` on iOS), not through the app.
- Logs: the bridge writes app-forwarded log lines to `$tmp_dir/app.log` in the same `[LEVEL]` format the Electron app uses, so the existing `wait_for_log` and `check_no_errors` helpers work unchanged.
- Networking and lifecycle are handled per platform by `lib/android.sh` and `lib/ios.sh` (build, install, launch with test-mode flags, `adb reverse` / simulator loopback, stop).

## Steps

1. Extract the shared DOM test driver. Create `packages/user-interface/src/lib/test-driver.ts` exporting `installTestDriver(transport: ITestTransport): void`, where `ITestTransport` is a named interface with `onCommand(handler: (command: string, payload: any) => Promise<any>): void` and `sendLog(level: string, message: string): void`. Move the DOM-action logic currently inline in `apps/desktop-frontend/src/index.tsx` (the `test-click`, `test-long-press-click`, `test-type`, `test-drop` handlers that resolve elements by `data-id` and dispatch events) into named functions in this module (`doClick`, `doLongPressClick`, `doType`, `doDrop`, `getValue`). Keep behaviour identical.

2. Re-wire the Electron renderer to the shared driver. In `apps/desktop-frontend/src/index.tsx`, replace the inline handlers with a call to `installTestDriver` using an Electron-IPC-backed `ITestTransport` (commands arrive via `electronAPI.onMessage`, logs go via `electronAPI.log`). This proves the extraction is behaviour-preserving against the existing desktop smoke tests.

3. Create the host control bridge. Add `apps/mobile-smoke-tests/lib/control-bridge.ts` (Bun, run as a standalone process). It starts an Express HTTP server on `PHOTOSPHERE_TEST_PORT` with the endpoint set listed in Architecture, and a WebSocket server the app connects to. Each HTTP command is forwarded to the connected app as a JSON WebSocket message `{ id, command, payload }`; the app replies `{ id, ok, value | error }`; the bridge resolves the HTTP request from the reply. `/ready` returns ok once the app has sent its `ready` message. `/screenshot` and `/quit` are handled host-side (see steps 8 and 9). The bridge appends forwarded `log` messages to the file given by `PHOTOSPHERE_LOG_DIR`/`app.log`.

4. Add the mobile app WebSocket test client. Add `packages/user-interface/src/lib/test-driver-ws.ts` exporting `connectTestDriverWebSocket(url: string): void` that opens the WebSocket, builds an `ITestTransport` over it, calls `installTestDriver`, patches `console` to forward logs (mirroring the Electron test-mode console patch), and sends `ready` after first render. Add the test-mode detection and call into `apps/android-frontend/src/index.tsx` and `apps/ios-frontend/src/index.tsx`: when a test-mode flag and host/port are present, call `connectTestDriverWebSocket`.

5. Pass test-mode configuration into each app. Android: read launch-intent extras in `android/app/src/main/java/com/example/app/MainActivity` (test flag, host, port) and expose them to the WebView (inject a `globalThis.__PHOTOSPHERE_TEST__ = { host, port }` via `bridge.eval` on load, or a URL query parameter). iOS: read `PHOTOSPHERE_TEST_MODE` / `PHOTOSPHERE_TEST_HOST` / `PHOTOSPHERE_TEST_PORT` env vars in `ios/App/App/AppDelegate.swift` (these arrive via `SIMCTL_CHILD_*` on simulator launch) and inject the same global into the WebView. The frontend (step 4) reads `globalThis.__PHOTOSPHERE_TEST__`.

6. Create the shared mobile smoke-test harness. Add `apps/mobile-smoke-tests/lib/common.sh` modelled on `apps/desktop/smoke-tests/lib/common.sh`, reusing `find_free_port`, `send_command`, `wait_for_ready`, `wait_for_log`, `check_no_errors` verbatim where possible. Replace `start_app` / `stop_app` with versions that: start `control-bridge.ts` (Bun) writing to `$tmp_dir/app.log`, then call the platform launcher (`lib/android.sh` or `lib/ios.sh` selected by a `PLATFORM` env var) to install, launch, and wire networking; `stop_app` stops the app via the platform launcher and kills the bridge.

7. Implement the Android launcher `apps/mobile-smoke-tests/lib/android.sh`. Functions: `android_build` (`./android/gradlew assembleDebug` in `apps/android-frontend`), `android_install` (`adb install -r <apk>`), `android_launch <port>` (`adb reverse tcp:<port> tcp:<port>` then `adb shell am start -n com.example.app/.MainActivity --ez photosphereTestMode true --es photosphereTestHost 10.0.2.2 --ei photosphereTestPort <port>`), `android_screenshot <outfile>` (`adb exec-out screencap -p > <outfile>`), `android_stop` (`adb shell am force-stop com.example.app`). Include `adb wait-for-device` and a boot-completed poll.

8. Implement the iOS launcher `apps/mobile-smoke-tests/lib/ios.sh`. Functions: `ios_boot` (`xcrun simctl boot <udid>` + `xcrun simctl bootstatus <udid> -b`), `ios_build` (`xcodebuild -workspace ios/App/App.xcworkspace -scheme App -sdk iphonesimulator -derivedDataPath <dd>`), `ios_install` (`xcrun simctl install booted <App.app>`), `ios_launch <port>` (`xcrun simctl launch --terminate-running-process booted <bundleId>` with env `SIMCTL_CHILD_PHOTOSPHERE_TEST_MODE=1 SIMCTL_CHILD_PHOTOSPHERE_TEST_HOST=localhost SIMCTL_CHILD_PHOTOSPHERE_TEST_PORT=<port>`), `ios_screenshot <outfile>` (`xcrun simctl io booted screenshot <outfile>`), `ios_stop` (`xcrun simctl terminate booted <bundleId>`). No port forwarding needed (shared loopback).

9. Wire `/screenshot` and `/quit` in the bridge to the platform launcher. The bridge invokes the host screenshot command for the active `PLATFORM` and writes to the requested `outputPath`; `/quit` triggers the platform stop. This keeps the test-script command surface identical to desktop.

10. Add an initial mobile smoke test. Add `apps/mobile-smoke-tests/tests/1-launch-and-navigate/test.sh` that: starts the app, `wait_for_ready`, navigates (`send_command navigate`), asserts via `wait_for_log` that the expected page log line appears, takes a screenshot, and `check_no_errors`. This is the first end-to-end proof on both platforms; it depends only on the UI loading, not on database/import features.

11. Add root npm scripts. In the root `package.json` add `test:android` (`cd apps/mobile-smoke-tests && PLATFORM=android ./run.sh`) and `test:ios` (`PLATFORM=ios ./run.sh`), and a `run.sh` in `apps/mobile-smoke-tests` that discovers and runs `tests/*/test.sh` the way `apps/desktop/smoke-tests.sh` does. Do not add these to `test:all` yet (they need an emulator/simulator; see Notes).

12. Gate data-level commands until mobile features exist. In the bridge, `/create-database`, `/import-assets`, `/get-value`, and `/data` forward to the app over the WebSocket; the app handles them through its real code paths once the storage and background-task plans land. Until then those handlers reply with a clear "not implemented on mobile yet" error and the tests that need them are not added. Reference `plan-mobile-storage-options.md` and `plan-mobile-background-tasks-options.md`.

## Unit Tests
- `test-driver.ts`: test each extracted DOM action (`doClick`, `doLongPressClick`, `doType`, `doDrop`, `getValue`) against a jsdom document with `data-id` elements, asserting the right element is targeted (including `nth`) and the right events dispatched. These also cover the desktop path since it now uses the same module.
- `test-driver-ws.ts`: with a mock WebSocket, assert it calls `installTestDriver`, forwards a received command to the driver and returns the reply with the matching `id`, sends `ready` after render, and forwards console output as `log` messages.
- `control-bridge.ts`: with a mock WebSocket client, assert each HTTP endpoint forwards the correct `{ command, payload }`, resolves on the matching reply, returns `ok:false` on an app error reply, that `/ready` blocks until the `ready` message, and that forwarded `log` messages are appended to `app.log` in the `[LEVEL]` format `check_no_errors` expects.

## Smoke Tests
- `apps/mobile-smoke-tests/tests/1-launch-and-navigate/test.sh` (step 10), run on an Android emulator and on an iOS simulator: launch in test mode, reach `ready`, navigate, assert the page log line, capture a screenshot, and `check_no_errors`.
- A bridge-only smoke test that runs without a device: start `control-bridge.ts`, connect a fake WebSocket client, drive every endpoint, and assert the HTTP responses and `app.log` contents. This makes the harness itself testable in CI with no emulator.

## Notes
- Feasibility (the original question): yes. iOS simulator shares the host network namespace, so the app reaches the host bridge on `localhost` and the host reaches the app's loopback directly. Android emulator uses `adb reverse tcp:<port> tcp:<port>` so the app reaching `10.0.2.2`/`localhost` lands on the host bridge, and `adb exec-out screencap` captures the screen. Both are driven entirely from host-run shell scripts.
- Why a host-side bridge instead of an in-app control server like Electron's: the app has no Node process, and binding an in-app HTTP server would need native server code (and likely a third-party library). Having the app open an outbound WebSocket needs only the standard WebView WebSocket API plus the existing shared DOM driver, and keeps the test-script HTTP command surface identical via the host bridge.
- Platform constraints: iOS smoke tests require macOS with Xcode and a booted simulator; Android requires the Android SDK/emulator and `adb`. Because of this they are kept out of `test:all` and run via dedicated `test:android` / `test:ios` scripts, mirroring how `test:stories` is excluded.
- Scope sequencing: the launch/navigate/screenshot/ready/log harness works with the current app. Database and import smoke tests depend on mobile storage and background tasks, so they are added after `plan-mobile-storage-options.md` and `plan-mobile-background-tasks-options.md` land; until then those bridge commands return a clear not-implemented error.
- Future option for Electron: the desktop smoke tests could later adopt the same model (host-side control bridge connected to the app over a WebSocket), which would let the `TestControlServer` be removed from the Electron main process entirely. That is a security win: no test-only HTTP control server is compiled into or runnable inside the shipped app. It is out of scope here because Electron has a working in-process server and Node-only capabilities (worker-pool task ops, `capturePage`, app lifecycle) that would need re-homing first; noted as a possible future convergence once the mobile bridge and shared DOM driver exist.
- The app bundle id is `com.example.app` in both native projects today; the launcher scripts use that. If the id changes, update `lib/android.sh` and `lib/ios.sh`.
- Emulator/simulator provisioning (creating an AVD, selecting a simulator UDID) is assumed to be done by the environment; the launcher scripts boot and wait for an already-installed emulator/simulator and fail with a clear message if none is available.
