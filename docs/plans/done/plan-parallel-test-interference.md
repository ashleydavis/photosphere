# Find test scripts that interfere with each other when run in parallel

## Overview

`bun run test:everything` runs the suites concurrently, so any two of them that touch the same file, port, directory, lock or device can fail each other in ways that never show up when the suite is run alone. That is a distinct failure class from ordinary flakiness: the suite is not unreliable in itself, it is unreliable in company. Today nothing detects it. `scripts/test-everything-parallel.sh` encodes two hand-found conflicts in `SERIAL_GROUPS` (the Android pair and the iOS pair, which share a build directory), and those were found by being bitten, not by testing for it. This plan adds `scripts/check-parallel-tests.sh`, which runs every script alone to establish a baseline, then runs every combination concurrently, and reports only the failures that appear in company and not alone. It also adds a harness test that proves the detector actually detects, using fixture scripts that collide on purpose.

This matters because that concurrency is on the commit path, not in an optional tool. `.githooks/pre-commit` runs `bun run test:everything`, which is `bun tools/what-changed/src/cli.ts` (`package.json:23`); the gate works out which targets are stale and then execs the runner named in `what-changed.json` with those target names appended (`tools/what-changed/src/lib/gate.ts:85`), and that runner is `scripts/test-everything-parallel.sh`. Every commit that touches code therefore goes through the parallel runner, so a pair of suites that interfere produces a refused commit that looks like a real failure and is not reproducible when the suite is rerun alone.

The scripts to cover are `test`, `test:cli`, `test:electron`, `test:and` and `test:ios`. `test:and` is included on any platform where the Android tooling is installed rather than on Linux only, and `test:ios` only on macOS. Note that this is deliberately wider than the gate's own view: `what-changed.json` pins `test:and` to `platforms: ["linux"]` and `test:ios` to `platforms: ["darwin"]`, but the check is hunting for contention, so it should cover any suite the machine can actually run.

Every combination is checked, including a script against itself (`test` with `test`). A self-pair is not a hypothetical: nothing in `test:everything` runs one suite twice at once, but two worktrees, two developers on one machine, or a rerun started before the last one finished all do, and `docs/flaky-tests-registry.md:141` already records a failure caused by another worktree's Electron suite announcing on the LAN during this one's discovery window. Self-pairs are also the cheapest way to surface a fixed path or a fixed port, because a suite that hardcodes one is guaranteed to collide with a second copy of itself.

`scripts/find-flakey-tests.sh` is the model for how this script behaves, because it is the same kind of instrument aimed at the neighbouring problem: it hunts a suite that is unreliable alone, this one hunts a suite that is unreliable in company. Everything it learned about running the real suites in a loop on this machine applies here unchanged, and most of it was learned the hard way. Specifically, this plan copies its shape in seven respects: a timestamped session directory under `tmp/` so a new run never destroys an older one's evidence; a header comment block that is the usage text, printed by `--help`; strict argument validation that rejects an unknown name with the valid ones listed; a table of distinct exit codes so an infrastructure halt is never mistaken for a real finding; an interactive prompt when it is run by hand with a terminal attached and no selection given; treating a crash of the Bun runtime as a retry rather than a result; and, on failure, a `report.txt` that names what failed, quotes the useful part of a very long log, snapshots the per-test logs the next attempt would overwrite, and records the state of the machine.

That last one is not decoration. `scripts/find-flakey-tests.sh` records that several of the failures it found were caused by the machine and not the code (the kernel's out-of-memory killer taking an emulator, an emulator keeping its adb connection while losing its route to the host), and this check is a heavier workload than that one: it deliberately runs two suites at once, over and over, which is the exact workload that has exhausted this machine's memory before. A run that reports `interference` because the out-of-memory killer took one side is worse than no result, because it sends someone hunting a shared resource that does not exist. The machine state has to be in the report for the verdict to be worth anything.

Four of its functions are wanted here verbatim (`capture_machine_state`, `snapshot_suite_logs`, `summarise_failure` and `check_devices_healthy`), so this plan extracts them into `scripts/lib/diagnostics.sh` and has both scripts source it rather than growing a second copy. That is a net gain in safety rather than a risk taken for tidiness: `scripts/find-flakey-tests.sh` has no automated test today (nothing in the repository references it except `package.json`), and the harness test added here would be the first coverage those four functions have ever had.

## Issues

## Steps

1. **Extract the shared diagnostics out of `scripts/find-flakey-tests.sh` into `scripts/lib/diagnostics.sh`.** Move `capture_machine_state`, `snapshot_suite_logs`, `summarise_failure` and `check_devices_healthy` across unchanged, along with the `BUN_CRASH_PATTERN` constant, and have `scripts/find-flakey-tests.sh` source the new file. `scripts/lib/` does not exist yet and this creates it. Take nothing else: the loop, the streak counting and the resume flags stay where they are, since only these four are wanted by both callers. Note that `docs/plans/new/plan-fix-leaked-test-processes.md` separately proposes `scripts/lib/process-control.sh` in the same directory; the two are independent files and neither plan blocks the other. Requires `bash -n` on both files, plus `bun run find-flakey-tests -- --command "true" --target 1` to reach its green exit and `--command "false"` to produce a report naming the failure, which is the only way to show the extraction did not break the script it came from. That script has no test today, which is exactly why this step must not be taken on trust.

2. **Create `scripts/check-parallel-tests.sh` with its header, argument handling and script list.** Follow the shape of `scripts/find-flakey-tests.sh`: a header comment block that is the usage text (purpose, usage examples, an option list, where output goes, and the exit status table), `set -uo pipefail`, and a `ROOT` resolved from `BASH_SOURCE` so it runs from any working directory. Accept `--runs N` (default 3), `--scripts "a b c"` (default the fast set: `test test:cli test:electron`), `--include-mobile`, `--pairs-only`, `--baseline-only`, `--command`, and `--help`. Any script name may be passed via `--scripts`, including ones outside the default set (`compile`, `test:and:unit`, `test:ios:unit`), which is how step 14's positive control selects the two `SERIAL_GROUPS` pairs. Validate arguments strictly the way `scripts/find-flakey-tests.sh` does: reject an unknown option and an unknown script name by naming the valid choices, and reject a `--runs` that is not a positive whole number, rather than failing thousands of seconds later. Requires `bash -n` to pass.

3. **Give `scripts/check-parallel-tests.sh` a `--help` that cannot go stale.** `scripts/find-flakey-tests.sh` prints its header with `sed -n '3,89p'` over hardcoded line numbers, and carries a comment recording that the range went stale once and silently truncated `--target` out of the help. Do not copy that. Delimit the header block with a sentinel line and have `print_usage` select between the sentinels, so the help cannot be truncated by the header growing. Requires case (g) of the harness test in step 12 asserting that `--help` output contains the last option in the header block.

4. **Give `scripts/check-parallel-tests.sh` a timestamped session directory and an exit status table.** Write everything under `tmp/parallel-check/<timestamp>/` in the repository root, stamped from `date +%Y%m%d-%H%M%S` exactly as `scripts/find-flakey-tests.sh` does, so a new session can never write over an older one's evidence; `tmp/` is already gitignored. The script must create directories and write new files only, and must never delete, clear or overwrite an existing path. Define and document distinct exit codes, following that script's precedent and extending it: 0 no interference found, 1 interference found, 2 bad usage, 3 too many Bun crashes, 4 the emulator pool degraded so the run was abandoned, 5 a script was `unstable-alone` so the answer is inconclusive. Distinct codes are the point: a caller must be able to tell "found a real conflict" from "the machine gave up", and `scripts/find-flakey-tests.sh` shows why this matters, since its own header lists only codes 0 to 3 while the code also exits 4 for a degraded pool. Print `LOGS=`, and on failure `REPORT=`, as the last lines of stdout the way that script does. Requires `bash -n` to pass.

5. **Add mobile suite detection to `scripts/check-parallel-tests.sh`.** `--include-mobile` adds `test:ios` only when `uname -s` reports `Darwin`, and adds `test:and` on any platform where the Android tooling is present rather than on Linux alone, so a macOS machine with Android Studio installed checks both. Detect Android by probing for the tooling the suite actually needs (`adb` on `PATH` or under `$ANDROID_HOME`/`$ANDROID_SDK_ROOT`) and then by `bun run emu:and:status` reporting a ready device, and skip `test:and` with a printed reason when either probe fails rather than adding it and letting every pair containing it fail. Print the resolved script list before running anything, so a run that quietly covered less than expected is visible at the top of its own output. Requires `bash -n` to pass.

6. **Add the interactive prompt for a hand-run invocation.** Copy the shape of `prompt_for_selection` in `scripts/find-flakey-tests.sh`: when no selection was given and a terminal is attached (`[ -t 0 ]`), ask which scripts to check, offering the fast set and the mobile-inclusive set as numbered choices, then ask for `--runs`. The terminal check is what keeps a scripted or CI invocation from blocking forever on input that will never arrive, and the harness test depends on that, since it always passes a selection. Requires the harness test to confirm that a run with `--scripts` given never prompts.

7. **Add baseline mode to `scripts/check-parallel-tests.sh`.** Add a function `run_alone` that runs one script by name via `mise exec -- bun run <script>` from the repository root, capturing combined output to `<session-dir>/alone-<script>-<attempt>.log` and recording its exit code to a sibling `.exit` file, repeated `--runs` times. Going through `mise exec` matches `scripts/find-flakey-tests.sh:457` and both branches of `run_script` in `scripts/test-everything-parallel.sh`, so the suites run against the pinned toolchain rather than whatever is first on `PATH`. Add `baseline_verdict`, which reads those exit files and prints one of `clean` (every attempt passed) or `unstable-alone` (any attempt failed) per script. A script that is `unstable-alone` is ordinary flakiness and must be excluded from combination classification, because it cannot be shown to have been broken by a partner. Requires `bash -n` to pass and the harness test from step 12 to cover both verdicts.

8. **Add combination mode to `scripts/check-parallel-tests.sh`.** Add `generate_pairs`, which prints every unordered combination of two of the selected scripts, one per line, **including self-pairs** (`test` with `test`), since two copies of one suite are exactly what a second worktree or an overlapping rerun produces. For n scripts that is n(n+1)/2 lines. Add `run_pair`, which starts both sides concurrently as background jobs from the repository root, waits for both, captures each side's output to `<session-dir>/pair-<a>-<b>-<side>-<attempt>.log`, and records both exit codes. The `<side>` component must be part of the filename for every combination, not only self-pairs, so the two sides of `test` with `test` never write the same path. Repeat each combination `--runs` times. Both sides must be started as close together as possible so their setup phases overlap, since that is where fixed paths and fixed ports collide. Requires `bash -n` to pass.

9. **Treat a Bun runtime crash as a retry, not a result, and stop when the emulator pool degrades.** Both behaviours come straight from `scripts/find-flakey-tests.sh` and both exist to stop the check reporting a finding it did not find. Match the run's output against the shared `BUN_CRASH_PATTERN` from step 1: a crash of the Bun runtime is not one suite breaking another, so the attempt is retried under the same number rather than counted, up to five consecutive crashes, after which the run stops with exit 3. Every crash is listed in the summary so none passes unnoticed. Separately, when the script set includes `test:and`, record the attached device count at the start and call `check_devices_healthy` between attempts, stopping with exit 4 and a message naming the combination reached when the pool has degraded. This function only ever reads, and must never start, stop or reconnect a device. Without both of these, an out-of-memory kill or a lost emulator is recorded as `interference`, which is the most expensive possible wrong answer here: it names an innocent pair and sends someone looking for a shared resource that does not exist.

10. **Add classification and the summary report to `scripts/check-parallel-tests.sh`.** Add `classify_pair`, which combines the baseline verdicts with the pair exit codes and yields exactly one of: `ok` (both sides passed every attempt), `interference` (both scripts are `clean` alone but at least one side failed when paired), or `inconclusive` (at least one script is `unstable-alone`, so the pair result proves nothing). A self-pair classifies by the same rule and is reported the same way: a script that is `clean` alone and fails against a second copy of itself is `interference`, and the summary must name it as a self-pair rather than hiding it among the rest. Add `print_summary`, which prints a table of combination, verdict, failing side and the path of the first failing log, sorted so every `interference` row comes first. Exit 1 when any combination is `interference`, 5 when none is but some were `inconclusive`, and 0 otherwise. Print an explicit count of combinations skipped as `inconclusive` rather than silently dropping them. Requires `bash -n` to pass.

11. **Write a `report.txt` on an `interference` verdict, following the failure report in `scripts/find-flakey-tests.sh`.** Into `<session-dir>/report.txt` write a header block naming the combination, which side failed, the attempt number, the exit codes of both sides, the baseline verdicts that make the finding meaningful, and the session directory; then `summarise_failure` over the failing side's log, so a multi-thousand-line build log is reduced to the failing lanes, the named failing tests and the tail of the run; then `capture_machine_state`, so memory, attached devices and recent kernel out-of-memory kills are attached to the verdict. Call `snapshot_suite_logs` before the next attempt starts, because the mobile and desktop suites clear their per-test logs at the start of each run and those logs are the evidence for why the side failed. All four functions come from `scripts/lib/diagnostics.sh` and are not reimplemented here. Print the report to stdout as well as writing it, and end with `REPORT=`, `LOGS=` lines.

12. **Create `scripts/check-parallel-tests.test.sh`, the harness test, following the shape of `apps/smoke-tests/android-lock.test.sh` and `apps/smoke-tests/runner.test.sh`.** It must drive `scripts/check-parallel-tests.sh` against fixture commands rather than the real suites. Use the `--command` escape hatch from step 2 for this, the way `scripts/find-flakey-tests.sh` documents its own `--command` as the thing "the harness's own tests use to drive the loop against commands with known outcomes": a fixture is then a shell command with a known outcome rather than a fake bun package that has to be installed to be named. Cover eight cases: (a) two fixture commands that touch nothing in common, expected verdict `ok`; (b) two fixture commands that both write and then read back one fixed path under the session's own fixture directory, so concurrent runs corrupt each other, expected verdict `interference`; (c) a fixture command that fails on a fixed proportion of attempts when run alone, paired with a clean one, expected verdict `inconclusive` and not `interference`, and exit 5 not 1; (d) exit 1 for case (b) and exit 0 for case (a); (e) a fixture using a fixed path is `interference` against a second copy of itself, a fixture using a per-process path is `ok` against itself, and the combination list for n fixtures has n(n+1)/2 entries, which proves self-pairs are generated rather than dropped; (f) a fixture command that prints text matching `BUN_CRASH_PATTERN` and exits non-zero is retried rather than classified, and appears in the crash list, and a fixture that does so five times running exits 3; (g) an unknown option and a non-numeric `--runs` each exit 2 with the valid choices named, and `--help` exits 0 and contains the last option in the header block; (h) a run given `--scripts` produces no prompt and completes with no terminal attached. The fixtures must create files only, never delete them. Requires the harness test to pass.

13. **Watch each assertion in `scripts/check-parallel-tests.test.sh` fail before accepting it.** For each of the eight cases, temporarily break the thing it covers, confirm the test reports failure, then restore. Specifically: make `classify_pair` always return `ok` and confirm cases (b) and (e) fail; make it always return `interference` and confirm cases (a) and (c) fail; make `print_summary` always exit zero and confirm cases (d) and (c) fail; make `generate_pairs` exclude self-pairs and confirm case (e) fails; remove the crash pattern match and confirm case (f) fails; accept an unknown option silently and confirm case (g) fails; remove the `[ -t 0 ]` guard and confirm case (h) hangs or fails. Record in the plan's Notes that this was done, naming the four extracted functions in `scripts/lib/diagnostics.sh` as now covered where they were not before. A test that has only ever passed does not count as complete for this step.

14. **Add the positive control over the real suites.** Add a `--serial-groups-are-expected` flag that marks the pairs named in `SERIAL_GROUPS` in `scripts/test-everything-parallel.sh` (`test:and:unit` with `test:and`, and `test:ios:unit` with `test:ios`) as expected interference: they are reported, and are not counted toward the non-zero exit. Read those pairs by parsing the `SERIAL_GROUPS` array out of `scripts/test-everything-parallel.sh` at run time rather than restating them, so the two cannot drift apart. `scripts/test-everything-parallel.sh` is frozen and must not be edited; this step only reads it. These pairs are known to conflict, so a run that does not report them means the detector is not working. Note that `test:and:unit` and `test:ios:unit` are not in the default script set, so this control must be run with them named explicitly, for example `--scripts "test:and test:and:unit" --serial-groups-are-expected`.

15. **Add the entry points to `package.json` at the repository root.** Add `"test:parallel": "bash ./scripts/check-parallel-tests.sh"` and `"test:parallel:self": "bash ./scripts/check-parallel-tests.test.sh"`. Do not attempt to add either to the default script list in `scripts/test-everything-parallel.sh`: that file is frozen, so the harness test is wired into CI in the next step instead. Give it a `timeout-minutes` value in line with the other small harness jobs. Add a rule stating that a mode only belongs in this section when the detector classified it `interference`, meaning both scripts passed alone and failed together, and that a mode reproducible from a single script alone belongs in the existing section instead. State plainly that `inconclusive` means ordinary flakiness masked the answer and that `bun run find-flakey-tests -- --script <name>` is the thing to run first in that case, since the two tools are a pair: one proves a suite is sound alone, the other proves it is sound in company, and the second is only meaningful once the first has passed. ## Unit Tests

The deliverable is shell, so it carries no new TypeScript functions and therefore no Jest tests. This matches the existing precedent for shell harnesses in this repository (`apps/smoke-tests/android-lock.sh` is covered by `apps/smoke-tests/android-lock.test.sh`, and `apps/smoke-tests/lib/runner.sh` by `apps/smoke-tests/runner.test.sh`), and the coverage requirement is met by the harness test in step 12 rather than by Jest.

If any step turns out to need something shell genuinely cannot do (the repository's rule allows a TypeScript helper only in that case, as a real file under `scripts/` invoked as `bun scripts/<name>.ts`), then that helper gets a Jest test under the owning package's `src/test` directory covering every exported function, and this section must be updated to name it before the step is considered complete.

## Notes

- `scripts/test-everything-parallel.sh` is frozen by the repository rules and must not be edited by any step here. Step 14 reads it, which is allowed, and step 15 explains why the harness test cannot be added to its default script list. This is also why the check is a new script rather than a mode added to the existing runner: the runner is on the commit path via `.githooks/pre-commit`, and its two defining behaviours (fail-fast, and `SERIAL_GROUPS` keeping the known conflicts apart) are the opposite of what this check needs, which is to run every combination to completion and to put the conflicting ones together on purpose.
- The check must invoke each suite directly through `bun run <script>` and never through `test:everything`. Going through the gate would write `.cache/what-changed`, which is shared mutable state, and concurrent gate runs would then be measuring the gate rather than the suites. It would also skip suites: the gate only execs the runner for targets it considers stale (`tools/what-changed/src/lib/gate.ts:78-85`), so a second run over an unchanged tree would run nothing at all and report a false `ok`.
- Candidate shared resources found while researching, useful for interpreting an `interference` verdict: fixed paths under `/tmp` used by several suites (for example `/tmp/test-run.log`, `/tmp/photosphere`, `/tmp/testing`); the Android device locks at `/tmp/photosphere-android-device-<serial>.lock`; the Capacitor and Gradle output inside `apps/android-frontend/android`; the equivalent Xcode project for iOS; and `apps/cli/test/tmp`, which `apps/cli/smoke-tests.sh` already allows to be moved with `TEST_TMP_DIR` precisely so parallel runs do not collide. Ports are largely safe already, since the harnesses bind port 0 and read the assigned port back, but a fixed port would show up here as an `interference` verdict.
- Cost is the main constraint. Including self-pairs, combinations grow as n(n+1)/2 rather than n(n-1)/2, so the three fast scripts are 6 combinations, adding `test:and` takes it to 10, and a macOS machine with both mobile suites reaches 15. Each is repeated `--runs` times, and the mobile suites take minutes per run. Default to the fast set, make `--include-mobile` opt-in, and expect a mobile-inclusive run to be an hours-long deliberate exercise rather than something run casually.
- Self-pairs are the highest-yield combinations and also the cheapest of the mobile ones to reason about, because a suite that hardcodes a path, a port or a device lock will always collide with a second copy of itself. Expect `test:and` against `test:and` to fail on the Android device lock, since the pool hands out a device per run; that is a genuine `interference` verdict about a real constraint, not a bug in the check, and it belongs in the registry with `Shared resource` naming the lock.
- `compile` was in an earlier draft of the default script set and has been dropped, because it is a build rather than a test and its contention with the suites is already covered by every suite building what it needs. It remains available through `--scripts` if it is ever worth checking.
- Memory is a real constraint on the development machine: running two heavy suites concurrently is the workload that has exhausted it before. The check should not be run with a large `--runs` alongside other work, and `--include-mobile` requires the emulator pool to already be up.
- `scripts/find-flakey-tests.sh` is not frozen, so step 1 may edit it, but it has no automated test and nothing in the repository references it except `package.json`. Treat it with the same care as a frozen file: move the four functions across unchanged, change nothing else about it, and run the two `--command` checks in the Smoke Tests section before accepting the step. Its own header comment lists exit codes 0 to 3 while the code also exits 4 for a degraded pool. Leave that alone rather than fixing it in passing; if it is worth correcting, it is a separate change with its own reason.
- Two features of `scripts/find-flakey-tests.sh` are deliberately not copied. Its streak model (`--target`, `--greens`, `--start`, requiring hundreds of consecutive green runs) does not transfer: a streak is how you prove an absence of flakiness, whereas this check is looking for a specific reproducible conflict, and `--runs` attempts per combination is the equivalent knob. Its `--test FILTER` narrowing is worth having later, once a combination has been flagged and the job is to shrink the reproduction from a two-suite pair to a two-test pair, but it is not needed to detect anything and would widen this plan for no gain in coverage.
- The check must never start, stop or restart an emulator. Per `apps/android-frontend/CLAUDE.md` that is the human's job, so when `bun run emu:and:status` does not report ready the check drops `test:and` from the script list and says so loudly, rather than trying to bring the pool up itself and rather than leaving it in and letting every combination containing it fail for a reason that is not interference. Dropping it must be reported at the top of the run and again in the summary, with the count of combinations not checked as a result, so a reduced run can never be mistaken for a clean one.
- No step here may write a destructive command. The check only creates directories and files, and the fixtures in the harness test do the same. Leftover fixture and log directories under `tmp/` are acceptable and must be left for the human to clear.
- Step 13 was carried out.
