# Stop the test scripts leaking Electron, Xvfb and CLI processes

## Overview

Test runs leave processes behind. Right now, with no test running, this machine holds 10 orphaned Electron processes and 2 orphaned `Xvfb` servers from a run that finished nearly three hours ago, about 1.5 GB, all reparented to init. An earlier accumulation of roughly 170 such processes holding ~8.8 GB was what pushed the machine into memory pressure and triggered `systemd-oomd` to kill 354 processes in one go, taking the Android emulator pool with it. This plan finds every path that stops a background process across all the test scripts, fixes them against one shared implementation, and adds a leak check that fails a suite which ends with more of its own processes alive than it started with, so a future regression is caught by the tests instead of by an out-of-memory kill weeks later. It also called for a reaper to clear leftovers a signal-killed run could never have cleaned up; that was built and then removed at the user's direction, and step 9 records what going without it costs.

**The cause this plan was written against was already fixed, and the plan is wrong about it.** It claimed that the per-test `cleanup` functions still `kill -9` the recorded pid and that none of them calls `kill_app_tree`. Neither is true any more: every desktop test reaches `kill_app_tree`, 27 of them directly and the remaining 6 through `stop_app`. The premise was checked against the code before implementation started and found stale, so step 5 became a consolidation rather than a fix.

The real defect is the one the plan identifies in its notes rather than its overview: a walk of the process tree cannot find what a leak leaves behind. `pgrep -P` asks the kernel who a process's children are, so it only works while the parent is alive. Once the parent dies the children are reparented to init and the walk reports an empty tree while the survivors sit there holding memory, which is precisely the situation being cleaned up after. That is why the process group, not the tree walk, is the substance of this work.

## Issues

## Steps

1. **Add the shared process-control library `scripts/lib/process-control.sh`.** New file, sourced by every test script that starts a background process. It must define, each with a `#` comment block above it per the repo style: `launch_in_process_group <log_file> <argv...>` which starts a command in its own process group where `setsid` is available and plainly in the background where it is not, and prints `<pid> <pgid>` for the caller to record, with the pgid field empty when no group of its own could be given; `process_group_of <pid>` which prints the pgid for a pid, empty when it cannot be read; `process_tree_pids <pid>` which prints the pid and every descendant deepest first, gathered before anything is killed; `kill_process_group <pgid>` which sends SIGTERM to the whole group, waits, then SIGKILL; and `kill_process_tree <pid>` which does the same over the tree walk. `kill_process_tree` must be the exact behaviour of the current `kill_app_tree` in `apps/desktop/smoke-tests/lib/common.sh` so that step 3 is a move rather than a change. The file must define functions only and must not act when sourced. `bash -n` must pass.

   Two things the plan did not anticipate, both required for correctness. `launch_in_process_group` must poll for the new group rather than reading it once: `setsid` changes the group between fork and exec, so a pgid read the instant the launch returns is still the launching shell's. And it must report an empty pgid whenever the observed group is the launching shell's own, with `kill_process_group` refusing that group outright and saying so, because that group holds the calling script: a suite that killed it would take out its own runner mid-run and report the damage as a test failure.

2. **Explain the group approach in that file's header comment.** State that the tree walk fails once a parent dies, because the children are reparented to init and `pgrep -P` then finds nothing, and that a process group survives reparenting, so killing the group is the reliable form and the tree walk is the fallback for platforms without `setsid` (macOS has no `setsid` binary). Do not restate this plan; a short paragraph.

3. **Make `apps/desktop/smoke-tests/lib/common.sh` use the library.** Source `scripts/lib/process-control.sh` near the top. Delete the local `process_tree_pids` and `kill_app_tree` definitions and keep `kill_app_tree` as a thin wrapper that prefers `kill_process_group` when a pgid was recorded for that pid and otherwise calls `kill_process_tree`, so the 19 call sites in step 5 have one name to use. Change `start_app` to launch through `launch_in_process_group` and to write the pgid to `$tmp_dir/app.pgid` next to the existing `$tmp_dir/app.pid`. Every existing behaviour of `start_app` must be unchanged: the same environment variables, the same `--no-sandbox --disable-gpu -geometry` arguments, the same `xvfb-run -a` wrapper decision, the same `app.log` redirection, and the same `wait_for_test_port` guard. `bash -n` must pass and `bun run test:electron` must pass before this step is done.

4. **Add `cleanup_apps` to `apps/desktop/smoke-tests/lib/common.sh`.** It takes any number of tmp directories and, for each, stops whatever that directory's `app.pid` and `app.pgid` describe, tolerating a missing file, a dead pid and a directory that was never used. This is the single function every per-test `cleanup` will call, so no test needs to know how a process is stopped.

5. **Replace the hand-rolled cleanup in every desktop test that has one.** The plan named 19 files; there are 27, because the suite has grown since it was written. Each holds the same three lines (`if [ -f "$TMP_DIR/app.pid" ]; then kill_app_tree ...; fi`), which become a single `cleanup_apps` call naming that test's tmp directories. The six two-app tests (`7-share-secret`, `8-share-database`, `29-share-database-cancel`, `30-receive-database-cancel`, `31-share-secret-cancel`, `32-receive-secret-cancel`) pass both `$TMP_DIR/sender` and `$TMP_DIR/receiver`; the plan named only the first two. The remaining 6 tests define no `cleanup` at all and trap `stop_app` directly, which routes through the same place, so they need no edit. Keep each test's `trap cleanup EXIT` exactly as it is. Change nothing else in these files. `bun run test:electron` must pass before this step is done.

6. **Give `apps/smoke-tests/lib/common.sh` the same treatment.** Source `scripts/lib/process-control.sh`, launch the `bun "$LIB_DIR/control-bridge-main.ts"` bridge through `launch_in_process_group`, record `$tmp_dir/bridge.pgid`, and change the pid-based kill inside `stop_app` to prefer that group and fall back to the tree walk. `bun` starts the bridge in a child process, so the current kill can orphan it exactly as the desktop one did. The existing `disown` goes, not by choice: launching through a process substitution means the bridge is never in this shell's job table, so there is no job to disown and no "Terminated: 15" notice for it to suppress.

   The plan also asked for a `trap cleanup EXIT` in `apps/smoke-tests/tests/28-host-emulator-comms/test.sh`, "the only one of the 41 mobile tests without one". **Not done, deliberately.** It is the only test without one because it is the only test that starts nothing: it runs two `adb` commands and exits. A trap there would have nothing to stop, and giving it one means either a no-op (a stub that pretends to work) or a call into the bridge-stopping machinery with an unset port. A comment in the file records why it has no trap and says to add one alongside the first `start_app` anyone puts there. `bun run test:and` must pass before this step is done.

7. **Fix the CLI suites.** In `apps/cli/smoke-tests.sh` the `TERM` trap the plan asks for already exists and routes to `handle_interrupt`, so that part is done; what is missing is that both it and `cleanup_and_show_summary` stop only the batch subshells themselves (`jobs -p | xargs kill`), leaving the CLI processes underneath them running and reparented to init. Both must take the whole tree of each job instead, and `cleanup_and_show_summary` must stop them at all, which today it does not. In `apps/cli/smoke-tests-lan-share.sh` delete the local `kill_tree` and use `kill_process_tree` from the library, keeping `kill_proc` and `test_cleanup` as they are, and give its `cleanup` the same tree treatment. In `apps/cli/hash-cache-smoke-test.sh` add an `EXIT`/`INT`/`TERM` trap that stops the backgrounded writers, which today has no trap of any kind. `bun run test:cli` and `bun run test:cli:hash-cache` must pass before this step is done.

8. **Use the library in `scripts/story-player.sh`.** Delete the local `collect_descendants`/`kill_capture_tree` implementation and call `kill_process_tree`. Its existing `EXIT`/`INT`/`TERM` traps stay. Do not change what the story player does or how it captures screenshots.

9. **The reaper. Built, then removed at the user's direction, and not part of this work.** The plan called for `scripts/reap-test-processes.sh` plus a `bun run reap` entry in the root `package.json`, to clear leftovers no trap could have cleaned up. It was written and it worked: scoped to this checkout by absolute path, restricted to orphans (parent pid 1 or the user's systemd manager), reaching an `Xvfb` through the X authority file of the leftover it belonged to, and reporting rather than killing unless given `--kill`. The user did not want it. The script and the `package.json` entry are gone, and the three suites no longer point at it in their leak-check output.

   What that leaves: a SIGKILLed run's leftovers have no automated cleanup path at all, which is exactly the case the plan says cleanup cannot cover. The leak check still reports them; stopping them is manual, via `ps` and `kill`. Anyone reconsidering should know the two matching rules that took the longest to get right. A worktree lives inside the checkout it was made from, so this checkout's path is a prefix of every worktree's path and a plain "contains the repo root" match claims their processes too; `<repo root>/.claude/worktrees/` has to be excluded explicitly. And a CLI process started by the lan-share suite runs as `bun run start`, whose command line names no absolute path at all, so it can only be claimed by its working directory, restricted to the programs the suites actually start or a shell left sitting in the repository becomes a candidate.

10. **Add the leak check and wire it into each suite.** Add `count_test_processes` to `scripts/lib/process-control.sh`, matching on this checkout's absolute path (and excluding `<repo root>/.claude/worktrees/`, so a worktree's run is never counted as this one's), and call it at the start and end of `apps/desktop/smoke-tests.sh`, `apps/cli/smoke-tests.sh` and `apps/smoke-tests/run.sh`. When the end count exceeds the start count the suite prints the surviving command lines and exits non-zero even if every test passed, because a suite that leaks has failed. The comparison must tolerate another worktree's concurrent run by matching this repo root only. Do not add this to `scripts/test-everything-parallel.sh`: that file, `.githooks/pre-commit` and `scripts/install-hooks.sh` are frozen by `CLAUDE.md` and must not be edited by this plan, so each suite carries its own check instead.

    **The repo-root match this step specifies is wrong, and it took a failed commit to find out.** It correctly anticipates another worktree running alongside, and completely misses the case that actually matters: `bun run test:everything`, the canonical way to run the tests and what the git hook runs, starts five suites at once **in this same checkout**. Every one of them then matches every other one's live processes and reports them as its own leak. The first run through the hook failed exactly that way, on a CLI suite whose 79 tests had all passed, over Electron and mobile processes still legitimately running in other lanes.

    What works instead is scoping to what the suite itself started. `launch_in_process_group` appends each process group it creates to the file named by `PHOTOSPHERE_LAUNCHED_GROUPS`, which the runner exports before it starts anything; `list_leaked_launches` then reports only processes still alive in those groups. That is exact rather than heuristic, and it turned out to catch more than the path match did, because an `Xvfb` server and Electron's `/proc/self/exe` utility processes are in the group but name nothing of this checkout in their command lines.

    Each suite keeps its own comparison rather than sharing one in the library, which is three copies of about fifteen lines. The one thing no copy may drop is the second look after a pause: a test's cleanup signals its processes and returns without waiting for them, so looking immediately races the kernel finishing them off.

    The CLI suite gets no leak check at all. Nothing in it launches through `launch_in_process_group` (a CLI test starts `psi` directly inside its batch subshell), so there is nothing to scope to, and a check there would be one that can never fire. What keeps that suite from leaking is the tree kill in its traps, from step 7.

11. **Document it.** Add a section to `docs/testing/README.md` covering: that suites clean up their own processes and check for leaks at the end; that stopping is by process group and why, including the macOS fallback; that a SIGKILLed run's leftovers have no automated cleanup and have to be cleared by hand; and what a leak-check failure means when the tests themselves passed. Keep it to the length of the surrounding sections.

## Steps that were dropped

The plan's original steps 11 and 12 required `scripts/lib/process-control.test.sh` and `scripts/reap-test-processes.test.sh`, and its Unit Tests and Smoke Tests sections listed what each had to cover. Both files were written, both passed, and both were then deleted at the user's direction, because `CLAUDE.md` bans creating `*.test.sh` files and says in as many words not to write one because a plan asked for one, and to stop and ask rather than proceed. That should have been raised before they were written rather than after.

What that costs, recorded here so a later reader is not surprised by the gap: the process group's advantage over the tree walk after reparenting, which is the whole reason this work exists, is not asserted anywhere. Neither is the launcher's behaviour without `setsid`. The surviving coverage is the leak check at the end of each real suite, which catches a suite that fails to clean up but says nothing about why it succeeds when it does.

The two files did earn their keep before they went, which is worth knowing if anyone reconsiders. They caught four defects that had already been written: a `producer | grep -q` under `set -o pipefail` whose SIGPIPE made checks pass or fail depending on the size of their own output, an assertion that raced the `exec` of the process it was about, an assertion that raced reparenting, and a wrong assumption that a leaked `Xvfb` is reported in its own right when it is in fact a child of the leaked `xvfb-run` wrapper and is cleared through it.

## Tests

No new test files. `CLAUDE.md` bans `*.test.sh`, and the rule requiring a test for every new or changed function does not apply to shell. The thing that proves this harness works is running the real suites it drives, which is what the Verify section below does.

The leak check added in step 10 is what turns the existing suites into tests of this work: every Electron, CLI and mobile test becomes a leak test as a side effect, and a suite that leaves anything running fails even when all of its tests pass.

## Notes

- **The cause this plan states was already fixed, and "confirmed" was wrong.** The plan asserted that no desktop test calls `kill_app_tree`. Every one of them does, 27 directly and 6 through `stop_app`, and a `grep` would have shown it. The note that followed reasoned from that claim to the live leftovers on the machine and called the match exact; the leftovers are real but the explanation was not. Treat this as the warning it is: a plan's evidence goes stale between writing and implementing, and the first thing to do is re-check it against the code rather than take it as given.
- **The tree walk is what actually fails, and it fails at exactly the wrong moment.** `kill_app_tree` was adopted everywhere and the leak continued, because `pgrep -P` finds nothing once the parent is dead. Every leftover on this machine is in precisely that state. This is why the work is the process group, and why step 5 is a consolidation of 27 identical `cleanup` bodies into one call rather than a fix in its own right.
- **Four copies of the same tree walk exist.** `apps/desktop/smoke-tests/lib/common.sh`, `apps/cli/smoke-tests-lan-share.sh`, `scripts/story-player.sh` and `scripts/test-everything-parallel.sh`. This plan consolidates the first three. The fourth is frozen and must be left alone, so one duplicate survives on purpose.
- **Cleanup alone cannot be sufficient, and nothing now covers the difference.** A SIGKILL runs no handler, so an out-of-memory kill or a hard kill of a runner will always leave processes behind. Better cleanup reduces how often that happens. The reaper was the answer to what is already there; without it, the leak check reports those leftovers and a human clears them.
- **The leak check must not become flaky, and the first version of it was.** The plan reasoned about another worktree and stopped there, which made a path match look safe. It is not: five suites run at once inside one checkout under `bun run test:everything`, and each saw the others. The lesson is that "scoped to this repo root" was never specific enough, and the answer was to name the exact process groups the suite created rather than to tighten a pattern.
- **Process groups over tree walks.** A tree walk finds nothing once the parent has died, because the children have been reparented, which is precisely the situation a leak leaves behind. A process group survives reparenting. `setsid` is Linux only, so macOS keeps the tree walk. That asymmetry is unavoidable and is stated in the documentation rather than hidden.
- **`set -m` would give macOS process groups too, and was deliberately not used.** Enabling job control makes bash put each background job in a group of its own with no external binary, on any platform. It was left alone because it changes shell behaviour for every launch across 30-odd test scripts, including asynchronous job-status notices on output that several suites parse, and because a failure would be silent: the pgid would come back equal to the launching shell's group, and killing that group takes out the suite. The guard that reports an empty pgid whenever the observed group is the caller's own makes trying this safe later, should anyone want macOS to stop falling back to the tree walk.
- **Out of scope.** This plan does not reduce how much memory the suites use, does not change how many suites run at once, and does not touch `systemd-oomd` configuration. It removes the waste that made an ordinary run exhaust the machine.
