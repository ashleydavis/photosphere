# Run ImageMagick and FFmpeg only from the built-in libraries in the Zig CLI and the Photosphere App

## Overview

ImageMagick and FFmpeg are already built from source under `third-party/` and linked into `packages-zig/media-tools-zig`, whose `MediaTools` runs `magick`, `ffmpeg` and `ffprobe` inside the program's own process through Ziggy's `InProcessRunner` interface (re-exported by `packages-zig/node-utils-zig/src/index.zig` from `ziggy-core`). The Photosphere App (`packages-zig/photosphere-core/src/lib/main-state.zig`) already makes a `MediaTools` and hands its runner to Ziggy's queue backend and to its file logger. The Zig CLI (`apps/cli-zig`) does not link `media-tools-zig` at all and passes `null` for the runner everywhere, so every command it runs for ImageMagick or FFmpeg is started as an installed program found on `PATH`. Any App path that passes `null` falls back to installed programs the same way. This plan removes that fallback from the Zig code so that the CLI and the App can only run the built-in libraries, runs the tests to find every caller that still depended on the installed programs, and then hands those callers the built-in runner. Only the Zig CLI and the Photosphere App are in scope. The TypeScript CLI (`apps/cli`), the Electron app (`apps/desktop`) and the shell scripts, test fixtures, test helpers and workflows that run installed `magick`, `ffmpeg`, `ffprobe` or `identify` themselves are not changed, except that workflows stop installing the tools in a job where nothing in that job runs them.

## How the work is split across subagents

The human asked for this plan to be done with as many subagents running at once as the machine can take, each independent piece in its own git worktree, with a merge subagent at the end bringing every change into one worktree. This section says which agent does what and in what order. The steps below say what each piece of work is.

### Worktrees

- The main worktree is `.claude/worktrees/built-in-media-tools` (branch `built-in-media-tools`). It is the base: every other worktree is made from it, and everything ends up back in it. The human has authorised making worktrees of it for this plan, so that the ImageMagick work (segment C) and the FFmpeg work (segment B) run in parallel, each in its own worktree, along with the other segments below. Only the orchestrating agent (the one that launches the others) edits this plan file, and it edits only the copy in the main worktree.
- Each segment below has its own worktree, made from inside the main worktree with `git worktree add -b bimt-<segment> ../bimt-<segment> built-in-media-tools`, so it sits beside the main worktree under `.claude/worktrees/`. Then, inside it, `mise trust` and `mise exec -- bun install`. Segments marked read-only work in the main worktree without editing anything and get no worktree.
- Phase 2 segments start from segment A's result: after making the worktree, copy in every file segment A changed, added or deleted, the way the merge does (below).
- Nothing is committed, staged or stashed in any worktree. Each segment's work stays as uncommitted changes in its worktree, and that worktree is never edited again once its agent has reported, so the merge can read it.

### Rules for every segment agent

- Work only inside its own worktree. Confirm the working directory before every edit and every command.
- Run only the test files and test scripts its own steps name. A subagent given one failing test to fix runs only that test. The wider suites run once, after the merge.
- Do not edit this plan file. Report back, for each step or part of a step it did: what was done, what was decided and why, and the test commands it ran with their exit codes. The orchestrator writes that into the plan under the step.
- Every rule in `CLAUDE.md` holds as written: no commits, no staging, no `rm -r`, no new workflow file, no edit to the git hook.

### Machine load

- Before launching each phase, read `nproc`, `uptime` and `free`. Zig builds of the tree, which compile ImageMagick and FFmpeg into each worktree's own `.zig-cache`, are the heavy work. While the one-minute load average is above the core count, or available memory is under a quarter of the total, launch the segments that do not build first and hold back the ones that build until it drops. Launch every segment that does not build straight away.

### Phase 1: start all of these at once

- **Segment 0, baseline `psi`** (main worktree, before any segment's files are copied into it): step 0.
- **Segment A, runner required** (worktree `bimt-runner`): steps 1 and 2, then step 3 except its image type check. Its report includes step 3's list of compile errors, which decides the work of phase 2.
- **Segment H, image types** (read-only): step 3's check that every image type the CLI and App import can be read by the built-in ImageMagick. If one cannot, the orchestrator stops and asks the human, as step 3 says.
- **Segment B, stopping `ffmpeg`** (worktree `bimt-ffmpeg-stop`): step 8's `ffmpeg-main.c` and `ffmpeg.zig` bullets and the `ffmpeg.test.zig` unit test. Not the `WorkerPoolBun` bullet, which needs step 5 and goes to segment A5.
- **Segment C, ImageMagick policy** (worktree `bimt-im-policy`): step 9 and the `image-magick.test.zig` unit test. Its callers of `ImageMagick.init` that exist now (`MediaTools.init`, `MainState.create`, their tests) get `try` here; the CLI's `main` and CLI tests that only call it after step 5 get it in the merge.
- **Segment D, smoke tests** (worktree `bimt-smoke`): step 7's `92-tools` bullet and step 10. Both are watched failing against segment 0's `psi`, which is the `psi` from before step 5. They are watched passing after the merge.
- **Segment E, workflows** (worktree `bimt-workflows`): step 11.

### Phase 2: start when segment A has reported

- **Segment A4, package tests** (worktree `bimt-package-tests`): step 4.
- **Segment A5, CLI** (worktree `bimt-cli`): step 5. Then, once segment B has reported, copy B's files in the way the merge does and do step 8's `WorkerPoolBun` bullet and the two CLI worker pool unit tests.
- **Segment A6, App** (worktree `bimt-app`): step 6, except that `bun run test:zig` passing in full moves to phase 3, because it also covers the CLI, which is segment A5's.
- In each, a test that still fails only because of another phase 2 segment's work is reported, not worked around.

### Phase 3: the merge

- **Segment M, merge** (main worktree), when every segment of phases 1 and 2 has reported. For each segment, list what it changed with `git -C <its worktree> status --porcelain` (which shows changed, deleted and new files). Copy each changed or new file into the main worktree and remove each deleted one by name. For a phase 2 segment, a file counts as its change only when it differs (`cmp`) from segment A's copy. A file changed by more than one segment is merged by hand from each segment's `diff` against the base it started from, keeping every segment's change. Then give the CLI's `main` and the CLI tests the `try` for `ImageMagick.init` (segment C), and fix every compile error at the seams. Then `zig build` and `bun run compile`, and run `bun run tev -- test:zig test:cli:zig test:ziggy` in one go (adding `test:ziggy:and` when `bun run emu:and:pool:status` exits 0 at that moment). That run is where step 6's full `test:zig`, the rest of step 7 and step 10's passing run are checked. Failures are fixed here, one subagent per failing test, each running only that test. The orchestrator ticks steps 1 to 11 only after this run passes.

### Phase 4: start both when the merge has passed

- **Segment F, whole set and timing** (main worktree): step 12.
- **Segment G, documentation** (main worktree, editing only the files step 13 names): step 13. Then `bun run tev` once more, since the documentation changed after step 12's run.
