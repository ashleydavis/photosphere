# Move lastDatabase Into databases.toml And Auto-Open Seeded Fixtures

## Overview

`lastDatabase` is the path of the database to reopen on launch. `packages/user-interface/src/main.tsx:263` reads it through `config.get('lastDatabase')` and calls `openDatabase` with it. On desktop that key resolves to `last_database` in `~/.config/photosphere/desktop.toml` (`packages/node-api/src/lib/desktop-config.ts`), written by the Electron main process at `apps/desktop/src/main.ts:641`. On mobile the same key resolves to WebView `localStorage` under the `photosphere.config.` prefix (`packages/mobile-frontend/src/lib/platform-provider-mobile.tsx:86` binds `window.localStorage`, and `:665` wires it into `createConfig`). Nothing outside the WebView can write `localStorage`, so the mobile value cannot be seeded from the host, and mobile auto-open has in fact never fired because no mobile code path writes the key at all.

This matters because `bun run and50`, `and1` and `and0` seed a fixture database onto a device and register it in `databases.toml`, but the app then starts on the welcome screen with nothing open. `databases.toml` already exists on every platform in one format (`~/.config/photosphere/databases.toml` on desktop and CLI, `files/databases.toml` on Android, `Documents/databases.toml` on iOS) and is already writable from the host by the deploy and smoke-test scripts. Moving `last_database` into that file makes it seedable on both mobile platforms by the mechanism that already exists, and removes a field that today lives in two different places depending on platform.

The change is deliberately shaped to avoid touching the shared UI or adding an Electron IPC channel. `IConfig` stays generic and `main.tsx` is unchanged; each platform's existing `getRaw`/`setRaw` pair routes the single key `lastDatabase` to its databases config instead of its generic config store. The plan then adds `last_database` seeding to the Android deploy script and creates the iOS hand-testing script that does not yet exist, so `and50` / `and1` / `and0` and new `ios50` / `ios1` / `ios0` scripts all leave the app opening straight into the seeded database.

## Steps

Each step must leave `bun run compile` clean and `bun run test` passing before it is considered complete. Steps 1 to 8 are the format and platform plumbing; steps 9 to 13 are the seeding; step 14 is documentation.

1. **Add the field to the shared file format.** In `packages/node-api/src/lib/databases-config-format.ts`, add an optional `lastDatabase?: string` to nothing (there is no whole-config TypeScript type in this module today) and instead add an optional `last_database?: string` to `ITomlDatabasesConfig`, documented as the path of the database to reopen on launch, absent when none is open. `IDatabaseEntry` and `ITomlDatabaseEntry` are per-entry types and are not touched. Because `ITomlDatabasesConfig` is the one shared definition, both platforms pick the field up from here.

2. **Carry the field through the desktop config module.** In `packages/node-api/src/lib/databases-config.ts`, add `lastDatabase?: string` to the `IDatabasesConfig` interface, and map it in both directions in `tomlToDatabasesConfig` and `databasesConfigToToml`. Then add two exported functions beside the existing accessors: `getLastDatabase(): Promise<string | undefined>` returning the stored path, and `setLastDatabase(databasePath: string | undefined): Promise<void>` which writes the path, or removes the field when passed `undefined`. Both go through the existing `loadDatabasesConfig` / `saveDatabasesConfig` pair so the recents and databases lists are preserved untouched. Export the two new functions from `packages/node-api/src/index.ts` if that file lists names explicitly rather than re-exporting the module wholesale.

3. **Migrate the desktop value on load.** In `loadDatabasesConfig` in `packages/node-api/src/lib/databases-config.ts`, when the loaded config has no `lastDatabase`, read `last_database` from `desktop.toml` via `loadDesktopConfig` and adopt it as the value. Do not write `desktop.toml`, and do not delete its key: the copy there becomes ignored legacy, which is non-destructive and means a downgrade still finds its old value. In `packages/node-api/src/lib/desktop-config.ts`, keep `lastDatabase` declared on `IDesktopConfig` and keep both `tomlToDesktopConfig` and `desktopConfigToToml` mapping it, but change its doc comment to say it is legacy, is no longer read by the app, and lives in `databases.toml`. Take care that this does not introduce an import cycle between `databases-config.ts` and `desktop-config.ts`; if it does, move the migration read into the desktop main process instead and record that in the Notes.

4. **Carry the field through the mobile worker handlers.** In `packages/node-api/src/lib/databases-config.worker.ts`: add `lastDatabase?: string` to `IWriteDatabasesConfigData` and to the read task's result interface; have `readDatabasesConfigHandler` return the parsed `last_database`; have `writeDatabasesConfigHandler` persist it. Change the signature of `buildDatabasesConfigToml` to take the last database as a third parameter, `buildDatabasesConfigToml(databases, recentDatabaseNames, lastDatabase)`, emitting `last_database` only when defined. Update its two in-repo callers in this step so the tree still compiles: `writeDatabasesConfigHandler` in this file, and `registerDatabaseInConfig` in this same file (which passes through whatever it parsed).

5. **Keep `recent_database_names` and `last_database` ahead of the tables.** Both are document-level TOML keys and must be emitted before the first `[[databases]]` table or `smol-toml` reads them as belonging to that table. `buildDatabasesConfigToml` builds an object literal, and key order in that literal is the emitted order, so place `last_database` next to `recent_database_names` and add a comment saying why the order matters. The wiki records this constraint in `Managing-Databases.md`.

6. **Carry the field through the mobile config store.** In `packages/mobile-frontend/src/lib/mobile-config-store.ts`, add `lastDatabase?: string` to the `IDatabasesConfig` interface, and add two exported functions `getLastDatabase(configFile: IDatabasesConfigFile): Promise<string | undefined>` and `setLastDatabase(configFile: IDatabasesConfigFile, databasePath: string | undefined): Promise<void>`. `setLastDatabase` must go through `withConfigLock` like the other mutators, and must preserve `databases` and `recentDatabaseNames`. In `packages/mobile-frontend/src/lib/mobile-databases-config-file.ts`, add `lastDatabase` to `IReadDatabasesConfigOutputs`, return it from `read`, and pass it in `write`.

7. **Route the key on mobile.** In `packages/mobile-frontend/src/lib/platform-provider-mobile.tsx`, change the `createConfig` call near line 665 so the `getRaw` and `setRaw` callbacks check for the key `lastDatabase` and route it to `configStore.getLastDatabase` / `configStore.setLastDatabase` against `mobileDatabasesConfigFile`, falling through to the existing `getConfigValue` / `setConfigValue` localStorage path for every other key. Extract the key literal to an exported constant `LAST_DATABASE_CONFIG_KEY` in `packages/mobile-frontend/src/lib/mobile-config-store.ts` and use that constant here, so the string is defined once. Also update `notifyDatabaseOpened` (line 174) to record the opened path as the last database, and `notifyDatabaseClosed` (line 191) to clear it, matching what the desktop main process already does. Update the stale comment at `:82` which still claims `localStorage` holds the configured-databases list.

8. **Route the key on desktop.** In `apps/desktop/src/main.ts`, change the existing `get-config` handler (around line 711) so a request for `lastDatabase` returns `getLastDatabase()` from `databases-config`, and the existing `set-config` handler (around line 728) so a write of `lastDatabase` calls `setLastDatabase`; every other key keeps going to `loadDesktopConfig` / `updateDesktopConfig`. Then change the `notify-database-opened` handler (line 641) and the `notify-database-closed` handler (line 697) to call `setLastDatabase` instead of mutating `desktopConfig.lastDatabase`. **Do not add a new IPC channel**: the project rule forbids action-specific channels, and reusing `get-config` / `set-config` is what keeps `packages/user-interface/src/main.tsx` unchanged.

9. **Set the last database when seeding a fixture.** In `packages/node-api/src/lib/databases-config.worker.ts`, change `registerDatabaseInConfig` so the fixture it registers also becomes the front of `recent_database_names` and the value of `last_database`. Today it strips every `test-`-prefixed name out of recents and adds none back, and never touches `last_database`. Preserve the existing guarantees exactly: entries the user owns are never removed, reordered or edited; only `test-`-prefixed entries are ever removed; malformed TOML still throws rather than being replaced. Add a doc comment explaining that a fixture is registered, made most-recent and made last-opened together, because the point of the deploy script is to land in the seeded database.

10. **Simplify the Android deploy script back to one call.** `apps/android-frontend/scripts/write-databases-config.ts` currently wraps `registerDatabaseInConfig` with its own recents handling (function `registerDatabaseAsRecent`). With step 9 in place that wrapper is redundant: delete it and its now-unused imports of `parseToml`, `buildDatabasesConfigToml`, `TEST_DATABASE_PREFIX`, `tomlEntryToDatabaseEntry` and `ITomlDatabasesConfig`, and call `registerDatabaseInConfig` directly again. Update the file's header comment to say the registration also marks the fixture most-recent and last-opened.

11. **Let smoke tests seed the field.** In `apps/smoke-tests/lib/write-databases-config.ts`, read an optional `LAST_DATABASE` environment variable and pass it as the third argument to `buildDatabasesConfigToml`; an unset or empty value means no `last_database` key is written, so every existing test that seeds a config keeps its current behaviour and still lands on the welcome screen. In `apps/smoke-tests/lib/android.sh` (`android_seed_databases_config`, line 402) and `apps/smoke-tests/lib/ios.sh` (`ios_seed_databases_config`, line 195), accept an optional third argument and pass it through as `LAST_DATABASE`. Do not change any existing test's call site in this step.

12. **Create the iOS hand-testing script.** Add `apps/ios-frontend/scripts/run-ios.sh`, the iOS counterpart of `apps/android-frontend/scripts/run-android.sh`, taking the same optional fixture argument (`50`, `1`, `0`, or a directory name under `test/dbs`). Reuse the container-resolution and seeding logic already proven in `apps/smoke-tests/lib/ios.sh` (`ios_app_container`, `ios_seed_database`, `ios_seed_databases_config`) rather than inventing a second approach; if that means extracting those two helpers into a file both can source, do the extraction as part of this step. The script must seed before the deploy when the app is already installed and after it otherwise, for the same reason `run-android.sh` does: the app reads the config at launch. Give it a `.sh` extension and never invoke it directly from documentation, only through a `bun run` script.

13. **Wire up the iOS package scripts.** In `apps/ios-frontend/package.json` add `"run:fixture": "bun run sync && bash ./scripts/run-ios.sh"` alongside the existing `run`, and in the root `package.json` add `run:ios:50` / `ios50`, `run:ios:1` / `ios1` and `run:ios:0` / `ios0` mirroring the existing `run:and:50` / `and50` pair exactly in naming and shape.

## Notes

- **Why route one key rather than add a platform method.** Adding `getLastDatabase` to `IPlatform` would mean changing `packages/user-interface/src/main.tsx` and both platform providers, and on desktop it would need a request/response IPC path. The existing `main-command` channel is `ipcMain.on`, which is fire-and-forget and cannot return a value, so a read would force a new channel, which the project rules forbid. Routing the single key inside the existing `get-config` / `set-config` handlers keeps the shared UI untouched and adds no channel. The cost is a special case in two providers, which is why step 7 requires the key literal to be a shared exported constant rather than a string in two places.
- **The migration deliberately does not rewrite `desktop.toml`.** Deleting the legacy key would mean a destructive edit of a user config file for no functional gain. Leaving it is inert: nothing reads it after step 3.
- **`last_database` holds a path, not a name.** Recents hold names because a rename should carry the recents entry with it. `main.tsx` passes the stored value straight to `openDatabase(dbPath)`, which takes a path, so the path is what must be stored. On mobile that path is a bare name relative to the storage sandbox, such as `50-assets`, which is the same value the entry's `path` field holds.
- **Whether `and0` should auto-open is a genuine question.** `no-assets` is an empty database, so auto-opening it means the app starts in an empty gallery rather than the welcome screen. The plan sets `last_database` for all three fixtures because that is what was asked for and because consistency is easier to reason about than an exception, but if the intent was to keep `and0` on the welcome screen, step 9 is where that exception goes.
- **The shared deploy-script question.** Step 12 needs the same TOML rendering `apps/android-frontend/scripts/write-databases-config.ts` performs. Copying it into `apps/ios-frontend/scripts/` would put a second copy of the format handling in the tree, which is what `databases-config-format.ts` was created to prevent. Prefer moving that script to a shared location both platforms invoke, for example `scripts/write-databases-config.ts` at the repository root, and updating `run-android.sh` to point at the new path in the same step.
- **Existing smoke tests must not change behaviour.** 34 tests seed `databases.toml` through the harness helpers. Step 11 makes the new argument optional and defaulted to unset for exactly that reason. If any existing test starts failing because a database now opens when it did not before, that is a bug in step 11, not a test that needs updating.
- **Related open work.** `docs/plans/new/plan-review-mobile-config-storage.md` audits mobile config storage as a whole, including the durability of leaving anything in WebView `localStorage` and field parity against `IDesktopConfig`. This plan moves one field for one concrete reason and does not attempt that review. Whoever runs the review should note that `lastDatabase` has already moved.
