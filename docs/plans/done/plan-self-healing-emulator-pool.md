# Self-healing Android emulator pool, and a repair path the agent can run without root

## Overview

On 2026-08-09 all five pool emulators died with SIGSEGV during a run in which the Android suite was stacked against twelve other lanes, and nothing could bring them back: `bun run emu:and:pool:restart` begins by removing the pool's taps, that needs `sudo`, and an agent with no tty cannot answer a password prompt. `docs/emulator-pool-retrospective.md` is the account of it. This plan removes all three parts of that failure. It adds a repair path that needs no privileges at all, because it never touches the bridge or the taps and only ever restarts emulators inside the user's own systemd session. It adds a monitor that watches the pool and repairs a broken emulator by itself, without pulling one out from under a running test. And it adds mechanical preconditions to the Android harness so a run cannot be started onto a machine that has no memory left, which is the condition that killed the emulators in the first place. The rule in `apps/android-frontend/CLAUDE.md` that forbids the agent from touching an emulator at all is narrowed rather than removed: the agent gets the no-root repair commands, and the bridge, the taps and the whole-pool teardown stay the human's.

## Issues

## Steps

Standing constraints for every step. Everything added here is shell, so per `CLAUDE.md` none of it gets a unit test and no `*.test.sh` file is created for it; what proves it works is running it against the real pool, which the Verify section does. No step may run `sudo`, and no step may add a call to `sudo` to any code path the agent is allowed to run. Before any statement about whether the pool is up, the agent runs `bun run emu:and:pool:status` and reads the exit code. Never kill a process selected by matching a command line; every kill in this plan targets either a systemd unit by name or a pid read from a file that recorded it.

1. **Name the pool's systemd units in one place.** In `apps/android-frontend/scripts/emulator.sh`, add `pool_unit_name()` taking an index and printing `psphere-emu-pool-<index>`, with the comment block every global gets. Change `start_emulator_bg` to build its `unit` variable from `pool_unit_name` when the log suffix names a pool emulator, so the repair code and the start code cannot disagree about a unit's name. `bun run compile` must pass and `bash -n apps/android-frontend/scripts/emulator.sh` must be clean before this step is complete.

2. **Read a pool unit's state without changing it.** Add `pool_unit_state()` taking an index and printing three space-separated fields from `systemctl --user show --value -p ActiveState -p Result -p MainPID`: the active state, the result, and the main pid. It must print `inactive none 0` rather than nothing when the unit does not exist, so callers never have to handle an empty string. Read-only.

3. **Find an emulator process that adb cannot see.** Add `pool_avd_lock_pids()` taking a pool AVD name and printing the pids recorded in that AVD's lock files under `$(avd_home)/<avd>.avd`. Before writing it, the agent must run `ls -la` inside a real pool AVD directory on this machine and read the actual lock layout and the actual file holding the pid rather than assuming it, and must record what it found in the function's comment block. This exists because `cmd_pool_down` kills only through `adb ... emu kill`, so a crashed emulator that adb has dropped is never stopped, keeps its AVD lock, and blocks the next start. That is the state the pool was left in on 2026-08-09.

4. **Stop one pool emulator, with escalation and a bound on the wait.** Add `stop_pool_emulator()` taking an index. It runs `timeout 30 systemctl --user stop <unit>`; if the unit is still loaded it runs `systemctl --user kill --signal=SIGKILL <unit>` and waits up to another 15 seconds; then it runs `systemctl --user reset-failed <unit>`. Afterwards it takes each pid from `pool_avd_lock_pids` for that index's AVD, confirms `/proc/<pid>` exists and that `/proc/<pid>/cmdline` contains the AVD's name (a check on a pid that was recorded, not a search for a process by name), and passes any survivor to `kill_process_tree` from `scripts/lib/process-control.sh`, which `emulator.sh` must source. The bounded escalation is the answer to the two-minute hang on a unit stuck in `stop-sigterm` described in the retrospective. It must print what it did at each stage, and must return non-zero when the emulator is still alive at the end rather than reporting success.

5. **Refuse to repair when the bridge is not there, and say so precisely.** Add `require_pool_network()`, which checks `br-psphere` exists, every pool tap `emu-pool-0..N-1` exists, and `dnsmasq_running`. When anything is missing it prints exactly which of the three is missing and that only `bun run emu:and:pool:up` can create it, that this needs `sudo`, and that the agent must stop and ask the human. It must never call `sudo` itself. Returns non-zero.

6. **Add `pool-repair`, the command that needs no root.** Add `cmd_pool_repair()` to `emulator.sh` and a `pool-repair` case to the dispatcher, and extend the usage text. Behaviour:
   - Refuses to run as root, the same way `cmd_pool_up` does.
   - Calls `require_pool_network` first and exits when it fails. It never removes or creates a tap, never runs `__bridge-up` or `__bridge-down`, and so never needs a password. This is the whole point of the command.
   - With no arguments, works out which indexes are broken: the unit is not active, or the unit is active but the emulator is not in `adb devices` as `device`, or it is attached but has no `192.168.55.x` address on `wlan0` after a grace period (`POOL_REPAIR_GRACE_SECONDS`, default 90, so an emulator that is merely still booting is left alone), or its free space on the device data path is below the threshold `scripts/android-pool-status.sh` already uses.
   - `--index N` repairs exactly that index. `--all` repairs every index regardless of state.
   - Repairs one index at a time, in order, never in parallel, so a partly working pool never goes fully dark and the machine never carries five simultaneous cold boots.
   - Before touching an index that currently has an attached serial, takes that serial's harness lock non-blocking. When the lock is held, it skips that emulator, says which test run holds it, and moves on. The lock path is `/tmp/photosphere-android-device-<serial>.lock`, currently written inline in `apps/smoke-tests/lib/runner.sh` near line 464; extract it into a function in `apps/android-frontend/scripts/emulator-config.sh` that both `runner.sh` and `emulator.sh` call, so one definition governs both and a rename cannot leave the repair path locking a path nobody else uses.
   - For each index it repairs: `stop_pool_emulator`, then `wait_for_pool_units_released`, then `ensure_avd_data_partition_size`, then `start_emulator_bg` with the wipe argument set, then waits up to `POOL_REPAIR_BOOT_TIMEOUT_SECONDS` (default 420) for that one emulator to reach the bridge.
   - Exits 0 only when every index it attempted is on the bridge at the end. On any failure it exits non-zero and calls the diagnostics report from step 8.

7. **Expose it.** Add `"emu:pool:repair": "bash ./scripts/emulator.sh pool-repair"` to `apps/android-frontend/package.json` only. It gets no entry in the root `package.json`: it is run as `bun run --filter=android-frontend emu:pool:repair`, which satisfies the rule against invoking a shell script directly without adding another line to the root file for a command the human rarely types. Every reference to it in a doc or a message must use that full form, so nobody is sent looking for a root script that does not exist.

8. **Keep the evidence the last incident did not have.** Two changes in `emulator.sh`:
   - Change the `StandardOutput` and `StandardError` properties in `start_emulator_bg` from `file:` to `append:`. `file:` truncates on open, so a restart destroys the crash output of the emulator that just died, and during the 2026-08-09 recovery the only content in those logs was old crash output with nothing to say whether the new processes had written anything at all. Note in the comment that the logs now grow, and that they live in `/tmp` so a reboot clears them.
   - Add `cmd_pool_diagnose()`, a `pool-diagnose` dispatcher case, and `"emu:pool:diagnose"` in `apps/android-frontend/package.json` only (run as `bun run --filter=android-frontend emu:pool:diagnose`, for the same reason as step 7). It writes a report to stdout for every pool index: `systemctl --user status` output, `ActiveState`/`Result`/`MainPID`, the process's accumulated CPU time from `/proc/<pid>/stat`, whether the process holds a descriptor on `/dev/kvm` and on its tap (from `/proc/<pid>/fd`), whether a console port is listening for that emulator, the AVD lock pids, and the last 40 lines of its log. Read-only, changes nothing. This is exactly the set of facts the retrospective had to gather by hand while guessing at causes, and `cmd_pool_repair` calls it automatically on failure.

9. **Share the health judgement before anything new consumes it.** Three places decide whether an emulator is healthy, and after this plan there would be four: `scripts/android-pool-status.sh`, `apps/android-frontend/scripts/emulator-health.sh`, `cmd_pool_repair` from step 6, and the monitor. Add `apps/android-frontend/scripts/emulator-status-lib.sh`, a sourced library and not a script anyone runs, holding the judgement itself: `emulator_adb_state()`, `emulator_boot_completed()`, `emulator_bridge_address()`, `emulator_free_mb()` and `emulator_health_verdict()`, which combines them into one word. Move the existing implementations out of `android-pool-status.sh` and `emulator-health.sh` into it and have both source it, along with `emulator.sh`. Nothing about what any caller reports may change in this step: `bun run emu:and:pool:status` must print the same lines and return the same exit codes before and after, which the agent checks by running it against the live pool on both sides of the change.

10. **Fold the health display into the monitor, so there is one watcher.** The monitor and `emulator-health.sh` are the same loop over the same judgement, differing only in whether they act on it and how they print. Make them one file: rename `apps/android-frontend/scripts/emulator-health.sh` to `apps/android-frontend/scripts/emulator-pool-monitor.sh` with `git mv` (leaving the index staged for the human, and not committing), keep its table and graph rendering, and add the repair loop to it. Delete nothing else. Requirements:
   - **Read-only unless told otherwise.** Repairing requires an explicit `--repair`. Without it the script watches and reports exactly as `emulator-health.sh` does today. The read-only guarantee that made the health script safe for the agent to run is preserved as a default rather than thrown away by the merge, so a mistyped invocation cannot restart an emulator.
   - **Two output modes.** `--watch` keeps the redrawn table and graphs, which needs a terminal. Without it the script prints one timestamped line per pass, which is what belongs in a log and what makes an unattended run readable afterwards. Redraw-in-place and a log file cannot be the same output, which is the only real reason these were two files.
   - Watches every attached emulator, as the health script does now, but repairs only pool indexes. A hand-testing emulator appears in the table and is never touched.
   - Loops on an interval (`--interval`, default 60 seconds in repair mode; the display keeps its 1 second sampling so the graphs are unchanged). `--once` does a single pass and exits. `--dry-run` reports what it would repair and repairs nothing.
   - One repairing instance per machine, held with `flock -n` on a fixed path, taken only in `--repair` mode so any number of people can watch at once. A fixed path is right here and must be justified in the file's comment block: this manages a machine-wide resource that already has fixed names (`br-psphere`, `psphere-pool-N`, `emu-pool-N`), it is not a test, and two monitors repairing the same pool would fight. The rule in `CLAUDE.md` about fixed paths is about tests, which must survive beside a second copy of themselves; a repairing monitor must not have a second copy at all.
   - Each pass classifies every index through `emulator_health_verdict` from step 9 and repairs at most one emulator per pass, by calling `emulator.sh pool-repair --index N`. Never repairs an emulator whose harness lock is held.
   - Keeps a consecutive-failure count per index. After `MONITOR_MAX_CONSECUTIVE_FAILURES` (default 3) it stops repairing that index, keeps reporting it as broken on every pass, writes the `pool-diagnose` report from step 8 once for that index, and says plainly that it has given up and why. Without this a machine-level fault turns into an endless cold-boot loop that makes the machine worse, which is close to what the recovery attempts did by hand.
   - Recycles a healthy emulator that has been up longer than `MONITOR_MAX_UPTIME_SECONDS` (default 12 hours), but only in `--repair` mode, only when its lock is free and only when every other index is healthy. The emulators that died had been up 23.5 hours and were holding 6.6 to 6.7GB of RAM plus up to 2GB of swap each. Proactive recycling while idle is the part of this plan that addresses that directly.
   - Never touches the bridge, the taps or the single hand-testing emulator, and never runs `sudo`. Reads uptime from the unit rather than from the guest.
   - When `require_pool_network` fails, it reports and keeps waiting rather than exiting, so a monitor left running survives the human bringing the bridge back.
   - Package entries carry the flags so nobody types them: `"emu:pool:monitor": "bash ./scripts/emulator-pool-monitor.sh --repair"` and `"emu:pool:health": "bash ./scripts/emulator-pool-monitor.sh --watch"` in `apps/android-frontend/package.json`; in the root `package.json`, `emu:and:pool:monitor` pointing at the first and the existing `emu:and:health` entry repointed at the second, so the command the docs already name keeps working and keeps meaning "watch, change nothing".

11. **Refuse to start an Android run onto a machine with no memory left.** In `apps/smoke-tests/lib/android.sh`, add `android_require_headroom()` and call it from `android_require_ready`. It reads `MemAvailable` from `/proc/meminfo` and refuses the run when it is below `PHOTOSPHERE_MIN_AVAILABLE_MB` (default 4096), printing the figure it read, the limit, and the name of the variable that overrides it. It skips silently when `/proc/meminfo` does not exist, so a non-Linux host is unaffected. This is the mechanical part of stopping the incident recurring: the third run on 2026-08-09 was started onto a machine already carrying twelve other lanes and a degraded pool, and no rule stopped it because rules are advice and this is a precondition.

12. **Report a degraded pool at the point a run starts, and name the repair.** Still in `android_require_ready`, when the pool is up but fewer emulators are on the bridge than `PHOTOSPHERE_EMULATOR_COUNT`, print a warning naming the missing indexes and `bun run --filter=android-frontend emu:pool:repair` as the fix. It stays a warning and not a refusal, because a run on a partial pool is legitimate and slower rather than wrong. Do not add an automatic repair here: a test run must not start restarting the machine's emulators underneath other runs.

13. **Stop the pair sweep from grinding the pool down.** `scripts/check-parallel-tests.sh` includes `test:and` and pairs it against every other suite, which is precisely the deliberate stacking that killed two emulators. Add two things: it records the number of pool emulators on the bridge before the sweep starts, and after every pair that included `test:and` it runs `scripts/android-pool-status.sh` again and stops the whole sweep with a clear message when the count has dropped. A sweep that keeps running after it has destroyed an emulator produces results about the wrong thing anyway.

14. **Narrow the rule that says the agent may never touch an emulator.** Rewrite the top section of `apps/android-frontend/CLAUDE.md` so it draws the line where the privileges are rather than at the emulator:
    - The agent may run `bun run emu:and:pool:status`, `bun run --filter=android-frontend emu:pool:diagnose`, `bun run --filter=android-frontend emu:pool:repair` and `bun run emu:and:pool:monitor -- --once`. These need no root, touch no tap, respect the harness's device locks and repair one emulator at a time. Write them out in full, because only the status and monitor entries exist in the root `package.json` and a shortened form of the other two would send a reader looking for a script that is not there.
    - The agent still may not run `emu:and:up`, `emu:and:down`, `emu:and:restart`, `emu:and:pool:up`, `emu:and:pool:down` or `emu:and:pool:restart`, may not create or remove a tap or the bridge, may not run `sudo`, and may not reconfigure a guest.
    - Keep the existing lessons list and add the four from the retrospective: check the pool before starting anything that uses it, never stack the Android suite against other suites by hand, treat an unexplained slow Android run as a signal to run `bun run --filter=android-frontend emu:pool:diagnose` rather than something to wait out, and never assert what did or did not kill an emulator before reading `systemctl --user status`.

15. **Update the root `CLAUDE.md` and the emulator guide.** Add the three commands to the command list in the root `CLAUDE.md`, next to the existing pool-status rule, saying which of them the agent may run and writing each one exactly as it is invoked: `bun run emu:and:pool:monitor` is a root script, while repair and diagnose are `bun run --filter=android-frontend emu:pool:repair` and `bun run --filter=android-frontend emu:pool:diagnose`. In `apps/android-frontend/scripts/emulator.md`, document `pool-repair` (what it fixes, why it needs no root, and that it is useless when the taps are gone), `pool-diagnose`, and the monitor including its defaults and its give-up behaviour.

16. **Optional, and the human's decision: let the privileged part run unattended.** `pool-repair` covers every case in which the bridge and taps survive, which is every case short of a reboot or somebody running `pool-down`. It cannot cover the rest, because creating a tap needs root. If the human wants that covered too, add `cmd_print_sudoers()` and a `print-sudoers` dispatcher case that prints a `sudoers` rule for the current user and a root-owned copy path, for the human to install with `sudo visudo -f /etc/sudoers.d/psphere-emulator`. The rule must point at a root-owned copy of the script installed outside the repository, not at the working tree: a NOPASSWD rule on a file inside a writable checkout hands root to anything that can edit that file, including this agent, which is a worse problem than the one it solves. The agent must not install anything, must not run `visudo`, and must state that trade-off when it reports. Leave this step unimplemented unless the human asks for it in the message being acted on.

## Unit Tests

None, and none may be added. Every file this plan touches is shell (`emulator.sh`, `emulator-config.sh`, `emulator-status-lib.sh`, `emulator-pool-monitor.sh`, `android.sh`, `runner.sh`, `android-pool-status.sh`, `check-parallel-tests.sh`), and `CLAUDE.md` says plainly that shell scripts in this repository get no unit tests and no `*.test.sh` files, that the requirement of a test per function does not apply to shell, and that a plan asking for one is not a reason to write one. The thing that proves this harness works is running it against the real pool, which is what the Verify section does. If a later step genuinely needs TypeScript, it becomes a real `.ts` file under `scripts/` with a comment block and a documented argument list, and it gets unit tests like any other TypeScript in the repository.

## Smoke Tests

These are run by the agent against the live pool, not written as new scripts. Each names what it breaks and what it expects, and each leaves the pool healthy.

1. **Repair a deliberately stopped emulator.** With the pool up and no test running, `systemctl --user stop psphere-emu-pool-0`, confirm `bun run emu:and:pool:status` reports one fewer on the bridge, run `bun run --filter=android-frontend emu:pool:repair`, and confirm it repairs index 0 alone, exits 0, and that the status check reports the full count again.
2. **Repair a crashed emulator that adb cannot see.** Stop index 1 with `systemctl --user kill --signal=SIGKILL psphere-emu-pool-1` so it leaves a failed unit behind, then run `bun run --filter=android-frontend emu:pool:repair` and confirm it clears the failed unit and brings the index back. This is the case `pool-down` cannot handle.
3. **A repair never runs as root and never prompts.** Confirm from the output of both runs above that no `sudo` line appears and that neither command blocked on input.
4. **A repair refuses when the network is gone.** Without removing anything, confirm the refusal path by reading `require_pool_network`'s output on a tap name that does not exist (call the function with a bogus index in a scratch invocation, or temporarily set `PHOTOSPHERE_EMULATOR_COUNT` above the number of taps that exist, which makes the last tap missing without changing anything on the machine). Confirm it names what is missing, tells the human to run `pool-up`, and exits non-zero without calling `sudo`.
5. **A repair leaves a busy emulator alone.** Start `bun run test:and` and, while it is running, run `bun run --filter=android-frontend emu:pool:repair --index <a serial the run is using>`. Confirm it reports the lock as held, changes nothing, and that the suite finishes normally.
6. **The monitor sees and repairs.** `bun run emu:and:pool:monitor -- --once --dry-run` after stopping index 2 must name index 2 and change nothing. `bun run emu:and:pool:monitor -- --once` must then repair it and exit.
7. **The monitor gives up rather than looping.** Confirm the failure counter from the code path by running the monitor with `MONITOR_MAX_CONSECUTIVE_FAILURES=1` against an index whose repair cannot succeed (set `POOL_REPAIR_BOOT_TIMEOUT_SECONDS` very low for that run), and confirm it reports giving up on that index and keeps reporting it on later passes without starting another emulator.
8. **The headroom check refuses.** Run `bun run test:and` with `PHOTOSPHERE_MIN_AVAILABLE_MB` set above the machine's current `MemAvailable`, and confirm the run refuses immediately, names both figures, and starts no build.
9. **Diagnostics say something useful.** Run `bun run --filter=android-frontend emu:pool:diagnose` with the pool healthy and confirm every index reports an active unit, non-zero CPU time, an open descriptor on `/dev/kvm`, and a non-empty log tail. This is the reading that would have identified the 2026-08-09 state in one command.
10. **The health display survived the merge and still changes nothing.** `bun run emu:and:health` must render the same table and graphs it did before, against a healthy pool, and must repair nothing while an emulator is deliberately stopped: stop index 3, watch a few passes, confirm the display shows it as unhealthy and that `bun run emu:and:pool:status` reports the same count throughout, then repair it explicitly. This is the check that the read-only default survived the merge, and it is the one worth running twice.

11. **The Android suite still passes.** `bun run test:and` green on the repaired pool.

## Notes

**Why the sudo block exists and why removing the tap teardown removes it.** `cmd_pool_down` ends with `sudo PSPHERE_TAPS="$taps" "$0" __bridge-down`, and `cmd_pool_restart` is `cmd_pool_down` followed by `cmd_pool_up --wipe`, so the supported repair cannot start without a password. `cmd_pool_up` only calls `sudo` when `bridge_is_up` is false for the last pool tap. Taps and the bridge are reusable across emulator restarts and nothing in a restart requires them to be recreated, so a repair that leaves them in place needs no privileges at all. That is the entire mechanism behind step 6, and it is why `pool-repair` is a new command rather than a flag on `pool-restart`: `pool-restart` keeps its meaning, and the command the agent is allowed to run cannot reach a `sudo` call by any path.

**What `pool-repair` cannot fix.** Anything that removes the taps or the bridge: a reboot, `pool-down`, `down` when it takes the bridge with it. In those cases the agent stops and asks, and step 15 is the optional way to cover them if the human decides the trade-off is worth it.

**The unexplained part of the incident is not addressed here, deliberately.** During recovery, emulator processes started, stayed resident, burned under a second of CPU in eleven minutes, opened no descriptor on `/dev/kvm` or on their tap, opened no console port and wrote nothing to their logs. Four causes were proposed and all four were wrong. This plan does not propose a fifth. What it does is make the next occurrence produce evidence in one command (`pool-diagnose`, step 8) and stop the logs being truncated over the top of the previous crash (`append:`, step 8), so the cause can be found from data rather than guessed at.

**The device lock is what makes self-healing safe.** `apps/smoke-tests/lib/runner.sh` already claims each emulator under `flock` on `/tmp/photosphere-android-device-<serial>.lock` for the duration of one test. A repair that takes the same lock non-blocking can never restart an emulator a test is using, and a repair that skips a locked emulator degrades to doing nothing rather than to breaking a run. Extracting that path into one shared definition (step 6) matters more than it looks: two copies of a lock path that drift apart would leave the monitor locking something nobody else respects, and the failure would be a test dying mid-run with no explanation.

**One watcher, not two, and what the merge costs.** `emulator-health.sh` and a separate monitor would be the same loop over the same judgement, differing only in whether they act on it, so they become one file (step 10). The two things the merge could have destroyed are handled explicitly rather than assumed: the display's redraw-in-place is unusable in a log file, so the merged script prints plain timestamped lines unless `--watch` is passed; and the health script's value to the agent was that the file itself could not change anything, which becomes a default instead, with repairing behind an explicit `--repair` that only the `emu:*:monitor` package entry passes. If either of those slips, the merge has made things worse rather than simpler, which is what smoke test 10 exists to catch.

**One emulator at a time, everywhere.** Both `pool-repair` and the monitor repair serially and never in parallel. Five simultaneous cold boots with `-wipe-data` is a large load on the machine, and the pool died under load. A repair that recreates the original conditions is not a repair.

**`PHOTOSPHERE_EMULATOR_COUNT` is 5 in `emulator.sh` despite the comment above it saying it was reduced to 3.** The comment and the value disagree, and the value is what runs. Nothing in this plan changes it, but whoever executes this should read that comment and either correct it or tell the human, because the retrospective's memory figures were measured against five.
