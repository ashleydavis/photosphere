# Mobile Asset Import (Android + iOS)

## Overview
Asset importing does not work on mobile and the Android import smoke test (`apps/smoke-tests/tests/4-import-photos/test.sh`) fails. Two things block it. First, the `import-assets` background task is an orchestrator: its handler constructs `new TaskQueue(...)` and enqueues `hash-file` and `upload-asset` child tasks. On desktop/CLI the worker installs a `WorkerQueueBackend` via `setQueueBackend()` so those child tasks travel over IPC to the main-thread queue; the mobile embedded engine never calls `setQueueBackend()`, so `getQueueBackend()` throws "Queue backend not initialised" and any subtask fails immediately. Second, the import page relies on drag-and-drop plus a filesystem folder/file picker, neither of which exists on a phone. This plan (1) makes mobile subtasks travel back to the native engine pool and queue there for the next free engine, exactly like Electron routes `queue-task` to `WorkerPoolElectronMain`, and (2) hides drag-and-drop on mobile and replaces it with a native photo picker (Android `PickMultipleVisualMedia` / iOS `PHPickerViewController`) that copies the chosen images into the app sandbox and hands their sandbox-relative paths to the existing path-based importer. ImageMagick/ffmpeg and the native fs host functions are already wired (commit `acdd54f7`), so no media/binary work is required.

## Discovered during implementation
- **Import handlers were not registered in the mobile worker.** `packages/mobile-worker/mobile-worker-entry.ts` registered `load-assets`, `asset-server`, etc. but not `import-assets` / `hash-file` / `upload-asset`, so the import task failed with "No handler registered". Registered all three (import-assets is the orchestrator; hash-file/upload-asset are its subtasks).
- **The Android engine never exposed the media host functions.** `HostBridge.java` (from commit acdd54f7) implements `imageMagick` / `ffmpeg` / `ffprobe`, but `QuickJsTaskEngine.ensureContext` never installed them on `globalThis.host` (iOS `HostBridge.swift` does). So on Android `host.imageMagick` was the NOT IMPLEMENTED thrower and import could not analyse images. Wired the three existing methods into the engine host object (no new media code; just exposes what acdd54f7 added).
- **The smoke-test control bridge needs a route per command.** Added a `/pick-files` route to `apps/smoke-tests/lib/control-bridge.ts` (mirroring `/drop`); without it the command 404'd and `send_command` did not catch it.
- **`supportsDragAndDropImport` is true on web**, not false: browser drag-and-drop works, so only mobile hides the drop zone.
- **On-device verification (Android emulator): all 24 Android smoke tests pass, including test 4 (import-photos).** The import-assets orchestrator spawns hash-file/upload-asset subtasks that queue back on the native engine pool, run on other engine slots, and route their completions/failures back to the parent engine (the Part-1 round trip); the picked paths flow through `pickFiles` into the import task; and the two fixture images import end-to-end (thumbnails + display generated by native ImageMagick), yielding "2 assets imported" and "Gallery loaded: 2 assets".
- **The Android ImageMagick/ffmpeg activation was missing.** `acdd54f7` committed the media code and docs but not the activation. Rather than vendor/commit any binaries, source, or headers, a fetch-from-downstream step was added: `scripts/fetch-mobile-media-tools.sh` downloads the prebuilt `MolotovCherry/Android-ImageMagick7` `.so` from its GitHub release, downloads the matching ImageMagick source for the API headers, and runs ImageMagick's `configure` with the NDK per ABI to generate the per-ABI config headers — all into git-ignored locations. `bun run sync` invokes it (via a `fetch:media` script), so `bun run test:android` pulls and builds ImageMagick with no committed artifacts. `build.gradle` gains the `externalNativeBuild`/`ndk`/`packagingOptions` + FFmpegKit Maven dependency and `minSdkVersion 24`; ffmpeg is a Maven dep (no fetch needed). iOS mirrors the model via `ios/build-imagemagick.sh` (git-ignored `vendor/im`). `jniLibs/`, `cpp/imagemagick/`, `.media-fetch/`, and `vendor/` are git-ignored on both platforms.
- **Two mobile-serialization bugs in the subtask path, found and fixed.** (1) Binary (Uint8Array/Buffer) and Date fields do not survive the JSON bridge crossing (Electron uses structured clone); a base64/epoch replacer+reviver in `mobile-worker-runtime.ts` now preserves them. (2) Child-task **messages** must go to the WebView, not the origin engine (the UI consumes `import-pending` from the upload-asset subtask); the native pools now route child messages to the WebView and only child completions to the origin engine, matching Electron.
- **The smoke-test control bridge needed a `/pick-files` route** (`apps/smoke-tests/lib/control-bridge.ts`); without it the command 404'd and `send_command` did not catch it.
- **Android ffmpeg (FFmpegKit) was not actually wired and needed an AGP bump.** The `implementation 'com.moizhassan.ffmpeg:ffmpeg-kit-16kb:6.1.1'` line was missing from `build.gradle` (only ImageMagick was exercised by the image import, so it went unnoticed). Adding it exposed a D8 dexing crash on that AAR under AGP 8.0.0; bumping the Android Gradle Plugin to 8.1.4 (matching the prototype) fixes it. A new video-import smoke test (`apps/smoke-tests/tests/21-import-video/test.sh`) imports `test.mp4`, exercising ffprobe (metadata) + ffmpeg (screenshot thumbnail) end to end, and passes on Android. ffmpeg is a Maven dependency (no vendored binaries); iOS ffmpeg still needs its FFmpegKit Swift Package added to the Xcode project.

## Notes
- **Why route subtasks through native, not the WebView.** On Electron the main process (not the renderer) owns the queue and workers post `queue-task` straight to it; the renderer never sees child tasks. The native `EnginePool` is the exact analogue of `WorkerPoolElectronMain`, so child tasks are routed engine→native-pool→origin-engine and are never surfaced to the WebView. This matches the "as close to Electron as possible" requirement and avoids involving the React layer in every subtask.
- **No in-worker queue, no inline execution.** The engine installs a `WorkerQueueBackend` whose `addTask` only emits `queueTask` to native (identical in spirit to `worker-queue-backend.ts` posting `queue-task`). Nothing runs inside the engine that spawned the subtask.
- **Concurrency / deadlock.** `POOL_SIZE = 3`: a parent orchestrator occupies one engine slot while awaiting children that run on the other two, mirroring Electron's multi-worker pool. A `POOL_SIZE` of 1 would serialise and deadlock, but production uses 3; note this constraint rather than changing it.
- **Cancellation parity.** `WorkerQueueBackend.cancelTasks` fires only local callbacks (it does not post to the main side), so on Electron a shut-down orchestrator lets in-flight children finish and ignores their results. Mobile mirrors this: no native cancel path for child tasks is added. Root-task cancellation continues to flow WebView→`plugin.cancelTasks`→`EnginePool.cancelTasks` unchanged.
- **Sandbox for picked media.** The importer is path-based and the fs host functions are sandboxed to the app storage root, so the native picker must copy chosen items into `<storageRoot>/.import-tmp/` and return sandbox-relative paths. Cleaning up `.import-tmp/` after import is a follow-up nicety, not required for correctness; note it as an open item.
- **Hashing works already.** `hash-file` hashes via the pure-JS `create-hash` crypto shim (`packages/mobile-worker/src/shims/node-crypto.ts`), so no native SHA is needed for import; `host.sha256` remains a demonstrator and is unused on this path.
- **Media tools are done.** `Image`/`Video`/`getFileInfo` are alias-bundled to `mobile-tools.ts` and run over `host.imageMagick`/`host.ffmpeg`/`host.ffprobe` (commit `acdd54f7`). No binary, vendoring, or media work is in scope.
- **Open question.** Whether the Android visual-media picker should use `PickMultipleVisualMedia` (photos-only, cleanest UX) or `ACTION_OPEN_DOCUMENT` (also allows arbitrary files/videos) — pick the former for images/videos where available and fall back as needed; confirm during implementation against the minSdkVersion.
